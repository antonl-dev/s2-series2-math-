## PART A: Why Do We Need a Multi-Level Index?

### 1. The Limitation of a Single-Level Index
In Module 3.4, we saw that for our $10,000\text{-record}$ `EMPLOYEE` file ($1,667$ data blocks), a Single-Level Primary Index occupied **$b_1 = 67\text{ index blocks}$**.
* To search those $67$ index blocks using Binary Search, the DBMS still had to perform:
  $$\left\lceil \log_2(67) \right\rceil = \mathbf{7\text{ block accesses}} \quad (\text{plus } 1 \text{ data block access} = 8\text{ total})$$
* What if the file had $10,000,000$ records? Then the single-level index itself would be thousands of blocks long, and binary-searching the index on disk (jumping back and forth across disk cylinders) would still be slow!

---

### 2. The Multi-Level Index Idea: "Build an Index on Top of the Index!"

Think about how a multi-volume encyclopedia works: instead of flipping through a 67-page index using binary search, you put a **1-page Master Table of Contents** at the very front that tells you which page of the index to open!

In a **Multi-Level Index**:
1. **First-Level (Base Level) Index:** The original single-level index (with $b_1$ blocks).Since the First-Level Index is itself a sorted file with distinct keys, we can treat the First-Level Index as a data file and build a **Sparse Primary Index** on top of it!
2. **Second-Level Index:** Has **one entry for each block of the First-Level Index** ($r_2 = b_1$).
3. **Third-Level Index (and so on):** If the Second-Level Index still occupies more than $1$ block ($b_2 > 1$), we build a **Third-Level Index** on top of the Second-Level Index ($r_3 = b_2$).
4. **When Do We Stop?** We repeat this process until the **Top-Level (Root) Index fits completely inside a SINGLE disk block ($b_t = 1\text{ block}$)**!

## PART B: Fan-Out ($fo$) & Mathematical Formulas for Multi-Level Indexing

### 1. What is Fan-Out ($fo$)?
* **Definition:** The **Blocking Factor of the Index ($bfr_i$)**—which is the number of index entries `<Key, Pointer>` that can fit into a single index block—is called the **Fan-out ($fo$)** of the multi-level index:
  $$fo = bfr_i = \left\lfloor \frac{B}{R_i} \right\rfloor = \left\lfloor \frac{B}{V + P} \right\rfloor$$
* **Why does Fan-out matter?**
  * In simple Binary Search, each step divides the search space by **$2$**.
  * In a Multi-Level Index, each index block holds **$fo$ pointers** (e.g., $fo = 25$), so each step down the index divides the search space by a factor of **$fo = 25$** instead of $2$!

---

### 2. Step-by-Step Division Method to Find Index Levels ($t$)

Suppose the **First-Level Index** has **$b_1$ blocks**, and the index blocking factor (fan-out) is **$bfr_i$** (or $fo$). We divide by $bfr_i$ and **round UP ($\lceil \cdot \rceil$)** at each level until we get **$1\text{ block}$**:

1. **Level 1 Index Blocks ($b_1$):**
   $$b_1 = \left\lceil \frac{r_1}{bfr_i} \right\rceil \text{ blocks}$$
   *(where $r_1 = b$ for a Primary/Sparse Index, or $r_1 = r$ for a Secondary/Dense Index).*
2. **Level 2 Index Blocks ($b_2$):**
   $$b_2 = \left\lceil \frac{b_1}{bfr_i} \right\rceil \text{ blocks}$$
3. **Level 3 Index Blocks ($b_3$):**
   $$b_3 = \left\lceil \frac{b_2}{bfr_i} \right\rceil \text{ blocks}$$
4. **Continue until Level $t$ where:**
   $$b_t = \left\lceil \frac{b_{t-1}}{bfr_i} \right\rceil = \mathbf{1\text{ block}} \quad \text{(STOP!)}$$

*(Shortcut Logarithm Check Formula: The total number of index levels $t$ is always $t = \left\lceil \log_{fo}(b_1) \right\rceil + 1$).*

---

### 3. Total Block Accesses in a $t$-Level Index

Once you have **$t$ index levels**, retrieving any record requires:
* **$1$ block access** at Level $t$ (the Root index block)
* **$1$ block access** at Level $t-1$
* $\dots$
* **$1$ block access** at Level $1$
* **Plus $1$ block access** to fetch the actual record from the **Data File**!

Therefore:
$$\boxed{\text{Total Block Accesses} = t + 1}$$
*(where $t$ = number of index levels, and $+1$ = reading the data block from the Data File!)*

## PART C: Dynamic Multi-Level Indexes – B-Trees and B+ Trees

A standard static multi-level index (called **ISAM – Indexed Sequential Access Method**) has one problem: if you insert or delete many records, the fixed index blocks overflow.
To handle insertions and deletions dynamically without ever losing balance, modern DBMSs implement Multi-Level Indexes as **B-Trees** and **B+ Trees**!

📸 **[Click here to view B-Tree vs B+ Tree Structure Diagrams on Google Images](https://www.google.com/search?q=difference+between+B+tree+and+B%2B+tree+in+dbms+diagram&udm=2)**

```text
1. B-TREE (Stores Data Pointers inside BOTH Internal Nodes AND Leaf Nodes)
                  [ 40 | *Data40 ]  <-- Internal node ALSO holds data pointer!
                   /            \
      [ 10|*D10 | 20|*D20 ]    [ 50|*D50 | 60|*D60 ]


2. B+ TREE (Stores Data Pointers ONLY in Leaf Nodes + Leaves Linked Together!)
                  [   40   ]        <-- Internal nodes hold ONLY routing keys & tree pointers!
                   /      \
      [ 10 | 20 | 30 ] ===> [ 40 | 50 | 60 ]  <-- ALL keys & data pointers at Leaf Level!
        |    |    |           |    |    |         (Linked via ===> for fast range queries!)
       *D10 *D20 *D30        *D40 *D50 *D60
```

### Side-by-Side Comparison: B-Tree vs. B+ Tree *(Popular 3-Mark Theory Question)*

| Feature | B-Tree | B+ Tree (Used in Almost All SQL DBMSs!) |
| :--- | :--- | :--- |
| **1. Where are Data Pointers Stored?** | Stored in **BOTH internal nodes and leaf nodes**. | Stored **ONLY in the leaf nodes** (internal nodes hold only routing keys and child pointers). |
| **2. Are Search Keys Repeated?** | **No**, each search key appears only once in the tree. | **Yes**, internal routing keys are repeated in the leaf nodes so every key is present at the leaf level. |
| **3. Fan-Out of Internal Nodes** | **Lower** (because data pointers waste space inside internal nodes). | **Higher!** (Internal nodes are smaller, so more keys fit per block $\rightarrow$ **shorter tree height!**). |
| **4. Leaf Node Linking** | Leaf nodes are **not** linked together. | Leaf nodes are **linked together as a sequential linked list** (`===>`). |
| **5. Range Queries (`BETWEEN 10 AND 50`)** | **Slow** (requires traversing up and down the tree). | **Extremely Fast** (find `10` at a leaf, then just follow the leaf linked list horizontally!). |
| **6. Search Time Consistency** | Varies (some keys found near root, others at leaves). | **Uniform** (every search goes from root to leaf in exactly $t$ steps). |

## PART D: Past Year Question (PYQ) – Full Solved Answer

### PYQ 1: Nov 2025 End-Sem Exam – Question 5(a) [6 Marks]

> **Question 5(a) [6 Marks]:**
> *"Consider an EMPLOYEE file with $10000$ records where each record is of size $80\text{ bytes}$. The file is sorted on employee number ($15\text{ bytes}$ long), which is the primary key. Assuming un-spanned organization, block size of $512\text{ bytes}$ and block pointer size of $5\text{ bytes}$. Compute the number of block accesses needed for retrieving an employee record based on employee number if:*
> *(i) No index is used*
> *(ii) Multi-level primary index is used. (6 marks)"*

---

#### ✅ Model Exam Answer (Write this verbatim for 6 / 6 Marks):

**Given Data:**
* Number of records in the `EMPLOYEE` file ($r$) = $10,000$
* Size of each record ($R$) = $80\text{ bytes}$
* Block size ($B$) = $512\text{ bytes}$
* Ordering Primary Key (`employee number`) size ($V$) = $15\text{ bytes}$
* Block pointer size ($P$) = $5\text{ bytes}$
* Record Organization = **Unspanned**

---

#### Part (i): Number of Block Accesses When NO Index is Used [2.5 Marks]

1. **Blocking Factor of the Data File ($bfr$):**
   Since the file uses unspanned organization:
   $$bfr = \left\lfloor \frac{B}{R} \right\rfloor = \left\lfloor \frac{512}{80} \right\rfloor = \lfloor 6.4 \rfloor = \mathbf{6\text{ records/block}}$$

2. **Total Number of Data Blocks ($b$) in the File:**
   $$b = \left\lceil \frac{r}{bfr} \right\rceil = \left\lceil \frac{10000}{6} \right\rceil = \lceil 1666.67 \rceil = \mathbf{1667\text{ data blocks}}$$

3. **Block Accesses Required to Retrieve a Record (No Index):**
   * Since the file is sorted on the primary key (`employee number`), we use **Binary Search** across the $b = 1667$ data blocks:
     $$\text{Block Accesses (Binary Search)} = \left\lceil \log_2(b) \right\rceil = \left\lceil \log_2(1667) \right\rceil = \mathbf{11\text{ block accesses}}$$
   * *(If Linear Search is used: Average block accesses = $\lceil 1667 / 2 \rceil = 834$ blocks; Worst case = $1667$ blocks).*

---

#### Part (ii): Number of Block Accesses When a MULTI-LEVEL PRIMARY INDEX is Used [3.5 Marks]

1. **Size of One Index Entry ($R_i$):**
   Each index entry contains `<Employee_Number (V), Block_Pointer (P)>`:
   $$R_i = V + P = 15 + 5 = \mathbf{20\text{ bytes}}$$

2. **Blocking Factor (Fan-out $fo$) of the Index ($bfr_i$):**
   $$bfr_i = fo = \left\lfloor \frac{B}{R_i} \right\rfloor = \left\lfloor \frac{512}{20} \right\rfloor = \lfloor 25.6 \rfloor = \mathbf{25\text{ index entries/block}}$$

3. **Calculating the Number of Blocks at Each Index Level:**
   * **First-Level (Base) Primary Index ($b_1$):**
     Since a Primary Index is **sparse**, it has **one entry per data block** ($r_1 = b = 1667\text{ entries}$):
     $$b_1 = \left\lceil \frac{r_1}{bfr_i} \right\rceil = \left\lceil \frac{1667}{25} \right\rceil = \lceil 66.68 \rceil = \mathbf{67\text{ blocks}}$$
   * **Second-Level Index ($b_2$):**
     Has one entry for each block of the First-Level Index ($r_2 = b_1 = 67\text{ entries}$):
     $$b_2 = \left\lceil \frac{b_1}{bfr_i} \right\rceil = \left\lceil \frac{67}{25} \right\rceil = \lceil 2.68 \rceil = \mathbf{3\text{ blocks}}$$
   * **Third-Level Index ($b_3$):**
     Has one entry for each block of the Second-Level Index ($r_3 = b_2 = 3\text{ entries}$):
     $$b_3 = \left\lceil \frac{b_2}{bfr_i} \right\rceil = \left\lceil \frac{3}{25} \right\rceil = \lceil 0.12 \rceil = \mathbf{1\text{ block}}$$
     *(Since we have reached **1 block**, the Third Level is the Top/Root Level!)*

4. **Total Number of Index Levels ($t$):**
   $$t = \mathbf{3\text{ levels}}$$

5. **Total Block Accesses Needed to Retrieve an Employee Record:**
   To retrieve a record, we access $1$ block at each of the $3$ index levels plus $1$ block from the data file:
   $$\text{Total Block Accesses} = t + 1 = 3 + 1 = \mathbf{4\text{ block accesses}}$$

---

### ⭐ Bonus Twist: What if Nov 2026 Asks for a Multi-Level SECONDARY Index (Dense) on the Same File?

Suppose the question is identical ($r = 10000$, $R = 80\text{ B}$, $B = 512\text{ B}$, $V = 15\text{ B}$, $P = 5\text{ B}$), except the search is on a **Non-Ordering Candidate Key (Multi-Level Secondary Index)**:
1. $b = 1667$ data blocks, $R_i = 20\text{ B}$, $bfr_i = 25\text{ entries/block}$.
2. **Level 1 Index ($b_1$):** Since a Secondary Index is **Dense** at the first level, it has **$r_1 = r = 10,000$ entries** (one per record!):
   $$b_1 = \left\lceil \frac{10000}{25} \right\rceil = \mathbf{400\text{ blocks}}$$
3. **Level 2 Index ($b_2$):** *(Note: Higher levels $2, 3, \dots$ are ALWAYS sparse because Level 1 is sorted!)*
   $$b_2 = \left\lceil \frac{400}{25} \right\rceil = \mathbf{16\text{ blocks}}$$
4. **Level 3 Index ($b_3$):**
   $$b_3 = \left\lceil \frac{16}{25} \right\rceil = \mathbf{1\text{ block}} \quad \text{(STOP! } t = 3 \text{ levels)}$$
5. **Total Block Accesses:** $t + 1 = 3 + 1 = \mathbf{4\text{ block accesses}}$!

---

### 🎉 Module 3 Complete! Quick Side-by-Side Comparison of All 3 Methods on the $10,000$-Record File:

| Method Used on `EMPLOYEE` File ($r=10000, b=1667$) | Formula Used | Block Accesses Needed |
| :--- | :--- | :--- |
| **1. No Index (Linear Search)** | Average $\lceil b/2 \rceil$, Worst $b$ | **$834$** (avg) / **$1667$** (worst) |
| **2. No Index (Binary Search on Sorted File)** | $\lceil \log_2(b) \rceil = \lceil \log_2(1667) \rceil$ | **$11\text{ block accesses}$** |
| **3. Single-Level Primary Index** *(Oct 2025 Q3b)* | $\lceil \log_2(b_1) \rceil + 1 = \lceil \log_2(67) \rceil + 1$ | **$8\text{ block accesses}$** |
| **4. Multi-Level Primary Index** *(Nov 2025 Q5a)* | $t + 1 = 3 + 1$ *(since $1667 \to 67 \to 3 \to 1$)* | **$4\text{ block accesses}$** |
