## PART A: Physical Records (Disk Blocks) vs. Logical Records

A database is stored persistently on secondary storage (Magnetic Hard Disks or SSDs). To understand how fast a database is, you must understand the difference between a **Logical Record** and a **Physical Record (Disk Block)**.

📸 **[Click here to view Disk Blocks and Records in DBMS Storage Diagrams on Google Images](https://www.google.com/search?q=disk+block+and+logical+records+blocking+factor+in+dbms+diagram&udm=2)**

```text
HARD DISK / SSD                                          MAIN MEMORY (RAM)
+---------------------------------------------------+    +-------------------+
|PHYSICAL RECORD (DISK BLOCK)  Size B = 512 Bytes   |    |   Memory Buffer   |
| +-------------+ +-------------+ +-------------+   |    |                   |
| | Logical Rec | | Logical Rec | | Logical Rec |   |===>| Reads/Writes 1    |
| |   1 (80 B)  | |   2 (80 B)  | |   3 (80 B)  |   |    | WHOLE Block at a  |
| +-------------+ +-------------+ +-------------+   |    | time! (1 Disk I/O)|
| | Logical Rec | | Logical Rec | | Logical Rec |   |    +-------------------+
| |   4 (80 B)  | |   5 (80 B)  | |   6 (80 B)  |   |
| +-------------+ +-------------+ +-------------+   |
| [ 32 Bytes Unused Space ]                         |
+---------------------------------------------------+
```

### 1. Logical Record (or File Record)
* **Definition:** A **Logical Record** is a collection of related field values that represents **one single tuple (row)** of a table as seen by the user or application program.
* **Size ($R$):** Measured in bytes.
  * *Example (from your Oct 2025 & Nov 2025 exam papers):* One `EMPLOYEE` row containing `(ENO, NAME, DEPT, SALARY, ...)` has a logical record size of **$R = 80\text{ bytes}$**.
* **Fixed-Length vs. Variable-Length Logical Records:**
  * **Fixed-Length Record:** Every record in the file has the exact same size in bytes (e.g., every `EMPLOYEE` record is exactly $80\text{ bytes}$).
  * **Variable-Length Record:** Different records have different byte lengths (e.g., because of `VARCHAR` columns or repeating fields). Requires special separator characters or length headers.

---

### 2. Physical Record (or Disk Block / Page)
* **Definition:** A **Physical Record**—almost always called a **Disk Block** (or **Page**)—is the **smallest unit of data transfer (I/O)** between the secondary storage disk and main memory (RAM).
* **Size ($B$):** Determined by the operating system/hardware, typically ranging from **$512\text{ bytes}$** to **$4096\text{ bytes}$ ($4\text{ KB}$)** or **$8\text{ KB}$**.
* **Why Physical Blocks Matter for Database Speed:**
  * Even if your SQL query only wants **one single $80\text{-byte}$ `EMPLOYEE` record**, the hard disk **cannot** send just $80\text{ bytes}$ to RAM!
  * The disk controller must read and transfer the **entire $512\text{-byte}$ Disk Block** containing that record into RAM.
  * Because reading/writing a disk block is **thousands of times slower** than CPU operations in RAM, the cost of any database operation is always measured by the **Number of Block Accesses (Disk I/O Transfers)**!

### Comparison Table: Logical Record vs. Physical Record (Disk Block)

| Feature | Logical Record | Physical Record (Disk Block) |
| :--- | :--- | :--- |
| **1. Meaning** | One single data row/tuple of a table (e.g., 1 Employee's details). | The contiguous chunk of bytes transferred in a single Disk-to-RAM I/O operation. |
| **2. Who Sees It?** | Seen by users, SQL queries, and application programs. | Managed internally by the Operating System and DBMS Storage Manager. |
| **3. Typical Size** | Small (e.g., $R = 80\text{ bytes}$ or $100\text{ bytes}$). | Larger (e.g., $B = 512\text{ bytes}$, $4\text{ KB}$, or $8\text{ KB}$). |
| **4. Relationship** | **Many** logical records are packed inside **one** physical disk block. | One physical disk block holds **$bfr$ (Blocking Factor)** logical records. |

## PART B: Blocking Factor ($bfr$) & Unspanned vs. Spanned Organization

### 1. Blocking Factor ($bfr$) – The Most Important Formula in Module 3!
* **Definition:** The **Blocking Factor ($bfr$)** of a file is the **number of logical records that can fit inside a single physical disk block**.
* **Formula (for Unspanned Fixed-Length Records):**
  $$bfr = \left\lfloor \frac{B}{R} \right\rfloor \text{ records per block}$$
  * Where:
    * $B$ = Block size in bytes
    * $R$ = Logical record size in bytes
    * $\lfloor \cdot \rfloor$ = **Floor function** (always **round DOWN** to the nearest whole integer!).

#### Why Do We Round DOWN ($\lfloor \cdot \rfloor$) for $bfr$?
* Suppose Block Size $B = 512\text{ bytes}$ and Record Size $R = 80\text{ bytes}$:
  $$\frac{512}{80} = 6.4$$
* Six full records take $6 \times 80 = 480\text{ bytes}$, leaving $512 - 480 = \mathbf{32\text{ bytes}}$ of free space at the end of the block.
* Can a 7th $80\text{-byte}$ record fit inside those remaining $32\text{ bytes}$? **No!** So only **$bfr = 6$ whole records** fit in 1 block!

---

### 2. Total Number of Blocks ($b$) Needed to Store a File
If a file has a total of **$r$ records**, and each block holds **$bfr$ records**, how many disk blocks ($b$) do we need to store the entire file?

* **Formula:**
  $$b = \left\lceil \frac{r}{bfr} \right\rceil \text{ blocks}$$
  * Where $\lceil \cdot \rceil$ is the **Ceiling function** (always **round UP** to the nearest whole integer!).

#### Why Do We Round UP ($\lceil \cdot \rceil$) for Total Blocks $b$?
* Suppose we have $r = 10,000$ records and $bfr = 6$ records per block:
  $$\frac{10000}{6} = 1666.666\dots$$
* The first $1666$ blocks hold $1666 \times 6 = 9,996$ records.
* What about the remaining $4$ records ($9997, 9998, 9999, 10000$)? We cannot throw them away—they need **1 more disk block** (Block #1667)!
* Therefore, Total Blocks $b = \lceil 1666.67 \rceil = \mathbf{1667\text{ blocks}}$!

> 🧠 **Exam Memory Rule (Never Mix These Up!):**
> * **Blocking Factor ($bfr$) $\rightarrow$ FLOOR $\lfloor B / R \rfloor$ (Round DOWN)** *(can't squeeze a whole record into tiny leftover bytes)*.
> * **Total Blocks ($b$) $\rightarrow$ CEILING $\lceil r / bfr \rceil$ (Round UP)** *(leftover records still need one final block)*.

---

### 3. Unspanned vs. Spanned Record Organization

What should the DBMS do with those leftover $32\text{ bytes}$ at the end of Block 1? Depending on whether we leave them empty or use them to start the next record, we get **Unspanned** vs. **Spanned** organization:

📸 **[Click here to view Spanned vs Unspanned Record Organization Diagrams on Google Images](https://www.google.com/search?q=spanned+and+unspanned+record+organization+in+dbms+diagram&udm=2)**

```text
1. UNSPANNED ORGANIZATION (Records NEVER cross block boundaries)
Block 1 (512 Bytes)                                Block 2 (512 Bytes)
+-------+-------+-------+-------+-------+-------+----+ +-------+-------+-------+---
| Rec 1 | Rec 2 | Rec 3 | Rec 4 | Rec 5 | Rec 6 |32B | | Rec 7 | Rec 8 | Rec 9 |...
| (80B) | (80B) | (80B) | (80B) | (80B) | (80B) |Free| | (80B) | (80B) | (80B) |
+-------+-------+-------+-------+-------+-------+----+ +-------+-------+-------+---
                                                  ^
                                        (Wasted unused space!)

2. SPANNED ORGANIZATION (Record 7 is split across Block 1 and Block 2!)
Block 1 (512 Bytes)                                    Block 2 (512 Bytes)
+-------+-------+-------+-------+-------+-------+----+ +-------+-------+-------+---
| Rec 1 | Rec 2 | Rec 3 | Rec 4 | Rec 5 | Rec 6 |Rec7| |Rec7   | Rec 8 | Rec 9 |...
| (80B) | (80B) | (80B) | (80B) | (80B) | (80B) |Pt.1|-->(Pt.2)| (80B) | (80B) |
+-------+-------+-------+-------+-------+-------+----+ +-------+-------+-------+---
                                                  ^
                                    (Pointer to rest of Rec 7 in Block 2)
```

#### Comparison Table: Unspanned vs. Spanned Organization

| Feature | Unspanned Organization | Spanned Organization |
| :--- | :--- | :--- |
| **1. Definition** | Each logical record must fit **completely inside a single disk block**; records never cross block boundaries. | A logical record **can be split across two or more disk blocks** if it does not fit in the remaining space of the current block. |
| **2. Pointer Needed?** | **No** intra-record pointer needed. | **Yes**, a block pointer is stored at the end of the first fragment pointing to the block containing the rest of the record. |
| **3. Space Utilization** | Wastes space at the end of every block ($B - bfr \times R$ bytes lost per block). | **No wasted space** at the end of blocks (100% packing efficiency, minus tiny pointer size). |
| **4. Reading Speed** | **Faster** (reading any 1 record always requires **only 1 block access**). | **Slower** for split records (reading a spanned record requires **2 block accesses**!). |
| **5. When is it Mandatory?** | Used whenever record size $R \le B$ (default in almost all exam numericals!). | **Mandatory** whenever a record is larger than an entire block ($R > B$). |

## PART C: Pinned vs. Unpinned Record Organization

When records are stored inside disk blocks, how do external indexes or other records point to them, and what happens when a record is deleted or moved? This gives rise to **Pinned** vs. **Unpinned** organization:

📸 **[Click here to view Pinned vs Unpinned Records (Slotted Page) Diagrams on Google Images](https://www.google.com/search?q=slotted+page+structure+unpinned+records+in+dbms+diagram&udm=2)**

```text
1. PINNED RECORD ORGANIZATION (External pointer points to EXACT physical byte offset!)
   External Index ----> [ Block 5, Byte Offset 160 ]
                              |
                              v
   Block 5:  [ Rec 1 (0..79) | Rec 2 (80..159) | Rec 3 (160..239) ]
   (We CANNOT move Rec 3 to Byte 80 if Rec 2 is deleted, or the external pointer breaks!)

2. UNPINNED RECORD ORGANIZATION (Uses a Block Header / Slot Directory!)
   External Index ----> [ Block 5, Slot #3 ]
                              |
                              v
   Block 5:  [ HEADER: Slot1->0 | Slot2->80 | Slot3->160 ] ... [ Rec 1 | Rec 2 | Rec 3 ]
   (If Rec 2 is deleted, we CAN slide Rec 3 left to Byte 80 and just update Slot3->80 in the Header!)
```

### 1. Pinned Organization (Pinned Records)
* **Definition:** A record is said to be **Pinned** to its physical disk block and byte offset if other records or indexes in the database hold **direct physical pointers** (exact `Block_Address + Byte_Offset`) pointing straight to that record's physical location.
* **Why is it called "Pinned"?** Because the record is "nailed down" to that exact spot on disk! You **cannot move** the record to another block (or even slide it left inside the same block to fill empty space after a deletion) without turning all external pointers into **dangling pointers** (pointing to garbage data).
* **How Deletions Work in Pinned Files:** When a pinned record is deleted, we cannot shift the remaining records over. Instead, we leave the empty hole in place and set a special 1-bit flag called a **Tombstone (Deletion Marker)** so the DBMS knows that slot is dead.

### 2. Unpinned Organization (Unpinned Records)
* **Definition:** Records are **Unpinned** if no external pointer points directly to their exact physical byte address. Instead, references use either:
  1. **Logical Pointers** (such as the record's Primary Key value), **OR**
  2. **Indirect Pointers (Record ID = `Block_No + Slot_No`)** via a **Block Header Directory (Slotted Page Architecture)** at the beginning of the block.
* **Advantage:** Because external pointers only point to `Slot #3` in the block header—and the block header stores the actual byte offset inside the block—the DBMS can freely move, compact, or resize records inside the block and simply update the byte offset inside `Slot #3`!

### Comparison Table: Pinned vs. Unpinned Organization

| Feature | Pinned Organization | Unpinned Organization |
| :--- | :--- | :--- |
| **1. Type of Pointer Used** | **Direct Physical Address** (`Block_No + Exact Byte Offset`). | **Logical Key** or **Indirect Slot Pointer** (`Block_No + Slot_ID` via Block Header). |
| **2. Can Records Be Moved Easily?** | **No!** Moving a record breaks external physical pointers (creates dangling pointers). | **Yes!** Records can be moved/compacted freely by updating the block header directory. |
| **3. Handling Deletions** | Uses a **Tombstone / Deletion Marker bit**; leaves unused gaps until reorganization. | Can immediately shift remaining records to reclaim contiguous free space. |
| **4. Variable-Length Records** | Very difficult to manage if a record grows during an `UPDATE`. | Easy to manage (standard **Slotted-Page** architecture used in modern RDBMS). |

## PART D: Heap Files (Unordered) vs. Ordered (Sequential) Files

How do we arrange the records across the $b$ blocks of a file when **no index is used**? There are two primary file organizations:

📸 **[Click here to view Heap File vs Sequential (Ordered) File Organization on Google Images](https://www.google.com/search?q=heap+file+organization+vs+sequential+file+organization+in+dbms+diagram&udm=2)**

---

### 1. Heap File (or Pile File / Unordered File)
* **How it works:** Records are placed in the file in the **exact chronological order in which they are inserted**. There is **no sorting** on any attribute.
* **How `INSERT` works (Very Fast!):**
  * New records are simply **appended at the very end of the file** (inside the last disk block).
  * Requires only **2 block accesses**: $1$ read to bring the last block into RAM + $1$ write to save the modified last block back to disk!
* **How `SEARCH` works (Very Slow – Linear Search!):**
  * Because records are completely unsorted, finding a record with a specific `Employee_ID` requires a **Linear Search** (reading blocks one by one from Block $1, 2, 3, \dots, b$):
    * **Average Block Accesses to find a unique key:** **$\frac{b}{2}$ blocks** *(on average you find it halfway through the file)*.
    * **Worst-Case Block Accesses (or if record is not found / non-unique field):** **$b$ blocks** *(must read every single block in the file)*.
* **How `DELETE` works:**
  * Search for the block ($\frac{b}{2}$ reads), mark the record as deleted in RAM, and write the block back ($+1$ write). Periodic reorganization is used to pack wasted tombstone spaces.

---

### 2. Ordered File (or Sequential / Sorted File)
* **How it works:** The records in the file are physically stored on disk **sorted in ascending/descending order** of a specific field called the **Ordering Field** (if the ordering field is also the Primary Key, it is called the **Ordering Key**).
* *Example (from your Oct 2025 Q3b & Nov 2025 Q5a papers!):*
  > *"The EMPLOYEE file with 10000 records is **sorted on employee number**, which is the primary key."*
  This means the `EMPLOYEE` file is an **Ordered (Sequential) File**!

```text
ORDERED (SEQUENTIAL) FILE (Sorted on ENO -> Enables Binary Search!)
Block 1                  Block 2                  ...   Block 1667
+----------------------+ +----------------------+       +----------------------+
| ENO: 1, 2, 3, 4, 5, 6| | ENO: 7, 8, 9,10,11,12|  ...  | ENO: 9997..10000     |
+----------------------+ +----------------------+       +----------------------+
```

* **How `SEARCH` works on the Ordering Key (Super Fast – Binary Search!):**
  * Because the blocks are sorted by `ENO`, we do **NOT** need to scan all $b$ blocks linearly! Instead, we perform **Binary Search** on the $b$ disk blocks (check middle block $\frac{b}{2}$, then quarter block $\frac{b}{4}$, etc.):
  * **Block Accesses using Binary Search on an Ordered File:**
    $$\text{Block Accesses} = \left\lceil \log_2(b) \right\rceil \text{ blocks}$$
  * *(Look at the massive speedup: for $b = 1667$ blocks, Linear Search takes up to **$1667$ block accesses** [or $834$ on average], whereas Binary Search takes only $\lceil \log_2(1667) \rceil = \mathbf{11\text{ block accesses}}$!)*
* **How `INSERT` works (Slow!):**
  * Inserting a new record (say `ENO = 5`) into the middle of a sorted file is expensive because we must shift subsequent records to keep the file sorted (or use temporary unsorted **Overflow Blocks** and periodically merge/reorganize them).

---

### Summary Table of Block Access Formulas (When NO Index is Used)

| Operation | Heap (Unordered) File ($b$ blocks) | Ordered (Sorted) File ($b$ blocks, on Ordering Key) |
| :--- | :--- | :--- |
| **1. Search for a Record (Average)** | **$\frac{b}{2}$** *(Linear Search)* | **$\left\lceil \log_2(b) \right\rceil$** *(Binary Search)* |
| **2. Search for a Record (Worst Case)** | **$b$** *(Linear Search all blocks)* | **$\left\lceil \log_2(b) \right\rceil$** *(Binary Search)* |
| **3. Insert a New Record** | **$2$** *(Read last block + Write last block)* | $\left\lceil \log_2(b) \right\rceil + \text{shifting cost (or overflow block)}$ |

## PART E: Solved Exam Numerical – Part (i) of Oct 2025 Q3(b) & Nov 2025 Q5(a)

Look at how Part (i) of the numerical from **both** your **Oct 2025 Internal Test Q3(b)** and **Nov 2025 End-Sem Exam Q5(a)** is solved using what you just learned in `3.3`:

> **Problem Statement (Part i):**
> *"Consider an EMPLOYEE file with $10000$ records where each record is of size $80\text{ bytes}$. The file is sorted on employee number ($15\text{ bytes}$ long), which is the primary key. Assuming un-spanned organization, block size of $512\text{ bytes}$ and block pointer size of $5\text{ bytes}$. Compute the number of block accesses needed for retrieving an employee record based on employee number if **(i) No index is used**."*

### ✅ Step-by-Step Solution for Part (i):

**1. Given Data:**
* Total number of records in the file ($r$) = $10,000$ records
* Size of each logical record ($R$) = $80\text{ bytes}$
* Block size ($B$) = $512\text{ bytes}$
* Record organization = **Unspanned**
* File organization = **Sorted (Ordered)** on Primary Key (`employee number`)

**2. Step 1 – Calculate Blocking Factor ($bfr$) of the Data File:**
Since the organization is **unspanned**, each record must fit completely within a block:
$$bfr = \left\lfloor \frac{B}{R} \right\rfloor = \left\lfloor \frac{512}{80} \right\rfloor = \lfloor 6.4 \rfloor = \mathbf{6\text{ records per block}}$$

**3. Step 2 – Calculate Total Number of Data Blocks ($b$) Required:**
$$b = \left\lceil \frac{r}{bfr} \right\rceil = \left\lceil \frac{10000}{6} \right\rceil = \lceil 1666.67 \rceil = \mathbf{1667\text{ blocks}}$$

**4. Step 3 – Calculate Block Accesses when (i) No Index is Used:**
*(Pro-Tip: In exams, write **both** the Binary Search value [since the file is sorted on employee number] AND the Linear Search value—that way, whichever one is printed on the teacher's answer key, you get 100% full marks!)*

* **Using Binary Search (since the file is sorted on the search key `employee number`):**
  $$\text{Number of Block Accesses} = \left\lceil \log_2(b) \right\rceil = \left\lceil \log_2(1667) \right\rceil$$
  *(Since $2^{10} = 1024$ and $2^{11} = 2048$, $\log_2(1667) \approx 10.70$, so rounding up gives:)*
  $$\text{Block Accesses (Binary Search)} = \mathbf{11\text{ block accesses}}$$

* **Using Linear Search (if searched sequentially without binary search):**
  * **Average case:** $\left\lceil \frac{b}{2} \right\rceil = \left\lceil \frac{1667}{2} \right\rceil = \mathbf{834\text{ block accesses}}$
  * **Worst case:** $b = \mathbf{1667\text{ block accesses}}$

### Quick 30-Second Recap of 3.3
* **Logical Record ($R$):** 1 row of data ($80\text{ bytes}$). **Physical Record / Block ($B$):** 1 unit of disk transfer ($512\text{ bytes}$).
* **Blocking Factor:** $bfr = \lfloor B / R \rfloor$ *(always round DOWN)*.
* **Total Data Blocks:** $b = \lceil r / bfr \rceil$ *(always round UP)*.
* **Unspanned vs Spanned:** Unspanned = records never split across blocks; Spanned = records split across blocks using a pointer.
* **Pinned vs Unpinned:** Pinned = external pointers point to exact physical byte offsets (can't move records); Unpinned = uses a Block Header / Slot Directory (can move records freely).
* **Heap File:** Unsorted, fast insert ($2$ accesses), slow linear search ($b/2$ average, $b$ worst).
* **Ordered File:** Sorted on Ordering Key, fast **Binary Search** ($\lceil \log_2(b) \rceil$ accesses).
