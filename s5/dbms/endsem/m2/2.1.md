## PART A: Structure of Relational Databases

The **Relational Model** of data was introduced by **Dr. E. F. Codd in 1970**. It is the foundation of almost all modern commercial database systems (PostgreSQL, MySQL, Oracle, SQL Server).

In the relational model, the database is perceived by the user as a collection of **two-dimensional tables**, formally called **Relations**.

### 2. Core Terminology (Formal vs. Informal Terms)

In exams, teachers look for the **formal relational terms** alongside their everyday table meanings:

| Formal Relational Term | Informal Equivalent | Clear Definition & Example |
| :--- | :--- | :--- |
| **1. Relation** | Table | A two-dimensional table composed of rows and columns representing an entity or relationship. *(e.g., `STUDENT`)* |
| **2. Tuple ($t$)** | Row / Record | A single horizontal row in a relation representing one real-world object/instance. *(e.g., `(7, 'Adhil', 'EEE', 8.6)`)* |
| **3. Attribute ($A_i$)** | Column / Field | A named vertical column of a relation describing a property of the entity. *(e.g., `Roll_No`, `Name`, `Branch`)* |
| **4. Domain ($D_i$)** | Data Type & Allowed Values | The pool/set of permitted **atomic (indivisible)** values that an attribute is allowed to take. *(e.g., Domain of `Branch` is `{'EEE', 'CSE', 'ECE', 'ME'}`)* |
| **5. Degree (or Arity)** | Number of Columns | The total number of **attributes (columns)** in the relation schema. *(In the table above, Degree = 4).* |
| **6. Cardinality** | Number of Rows | The total number of **tuples (rows)** present in the relation at a given moment. *(In the table above, Cardinality = 4).* |
| **7. Relation Schema** | Table Structure | Denoted as $R(A_1, A_2, \dots, A_n)$. Specifies the relation name and its attributes. *(e.g., `STUDENT(Roll_No, Name, Branch, CGPA)`)* |
| **8. Relation State ($r(R)$)** | Table Data (Instance) | The set of actual tuples stored in relation $R$ at a specific moment in time. |

> **Quick Memory Trick for Degree vs. Cardinality:**
> * **D**egree = **D**efinition (Columns in the schema; rarely changes).
> * **C**ardinality = **C**ount of rows (Tuples in the table; changes with every `INSERT` or `DELETE`).

### 3. Four Fundamental Properties of a Relation

Because a Relation is mathematically defined as a **set of tuples**, every relation has four strict properties:

1. **Values in Tuples are Atomic (Indivisible):**
   * Each cell (intersection of a row and column) must hold **only one single value**.
   * Multivalued attributes (like storing two phone numbers `9847011111, 9847022222` inside one cell) or composite structures are **not allowed**. *(This is also known as the **First Normal Form (1NF)** rule!)*
2. **No Duplicate Tuples Exist:**
   * Since a relation is a mathematical *set* of tuples, no two rows in a relation can be 100% identical across all columns.
3. **Ordering of Tuples is Unimportant:**
   * A set has no order. Whether `(7, 'Adhil', 'EEE', 8.6)` is displayed as the 1st row or the 4th row, the relation is mathematically identical.
4. **NULL Values Represent Unknown or Inapplicable Data:**
   * A special value **`NULL`** is used when the value of an attribute for a tuple is either:
     * **Unknown** (e.g., an employee's date of birth exists, but we don't know it yet), or
     * **Not Applicable / Undefined** (e.g., `First_Sem_CGPA` for a newly admitted student who hasn't taken any exams yet).
   * **Important:** `NULL` is **not** zero (`0`) and **not** an empty string (`''`). Two `NULL` values are never considered equal (`NULL = NULL` is `UNKNOWN`, not `TRUE`).

## PART B: Keys in a Relational Database

Before you can understand Integrity Constraints (or Normalization in Module 4), you must clearly understand the **6 types of Keys**.

Suppose we have a `STUDENT` table with attributes:
`STUDENT (Roll_No, Aadhar_No, Email, Name, Branch, Dept_ID)`

```text
|   |    | Chosen by Designer     |  |  Unchosen CKs       |    |   |

|   +-----------------------------------------------------------+   |

```

### 1. Superkey ($SK$)
* **Definition:** A **Superkey** is any single attribute, or set of attributes, that **uniquely identifies a tuple** in a relation. No two distinct tuples in any valid state of the relation can have the exact same value for the Superkey.
* **Key Property:** If $K$ is a Superkey, then adding *any* arbitrary attribute to $K$ also forms a Superkey!
* **Examples in `STUDENT`:**
  * `{Roll_No}` (Unique)
  * `{Aadhar_No}` (Unique)
  * `{Roll_No, Name}` (Still unique! Even though `Name` is redundant)
  * `{Roll_No, Name, Branch}` (Still unique!)

### 2. Candidate Key ($CK$)
* **Definition:** A **Candidate Key** is a **minimal Superkey**—that is, a Superkey from which **no attribute can be removed** without losing the uniqueness property.
* **Examples in `STUDENT`:**
  * Is `{Roll_No, Name}` a Candidate Key? **No!** Because if we remove `Name`, `{Roll_No}` alone is still unique. So `{Roll_No, Name}` is a Superkey, *not* a Candidate Key.
  * What are the Candidate Keys of `STUDENT`?
    1. `{Roll_No}`
    2. `{Aadhar_No}`
    3. `{Email}`
* **Note:** Every Candidate Key is a Superkey, **but not every Superkey is a Candidate Key**.

### 3. Primary Key ($PK$)
* **Definition:** When a relation has multiple Candidate Keys, the database designer chooses **one** of them to be the principal identifier of tuples in that relation. This chosen Candidate Key is called the **Primary Key**.
* **Rules for Primary Key:**
  1. There can be **at most ONE Primary Key** per table.
  2. It must be **Unique** AND **Cannot be `NULL`** (`NOT NULL`).
  3. In relational schemas, the Primary Key is always **underlined**:
     $$\text{STUDENT}(\underline{\text{Roll\_No}}, \text{Aadhar\_No}, \text{Email}, \text{Name}, \text{Branch}, \text{Dept\_ID})$$

### 4. Alternate Key (or Secondary Key)
* **Definition:** Any Candidate Key that was **not** chosen by the designer to be the Primary Key.
* **Formula:** $\text{Alternate Keys} = \text{Candidate Keys} - \text{Primary Key}$
* **Example:** Since `Roll_No` was chosen as the Primary Key, `Aadhar_No` and `Email` become **Alternate Keys**.

### 5. Composite Key (or Concatenated Key)
* **Definition:** When a Primary Key (or Candidate Key) consists of **two or more attributes combined together** because no single attribute can uniquely identify a row on its own.
* **Example:** In your **Oct 2026 Internal Test Q2**, a student registers for many courses:
  $$\text{REGISTRATION}(\underline{\text{Student\_ID}, \text{Course\_ID}}, \text{Semester}, \text{Grade})$$
  * Here, `Student_ID` alone repeats (one student takes 6 courses), and `Course_ID` alone repeats (60 students take DBMS). Only the pair **`(Student_ID, Course_ID)` together** uniquely identifies a registration row!

### 6. Foreign Key ($FK$)
* **Definition:** An attribute (or set of attributes) in one relation $R_1$ (called the **Referencing / Child Relation**) whose values are required to match the **Primary Key** of another relation $R_2$ (called the **Referenced / Parent Relation**).
* **Purpose:** Foreign keys act as the "glue" that links two tables together to represent relationships.
* **Important Rules:**
  * Unlike a Primary Key, a Foreign Key **CAN have duplicate values** (e.g., 60 students can all have `Dept_ID = 'D01'`).
  * A Foreign Key **CAN be `NULL`** (unless explicitly restricted by `NOT NULL`).

### 7. Prime vs. Non-Prime Attributes (Important for Module 4!)
* **Prime Attribute:** Any attribute that is a member of **any Candidate Key**.
* **Non-Prime Attribute:** Any attribute that is **not** part of any Candidate Key.

## PART C: Relational Integrity Constraints

> ⭐ **DIRECT EXAM QUESTION:** Asked in **Oct 2025 Internal Test Q2(a) (3.5 Marks)**: *"Distinguish Entity Integrity constraints and Referential Integrity constraints with suitable examples."*

**Integrity Constraints** are conditions/rules specified on a database schema that restrict the data that can be stored in an instance of the database. If an `INSERT`, `DELETE`, or `UPDATE` operation violates an integrity constraint, the DBMS rejects the operation to keep the database consistent.

The core constraints of the Relational Model (often called **Relational Model Constraints** or **Schema-Based Constraints**) are divided into **three main categories**:
1. **Domain Constraints**
2. **Key Constraints & Entity Integrity Constraint**
3. **Referential Integrity Constraint**

📸 **[Click here to view Types of Integrity Constraints in DBMS on Google Images](https://www.google.com/search?q=integrity+constraints+in+dbms+domain+entity+referential+diagram&udm=2)**

---

### 1. Domain Constraints
* **Rule:** Domain constraints specify that within each tuple, the value of each attribute $A$ must be an **atomic (indivisible) value** from the specified domain $\text{dom}(A)$ of that attribute.
* **What it checks:**
  1. **Data Type:** Integer, Floating-point, Fixed-length character (`CHAR`), Variable-length character (`VARCHAR`), Date, Boolean.
  2. **Value Range / Enumeration (`CHECK` constraint):** e.g., `Age` must be between `18` and `65`; `Semester` must be between `1` and `8`.
  3. **Atomicity:** A single cell cannot contain a list/array of values.
* **Example of Violation:**
  Suppose we have `STUDENT(Roll_No INT, Name VARCHAR(30), Marks INT CHECK(Marks BETWEEN 0 AND 100))`.
  * Inserting `(7, 'Adhil', 'Eighty-Five')` $\rightarrow$ **Violates Domain Constraint** (string `'Eighty-Five'` inserted into an `INT` domain).
  * Inserting `(8, 'Rahul', 120)` $\rightarrow$ **Violates Domain Constraint** (`120` is outside the permitted domain `0..100`).

---

### 2. Entity Integrity Constraint (and Key Constraints)
* **Key Constraint (Uniqueness Rule):** All values of the Primary Key (or any Candidate Key) must be **unique** across all tuples in a relation. No two rows can have the same Primary Key value.
* **Entity Integrity Constraint (Formal Statement):**
  > *"The **Entity Integrity Constraint** states that **no Primary Key value (or any component attribute of a composite Primary Key) can be `NULL`**."*
* **Why is `NULL` forbidden in a Primary Key? (Always write this reason in the exam!):**
  * The Primary Key is used to **uniquely identify individual tuples** in a relation.
  * Having `NULL` values for the primary key implies that we cannot identify some tuples! Furthermore, if two or more tuples had `NULL` as their primary key, we would not be able to distinguish them from one another.
* **Suitable Example (Valid vs. Invalid):**

  **Table: `STUDENT` ($\underline{\text{Roll\_No}}$ is the Primary Key)**
  | Roll_No (PK) | Name | Branch | Status |
  | :--- | :--- | :--- | :--- |
  | `7` | Adhil | EEE | ✅ **Valid** (Unique & Not NULL) |
  | `8` | NULL | EEE | ✅ **Valid** (`Name` is NOT a PK, so `NULL` is allowed unless marked `NOT NULL`) |
  | `7` | Meera | CSE | ❌ **Invalid!** Violates **Key Constraint** (Duplicate PK `7`) |
  | **`NULL`** | Arjun | ECE | ❌ **Invalid!** Violates **Entity Integrity Constraint** (PK cannot be `NULL`!) |

* **Note on Composite Primary Keys:** If a table has a composite primary key $\text{REGISTRATION}(\underline{\text{Student\_ID}, \text{Course\_ID}})$, **neither** `Student_ID` **nor** `Course_ID` is allowed to be `NULL` (so `(7, NULL)` is also rejected!).

---

### 3. Referential Integrity Constraint
While Entity Integrity applies to a **single relation**, the **Referential Integrity Constraint** is specified **between two relations** (or between two tuples of the same relation) and is used to maintain consistency among tuples in the two relations.

* **Informal Meaning:** If a tuple in one relation refers to another relation, it must refer to an **existing tuple** in that relation (no "dangling references" to non-existent records!).
* **Formal Statement:**
  > *"A tuple $t_1$ in a **Referencing Relation $R_1$** (Child Table) that has a **Foreign Key ($FK$)** referencing the **Primary Key ($PK$)** of a **Referenced Relation $R_2$** (Parent Table) must satisfy one of two conditions:*
  > 1. *The value of $FK$ in $t_1$ must **match an existing Primary Key ($PK$) value** of some tuple $t_2$ in $R_2$, **OR***
  > 2. *The value of $FK$ in $t_1$ must be wholly **`NULL`** (provided $FK$ is not part of $R_1$'s own Primary Key)."*

📸 **[Click here to view Referential Integrity Foreign Key to Primary Key Diagrams on Google Images](https://www.google.com/search?q=referential+integrity+constraint+in+dbms+example+diagram&udm=2)**

#### Suitable Example (Diagram + Tables to Draw in Exam):

Consider two relations: `DEPARTMENT` (**Referenced / Parent Table**) and `EMPLOYEE` (**Referencing / Child Table**), where `DNO` in `EMPLOYEE` is a **Foreign Key** referencing `DNO` in `DEPARTMENT`.

```text
REFERENCING RELATION (Child)                 REFERENCED RELATION (Parent)
EMPLOYEE                                     DEPARTMENT
+-----+--------+-----------+                 +-----+------------+
| ENO | ENAME  | DNO (FK)  |                 | DNO | DNAME      |
| (PK)|        |           |                 | (PK)|            |
+=====+========+===========+                 +=====+============+
| 101 | Adhil  |    10 ----+---------------->| 10  | EEE        |  (Valid: 10 exists)
| 102 | Rahul  |    20 ----+-------+         | 20  | CSE        |  (Valid: 20 exists)
| 103 | Meera  |    10 ----+-----+ |         | 30  | Accounts   |
| 104 | Kiran  |   NULL    |     | +-------->+-----+------------+  (Valid: NULL allowed)
+-----+--------+-----------+     +---------->  (Points to 10)
| 105 | Manoj  |    99 ----+---> ❌ ERROR! Violates Referential Integrity!
+-----+--------+-----------+     (Because DNO = 99 does NOT exist in DEPARTMENT!)
```

#### Special Case: Self-Referencing Foreign Key (Appeared in Oct 2025 Q2b & Nov 2025 Q4!)
Can a Foreign Key reference the Primary Key of the **exact same table**? **YES!**
* In your exam papers, the `EMPLOYEE` table has:
  $$\text{EMPLOYEE}(\underline{\text{ENO}}, \text{NAME}, \dots, \text{SUPERENO})$$
* Here, `SUPERENO` (Supervisor's Employee Number) is a **Foreign Key** that references `ENO` (Primary Key) of the **same `EMPLOYEE` table**!
* Every employee's `SUPERENO` must either match an existing employee's `ENO`, or be `NULL` (for the CEO who has no supervisor).

### 4. How Referential Integrity Violations Happen & How DBMS Handles Them

How can an operation break Referential Integrity, and what does the DBMS do?

#### Case 1: Inserting into the Child Table (`EMPLOYEE`)
* If you try to `INSERT` an employee with `DNO = 99` when Department `99` does not exist in `DEPARTMENT`, the DBMS simply **REJECTS** the insertion.

#### Case 2: Deleting or Updating a Row in the Parent Table (`DEPARTMENT`)
* Suppose Department `10` (`EEE`) already has employees `101 (Adhil)` and `103 (Meera)` working in it. What happens if someone tries to run `DELETE FROM DEPARTMENT WHERE DNO = 10;`?
* If Department `10` is deleted, Adhil and Meera will be left pointing to a non-existent department! To prevent this violation, SQL allows the designer to specify one of **4 Referential Triggered Actions** (`ON DELETE` / `ON UPDATE`):

| Action | SQL Syntax | What the DBMS Does |
| :--- | :--- | :--- |
| **1. RESTRICT / NO ACTION** *(Default)* | `ON DELETE RESTRICT` | **Rejects** the deletion of Department `10` as long as any employee still references `DNO = 10`. |
| **2. CASCADE** | `ON DELETE CASCADE` | Deletes Department `10` from `DEPARTMENT` **AND automatically deletes** all employees in `EMPLOYEE` who had `DNO = 10`! |
| **3. SET NULL** | `ON DELETE SET NULL` | Deletes Department `10`, and automatically changes `DNO` of Adhil and Meera in `EMPLOYEE` to **`NULL`**. |
| **4. SET DEFAULT** | `ON DELETE SET DEFAULT` | Deletes Department `10`, and sets `DNO` of those employees to a pre-defined default department (e.g., `'00'`). |

## PART D: Comparison Table: Entity Integrity vs. Referential Integrity

> ⭐ **MEMORIZE THIS TABLE:** Directly answers **Oct 2025 Internal Test Q2(a) (3.5 Marks)**!

| Feature | Entity Integrity Constraint | Referential Integrity Constraint |
| :--- | :--- | :--- |
| **1. Core Rule** | States that **no Primary Key attribute can be `NULL`** (and must be unique). | States that a **Foreign Key value must either match an existing Primary Key value** in the referenced table, or be **`NULL`**. |
| **2. Key Involved** | Applies to the **Primary Key (PK)** of a relation. | Applies to the **Foreign Key (FK)** referencing a Primary Key. |
| **3. Number of Tables** | Enforced on a **single relation** (table) independently. | Enforced **between two relations** (Parent/Referenced and Child/Referencing tables), or self-referencing. |
| **4. Are `NULL` Values Allowed?** | **No (`NULL` is strictly prohibited)** in any part of a Primary Key. | **Yes (`NULL` is allowed)** in a Foreign Key (if the relationship is optional and FK is not part of a PK). |
| **5. Are Duplicate Values Allowed?** | **No**, Primary Key values must be unique across all rows. | **Yes**, multiple child rows can have the same Foreign Key value (e.g., many employees in Dept `10`). |
| **6. Purpose** | Ensures that every tuple in a table can be **uniquely identified**. | Ensures **valid links/references** between related tables (prevents orphan/dangling records). |
| **7. Example of Violation** | Inserting a student with `Roll_No = NULL` into `STUDENT`. | Inserting an employee with `DNO = 99` when `DNO = 99` does not exist in `DEPARTMENT`. |

## PART E: Past Year Question (PYQ) from Your Papers – Full Answer

### PYQ 1: Oct 2025 Internal Test – Question II(a) [3.5 Marks]
> **Question:** *"Distinguish Entity Integrity constraints and Referential Integrity constraints with suitable examples."*

#### ✅ Model Exam Answer (Write this verbatim for 3.5 / 3.5 Marks):

**1. Entity Integrity Constraint:**
* **Definition:** The Entity Integrity Constraint states that in a base relation, **no attribute of a Primary Key can be `NULL`** (and every Primary Key value must be unique).
* **Justification:** Since the Primary Key is used to uniquely identify individual tuples in a relation, allowing `NULL` values would make it impossible to identify those tuples or distinguish between multiple tuples having `NULL` keys.
* **Example:**
  Consider the relation $\text{STUDENT}(\underline{\text{Roll\_No}}, \text{Name}, \text{Branch})$ where `Roll_No` is the Primary Key:
  * Tuple `(7, 'Adhil', 'EEE')` $\rightarrow$ **Valid** (`Roll_No` is unique and not null).
  * Tuple `(NULL, 'Rahul', 'CSE')` $\rightarrow$ **Invalid (Violates Entity Integrity)** because the Primary Key `Roll_No` is `NULL`.

**2. Referential Integrity Constraint:**
* **Definition:** The Referential Integrity Constraint is specified between two relations (a **Referencing/Child relation** and a **Referenced/Parent relation**) to maintain consistency among tuples. It states that a tuple in the referencing relation having a **Foreign Key ($FK$)** must either:
  1. Have a value that **matches an existing Primary Key ($PK$) value** in the referenced relation, **OR**
  2. Have a **`NULL`** value (if participation is optional).
* **Example:**
  Consider two relations:
  * Parent Relation: $\text{DEPARTMENT}(\underline{\text{DNO}}, \text{DNAME})$ containing departments `DNO = 10` and `DNO = 20`.
  * Child Relation: $\text{EMPLOYEE}(\underline{\text{ENO}}, \text{ENAME}, \text{DNO})$ where `DNO` is a **Foreign Key** referencing `DEPARTMENT(DNO)`.
  * Tuple `(101, 'Adhil', 10)` in `EMPLOYEE` $\rightarrow$ **Valid** (`DNO = 10` exists in `DEPARTMENT`).
  * Tuple `(102, 'Kiran', NULL)` in `EMPLOYEE` $\rightarrow$ **Valid** (Foreign Key can be `NULL`).
  * Tuple `(103, 'Manoj', 99)` in `EMPLOYEE` $\rightarrow$ **Invalid (Violates Referential Integrity)** because `DNO = 99` does not exist in the `DEPARTMENT` relation.

**3. Key Differences Summary:**

| Parameter | Entity Integrity Constraint | Referential Integrity Constraint |
| :--- | :--- | :--- |
| **Key Used** | Primary Key (PK) | Foreign Key (FK) referencing a PK |
| **Scope** | Within a **single** relation | Between **two** relations (Parent & Child) |
| **`NULL` Values** | Strictly **NOT allowed** | **Allowed** (unless specified `NOT NULL`) |
| **Duplicates** | Strictly **NOT allowed** | **Allowed** (many child rows can point to 1 parent) |

### Quick 30-Second Recap of 2.1
* **Degree** = Number of Columns (Attributes). **Cardinality** = Number of Rows (Tuples).
* **Superkey** = Any attribute combination that uniquely identifies a row.
* **Candidate Key** = Minimal Superkey (no extra attributes).
* **Primary Key** = Chosen Candidate Key (Unique + `NOT NULL`).
* **Domain Constraint** = Values must be atomic and match the column's data type/range.
* **Entity Integrity** = **Primary Key cannot be `NULL`**.
* **Referential Integrity** = **Foreign Key must match an existing Primary Key** in the parent table (or be `NULL`).
