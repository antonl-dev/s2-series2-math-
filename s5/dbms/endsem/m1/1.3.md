## PART A: Data Models and Their Types

> ⭐ **DIRECT EXAM QUESTION:** Asked in **Oct 2026 Internal Test Q1(b) (4 Marks)**: *"Explain the different types of data models with suitable examples."* and **Nov 2025 End-Sem Q1(b)(i)**: *"Explain Data Model."*

### 1. What is a Data Model?
* **Definition:** A **Data Model** is a collection of conceptual tools/concepts that can be used to describe the **structure of a database**—namely, the data types, the relationships between data, and the consistency constraints that must hold on the data. Most data models also include a set of **basic operations** for specifying retrievals and updates on the database.
* **Why we need it:** It provides **Data Abstraction**—hiding complex low-level disk storage details so designers and users can understand the database logically.

---

### 2. Classification of Data Models (With Suitable Examples)

📸 **[Click here to view Types of Data Models diagrams on Google Images](https://www.google.com/search?q=types+of+data+models+in+dbms+diagram&udm=2)**

According to the level of abstraction they provide, data models are grouped into **three main categories**:

```

---

#### Category 1: High-Level or Conceptual Data Models
Conceptual data models provide concepts that are **close to the way many users perceive data** in the real world. They are used during the initial database design phase to communicate with non-technical users.

##### a) Entity-Relationship (ER) Model (Most Popular Conceptual Model)
Uses three core concepts:
1. **Entities:** Real-world objects or concepts (e.g., `STUDENT`, `COURSE`, `EMPLOYEE`).
2. **Attributes:** Properties that describe an entity (e.g., `Roll_No`, `Name`, `Branch`).
3. **Relationships:** Associations among two or more entities (e.g., a `STUDENT` *enrolls in* a `COURSE`).

* **Example Diagram (ER Model):**
```text
 (Roll_No)   (Name)                          (Course_ID)  (Credits)
     \         /                                   \         /
   +-------------+          /+-----------+\      +-------------+
   |   STUDENT   |---------< | Enrolls_In| >-----|   COURSE    |
   +-------------+    M     \+-----------+/  N   +-------------+
```

##### b) Object-Oriented Data Model
* Defines a database as a collection of **Objects** (like in C++/Java) that encapsulate both **data values (attributes)** and **operations/methods (behavior)**, supporting classes and inheritance.

---

#### Category 2: Representational or Implementation (Logical) Data Models
Representational data models provide concepts that may be easily understood by end users, **but are not too far removed from the way data is organized within the computer storage**. These are the models actually implemented in commercial DBMS software!

##### a) Relational Data Model (Most Widely Used!)
* Proposed by **E. F. Codd (1970)**.
* Represents all data as a collection of two-dimensional tables called **Relations**.
* Each table has **Rows (Tuples / Records)** and **Columns (Attributes / Fields)**.
* Relationships between tables are represented using **Primary Keys (PK)** and **Foreign Keys (FK)** rather than physical pointers.
* **Example (Relational Model):**

  **Table: `STUDENT`**
  | Roll_No (PK) | Name | Dept_ID (FK) |
  | :--- | :--- | :--- |
  | 7 | Adhil | D01 |
  | 8 | Rahul | D02 |

  **Table: `DEPARTMENT`**
  | Dept_ID (PK) | Dept_Name |
  | :--- | :--- |
  | D01 | EEE |
  | D02 | CSE |

##### b) Hierarchical Data Model
* Organizes data in a **tree-like structure** consisting of nodes (records) and branches (links).
* **Rule:** Every child node can have **at most ONE parent node** (supports $1:N$ relationships naturally, but struggles with $M:N$ relationships without duplicating data).
* **Example:** A `College` (Root) $\rightarrow$ has multiple `Departments` $\rightarrow$ each Department has multiple `Students`. (Used in early IBM IMS systems).
```text
          [ College ]
           /       \
     [EEE Dept]  [CSE Dept]
      /      \
 [Student 1] [Student 2]
```

##### c) Network Data Model
* Organizes data as a **directed graph** rather than a strict tree.
* **Rule:** A child record (called a *Member*) can have **more than one parent record** (called an *Owner*), allowing it to model **Many-to-Many ($M:N$)** relationships directly using pointers/links.
* **Example:** A `Student` can belong to both the `EEE Department` (Parent 1) and the `Robotics Club` (Parent 2).

##### d) Semi-Structured / NoSQL Data Models (Modern Addition)
* Includes **Document Models** (JSON documents in MongoDB), **Key-Value Models** (Redis), and **Graph Models** (Neo4j).

---

#### Category 3: Low-Level or Physical Data Models
Physical data models provide concepts that describe the **exact details of how data is stored on the computer's physical storage media** (hard disks / SSDs).
* They are meant for **computer specialists and DBAs**, not end users.
* **What they describe:**
  1. **Record Formats:** Exact byte lengths and offsets of fields inside a disk block.
  2. **Record Orderings:** Whether records are stored unsorted (heap file) or sorted by a key.
  3. **Access Paths:** Structures that make searching for records fast, such as **Indexes (B+ Trees)** and **Hash Tables**.

## PART B: Database Schema vs. Database State (Instance) & Meta-Data

> ⭐ **DIRECT EXAM QUESTION:** Asked in **Nov 2025 End-Sem Q1(b) (3 Marks)**: *"Explain: i) Data Model ii) Database Schema iii) Meta-Data."*

### 1. Database Schema (Also called Intension)
* **Definition:** The **overall description or logical blueprint of the database** is called the **Database Schema**.
* **When is it specified?** It is specified during the database design phase (using DDL like `CREATE TABLE`) and is **not expected to change frequently**.
* **Schema Diagram:** A displayed schema is called a *schema diagram*. It shows the names of record types (tables) and data items (columns), and some constraints, **but NOT the actual data rows**.
* **Example of a Schema Construct:**
  ```text
  STUDENT (Roll_No, Name, Branch, Semester)
  COURSE  (Course_ID, Course_Name, Credits)
  ```

### 2. Database State / Instance / Snapshot (Also called Extension)
* **Definition:** The **actual data stored in the database at a particular moment in time** is called the **Database State** (or *Database Instance* / *Snapshot* / *Current Set of Occurrences*).
* **How often does it change?** It changes **every single time** we insert a new row, delete a row, or update a value in the database!
* **Life-Cycle of Database States:**
  1. **When a new database is first defined:** We only specify the schema to the DBMS. At this point, the database state is the **Empty State** (tables exist, 0 rows inside).
  2. **Initial State:** When the database is first populated/loaded with initial data.
  3. **Valid State:** Any state that satisfies the structure and constraints specified in the schema.

### Comparison Table: Database Schema vs. Database Instance (State)

| Feature | Database Schema (Intension) | Database State / Instance (Extension) |
| :--- | :--- | :--- |
| **1. Meaning** | The structural blueprint/skeleton of the database. | The actual data rows present at a specific moment in time. |
| **2. Frequency of Change** | Rarely changes (static/stable over time). | Changes constantly (with every `INSERT`, `UPDATE`, `DELETE`). |
| **3. Initial Condition** | Defined first when creating the database. | Initially empty (0 rows) right after schema creation. |
| **4. Programming Analogy** | Like declaring a variable type: `int score;` | Like the current value inside the variable: `score = 95;` |
| **5. Example** | `STUDENT(Roll_No, Name, Branch)` | `(7, 'Adhil', 'EEE')`, `(8, 'Rahul', 'EEE')` |

### 3. Meta-Data (Data About Data)
* **Definition:** **Meta-data** is the information that describes the database schema, data types, table structures, column lengths, integrity constraints, views, and user access privileges.
* **Where it is stored:** Stored inside the **DBMS System Catalog** (or **Data Dictionary**).
* **Why it matters:** Whenever a user runs a query, the DBMS software first checks the **Meta-data** in the catalog to verify whether the table exists, what data types its columns have, and whether the user has permission to read it.

## PART C: The Three-Schema Architecture & Data Independence

> ⭐ **DIRECT EXAM QUESTION:** Asked in **Oct 2026 Internal Test Q1(a) (3.5 Marks)**: *"Explain the three-schema architecture of DBMS."*

### 1. Goal of the Three-Schema Architecture
Proposed by the **ANSI/SPARC committee**, the primary goal of the Three-Schema Architecture is to **separate the user applications from the physical database**. In this architecture, schemas can be defined at **three levels**:

                                 |  (On Hard Disk)|
                                 (================)
```

### 2. Detailed Explanation of the Three Levels

#### Level 1: Internal Level (Physical Level)
* **Closest to:** Physical disk storage.
* **Has an *Internal Schema*:** Describes the **physical storage structure** of the database.
* **What it uses:** Uses a **Physical Data Model** and describes the complete details of data storage (how records are laid out in disk blocks, byte sizes, compression, encryption) and **access paths** (such as B+ Tree indexes or hashing) for the database.

#### Level 2: Conceptual Level (Logical Level)
* **Middle Level:** Sits between the physical storage and the individual user views.
* **Has a *Conceptual Schema*:** Describes the structure of the **whole database** for a community of users.
* **What it does:** It **hides the details of physical storage structures** and concentrates on describing:
  * Entities, data types, relationships, user operations, and integrity constraints.
* **What it uses:** Usually uses a representational/logical data model (like the Relational Model) or a high-level conceptual data model (like the ER Model) during design.

#### Level 3: External Level (or View Level)
* **Closest to:** End users.
* **Has multiple *External Schemas* (or *User Views*):** Each external schema describes the **specific part of the database that a particular user group is interested in** and hides the rest of the database from that user group.
* **Example:** In a college database:
  * **External View 1 (Students):** Shows `Roll_No, Name, Subject_Marks, Attendance`.
  * **External View 2 (Library Staff):** Shows `Roll_No, Name, Books_Borrowed, Fine_Amount` (hides marks and faculty salaries).

---

### 3. Mappings in Three-Schema Architecture
Notice that the actual data exists **only on the physical hard disk** at the bottom! The three schemas are just *descriptions* of data.
* Therefore, the DBMS must transform a request specified on an **External Schema** $\rightarrow$ into a request on the **Conceptual Schema** $\rightarrow$ and then into a request on the **Internal Schema** for processing over the stored database.
* This process of transforming requests and results between levels is called **Mapping**:
  1. **External / Conceptual Mapping:** Translates between a user view and the global conceptual schema.
  2. **Conceptual / Internal Mapping:** Translates between the global conceptual schema and the physical disk files.

---

### 4. Data Independence (Achieved via Three-Schema Architecture!)

📸 **[Click here to view Logical vs Physical Data Independence diagrams on Google Images](https://www.google.com/search?q=logical+and+physical+data+independence+in+dbms+diagram&udm=2)**

Because of the Three-Schema Architecture, we can change the schema at one level of a database system **without having to change the schema at the next higher level**. This capability is called **Data Independence**, and there are two types:

#### 1. Logical Data Independence
* **Definition:** The capacity to change the **Conceptual Schema** without having to change the **External Schemas (User Views)** or application programs.
* **When do we change the Conceptual Schema?**
  * Expanding the database (e.g., adding a new table `HOSTEL` or adding a new column `Aadhar_No` to `STUDENT`).
  * Reducing the database (removing an unused attribute) or splitting a table into two tables.
* **How it works:** Only the *External/Conceptual Mapping* and view definitions need to be updated by the DBA; the application programs that use the existing views continue working untouched.
* **Note:** Logical data independence is **harder to achieve** than physical data independence because application programs are heavily dependent on the logical structure of the data they access.

#### 2. Physical Data Independence
* **Definition:** The capacity to change the **Internal Schema** without having to change the **Conceptual Schema** (and consequently, the External Schemas never change either).
* **When do we change the Internal Schema?**
  * Creating a new **B+ Tree Index** or Hash Index to improve query speed.
  * Reorganizing physical files on disk (e.g., changing from unsorted heap file to sorted file) or moving data from HDD to SSD.
* **How it works:** Only the *Conceptual/Internal Mapping* is updated inside the DBMS. The tables, SQL queries, and user views remain 100% unchanged!

## PART D: Database Languages

Once a database design is completed, how do we actually talk to the DBMS to define schemas, insert rows, control security, and manage transactions? We use **Database Languages** (most commonly integrated into **SQL**):

📸 **[Click here to view Database Languages classification diagrams on Google Images](https://www.google.com/search?q=types+of+database+languages+in+dbms+diagram&udm=2)**

```text
                     +----------------------------------+
                     |        DATABASE LANGUAGES        |
                     +-----------------+----------------+
                                       |
      +--------------------+-----------+-----------+--------------------+
      |                    |                       |                    |
      v                    v                       v                    v
+-----+------+       +-----+------+          +-----+------+       +-----+------+
|  1. DDL    |       |  2. DML    |          |  3. DCL    |       |  4. TCL    |
| (Define    |       | (Manipulate|          | (Control   |       | (Manage    |
|  Schema)   |       |   Data)    |          |  Security) |       |Transactions|
+------------+       +------------+          +------------+       +------------+
| - CREATE   |       | - SELECT   |          | - GRANT    |       | - COMMIT   |
| - ALTER    |       | - INSERT   |          | - REVOKE   |       | - ROLLBACK |
| - DROP     |       | - UPDATE   |          |            |       | - SAVEPOINT|
| - TRUNCATE |       | - DELETE   |          |            |       |            |
+------------+       +------------+          +------------+       +------------+
*(Plus architectural languages: SDL = Storage Definition, VDL = View Definition)*
```

### 1. DDL – Data Definition Language
* **Purpose:** Used by the DBA and Database Designers to **define the conceptual and internal schemas** (tables, attributes, data types, and constraints).
* The DBMS has a **DDL Compiler** whose function is to process DDL statements in order to identify descriptions of the schema constructs and store the schema description (**Meta-data**) in the **DBMS Catalog**.
* **Common SQL DDL Commands:**
  * `CREATE`: Creates a new database, table, index, or view.
  * `ALTER`: Modifies an existing table structure (e.g., adding/dropping a column).
  * `DROP`: Deletes an entire table along with its schema and data.
  * `TRUNCATE`: Removes all rows from a table quickly while keeping the table schema intact.

### 2. SDL (Storage Definition Language) & VDL (View Definition Language)
* **SDL (Storage Definition Language):** In DBMSs where a strict separation is maintained between the conceptual and internal levels, **DDL** is used to specify the *Conceptual Schema* only, while **SDL** is used to specify the *Internal Schema* (physical storage parameters, block allocation).
* **VDL (View Definition Language):** Used to specify **User Views (External Schemas)** and their mappings to the conceptual schema. *(In modern SQL, `CREATE VIEW` serves as the VDL).*

### 3. DML – Data Manipulation Language
* **Purpose:** Once the database schemas are compiled and the database is populated, users need a language to **retrieve, insert, delete, and modify** the actual data (the Database State). This is the **DML**.
* **Common SQL DML Commands:** `SELECT` (Query), `INSERT`, `UPDATE`, `DELETE`.
* **Two Types of DML (Frequently asked 2-mark distinction!):**

| Type of DML | How It Works | Example |
| :--- | :--- | :--- |
| **1. High-Level / Non-Procedural (Declarative) DML** | The user specifies **WHAT** data is needed, **without** specifying *how* (which algorithm/loop) to retrieve it. Processes multiple records at once (**Set-at-a-time**). | **SQL** (`SELECT Name FROM Student WHERE Dept='EEE';`) |
| **2. Low-Level / Procedural DML** | The user must specify **WHAT** data is needed **AND HOW** to retrieve it step-by-step (using loops and pointers). Processes one record at a time (**Record-at-a-time**). | **Relational Algebra**, navigational embedded code using cursors. |

### 4. DCL (Data Control Language) & TCL (Transaction Control Language)
* **DCL (Data Control Language):** Used by the DBA to manage security, permissions, and access control (`GRANT`, `REVOKE`).
* **TCL (Transaction Control Language):** Used to manage changes made by DML statements and group them into logical transactions (`COMMIT` to save permanently, `ROLLBACK` to undo changes, `SAVEPOINT` to set a checkpoint within a transaction).

### PYQ 1: Oct 2026 Internal Test – Question I(a) [3.5 Marks]
> **Question:** *"Explain the three-schema architecture of DBMS."*

#### ✅ Model Exam Answer (Write this verbatim + draw the diagram for 3.5 / 3.5 Marks):

The **Three-Schema Architecture** (proposed by ANSI/SPARC) is a framework designed to separate user applications from the physical database, thereby achieving **Program-Data Independence** and supporting **Multiple User Views**.

*(Draw the 3-level diagram from Part C here: External Views $\leftrightarrow$ Conceptual Schema $\leftrightarrow$ Internal Schema $\leftrightarrow$ Stored Database)*

In this architecture, database schemas are defined at **three levels**:

**1. Internal Level (Physical Level):**
* It has an **Internal Schema**, which describes the physical storage structure of the database on disk.
* It uses a **physical data model** and specifies complete details of data storage (record layouts, byte sizes) and **access paths** (such as B+ tree indexes and hashing) for the database.

**2. Conceptual Level (Logical Level):**
* It has a **Conceptual Schema**, which describes the structure of the **whole database** for a community of users.
* It hides the details of physical storage structures and concentrates on describing **entities, data types, relationships, user operations, and integrity constraints**.

**3. External Level (View Level):**
* It includes a number of **External Schemas** or **User Views**.
* Each external schema describes the specific part of the database that a particular user group is interested in and hides the rest of the database from that user group.

**Mappings and Data Independence:**
* The DBMS transforms requests and results between the three levels using **External/Conceptual Mapping** and **Conceptual/Internal Mapping**.
* This separation provides **Logical Data Independence** (changing the conceptual schema without affecting external views) and **Physical Data Independence** (changing physical storage/internal schema without affecting the conceptual schema).

### PYQ 2: Oct 2026 Internal Test – Question I(b) [4 Marks]
> **Question:** *"Explain the different types of data models with suitable examples."*

#### ✅ Model Exam Answer (Write this verbatim for 4 / 4 Marks):

A **Data Model** is a collection of concepts that can be used to describe the structure of a database (data types, relationships, and constraints) along with basic operations for retrievals and updates. Based on the level of abstraction, data models are classified into **three categories**:

**1. High-Level or Conceptual Data Models:**
These models provide concepts that are close to the way human users perceive data in the real world.
* **a) Entity-Relationship (ER) Model:** Represents real-world data using **Entities** (objects), **Attributes** (properties), and **Relationships** (associations).
  * *Example:* An entity `STUDENT` (with attributes `Student_ID`, `Name`) connected via an `Enrolls_In` relationship to an entity `COURSE` (with attributes `Course_ID`, `Credits`).
* **b) Object-Oriented Data Model:** Represents data as objects encapsulating both attributes and methods/operations, supporting classes and inheritance.

**2. Representational or Implementation (Logical) Data Models:**
These models provide concepts that are easily understood by end users while also reflecting how data is logically organized in commercial DBMSs:
* **a) Relational Data Model:** Represents a database as a collection of tables (**Relations**) consisting of rows (**Tuples**) and columns (**Attributes**). Relationships are maintained using Primary Keys and Foreign Keys.
  * *Example:* A `STUDENT(Roll_No, Name, Dept_ID)` table linked to a `DEPARTMENT(Dept_ID, Dept_Name)` table.
* **b) Hierarchical Data Model:** Organizes data in a **tree-like structure** where each child record has at most **one** parent record ($1:N$ relationship).
  * *Example:* A `University` root node branching into `Departments`, which branch into `Students`.
* **c) Network Data Model:** Organizes data as a **graph** where a child record can have **multiple parent records**, directly supporting $M:N$ relationships.
  * *Example:* A `Student` record linked to both a `Department` parent and a `Sports_Club` parent.

**3. Low-Level or Physical Data Models:**
These models describe the exact low-level details of how data is stored on physical storage media (disks/SSDs).
* They specify **record formats, record orderings, and access paths** (such as B+ Tree indexes and hash structures).
* *Example:* Specifying that an `EMPLOYEE` file uses unspanned blocks of 512 bytes sorted by `Employee_ID` with a primary B+ tree index.

#### ✅ Model Exam Answer (Write this verbatim for 3 / 3 Marks):

**i) Data Model (1 Mark):**
* A **Data Model** is a collection of conceptual tools used to describe the structure of a database—specifically its data types, relationships, and consistency constraints—along with a set of basic operations for specifying retrievals and updates.
* *Examples:* Entity-Relationship (ER) Model, Relational Model.

* **Meta-data** means **"data about data"**. It is the information that describes the database structure, table names, column data types, storage formats, and integrity constraints.
* It is stored inside the **DBMS System Catalog (Data Dictionary)** and makes the database system self-describing.

### Quick 30-Second Recap of 1.3
* **3 Categories of Data Models:**
  1. **Conceptual (High-level):** ER Model (`Entity`, `Attribute`, `Relationship`), Object-Oriented Model.
  2. **Representational (Logical):** Relational (Tables/Rows/Cols), Hierarchical (Tree, 1 parent), Network (Graph, multiple parents).
  3. **Physical (Low-level):** Disk blocks, byte offsets, B+ Tree indexes, hashing.
* **Schema vs. Instance:** Schema = Blueprint (`STUDENT(RollNo, Name)`), rarely changes. Instance/State = Actual rows right now, changes constantly.
* **Three-Schema Architecture:**
  * **External Level** (User Views) $\leftrightarrow$ **Conceptual Level** (Whole DB logical structure) $\leftrightarrow$ **Internal Level** (Physical storage & indexes).
  * Gives **Logical Data Independence** (change Conceptual without breaking Views) & **Physical Data Independence** (change Internal without breaking Conceptual).
