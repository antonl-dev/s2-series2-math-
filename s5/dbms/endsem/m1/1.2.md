## PART A: Database Users and Their Responsibilities

> ⭐ **VERY HIGH-PROBABILITY EXAM TOPIC:**
> * Asked in **Oct 2025 Internal Test Q5(a) (3.5 Marks):** *"List any three categories of database users, highlighting any one important characteristic of each user."*
> * Asked in **Nov 2025 End-Sem Exam Q1(a) (5 Marks):** *"Define different database users with their responsibility."*

In a large database system, many people are involved in designing, using, and maintaining the database. Based on how they interact with the system, textbook authors (Elmasri & Navathe / Korth) divide people into **two main groups**:

1. **Actors on the Scene:** The people whose jobs involve the day-to-day use, design, or administration of the actual database content.
2. **Workers Behind the Scene:** The people who work to maintain the DBMS software and computer hardware environment itself (they are not interested in the business data stored inside).

## 1. Detailed Breakdown: "Actors on the Scene"

When an exam question asks about **Database Users**, 90% of your marks come from explaining these **4 categories of Actors on the Scene**:

### Category 1: Database Administrators (DBA)
In any organization where many people share a database, there must be a chief administrator (and team) who oversees and manages the database system. This person is the **Database Administrator (DBA)**—the "super-user" of the database.

📸 **[Click here to view DBA Responsibilities diagrams on Google Images](https://www.google.com/search?q=roles+and+responsibilities+of+DBA+in+dbms+diagram&udm=2)**

* **Key Characteristic:** Has the highest level of control over both the data and the DBMS software configuration.
* **Major Responsibilities of a DBA:**
  1. **Schema Definition:** Creating the original database schema by executing DDL (Data Definition Language) statements.
  2. **Authorizing Access to the Database (Security):** Granting and revoking permissions (`GRANT` / `REVOKE`) so users can only access the specific data they are authorized to see.
  3. **Storage Structure and Access-Method Definition:** Deciding how data is stored on physical disks and creating indexes to speed up slow queries.
  4. **Coordinating and Monitoring Use:** Monitoring CPU, disk usage, and query performance, and resolving bottlenecks when the database slows down.
  5. **Backup and Recovery:** Setting up automated periodic backups and restoring the database to a consistent state after hardware crashes or cyber-attacks.
  6. **Acquiring Software and Hardware Resources:** Upgrading DBMS versions and disk storage as data grows.

---

### Category 2: Database Designers
Database designers are the architects who design the structure of the database **before** it is actually built and populated with data.

* **Key Characteristic:** They interact with all potential user groups to understand their requirements and design a database structure that meets everyone's needs.
* **Responsibilities of Database Designers:**
  1. **Identifying the Data:** Determining *what* data needs to be stored in the database and *what* constraints/rules apply to it.
  2. **Choosing Appropriate Structures (Conceptual & Logical Design):** Drawing ER (Entity-Relationship) diagrams, converting them into relational tables, and normalizing tables (1NF, 2NF, 3NF) to prevent anomalies.
  3. **Designing Views:** Creating external views tailored for different user groups (e.g., a view for students vs. a view for professors).
  4. **Communicating with Users:** Interviewing end users to make sure no required attribute or business rule is left out.

---

### Category 3: End Users (And Their 4 Sub-Types)
**End Users** are the people whose jobs require access to the database for querying, updating, and generating reports. The database exists primarily for their use!

Depending on how they interact with the database, End Users are divided into **4 sub-categories**:

#### a) Naive (or Parametric) End Users
* **Who they are:** The largest category of database users. Their entire job revolves around constantly querying and updating the database using standard, pre-programmed forms.
* **Key Characteristic:** They know **zero SQL** and nothing about how the database works internally. They interact through simple menus, buttons, or mobile app screens to run pre-written queries called **Canned Transactions** (queries that have been carefully programmed and tested in advance).
* **Real-World Examples:**
  * **Bank Tellers:** Checking account balances and posting withdrawals/deposits all day.
  * **Railway / Airline Reservation Clerks:** Checking seat availability and booking tickets.
  * **E-commerce / Mobile Banking Customers:** Checking order status on Amazon or transferring money via GPay/YONO.

#### b) Casual End Users
* **Who they are:** Typically middle- or high-level managers, executives, or deans who occasionally access the database.
* **Key Characteristic:** They do not use the database every minute, but when they do, they need **different information each time**. They use interactive query interfaces, dashboards, or high-level query languages to specify their requests.
* **Real-World Example:** A College Principal logging in once a month to check *"Which department had the highest pass percentage in Semester 5 compared to last year?"*

#### c) Sophisticated End Users
* **Who they are:** Engineers, scientists, business analysts, and data scientists.
* **Key Characteristic:** They thoroughly familiarize themselves with the facilities of the DBMS so they can write their own complex **SQL queries** or use data analysis/OLAP tools to answer complex, custom questions without needing a programmer to build a form for them.
* **Real-World Example:** A financial analyst at a bank writing complex nested SQL queries to detect fraudulent credit card patterns across millions of transactions.

#### d) Stand-alone Users
* **Who they are:** Individuals who maintain personal databases for their own private use.
* **Key Characteristic:** They use ready-made, off-the-shelf software packages that provide easy-to-use menu-based or graphic interfaces.
* **Real-World Example:** A small shop owner using Tally/QuickBooks for tax and inventory tracking, or a user maintaining a personal book/recipe collection in Microsoft Access.

---

### Category 4: System Analysts and Application Programmers (Software Engineers)
These are the software developers who build the bridge between the database and the Naive/Parametric End Users.

* **System Analysts:**
  * **Responsibility:** Determine the exact requirements of end users (especially naive users) and develop specifications for standard **canned transactions** that meet these requirements.
* **Application Programmers:**
  * **Responsibility:** Take the specifications created by the System Analysts and write, test, debug, document, and maintain the actual application code (in Java, Python, C#, JS) that executes DML (Data Manipulation Language) queries against the DBMS.

## 2. Detailed Breakdown: "Workers Behind the Scene"

*(Mentioning these for 2–3 lines in a 5-mark question makes your answer stand out as complete!)*

1. **DBMS System Designers and Implementers:**
   * Software engineers at companies like Oracle, Microsoft, or PostgreSQL who design and write the core DBMS software modules (query compiler, storage manager, buffer manager, concurrency control engine).
2. **Tool Developers:**
   * Engineers who design and build auxiliary software tools—such as ER modeling tools, performance monitoring dashboards, backup utilities, and graphical interfaces (like pgAdmin, MySQL Workbench).
3. **Operators and Maintenance Personnel (System Administrators):**
   * IT personnel responsible for the actual physical running and maintenance of the server hardware, network, cooling, and operating system on which the DBMS runs.

## PART B: Structured, Semi-Structured, and Unstructured Data

Not all data in the world fits neatly into rows and columns. Modern systems classify data into **three types** based on how organized and predictable its structure is.

📸 **[Click here to view Structured vs Semi-Structured vs Unstructured Data diagrams on Google Images](https://www.google.com/search?q=structured+semi+structured+unstructured+data+diagram&udm=2)**

  | 8  | Rahul | 90    |     }                           | "Free text..."    |

```

### 1. Structured Data
* **Definition:** Data that strictly conforms to a **pre-defined data model (schema)** and is organized into a formatted repository, typically a **tabular format with rows and columns**.
* **How it works (Schema-on-Write):** Before you can insert a single record, you must first define the table structure (column names, data types like `INT`, `VARCHAR(50)`, `DATE`, and constraints). Every row must follow this exact blueprint.
* **Where it is stored:** Relational Database Management Systems (**RDBMS**) such as MySQL, PostgreSQL, Oracle, SQL Server, and Data Warehouses.
* **How it is queried:** Easily searched and manipulated using **SQL (Structured Query Language)**.
* **Examples:**
  * University `STUDENT(Roll_No, Name, Branch, CGPA)` table.
  * Bank account transaction ledgers.
  * Airline reservation records, Excel spreadsheets with strict columns.

---

### 2. Semi-Structured Data
* **Definition:** Data that does **not** reside in strict relational tables of rows and columns, **but still contains organizational properties—such as tags, keys, hierarchies, or markers**—that separate semantic elements and make it easier to parse and analyze.
* **Why it is called "Self-Describing":** The schema information (field names/tags) is mixed directly in with the data values themselves. Different records in the same collection can have different fields!
* **How it works (Schema-on-Read):** You can store a record without enforcing a rigid table structure upfront; the application interprets the tags when reading the data.
* **Where it is stored:** NoSQL Document Databases (like **MongoDB**, CouchDB), Key-Value/Wide-Column stores, or raw `.json` and `.xml` files.
* **Examples:**
  1. **JSON (JavaScript Object Notation):**
     ```json
     {
       "roll_no": 7,
       "name": "Adhil",
       "hobbies": ["Coding", "Football"]
     }
     ```
  2. **XML (eXtensible Markup Language) & HTML:** Uses tags like `<student><name>Adhil</name></student>`.
  3. **Emails:** An email is a classic exam example of semi-structured data! Its headers (`From:`, `To:`, `Subject:`, `Date:`) are strictly structured, while the email body text and attachments are unstructured.
  4. **CSV / Log Files:** Server log files that have timestamps and status codes alongside free-text error messages.

---

### 3. Unstructured Data
* **Definition:** Data that has **no pre-defined data model** and is not organized in a pre-defined manner. It lacks any structural tags or tabular format that a standard database query engine can immediately understand.
* **Scale:** Accounts for **over 80% of all data** generated by organizations today.
* **Challenge:** Because there are no columns or tags, traditional SQL cannot easily search *inside* the content without using AI, Natural Language Processing (NLP), Computer Vision, or full-text search indexing.
* **Where it is stored:** Data Lakes, Object Storage (Amazon S3, Google Cloud Storage), File Systems, or NoSQL BLOB (Binary Large Object) stores.
* **Examples:**
  * **Multimedia files:** Videos (`.mp4`, CCTV footage), Audio recordings (`.mp3`, customer care call recordings), Images (`.jpg`, Medical X-rays, MRI scans, Satellite imagery).
  * **Text documents:** PDFs, Word documents, legal contracts, textbooks.
  * **Social Media & Communications:** Tweets, WhatsApp messages, product reviews, blog posts.

---

### Side-by-Side Comparison Table: Structured vs. Semi-Structured vs. Unstructured Data

*(Memorize 5 rows of this table—if this comes for 3–5 marks, drawing this table guarantees full marks!)*

| Feature | Structured Data | Semi-Structured Data | Unstructured Data |
| :--- | :--- | :--- | :--- |
| **1. Data Model / Schema** | Rigid, pre-defined schema (**Schema-on-Write**). | Flexible, self-describing tags/hierarchy (**Schema-on-Read**). | No pre-defined schema or internal structure at all. |
| **2. Organization** | Tabular (Rows and Columns). | Tree / Graph / Key-Value / Tag-based. | Raw binary files or free-form text streams. |
| **3. Storage System** | Relational Databases (**RDBMS** like MySQL, Oracle). | NoSQL Document DBs (**MongoDB**), XML/JSON files. | Data Lakes, Object Storage (AWS S3), File Systems. |
| **4. Ease of Querying** | Very easy and fast using standard **SQL**. | Moderate (uses JSONPath, XQuery, MongoDB queries). | Difficult (requires NLP, AI, or metadata tagging). |
| **5. Flexibility** | Low (changing schema requires `ALTER TABLE`). | High (each record can have different attributes). | Highest (can store literally any file format). |
| **6. Transaction Management** | Strong **ACID** compliance and concurrency support. | Partial / Configurable (often BASE or eventual consistency). | No native transaction management (file-level only). |
| **7. Real-World Examples** | Student marks table, Bank ledger, Inventory table. | **JSON**, **XML**, HTML pages, Emails, Server logs. | **Videos, Audio, X-ray images**, PDFs, Social media posts. |

## PART C: Past Year Questions (PYQs) from Your Papers – Full Answers

### PYQ 1: Oct 2025 Internal Test – Question V(a) [3.5 Marks]
> **Question:** *"List any three categories of database users, highlighting any one important characteristics of each user."*

#### ✅ Model Exam Answer (Write this verbatim for 3.5 / 3.5 Marks):

The major categories of database users ("Actors on the Scene") and their key characteristics are:

**1. Database Administrators (DBA):**
* **Role:** The super-user or central administrator who oversees and manages the entire database system and its resources.
* **Important Characteristic:** The DBA is responsible for **authorizing access** to the database (security), defining the database schema, monitoring system performance, and managing backup and recovery operations.

**2. Database Designers:**
* **Role:** The specialists who design the conceptual and logical structure of the database before it is implemented.
* **Important Characteristic:** They are responsible for **identifying the data to be stored** and choosing appropriate structures (such as ER diagrams and normalized relational schemas) by communicating with all prospective database users to understand their requirements.

**3. End Users:**
* **Role:** The people whose jobs require day-to-day access to the database for querying, updating, and generating reports.
* **Important Characteristic:** Depending on their technical expertise and frequency of access, they interact with the database differently:
  * **Naive / Parametric End Users** (e.g., bank tellers, reservation clerks) know no SQL and repeatedly execute pre-programmed **canned transactions** via simple forms.
  * **Sophisticated End Users** (e.g., data analysts, scientists) thoroughly understand the DBMS and write complex custom SQL queries to analyze data.
  * **Casual End Users** (e.g., managers) access the database occasionally and request different summary information each time.

**4. System Analysts and Application Programmers:**
* **Important Characteristic:** They determine the requirements of parametric end users and write, test, and maintain host-language application programs (canned transactions) that interact with the DBMS.

### PYQ 2: Nov 2025 End-Sem Exam – Question 1(a) [5 Marks]
> **Question:** *"Define different database users with their responsibility (5 marks)"*

#### ✅ Model Exam Answer (Write this verbatim for 5 / 5 Marks):

Database users are broadly classified into **Actors on the Scene** (who use and administer the database content) and **Workers Behind the Scene** (who build and maintain the DBMS software and hardware).

#### I. Actors on the Scene:

**1. Database Administrators (DBA):**
The DBA has central control over both the data and the programs that access that data.
* **Responsibilities:**
  * **Schema Definition:** Creating the original database schema using DDL.
  * **Access Control & Security:** Granting and revoking user permissions to ensure unauthorized users cannot access sensitive data.
  * **Performance Monitoring & Tuning:** Defining storage structures/indexes and optimizing slow queries.
  * **Backup and Recovery:** Performing regular backups and restoring the database after system failures.

**2. Database Designers:**
* **Responsibilities:**
  * Identifying what data must be stored in the database and what constraints apply.
  * Designing the conceptual schema (ER diagrams) and logical schema (normalized tables) so the database is free of redundancy and anomalies.
  * Designing external **views** for different user groups.

**3. End Users:**
People who use the database for querying, updating, and generating reports:
* **a) Naive / Parametric End Users:** (e.g., Bank tellers, railway booking clerks)
  * *Responsibility:* Repeatedly query and update the database using standard, pre-written **canned transactions** via form-based interfaces.
* **b) Casual End Users:** (e.g., Managers, executives)
  * *Responsibility:* Occasionally query the database for different summary/analytical information using interactive interfaces.
* **c) Sophisticated End Users:** (e.g., Engineers, business analysts)
  * *Responsibility:* Write complex custom queries (in SQL) and use data analysis tools to solve specialized business or scientific problems.
* **d) Stand-alone Users:**
  * *Responsibility:* Maintain personal databases using ready-made software packages (e.g., tax or personal inventory software).

**4. System Analysts and Application Programmers:**
* **Responsibilities:**
  * **System Analysts** analyze the needs of naive end users and design specifications for canned transactions.
  * **Application Programmers** implement, test, debug, and maintain these transactions as application programs (in Java, Python, C#, etc.).

#### II. Workers Behind the Scene:
* **1. DBMS System Designers & Implementers:** Design and build the core DBMS software modules (query processor, storage engine).
* **2. Tool Developers:** Develop supporting packages for database modeling, performance monitoring, and GUI administration.
* **3. Operators and Maintenance Personnel:** Manage the physical server hardware and operating system environment running the DBMS.
