## PART A: What is Database Normalization?

Before jumping into 1NF and 2NF, let's understand what **Normalization** actually means in plain English:

* **Definition:** Proposed by **E. F. Codd (1972)**, **Normalization** is a systematic, step-by-step process of analyzing and decomposing (splitting) poorly designed tables based on their **Candidate Keys** and **Functional Dependencies** to achieve two main goals:
  1. **Minimize Data Redundancy** (stop repeating the same data over and over).
  2. **Eliminate Insertion, Deletion, and Update Anomalies**.

```text
PROGRESSION OF NORMAL FORMS (Each outer circle is stricter than the previous!):

  [ Unnormalized Table (UNF) ]
        |
        |  Step 1: Remove Multivalued / Non-Atomic Attributes
        v
  [ First Normal Form (1NF)  ]  <-- Every cell has 1 single atomic value!
        |
        |  Step 2: Remove Partial Dependencies (on part of a Composite Key)
        v
  [ Second Normal Form (2NF) ]  <-- Every non-key col depends on the WHOLE Key!
        |
        |  Step 3: Remove Transitive Dependencies (Non-key -> Non-key)
        v
  [ Third Normal Form (3NF) & BCNF ]  (Covered in Module 4.4)
```

## PART B: First Normal Form (1NF)

> ⭐ **DIRECT EXAM QUESTIONS:**
> * **Oct 2026 Internal Test Q4(a) [3 Marks]:** *"Explain First Normal Form (1NF) with a suitable example."*
> * **Nov 2025 End-Sem Exam Q8(b) [3 Marks]:** *"Illustrate the rules of 1NF."*

### 1. Definition of First Normal Form (1NF)
* **Formal Definition:** A relation schema $R$ is in **First Normal Form (1NF)** if and only if **the domain of every attribute contains only atomic (indivisible, single) values**, and the value of every attribute in any tuple is a **single value** from that domain.
* **In Simple Words:** **"One Cell = One Single Value!"**
  * A table is **NOT in 1NF** if any single cell contains multiple values (like `'DBMS, OS'`), a comma-separated list of phone numbers (`'9847011111, 9847022222'`), a composite structure, or a nested table inside a cell.

### 2. The 4 Rules of First Normal Form (1NF) *(Memorize for Nov 2025 Q8b!)*

For a table to satisfy **1NF**, it must obey these **four strict rules**:

1. **Rule 1 – Atomic (Single-Valued) Attributes:**
   * Every cell (intersection of a row and a column) must hold **only ONE atomic (indivisible) value**.
   * **Multivalued attributes** (storing multiple values in one cell) and **Composite/Nested attributes** are strictly disallowed.
2. **Rule 2 – Attribute Domain Uniformity:**
   * All values stored in a particular column must belong to the **same domain (data type)**. For example, a `Roll_No` column of type `INT` cannot store text strings in some rows.
3. **Rule 3 – Unique Column Names & No Repeating Groups:**
   * Every attribute (column) in a table must have a **unique name**, and the table must **not** contain repeating column groups like `Course_1, Course_2, Course_3` to work around multivalued attributes.
4. **Rule 4 – Uniquely Identifiable Tuples (Primary Key) & Order Independence:**
   * Every row must be uniquely identifiable using a **Primary Key** (no duplicate rows), and the order in which rows or columns are stored does not affect the meaning of the data.

---

### 3. Suitable Example of Violating 1NF & Converting to 1NF

Suppose a college stores student course registrations in the following `STUDENT` table:

#### ❌ Table Before 1NF (Unnormalized Relation – Violates 1NF!):
| Roll_No (PK) | Name | Branch | Courses_Taken *(Multivalued!)* |
| :--- | :--- | :--- | :--- |
| **7** | Adhil | EEE | **`DBMS, Networks`** ❌ *(2 values in 1 cell!)* |
| **8** | Rahul | EEE | `Circuits` |
| **9** | Meera | CSE | **`DBMS, AI, OS`** ❌ *(3 values in 1 cell!)* |

* **Why this violates 1NF:** Look at the `Courses_Taken` column for Roll No. `7 (Adhil)` and `9 (Meera)`. They contain **multiple values inside a single cell** (`'DBMS, Networks'` and `'DBMS, AI, OS'`), which violates the **Atomicity Rule** of 1NF!

---

#### ✅ How to Convert This Table into 1NF (Two Valid Methods!):

##### Method 1: Flatten the Table (Put Each Value in Its Own Row & Expand the Primary Key)
We split each multivalued cell into separate rows so every cell holds **exactly 1 course**, and change the Primary Key to the composite key **`(Roll_No, Course_Taken)`**:

**Table in 1NF: $\text{STUDENT\_1NF}(\underline{\text{Roll\_No}, \text{Course\_Taken}}, \text{Name}, \text{Branch})$**
| Roll_No (PK) | Name | Branch | Course_Taken (PK) |
| :--- | :--- | :--- | :--- |
| **7** | Adhil | EEE | **DBMS** ✅ |
| **7** | Adhil | EEE | **Networks** ✅ |
| **8** | Rahul | EEE | **Circuits** ✅ |
| **9** | Meera | CSE | **DBMS** ✅ |
| **9** | Meera | CSE | **AI** ✅ |
| **9** | Meera | CSE | **OS** ✅ |
*(Now every single cell has only ONE atomic value—so the table is in **1NF**!)*

##### Method 2: Decompose into Two Separate Tables (Best Practice!)
Keep the single-valued attributes in `STUDENT` and move the multivalued attribute `Course_Taken` into a separate table along with `Roll_No` as a Foreign Key:
1. **$\text{STUDENT}(\underline{\text{Roll\_No}}, \text{Name}, \text{Branch})$**
2. **$\text{STUDENT\_COURSES}(\underline{\text{Roll\_No (FK)}, \text{Course\_Taken}})$**

## PART C: Second Normal Form (2NF)

> ⭐ **DIRECT EXAM QUESTION:**
> * **Oct 2026 Internal Test Q4(b) [4.5 Marks]:** *"Explain Second Normal Form (2NF). Consider a relation containing partial dependency and convert it into 2NF."*

Look back at **Method 1 (`STUDENT_1NF`)** above: even though every cell now has 1 value (so it is in **1NF**), notice how `'Adhil, EEE'` is repeated twice and `'Meera, CSE'` is repeated three times! Why? Because of **Partial Dependency**!
**Second Normal Form (2NF)** was created specifically to eliminate **Partial Dependencies**!

---

### 1. Two Essential Terms You Must Know for 2NF

Suppose a table has a Candidate Key (or Primary Key). We divide all columns of the table into two groups:
1. **Prime Attributes (Key Attributes):**
   * Any attribute that is a **member of ANY Candidate Key** (or Primary Key).
   * *Example:* If the Primary Key is $\underline{(\text{Student\_ID}, \text{Course\_ID})}$, then `Student_ID` and `Course_ID` are **Prime Attributes**.
2. **Non-Prime Attributes (Non-Key Attributes):**
   * Any attribute that is **NOT part of any Candidate Key**.
   * *Example:* `Student_Name`, `Course_Name`, and `Grade` are **Non-Prime Attributes**.

---

### 2. What is Partial Dependency vs. Full Functional Dependency?

Suppose a table has a **Composite Primary Key $\underline{(A, B)}$** and a non-prime attribute $C$:
* **Full Functional Dependency ($AB \rightarrow C$):**
  * You need **BOTH $A$ and $B$ together** to determine $C$. Neither $A$ alone ($A \not\rightarrow C$) nor $B$ alone ($B \not\rightarrow C$) can determine $C$.
  * ✅ **Allowed in 2NF!**
* **Partial Functional Dependency ($A \rightarrow C$ or $B \rightarrow C$):**
  * A **Non-Prime Attribute $C$** is determined by **ONLY A PART (proper subset)** of the Composite Primary Key (either $A$ alone determines $C$, or $B$ alone determines $C$)!
  * ❌ **FORBIDDEN in 2NF!**

---

### 3. Definition of Second Normal Form (2NF)

* **Formal Definition:** A relation schema $R$ is in **Second Normal Form (2NF)** if and only if:
  1. **Condition 1:** It is already in **First Normal Form (1NF)**, **AND**
  2. **Condition 2:** **Every non-prime attribute in $R$ is FULLY functionally dependent on the Primary Key (or every Candidate Key) of $R$**—that is, **no non-prime attribute is partially dependent on any proper subset of a candidate key**.

> 💡 **Golden Exam Shortcut:**
> What if a 1NF table has a **Single-Column Primary Key** (e.g., $\text{EMPLOYEE}(\underline{\text{ENO}}, \text{EName}, \text{Salary})$)?
> Then it is **AUTOMATICALLY in 2NF**! Why? Because a 1-column key cannot be split into a smaller "part", so a Partial Dependency is impossible!
> **A table can ONLY violate 2NF if it has a COMPOSITE Primary Key (2 or more columns in the key)!**

---

### 4. Complete Worked Example: Relation with Partial Dependency $\rightarrow$ Converted to 2NF!

Let's trace a crystal-clear example that you can write directly in any exam for **4.5 / 4.5 Marks**:

#### Step 1: Consider a Relation in 1NF That Violates 2NF
Consider the relation **`ENROLLMENT`** that stores student course registrations:

$$\text{ENROLLMENT} (\underline{\text{Student\_ID}, \text{Course\_ID}}, \;\text{Student\_Name}, \;\text{Course\_Name}, \;\text{Grade})$$

* **Composite Primary Key:** $\underline{(\text{Student\_ID}, \text{Course\_ID})}$
  * **Prime Attributes:** `Student_ID`, `Course_ID`
  * **Non-Prime Attributes:** `Student_Name`, `Course_Name`, `Grade`

**Sample Table (`ENROLLMENT` – In 1NF, but NOT in 2NF!):**
| Student_ID (PK) | Course_ID (PK) | Student_Name | Course_Name | Grade |
| :--- | :--- | :--- | :--- | :--- |
| **S01** | **C101** | Adhil | DBMS | A |
| **S01** | **C102** | Adhil | Networks | B |
| **S02** | **C101** | Rahul | DBMS | S |

---

#### Step 2: Analyze the Functional Dependencies (Identify Partial Dependencies!)

Look at how the three non-prime attributes (`Grade`, `Student_Name`, `Course_Name`) depend on the Primary Key `(Student_ID, Course_ID)`:

```text
          FD1: Full Dependency (Depends on BOTH Student_ID & Course_ID) ✅
            +-------------------------+
            |                         |
            |         +---------------+-----------------------+
            |         |                                       v
   ( _Student_ID_ , _Course_ID_ , Student_Name , Course_Name , Grade )
          |               |             ^             ^
          |               +-------------+-------------+
          |                   FD3: Partial Dependency! ❌ (Course_ID -> Course_Name)
          +-----------------------------+
              FD2: Partial Dependency! ❌ (Student_ID -> Student_Name)
```

1. **$\text{FD1: } \{\text{Student\_ID}, \text{Course\_ID}\} \rightarrow \text{Grade}$**
   * To know a student's `Grade`, we need **both** `Student_ID` and `Course_ID`.
   * Therefore, `Grade` is **fully functionally dependent** on the entire Primary Key. ✅ *(Satisfies 2NF)*

2. **$\text{FD2: } \text{Student\_ID} \rightarrow \text{Student\_Name}$**
   * `Student_Name` (a non-prime attribute) depends **only on `Student_ID`**, which is just a **proper subset (part)** of the composite Primary Key `(Student_ID, Course_ID)`!
   * Therefore, $\text{Student\_ID} \rightarrow \text{Student\_Name}$ is a **Partial Dependency**! ❌ *(Violates 2NF!)*

3. **$\text{FD3: } \text{Course\_ID} \rightarrow \text{Course\_Name}$**
   * `Course_Name` (a non-prime attribute) depends **only on `Course_ID`**, which is also a **proper subset (part)** of the composite Primary Key `(Student_ID, Course_ID)`!
   * Therefore, $\text{Course\_ID} \rightarrow \text{Course\_Name}$ is a **Partial Dependency**! ❌ *(Violates 2NF!)*

**Conclusion:** Because of the partial dependencies `FD2` and `FD3`, the `ENROLLMENT` relation is **NOT in 2NF**.

---

#### Step 3: How to Convert (Decompose) the Relation into 2NF!

> **The Mechanical Recipe to Convert Any Table into 2NF:**
> *"For each Partial Dependency $X \rightarrow Y$, **pull the partially dependent attribute(s) $Y$ out** of the original table and place them into a **new separate table** along with a copy of their determinant $X$ (where $X$ becomes the Primary Key of the new table)! Leave the fully dependent attributes in the original table."*

Applying this rule to `ENROLLMENT`, we decompose it into **three 2NF relations**:

##### 1. Relation 1: `STUDENT` (For Partial Dependency $\text{Student\_ID} \rightarrow \text{Student\_Name}$)
$$\text{STUDENT} (\underline{\text{Student\_ID}}, \;\text{Student\_Name})$$
| Student_ID (PK) | Student_Name |
| :--- | :--- |
| **S01** | Adhil |
| **S02** | Rahul |

##### 2. Relation 2: `COURSE` (For Partial Dependency $\text{Course\_ID} \rightarrow \text{Course\_Name}$)
$$\text{COURSE} (\underline{\text{Course\_ID}}, \;\text{Course\_Name})$$
| Course_ID (PK) | Course_Name |
| :--- | :--- |
| **C101** | DBMS |
| **C102** | Networks |

##### 3. Relation 3: `REGISTRATION` (Keeps the Composite PK & Fully Dependent Attribute `Grade`)
$$\text{REGISTRATION} (\underline{\text{Student\_ID}, \text{Course\_ID}}, \;\text{Grade})$$
| Student_ID (PK, FK) | Course_ID (PK, FK) | Grade |
| :--- | :--- | :--- |
| **S01** | **C101** | A |
| **S01** | **C102** | B |
| **S02** | **C101** | S |

✅ **Why All 3 Tables Are Now in 2NF:**
* `STUDENT` and `COURSE` each have a **single-attribute Primary Key**, and their non-prime attributes depend on the whole key.
* In `REGISTRATION`, the only non-prime attribute `Grade` depends **fully** on the entire composite key `(Student_ID, Course_ID)`.
* Zero Partial Dependencies remain!

---

### 5. Bonus Abstract `(A, B, C, D)` Example (In Case Exam Gives Letters Instead of Names!)

Suppose an exam asks:
> *"Given $R(A, B, C, D)$ with Candidate Key $AB$ and Functional Dependencies $F = \{AB \rightarrow C, \;\; B \rightarrow D\}$. Check if $R$ is in 2NF; if not, convert it to 2NF."*

1. **Candidate Key:** $AB$ $\implies$ **Prime attributes:** $\{A, B\}$, **Non-prime attributes:** $\{C, D\}$.
2. **Check FDs:**
   * $AB \rightarrow C$: Full dependency on the whole key $AB$. ✅
   * $B \rightarrow D$: Non-prime attribute $D$ depends on **$B$ alone** (part of key $AB$)! ❌ **Partial Dependency!** So $R$ is **NOT in 2NF**.
3. **Decompose into 2NF:**
   * Pull $B \rightarrow D$ out into its own table: **$R_1(\underline{B}, D)$**
   * Keep the remaining attributes in the original table: **$R_2(\underline{A, B}, C)$**
   * Now both $R_1$ and $R_2$ are in **2NF**!

### PYQ 2: Oct 2026 Internal Test – Question IV(b) [4.5 Marks]

> **Question IV(b) [4.5 Marks]:**
> *"Explain Second Normal Form (2NF). Consider a relation containing partial dependency and convert it into 2NF."*

#### ✅ Model Exam Answer (Write this verbatim for 4.5 / 4.5 Marks):

**1. Definition of Second Normal Form (2NF):**
* A relation $R$ is in **Second Normal Form (2NF)** if and only if:
  1. It is already in **First Normal Form (1NF)**, and
  2. **Every non-prime attribute (non-key attribute) of $R$ is FULLY functionally dependent on the ENTIRE Primary Key (or every Candidate Key) of $R$.**
* In other words, $R$ must not contain any **Partial Functional Dependency**, where a non-prime attribute depends on only a proper subset (part) of a composite candidate key.

**2. Example of a Relation Containing Partial Dependency:**
Consider the relation **`ENROLLMENT`** in 1NF:
$$\text{ENROLLMENT} (\underline{\text{Student\_ID}, \text{Course\_ID}}, \;\text{Student\_Name}, \;\text{Course\_Name}, \;\text{Grade})$$
* **Composite Primary Key:** `(Student_ID, Course_ID)`
  * **Prime Attributes:** `Student_ID`, `Course_ID`
  * **Non-Prime Attributes:** `Student_Name`, `Course_Name`, `Grade`

**Functional Dependencies in `ENROLLMENT`:**
1. $\{\text{Student\_ID}, \text{Course\_ID}\} \rightarrow \text{Grade}$ *(Full Functional Dependency — `Grade` requires both keys)*.
2. $\text{Student\_ID} \rightarrow \text{Student\_Name}$ *(**Partial Dependency!** Non-prime attribute `Student_Name` depends only on `Student_ID`, which is a part of the Primary Key)*.
3. $\text{Course\_ID} \rightarrow \text{Course\_Name}$ *(**Partial Dependency!** Non-prime attribute `Course_Name` depends only on `Course_ID`, which is a part of the Primary Key)*.

Because of the partial dependencies (2) and (3), `ENROLLMENT` violates **2NF**.

**3. Conversion (Decomposition) into 2NF:**
To convert `ENROLLMENT` into 2NF, we remove the partially dependent attributes and place them into separate relations along with their respective determinants as Primary Keys:

* **Relation 1 (`STUDENT`):**
  $$\text{STUDENT} (\underline{\text{Student\_ID}}, \;\text{Student\_Name}) \quad [\text{Satisfies } \text{Student\_ID} \rightarrow \text{Student\_Name}]$$
* **Relation 2 (`COURSE`):**
  $$\text{COURSE} (\underline{\text{Course\_ID}}, \;\text{Course\_Name}) \quad [\text{Satisfies } \text{Course\_ID} \rightarrow \text{Course\_Name}]$$
* **Relation 3 (`REGISTRATION`):**
  $$\text{REGISTRATION} (\underline{\text{Student\_ID}, \text{Course\_ID}}, \;\text{Grade}) \quad [\text{Satisfies } \{\text{Student\_ID}, \text{Course\_ID}\} \rightarrow \text{Grade}]$$

Now, all non-prime attributes in `STUDENT`, `COURSE`, and `REGISTRATION` are fully functionally dependent on the whole Primary Key of their respective relations. Hence, the database is in **2NF**.

### PYQ 3: Nov 2025 End-Sem Exam – Question 8(b) [3 Marks]

> **Question 8(b) [3 Marks]:**
> *"Illustrate the rules of 1NF. (3 marks)"*

#### ✅ Model Exam Answer (Write this verbatim for 3 / 3 Marks):

A relation is in **First Normal Form (1NF)** if it obeys the following **four fundamental rules**:

1. **Rule 1 – Single-Valued (Atomic) Attributes:**
   * Every cell (intersection of a tuple and an attribute) must hold **only one single, indivisible (atomic) value**. Multivalued attributes (e.g., `'C, Java'`) and composite/nested attributes are not permitted.
2. **Rule 2 – Attribute Domain Consistency:**
   * All values stored within a single column (attribute) must be of the **same data type and domain** (e.g., an `Age` column must store only integers in every row).
3. **Rule 3 – Unique Attribute Names & No Repeating Groups:**
   * Every column in the table must have a distinct attribute name, and there must not be repeating groups of columns (such as `Subject1, Subject2, Subject3`) in the same table.
4. **Rule 4 – Unique Tuples & Order Invariance:**
   * Each tuple must be uniquely identifiable (via a Primary Key), and the order in which rows or columns are stored has no significance.

**Illustration:**
* **Violating 1NF:** `EMP (ENO: 101, Name: 'Adhil', Skills: 'SQL, Python')` $\leftarrow$ *Violates Rule 1 (`Skills` has 2 values in 1 cell).*
* **Satisfying 1NF:** Splitting into two rows: `(101, 'Adhil', 'SQL')` and `(101, 'Adhil', 'Python')` with composite key `(ENO, Skills)`.

### Quick 30-Second Recap of 4.3
* **1NF Rule:** **Every cell must contain only 1 atomic value** (no multivalued cells, no lists, no nested tables).
* **Prime Attribute:** Part of any Candidate Key. **Non-Prime Attribute:** Not part of any Candidate Key.
* **Partial Dependency:** A non-prime attribute depends on **only PART** of a Composite Candidate Key (e.g., $A \rightarrow C$ when the key is $AB$).
* **2NF Rule:** **1NF + NO Partial Dependency** (every non-prime attribute must depend on the **WHOLE** Candidate Key).
* **How to Convert to 2NF:** Pull each partial dependency $X \rightarrow Y$ out into a new table $R_1(\underline{X}, Y)$ and leave the full dependencies in the main table!
