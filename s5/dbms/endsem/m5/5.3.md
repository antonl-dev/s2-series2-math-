## PART A: Schedules – Serial, Concurrent, and Serializable

### 1. What is a Schedule (or History)?
* **Definition:** When multiple transactions are executing concurrently in an interleaved manner, the exact **chronological order** in which their basic operations (`read_item`, `write_item`, `commit`, `abort`) are executed is called a **Schedule** (or **History**) $S$.
* **Rule:** A schedule $S$ of $n$ transactions $T_1, T_2, \dots, T_n$ must keep the operations of each individual transaction $T_i$ in the **exact same internal order** in which they appear inside $T_i$, though operations from different transactions can be interleaved.

---

### 2. Three Types of Schedules (Serial vs. Concurrent vs. Serializable)

📸 **[Click here to view Serial vs Non-Serial (Concurrent) vs Serializable Schedules on Google Images](https://www.google.com/search?q=serial+schedule+vs+non+serial+schedule+vs+serializable+schedule+in+dbms+diagram&udm=2)**

```text
+-------------------------------------------------------------------------+
|                         TYPES OF SCHEDULES                              |
+-------------------------------------------------------------------------+
| 1. SERIAL SCHEDULE:                                                     |
|    No interleaving at all! All of T1 runs first, then all of T2 runs.   |
|    - Always 100% Correct/Consistent, BUT very slow (low throughput).    |
+-------------------------------------------------------------------------+
| 2. CONCURRENT (NON-SERIAL) SCHEDULE:                                    |
|    Operations of T1 and T2 are interleaved in time.                     |
|    - Fast, high CPU throughput, BUT might corrupt data!                 |
+-------------------------------------------------------------------------+
| 3. SERIALIZABLE SCHEDULE (The Best of Both Worlds!):                    |
|    A Concurrent Schedule whose final effect on the database is          |
|    100% EQUIVALENT to some Serial Schedule!                             |
+-------------------------------------------------------------------------+
```

#### 1. Serial Schedule
* **Definition:** A schedule $S$ is **Serial** if the operations of different transactions are **not interleaved at all**—that is, for every transaction $T_i$, all operations of $T_i$ are executed consecutively from beginning to end before the next transaction begins.
* **How Many Serial Schedules Exist for $n$ Transactions?**
  * There are **$n!$ ($n$ factorial)** possible serial schedules!
  * *Example:* For 2 transactions ($T_1, T_2$), there are $2! = 2$ serial schedules: **$T_1 \rightarrow T_2$** or **$T_2 \rightarrow T_1$**.
  * For 3 transactions ($T_1, T_2, T_3$), there are $3! = \mathbf{6}$ possible serial schedules:
    $$(T_1 \to T_2 \to T_3), \;(T_1 \to T_3 \to T_2), \;(T_2 \to T_1 \to T_3), \;(T_2 \to T_3 \to T_1), \;(T_3 \to T_1 \to T_2), \;(T_3 \to T_2 \to T_1)$$
* **Why Don't We Just Use Serial Schedules All the Time?**
  * Because Serial Schedules forbid concurrency! While $T_1$ waits for slow disk I/O, $T_2$ is forced to wait, leading to terrible system throughput.

#### 2. Concurrent (or Non-Serial) Schedule
* **Definition:** A schedule where operations from multiple active transactions are **interleaved** (mixed together in time).
* While concurrent schedules give high performance, some concurrent schedules produce wrong results (like the Lost Update problem in Module 5.1).

#### 3. Serializable Schedule
* **Definition:** A concurrent schedule $S$ of $n$ transactions is said to be **Serializable** if it is **equivalent to at least one of the $n!$ Serial Schedules** of those same $n$ transactions!
* **Why Serializability is the Gold Standard:** Since every Serial Schedule is guaranteed to leave the database in a consistent state, any concurrent schedule that is equivalent to a Serial Schedule is **also guaranteed to be 100% correct**—while still giving us the high speed of interleaved execution!

## PART B: Conflicting Operations & Conflict Equivalence

How do we test mathematically whether a concurrent schedule is equivalent to a serial schedule? We look at **Conflicting Operations**!

### 1. When Do Two Operations Conflict? (The 3 Mandatory Conditions!)

Two operations in a schedule are said to **Conflict** if and only if they satisfy **ALL THREE** of the following conditions:
1. **Condition 1 (Different Transactions):** They belong to **two different transactions** ($T_i \neq T_j$).
2. **Condition 2 (Same Data Item):** They access the **exact same database item** (say, both access $X$).
3. **Condition 3 (At Least One is a `WRITE`):** **At least one** of the two operations is a **`write_item(X)`**!

> 🧠 **Super-Easy Memory Rule for Conflicts on Item $X$ (Between $T_i$ and $T_j$):**
> * **Two READs ($r_i(X)$ and $r_j(X)$) NEVER conflict!** *(Reading $X$ doesn't change $X$, so it doesn't matter who reads first).*
> * **If there is a WRITE ($w$), they ALWAYS conflict!**

| Pair of Operations (where $T_i \neq T_j$) | Name of Pair | Do They Conflict? | Why? |
| :--- | :--- | :--- | :--- |
| **$r_i(X)$ followed by $r_j(X)$** | **Read–Read ($R-R$)** | ❌ **NO Conflict!** | Swapping the order of two reads changes nothing. |
| **$r_i(X)$ followed by $w_j(X)$** | **Read–Write ($R-W$)** | ✅ **YES! Conflict!** | If swapped, $T_i$ would read the new value written by $T_j$ instead of the old value! |
| **$w_i(X)$ followed by $r_j(X)$** | **Write–Read ($W-R$)** | ✅ **YES! Conflict!** | If swapped, $T_j$ would miss the value written by $T_i$! |
| **$w_i(X)$ followed by $w_j(X)$** | **Write–Write ($W-W$)** | ✅ **YES! Conflict!** | Whichever write happens *second* determines the final value left in $X$! |

*(Also remember: Operations on **different** data items—like $w_1(X)$ and $w_2(Y)$—**NEVER conflict** because $X$ and $Y$ are completely separate variables!)*

---

### 2. Conflict Equivalence & Conflict Serializability

* **Conflict Equivalence:** Two schedules $S_1$ and $S_2$ over the same set of transactions are **Conflict Equivalent** if the relative order of **every pair of conflicting operations** is the **exact same** in both $S_1$ and $S_2$.
  *(In other words, you can transform $S_1$ into $S_2$ by swapping adjacent non-conflicting operations!)*
* **Conflict Serializability:** A schedule $S$ is **Conflict Serializable** if it is **Conflict Equivalent to some Serial Schedule**!

## PART C: The 4-Step Precedence Graph Method to Test Conflict Serializability

> ⭐ **MEMORIZE THIS 4-STEP RECIPE:** This is the exact method used to solve **Nov 2025 End-Sem Q10(i) [5 Marks]** in 2 minutes!

Instead of manually guessing swaps, we test whether a schedule $S$ is Conflict Serializable by drawing a tiny directed graph called a **Precedence Graph** (or **Serialization Graph**):

📸 **[Click here to view Precedence Graph for Conflict Serializability Examples on Google Images](https://www.google.com/search?q=precedence+graph+for+conflict+serializability+in+dbms+example+diagram&udm=2)**

---

### Step 1: Draw One Node (Circle) for Each Transaction
* If the schedule has 2 transactions ($T_1, T_2$), draw 2 circles: `(T1)` and `(T2)`.
* If the schedule has 3 transactions ($T_1, T_2, T_3$), draw 3 circles: `(T1)`, `(T2)`, and `(T3)`.

### Step 2: Find Conflicting Pairs Item-by-Item & Draw Directed Arrows!
Check each data item ($X$, $Y$, $Z$) one by one from left to right in the schedule:
* Whenever an operation of **$T_i$ comes BEFORE a conflicting operation of $T_j$** ($i \neq j$) on the same data item $X$:
  * $r_i(X)$ comes before $w_j(X)$, **OR**
  * $w_i(X)$ comes before $r_j(X)$, **OR**
  * $w_i(X)$ comes before $w_j(X)$
* **Draw a directed arrow from $T_i$ to $T_j$:**
  $$\mathbf{T_i \longrightarrow T_j}$$
  *(Meaning: In any equivalent serial schedule, **$T_i$ MUST execute before $T_j$**!)*

### Step 3: Check the Graph for Cycles (Loops)!
Look at your finished Precedence Graph:
* ❌ **If the graph contains a CYCLE (closed loop)** (for example, $T_1 \rightarrow T_2$ AND $T_2 \rightarrow T_1$, or $T_1 \rightarrow T_2 \rightarrow T_3 \rightarrow T_1$):
  * Then the schedule is **NOT Conflict Serializable**! *(Why? Because $T_1 \rightarrow T_2$ says $T_1$ must run before $T_2$, while $T_2 \rightarrow T_1$ says $T_2$ must run before $T_1$—which is impossible!)*
* ✅ **If the graph has NO CYCLES (it is Acyclic / a DAG):**
  * Then the schedule **IS Conflict Serializable**!

### Step 4: Write the Equivalent Serial Schedule (Topological Sort)
If there is **no cycle**, find the equivalent Serial Schedule by following the arrows (**Topological Sort**):
1. Pick the transaction node that has **NO incoming arrows (In-degree = 0)** $\rightarrow$ Write it **first**!
2. Erase that node and its outgoing arrows, and pick the next node with no incoming arrows $\rightarrow$ Write it **second**, and so on!

---

### Quick Warm-Up Example (A Schedule WITH a Cycle $\rightarrow$ NOT Serializable)

Suppose Schedule $S_1$ is:
$$S_1: \;\; r_1(X), \;\; r_2(X), \;\; w_1(X), \;\; w_2(X)$$

1. **Nodes:** $T_1$ and $T_2$.
2. **Conflicts on $X$:**
   * $r_2(X)$ comes before $w_1(X)$ $\implies$ Draw arrow **$T_2 \longrightarrow T_1$**.
   * $r_1(X)$ comes before $w_2(X)$ (and $w_1(X)$ before $w_2(X)$) $\implies$ Draw arrow **$T_1 \longrightarrow T_2$**.
3. **Precedence Graph:**
   ```text
        +------>------+
       /               \
   ( T1 )             ( T2 )
       \               /
        +------<------+
   ```
4. **Conclusion:** There is a **Cycle ($T_1 \rightarrow T_2 \rightarrow T_1$)**! Therefore, $S_1$ is **NOT Conflict Serializable**! *(In fact, look closely at $S_1$: it is the exact **Lost Update Problem** from Module 5.1!)*

## PART D: Past Year Question (PYQ) – Full Solved Answer

### PYQ 1: Nov 2025 End-Sem Exam – Question 10(i) [5 Marks]

> *"Consider the following schedule:*
> $$r_1(X), \; r_2(Z), \; r_1(Z), \; r_3(X), \; r_3(Y), \; w_1(X), \; c_1, \; w_3(Y), \; c_3, \; r_2(Y), \; w_2(Z), \; w_2(Y), \; c_2$$
> *i. Determine whether the schedule is conflict serializable or not. Justify (5 marks)"*

---

#### ✅ Model Exam Answer (Write this verbatim for 5 / 5 Marks):

**Step 1: Represent the Given Schedule $S$ in Tabular Timeline Form**
The schedule involves **three transactions ($T_1, T_2, T_3$)** and **three data items ($X, Y, Z$)**:

| Time Step | Transaction $T_1$ | Transaction $T_2$ | Transaction $T_3$ |
| :--- | :--- | :--- | :--- |
| 1 | $r_1(X)$ | | |
| 2 | | $r_2(Z)$ | |
| 3 | $r_1(Z)$ | | |
| 4 | | | $r_3(X)$ |
| 5 | | | $r_3(Y)$ |
| 6 | $w_1(X)$ | | |
| 7 | $c_1$ *(Commit)* | | |
| 8 | | | $w_3(Y)$ |
| 9 | | | $c_3$ *(Commit)* |
| 10 | | $r_2(Y)$ | |
| 11 | | $w_2(Z)$ | |
| 12 | | $w_2(Y)$ | |
| 13 | | $c_2$ *(Commit)* | |

---

**Step 2: Identify All Conflicting Operations & Precedence Edges**
Two operations conflict if they belong to different transactions ($T_i \neq T_j$), operate on the same data item, and at least one of them is a write ($w$) operation. Let us examine conflicts for each data item ($X$, $Y$, and $Z$):

**1. Conflicts on Data Item $X$:**
* Sequence of operations on $X$: **$r_1(X) \rightarrow r_3(X) \rightarrow w_1(X)$**
* Pair $(r_1(X), r_3(X))$: Both are Read operations ($R-R$), so **no conflict**.
* Pair **$(r_3(X), w_1(X))$**: $T_3$ reads $X$ at step 4 **before** $T_1$ writes $X$ at step 6 ($R-W$ conflict).
  $$\Longrightarrow \text{Add directed edge: } \mathbf{T_3 \longrightarrow T_1}$$

**2. Conflicts on Data Item $Y$:**
* Sequence of operations on $Y$: **$r_3(Y) \rightarrow w_3(Y) \rightarrow r_2(Y) \rightarrow w_2(Y)$**
* Comparing $T_3$ and $T_2$:
  * $r_3(Y)$ (step 5) precedes $w_2(Y)$ (step 12) $\implies T_3 \rightarrow T_2$ ($R-W$ conflict)
  * $w_3(Y)$ (step 8) precedes $r_2(Y)$ (step 10) $\implies T_3 \rightarrow T_2$ ($W-R$ conflict)
  * $w_3(Y)$ (step 8) precedes $w_2(Y)$ (step 12) $\implies T_3 \rightarrow T_2$ ($W-W$ conflict)
  $$\Longrightarrow \text{Add directed edge: } \mathbf{T_3 \longrightarrow T_2}$$

**3. Conflicts on Data Item $Z$:**
* Sequence of operations on $Z$: **$r_2(Z) \rightarrow r_1(Z) \rightarrow w_2(Z)$**
* Pair $(r_2(Z), r_1(Z))$: Both are Read operations ($R-R$), so **no conflict**.
* Pair **$(r_1(Z), w_2(Z))$**: $T_1$ reads $Z$ at step 3 **before** $T_2$ writes $Z$ at step 11 ($R-W$ conflict).
  $$\Longrightarrow \text{Add directed edge: } \mathbf{T_1 \longrightarrow T_2}$$

---

**Step 3: Construct the Precedence (Serialization) Graph**
* **Vertices (Nodes):** $\{T_1, \; T_2, \; T_3\}$
* **Directed Edges:**
  1. $T_3 \longrightarrow T_1$ *(from conflict on $X$)*
  2. $T_3 \longrightarrow T_2$ *(from conflict on $Y$)*
  3. $T_1 \longrightarrow T_2$ *(from conflict on $Z$)*

```text
             ( T3 )
             /    \
   (on X)   /      \   (on Y)
           v        v
        ( T1 ) ---> ( T2 )
              (on Z)
```

---

**Step 4: Check for Cycles & Find Equivalent Serial Schedule (Justification)**
1. **Cycle Check:** By inspecting the Precedence Graph above, we see that **there is NO cycle (loop)** in the graph (it is a Directed Acyclic Graph – DAG).
2. **Conclusion:** Since the Precedence Graph is **acyclic (contains no cycles)**, the given schedule **IS CONFLICT SERIALIZABLE**.
3. **Equivalent Serial Schedule (via Topological Sorting):**
   * Node **$T_3$** has no incoming edges (in-degree = $0$), so **$T_3$ executes first**.
   * Removing $T_3$ leaves node **$T_1$** with no incoming edges, so **$T_1$ executes second**.
   * Finally, node **$T_2$** executes **third**.
   * **Equivalent Serial Order:**
     $$\boxed{T_3 \longrightarrow T_1 \longrightarrow T_2}$$

---

### Quick 30-Second Recap of 5.3
* **Serial Schedule:** No interleaving ($T_1$ then $T_2$). Always consistent, but slow.
* **Serializable Schedule:** An interleaved schedule that is equivalent to some Serial Schedule.
* **When 2 Operations Conflict:** Different transactions ($T_i \neq T_j$) + Same data item ($X$) + At least one is a **Write ($w$)** (`R-W`, `W-R`, `W-W`). *(Two Reads `R-R` NEVER conflict!)*
* **Precedence Graph Test:**
  * Draw arrow $T_i \rightarrow T_j$ if $T_i$'s operation comes before $T_j$'s conflicting operation on the same item.
  * **Has Cycle $\rightarrow$ NOT Conflict Serializable.**
  * **NO Cycle $\rightarrow$ IS Conflict Serializable!** (Use Topological Sort to write the serial order).
