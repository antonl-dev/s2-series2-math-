## PART A: Why Do We Need Recoverable Schedules?

In Module 5.3, we checked whether a schedule is **Conflict Serializable** assuming that no transaction ever fails.
**But what happens if a transaction crashes or aborts mid-execution?**

 Remember the **Durability** rule of ACID:
> **"Once a transaction $T_j$ is COMMITTED ($c_j$), its effects are permanent—a committed transaction can NEVER be rolled back or undone!"**

Now imagine what goes wrong if Transaction $T_2$ **reads an uncommitted ("dirty") value of $X$ written by $T_1$**, and then **$T_2$ commits FIRST ($c_2$)**, and right after that, **$T_1$ crashes and aborts ($a_1$)**!
* Because $T_1$ aborted, the value of $X$ that $T_2$ read was completely invalid—so $T_2$ *should* be rolled back too.
* **But $T_2$ has ALREADY COMMITTED ($c_2$)** and told the user "Transaction Successful"! It is now **impossible** to roll $T_2$ back!
* Such a schedule is called a **Non-Recoverable (Unrecoverable) Schedule**, and a DBMS must **never** allow it!

---

## PART B: Recoverable Schedules

### 1. What Does "Transaction $T_j$ Reads From Transaction $T_i$" Mean?
In any schedule $S$, we say that **Transaction $T_j$ reads a data item $X$ from Transaction $T_i$** ($i \neq j$) if:
1. $T_i$ writes $X$ (**$w_i(X)$**) first,
2. Later, $T_j$ reads $X$ (**$r_j(X)$**),
3. $T_i$ has **not** aborted before $r_j(X)$, and no other transaction overwrote $X$ in between $w_i(X)$ and $r_j(X)$.

---

### 2. Definition & Golden Rule of a Recoverable Schedule

* **Formal Definition:** A schedule $S$ is **Recoverable** if and only if **no transaction $T_j$ in $S$ commits until ALL transactions $T_i$ that have written an item that $T_j$ reads have committed first**.

> 🧠 **The 10-Second Exam Rule for Recoverable Schedules:**
> Whenever you see **$w_i(X)$ followed by $r_j(X)$** ($T_j$ reads $X$ from $T_i$), check the order of their commits ($c_i$ and $c_j$):
> $$\text{If } w_i(X) \longrightarrow r_j(X), \quad \text{then we MUST have: } \boxed{c_i \text{ BEFORE } c_j}$$
> * **If $c_i$ comes BEFORE $c_j$** (for every $w_i \to r_j$ pair) $\implies$ ✅ **Recoverable Schedule!**
> * **If $c_j$ comes BEFORE $c_i$** (for any dirty read $w_i \to r_j$) $\implies$ ❌ **Non-Recoverable Schedule!**

*(Note: What if a schedule has **zero** cases where $T_j$ reads an uncommitted value from $T_i$? Then it is **automatically Recoverable**!)*

---

### 3. Visual Comparison: Non-Recoverable vs. Recoverable Schedule

| Time | ❌ **Schedule $S_A$ (NON-RECOVERABLE!)** | ✅ **Schedule $S_B$ (RECOVERABLE!)** |
| :--- | :--- | :--- |
| 1 | $T_1: \; \mathbf{w_1(X)}$ *($T_1$ writes $X$)* | $T_1: \; \mathbf{w_1(X)}$ *($T_1$ writes $X$)* |
| 2 | $T_2: \; \mathbf{r_2(X)}$ *($T_2$ reads dirty $X$ from $T_1$!)* | $T_2: \; \mathbf{r_2(X)}$ *($T_2$ reads $X$ from $T_1$)* |
| 3 | $T_2: \; w_2(X)$ | $T_2: \; w_2(X)$ |
| 4 | $T_2: \; \mathbf{c_2}$ ❌ ***($T_2$ commits BEFORE $T_1$!)*** | $T_1: \; \mathbf{c_1}$ ✅ ***($T_1$ commits FIRST!)*** |
| 5 | $T_1: \; a_1$ *(Now if $T_1$ aborts, $T_2$ cannot undo!)* | $T_2: \; \mathbf{c_2}$ ***($T_2$ commits AFTER $c_1$!)*** |

## PART C: Cascading Rollback & Cascadeless Schedules

### 1. The Problem With Merely Recoverable Schedules: Cascading Rollback!

Even if a schedule is **Recoverable** (because $T_2$ waits for $T_1$ to commit before $T_2$ commits), something very expensive can still happen if $T_2$ reads $X$ **before** $T_1$ commits!

Look at this schedule where **nobody has committed yet**:

```text
Time 1:  T1 writes X   -->  w1(X)
Time 2:  T2 reads X    -->          r2(X), w2(X)
Time 3:  T3 reads X    -->                         r3(X), w3(X)
Time 4:  T1 CRASHES!   -->  a1 (Abort!)
                             |
                             +---> Forces T2 to Abort! (because T2 read dirty X from T1)
                                          |
                                          +---> Forces T3 to Abort! (because T3 read dirty X from T2)
```

* **What is Cascading Rollback (or Cascading Abort)?**
  * **Definition:** A phenomenon in which the failure/abort of a **single transaction ($T_1$)** forces a chain reaction where **several other active transactions ($T_2, T_3, \dots$) must also be rolled back** because they read uncommitted ("dirty") data written by the failed transaction.
  * **Why it is bad:** Rolling back 10 transactions because 1 transaction failed wastes huge amounts of CPU and disk I/O time!

---

### 2. How to Prevent Cascading Rollback: Cascadeless Schedules!

How do we guarantee that **Cascading Rollback can NEVER happen**?
Simple: **Forbid Dirty Reads completely!** Never let $T_2$ read $X$ until $T_1$ has **already committed ($c_1$)**!

* **Definition of a Cascadeless Schedule (Avoids Cascading Rollback – ACR):**
  > *"A schedule is **Cascadeless** if every transaction in the schedule reads **ONLY items that were written by COMMITTED transactions**."*
* **Formal Rule for a Cascadeless Schedule:**
  Whenever $T_i$ writes $X$ ($w_i(X)$) and $T_j$ later reads $X$ ($r_j(X)$) ($i \neq j$), the commit operation of $T_i$ (**$c_i$**) must appear **BEFORE the read operation $r_j(X)$**!
  $$\boxed{\text{Cascadeless Rule: } \;\; w_i(X) \longrightarrow \mathbf{c_i} \longrightarrow r_j(X)}$$

## PART D: Strict Schedules & Comparison of All 3 Types

### 1. Strict Schedules (The Safest Schedule Used in Real DBMSs)
* **Definition:** A schedule is **Strict** if no transaction $T_j$ is allowed to **neither READ nor WRITE (overwrite)** a data item $X$ written by $T_i$ until $T_i$ has committed ($c_i$) or aborted ($a_i$).
* **Formal Rule for a Strict Schedule:**
  $$\boxed{\text{Strict Rule: } \;\; w_i(X) \longrightarrow \mathbf{c_i \text{ (or } a_i\text{)}} \longrightarrow r_j(X) \text{ or } w_j(X)}$$
* **Why DBMSs love Strict Schedules:** Because rolling back an aborted transaction in a Strict schedule is trivial—you simply restore the old Before-Image (`old_value`) from the System Log without worrying about overwriting any other transaction's write!

---

### 2. Hierarchy & Comparison Table: Recoverable vs. Cascadeless vs. Strict

```text
+-------------------------------------------------------------------+
| ALL SCHEDULES                                                     |
|   +-----------------------------------------------------------+   |
|   | RECOVERABLE SCHEDULES ( w_i(X) -> r_j(X) ==> c_i -> c_j ) |   |
|   |   +---------------------------------------------------+   |   |
|   |   | CASCADELESS SCHEDULES ( w_i(X) -> c_i -> r_j(X) ) |   |   |
|   |   |   +-------------------------------------------+   |   |   |
|   |   |   | STRICT SCHEDULES                          |   |   |   |
|   |   |   | ( w_i(X) -> c_i -> r_j(X) AND w_j(X) )    |   |   |   |
|   |   |   +-------------------------------------------+   |   |   |
|   |   +---------------------------------------------------+   |   |
|   +-----------------------------------------------------------+   |
+-------------------------------------------------------------------+
```
*(Notice: **Every Strict schedule is Cascadeless**, and **every Cascadeless schedule is Recoverable**!)*

| Feature | Recoverable Schedule | Cascadeless Schedule | Strict Schedule |
| :--- | :--- | :--- | :--- |
| **1. Exact Rule when $T_i$ writes $X$ ($w_i(X)$)** | $T_j$ **can read** $X$ before $c_i$, **BUT $c_i$ must happen before $c_j$**! | $T_j$ **cannot read** $X$ until **after $c_i$** ($w_i(X) \to c_i \to r_j(X)$). | $T_j$ **cannot read OR write** $X$ until **after $c_i$** ($w_i(X) \to c_i \to r_j(X)/w_j(X)$). |
| **2. Are Dirty Reads ($w_i \to r_j$ before $c_i$) Allowed?** | **Yes** (as long as $T_i$ commits before $T_j$). | **No!** (Zero dirty reads allowed). | **No!** (Zero dirty reads and zero dirty writes). |
| **3. Can Cascading Rollback Happen?** | **Yes**, cascading rollback is possible if $T_i$ aborts. | **No!** Completely avoids cascading rollback. | **No!** Completely avoids cascading rollback. |

## PART E: Past Year Question (PYQ) – Full Solved Answer

### PYQ 1: Nov 2025 End-Sem Exam – Question 10(ii) [3 Marks]

> **Question 10(ii) [3 Marks]:**
> *"Consider the following schedule:*
> $$r_1(X), \; r_2(Z), \; r_1(Z), \; r_3(X), \; r_3(Y), \; w_1(X), \; c_1, \; w_3(Y), \; c_3, \; r_2(Y), \; w_2(Z), \; w_2(Y), \; c_2$$
> *ii. Is the schedule recoverable? Justify your answer. (3 marks)"*

---

#### ✅ Model Exam Answer (Write this verbatim for 3 / 3 Marks):

**Answer:** **YES**, the given schedule is **Recoverable** (and in fact, it is also **Cascadeless**).

**Justification:**

**1. Definition of a Recoverable Schedule:**
* A schedule $S$ is **recoverable** if no transaction $T_j$ in $S$ commits until all transactions $T_i$ that have written a data item that $T_j$ subsequently reads have committed first.
* That is, whenever a Write–Read dependency **$w_i(A) \rightarrow r_j(A)$** ($i \neq j$) occurs in the schedule, the commit operation **$c_i$ must precede $c_j$**.

**2. Checking All Write–Read ($w_i \rightarrow r_j$) Dependencies in the Given Schedule:**
Let us inspect the write operations and any subsequent read operations on each data item ($X$, $Y$, and $Z$):

* **On Data Item $X$:**
  * $T_1$ performs **$w_1(X)$** at step 6 ( after $r_1(X)$ at step 1 and $r_3(X)$ at step 4).
  * No transaction reads $X$ *after* $w_1(X)$. Hence, no transaction reads $X$ from $T_1$.
* **On Data Item $Z$:**
  * $T_2$ performs **$w_2(Z)$** at step 11 (after $r_2(Z)$ at step 2 and $r_1(Z)$ at step 3).
  * No transaction reads $Z$ *after* $w_2(Z)$. Hence, no transaction reads $Z$ from $T_2$.
* **On Data Item $Y$:**
  * $T_3$ writes $Y$ (**$w_3(Y)$**) at **step 8**, and later $T_2$ reads $Y$ (**$r_2(Y)$**) at **step 10**.
  * Therefore, **Transaction $T_2$ reads item $Y$ from Transaction $T_3$** ($w_3(Y) \rightarrow r_2(Y)$).

**3. Verifying the Commit Order for $T_3$ and $T_2$:**
* Since $T_2$ reads $Y$ from $T_3$, for the schedule to be recoverable, **$T_3$ must commit ($c_3$) before $T_2$ commits ($c_2$)**.
* Looking at the schedule:
  $$w_3(Y) \text{ [step 8]} \longrightarrow \mathbf{c_3 \text{ [step 9]}} \longrightarrow r_2(Y) \text{ [step 10]} \longrightarrow \mathbf{c_2 \text{ [step 13]}}$$
* Here, **$c_3$ occurs at step 9**, which is **before $c_2$ at step 13** (and even before $r_2(Y)$ at step 10, meaning $T_2$ reads only committed data!).

**Conclusion:**
Since $T_3$ commits ($c_3$) before $T_2$ commits ($c_2$) (and before $T_2$ even reads $Y$), there are no dirty reads of uncommitted data. Therefore, **the given schedule is Recoverable (as well as Cascadeless)**.

---

### Quick 30-Second Recap of 5.4
* **How to test if a schedule is Recoverable:**
  1. Look for any **Write followed by a Read on the same variable** by another transaction: **$w_i(X) \dots r_j(X)$** (*"$T_j$ reads $X$ from $T_i$"*).
  2. Check their commits: Does **$c_i$ come BEFORE $c_j$**?
     * If **YES** $\rightarrow$ **Recoverable!**
     * If **NO** ($c_j$ commits before $c_i$) $\rightarrow$ **NOT Recoverable!**
* **Cascadeless Schedule:** Even better—$c_i$ happens **before $r_j(X)$** ($w_i(X) \rightarrow c_i \rightarrow r_j(X)$), so $T_j$ never reads uncommitted dirty data and **Cascading Rollback is impossible**!
