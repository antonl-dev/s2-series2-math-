## PART A: What is a Transaction?

### 1. Definition of a Transaction
* **Definition:** A **Transaction ($T$)** is a **logical unit of database processing** that includes one or more database access operations (such as insertion, deletion, modification, or retrieval).
* **The "All-or-Nothing" Principle:**
  * Even if a transaction consists of 10 separate SQL statements, the DBMS treats the entire transaction as **one single indivisible unit of work**.
  * Either **ALL** operations inside the transaction are completed successfully and saved permanently (**Committed**), or **NONE** of them take effect and any partial changes are undone (**Aborted / Rolled Back**).

### 2. Real-World Example: Bank Fund Transfer
Suppose **Adhil (Account $X$, Balance = ₹5,000)** transfers **₹1,000** to **Rahul (Account $Y$, Balance = ₹2,000)** via UPI.
To Adhil, this feels like 1 single action ("Send ₹1,000"). However, inside the database, this transaction $T_1$ requires **6 separate low-level steps**:

1. Read Adhil's balance ($X = 5000$) from disk into RAM.
2. Subtract ₹1,000 in RAM ($X = X - 1000 = 4000$).
3. Write Adhil's new balance ($X = 4000$) back to disk.
4. Read Rahul's balance ($Y = 2000$) from disk into RAM.
5. Add ₹1,000 in RAM ($Y = Y + 1000 = 3000$).
6. Write Rahul's new balance ($Y = 3000$) back to disk.

* **Why Transaction Processing Matters:** If the server crashes right after Step 3, Adhil has lost ₹1,000 and Rahul has received ₹0! Grouping Steps 1–6 inside a single **Transaction** ensures that if a crash occurs after Step 3, the DBMS automatically undoes Step 3 and restores Adhil's balance to ₹5,000!

### 3. Single-User vs. Multi-User Database Systems

1. **Single-User DBMS:**
   * At most **one user** at a time can access the database (e.g., a personal MS Access file on a laptop). Concurrency control is not needed.
2. **Multi-User DBMS:**
   * Hundreds or thousands of users submit transactions **simultaneously (concurrently)** (e.g., banking ATMs, IRCTC railway ticket booking, Amazon checkout).
   * **How Interleaved Concurrency Works:**
     * Reading a disk block takes milliseconds, while CPU instructions take nanoseconds.
     * Instead of letting the CPU sit idle while Transaction $T_1$ waits for a disk read, the operating system switches the CPU to execute Transaction $T_2$, then switches back to $T_1$!
     * Thus, operations of $T_1$ and $T_2$ are **interleaved** in time.

📸 **[Click here to view Interleaved vs Parallel Transaction Execution Diagrams on Google Images](https://www.google.com/search?q=interleaved+concurrency+vs+parallel+processing+in+dbms+diagram&udm=2)**

```text
SERIAL EXECUTION (Slow - CPU sits idle during disk I/O):
  Time --->  [------- Transaction T1 -------] [------- Transaction T2 -------]

INTERLEAVED CONCURRENT EXECUTION (Fast - CPU switches between T1 and T2):
  Time --->  [T1] [T2] [T1] [T2] [T2] [T1] [T2]
```

## PART B: The Transaction Model (`read_item` and `write_item`)

To analyze concurrent transactions mathematically (like in your **Nov 2025 End-Sem Q10** problem!), DBMS theory simplifies all database operations into **two basic operations** on a data item $X$:

1. **`read_item(X)`** — written in schedules as **$r_i(X)$** or **$R_i(X)$**
2. **`write_item(X)`** — written in schedules as **$w_i(X)$** or **$W_i(X)$**

### 1. What Happens Internally During `read_item(X)` and `write_item(X)`?

Remember from Module 3.3 that data items live inside **Disk Blocks** on the hard disk, and the CPU can only modify variables in **Main Memory (RAM)**.

📸 **[Click here to view Read and Write Transaction Model Buffer Diagrams on Google Images](https://www.google.com/search?q=read_item+and+write_item+operations+in+transaction+processing+dbms+diagram&udm=2)**

```text
HARD DISK                               MAIN MEMORY (RAM)
+-------------------------+             +-------------------------+       +--------------------+
| Disk Block containing X |  1. Read    | DBMS Main Memory Buffer |  2.   | Program Variable X |
|      [ X = 5000 ]       | ==========> |      [ X = 5000 ]       | ====> |  (Inside Trans T1) |
|                         | <========== |      [ X = 4000 ]       | <==== |    X := X - 1000   |
+-------------------------+  4. Flush   +-------------------------+  3.   +--------------------+
                               to Disk                              Write
```

#### Exact Steps Executed by `read_item(X)`:
1. Find the address of the **disk block** that contains item $X$.
2. Copy that disk block into a **DBMS buffer in main memory (RAM)** *(if that block is not already in RAM)*.
3. Copy item $X$ from the main memory buffer into the local **program variable** named $X$ inside the transaction.

#### Exact Steps Executed by `write_item(X)`:
1. Find the address of the **disk block** that contains item $X$.
2. Copy that disk block into a **DBMS buffer in main memory (RAM)** *(if that block is not already in RAM)*.
3. Copy the updated value from the local **program variable $X$** into its proper location inside the **main memory buffer**.
4. Store (flush) the updated block from the main memory buffer back to the **hard disk** *(either immediately or at a later time determined by the Recovery Manager)*.

### 2. Representing Transactions in the Transaction Model

Using `read_item` and `write_item`, here is how our two bank transactions look:

| **Transaction $T_1$** *(Transfers ₹1,000 from $X$ to $Y$)* | **Transaction $T_2$** *(Deposits ₹500 into Account $X$)* |
| :--- | :--- |
| `read_item(X);` | `read_item(X);` |
| `X := X - 1000;` | `X := X + 500;` |
| `write_item(X);` | `write_item(X);` |
| `read_item(Y);` | |
| `Y := Y + 1000;` | |
| `write_item(Y);` | |

* **In Compact Schedule Notation (Used in Nov 2025 Q10!):**
  * Transaction $T_1$'s database actions are written simply as: **`r1(X), w1(X), r1(Y), w1(Y)`** (followed by **`c1`** for Commit or **`a1`** for Abort).
  * Transaction $T_2$'s database actions are written simply as: **`r2(X), w2(X)`** (followed by **`c2`** for Commit).

## PART C: Overview of Concurrency Control – Why Do We Need It?

> ⭐ **VERY HIGH-PROBABILITY EXAM QUESTION (4–5 Marks):**
> *"What is concurrency control? Explain the different problems (anomalies) that arise when multiple transactions execute concurrently in an uncontrolled manner."*

When multiple transactions execute concurrently in an **uncontrolled** manner (without locking or concurrency control), their interleaved `read_item` and `write_item` operations can interfere with each other and corrupt the database!

Suppose initially **Account $X = ₹5,000$** and **Account $Y = ₹2,000$**:
* If $T_1$ (subtracts ₹1,000 from $X$) and $T_2$ (adds ₹500 to $X$) run one after another, the final correct value of $X$ **MUST be**:
  $$X = 5000 - 1000 + 500 = \mathbf{₹4,500}$$

Now look at the **4 Classic Concurrency Problems** that happen when $T_1$ and $T_2$ interleave without concurrency control:

### Problem 1: The Lost Update Problem *(Write–Write Conflict)*

* **When it happens:** Two transactions $T_1$ and $T_2$ both access the **same database item $X$** and have their operations interleaved in a way that makes the value of some database item incorrect because **one update overwrites the other**!
* **Step-by-Step Timeline Trace (Initial $X = 5000$):**

| Time | Transaction $T_1$ *(Withdraws ₹1,000)* | Transaction $T_2$ *(Deposits ₹500)* | Value of $X$ in Database |
| :--- | :--- | :--- | :--- |
| $t_1$ | `read_item(X);` *(reads $X = 5000$)* | | $5000$ |
| $t_2$ | `X := X - 1000;` *($T_1$'s local $X = 4000$)* | **`read_item(X);`** *(also reads $X = 5000$!)* | $5000$ |
| $t_3$ | | `X := X + 500;` *($T_2$'s local $X = 5500$)* | $5000$ |
| $t_4$ | **`write_item(X);`** *(writes $X = 4000$)* | | **$4000$** |
| $t_5$ | | **`write_item(X);`** *(overwrites $X$ with $5500$!)* | **$5500$ ❌ (WRONG!)** |
| $t_6$ | `read_item(Y); Y:=Y+1000; write_item(Y);` | | |

* **What Went Wrong?**
  * At $t_4$, $T_1$ wrote $X = 4000$.
  * At $t_5$, $T_2$ overwrote $X$ with $5500$ (because $T_2$ had read the old value $5000$ at $t_2$ before $T_1$ wrote its update!).
  * **$T_1$'s update ($-\text{₹}1,000$) was completely LOST!** Final balance is ₹5,500 instead of ₹4,500!

---

### Problem 2: The Temporary Update (or Dirty Read) Problem *(Write–Read Conflict)*

* **When it happens:** One transaction $T_1$ updates a database item $X$ and then **$T_1$ fails/aborts** for some reason. However, **BEFORE** $T_1$ rolls back $X$ to its original value, another transaction **$T_2$ reads the temporary ("dirty"), uncommitted value of $X$**!
* **Why is it called a "Dirty Read"?** Because the value $X = 4000$ written by $T_1$ was never committed and was later rolled back—so $T_2$ read a "dirty" value that **never officially existed** in the database!
* **Step-by-Step Timeline Trace (Initial $X = 5000$):**

| Time | Transaction $T_1$ *(Updates $X$, then crashes!)* | Transaction $T_2$ *(Reads $X$)* | Value of $X$ in Database |
| :--- | :--- | :--- | :--- |
| $t_1$ | `read_item(X);` *(reads $X = 5000$)* | | $5000$ |
| $t_2$ | `X := X - 1000;` | | $5000$ |
| $t_3$ | **`write_item(X);`** *(writes uncommitted $X = 4000$)* | | **$4000$ *(Dirty!)* ** |
| $t_4$ | | **`read_item(X);`** *(reads dirty $X = 4000$!)* ❌ | $4000$ |
| $t_5$ | | `X := X + 500;` | $4000$ |
| $t_6$ | | `write_item(X); COMMIT;` *(saves $4500$)* | $4500$ |
| $t_7$ | ❌ **$T_1$ FAILS & ABORTS!** *(Rolls back $X$ to $5000$)* | | *(Should be $5500$, not $4500$!)* |

* **What Went Wrong?**
  * Because $T_1$ aborted at $t_7$, $T_1$'s withdrawal of ₹1,000 never happened.
  * Yet $T_2$ already read $T_1$'s uncommitted value ($4000$) at $t_4$ and calculated its deposit based on that nonexistent value!

---

### Problem 3: The Incorrect Summary Problem

* **When it happens:** One transaction $T_3$ is calculating an **aggregate summary function** (like `SUM` or `AVG`) over a set of database items while another transaction $T_1$ is actively updating some of those items!
* **Result:** $T_3$ may read some items **before** they are updated and other items **after** they are updated, producing a wrong total!
* **Step-by-Step Timeline Trace (Initial $X = 5000, Y = 2000 \implies \text{True Total} = ₹7,000$):**

| Time | Transaction $T_1$ *(Transfers ₹1,000 from $X$ to $Y$)* | Transaction $T_3$ *(Computes `Sum = X + Y`)* |
| :--- | :--- | :--- |
| $t_1$ | `read_item(X); X := X - 1000;` | `Sum := 0;` |
| $t_2$ | **`write_item(X);`** *($X$ becomes $4000$)* | |
| $t_3$ | | **`read_item(X);`** *(reads $X = 4000$ **AFTER** deduction!)* |
| $t_4$ | | `Sum := Sum + X;` *($\text{Sum} = 4000$)* |
| $t_5$ | | **`read_item(Y);`** *(reads $Y = 2000$ **BEFORE** addition!)* |
| $t_6$ | | `Sum := Sum + Y;` *($\text{Sum} = 4000 + 2000 = \mathbf{6000}$ ❌)* |
| $t_7$ | `read_item(Y); Y := Y + 1000; write_item(Y);` *($Y$ becomes $3000$)* | |

* **What Went Wrong?** Both before and after $T_1$, the total money in the bank ($X + Y$) is **$₹7,000$** ($5000+2000 = 7000$, and $4000+3000 = 7000$). Yet $T_3$ computed a sum of **$₹6,000$**—missing ₹1,000 that was in transit!

---

### Problem 4: The Unrepeatable Read Problem *(Read–Write Conflict)*

* **When it happens:** A transaction $T_1$ reads the **exact same data item $X$ twice** during its execution, and between the two reads, another transaction $T_2$ modifies and commits a new value for $X$.
* **Result:** $T_1$ receives **two different values** for the same item $X$ within the same transaction!
  * *Example:* While booking a flight ticket, Transaction $T_1$ checks the seat price ($X = ₹4,000$). Before $T_1$ proceeds to payment, Transaction $T_2$ updates the flight price to $X = ₹6,500$. When $T_1$ re-reads $X$ to bill the customer, the price has changed mid-transaction!

---

### Summary Table of the 4 Concurrency Problems

| Problem Name | Conflict Pattern | What Happens in 1 Sentence |
| :--- | :--- | :--- |
| **1. Lost Update Problem** | **Write–Write ($W-W$)** | $T_2$ overwrites $T_1$'s update on $X$ because both read the same old value of $X$. |
| **2. Dirty Read (Temporary Update)** | **Write–Read ($W-R$)** | $T_2$ reads an uncommitted value of $X$ written by $T_1$, and then $T_1$ aborts/rolls back. |
| **3. Incorrect Summary Problem** | Interleaved Aggregate | $T_3$ sums items while $T_1$ is transferring between them, reading some before and some after update. |
| **4. Unrepeatable Read** | **Read–Write ($R-W$)** | $T_1$ reads $X$ twice, and $T_2$ modifies $X$ in between, so $T_1$ sees two different values of $X$. |

## PART D: Model Exam Question & Full Word-for-Word Answer for 5.1

### Model Question [5 Marks]:
> *"What is a transaction? Explain the problems that occur when concurrent transactions execute in an uncontrolled manner with suitable schedules."*

#### ✅ Model Exam Answer (Write this verbatim for 5 / 5 Marks):

**1. Concept of a Transaction:**
* A **Transaction ($T$)** is a logical unit of database processing that consists of one or more database access operations—abstracted in the transaction model as **`read_item(X)`** and **`write_item(X)`**.
* A transaction obeys the **"All-or-Nothing"** principle: either all of its operations execute completely and are permanently saved (**Committed**), or none of them take effect (**Aborted / Rolled Back**).

**2. Problems Caused by Uncontrolled Concurrent Execution:**
When multiple transactions execute concurrently by interleaving their operations without a Concurrency Control mechanism, the following four problems arise:

**i) The Lost Update Problem:**
* Occurs when two transactions access the same data item $X$ and interleave their operations such that one transaction overwrites the update made by the other.
* *Example Schedule (Initial $X = 5000$):*
  * $T_1$ reads $X = 5000$ and computes $X = 5000 - 1000 = 4000$.
  * Before $T_1$ writes $X$, $T_2$ also reads $X = 5000$ and computes $X = 5000 + 500 = 5500$.
  * $T_1$ writes $X = 4000$, and then $T_2$ writes $X = 5500$.
  * Here, $T_1$'s update ($-1000$) is completely lost!

**ii) The Temporary Update (Dirty Read) Problem:**
* Occurs when a transaction $T_1$ updates a data item $X$ and later **fails/aborts**, but **before** $T_1$ rolls back $X$ to its original value, another transaction $T_2$ reads the uncommitted ("dirty") value of $X$.
* *Example Schedule:*
  * $T_1$ writes $X = 4000$ (uncommitted).
  * $T_2$ reads $X = 4000$.
  * $T_1$ aborts and rolls $X$ back to $5000$, leaving $T_2$ with a dirty, invalid value that never committed.

**iii) The Incorrect Summary Problem:**
* Occurs when one transaction $T_3$ is calculating an aggregate summary (e.g., `SUM`) over several data items while another transaction $T_1$ is updating those items.
* Because $T_3$ reads some items before they are updated and other items after they are updated, the computed summary is incorrect.

**iv) The Unrepeatable Read Problem:**
* Occurs when a transaction $T_1$ reads the same data item $X$ twice, and between the two reads, another transaction $T_2$ modifies $X$. As a result, $T_1$ receives two different values for the same item within a single execution.

### Quick 30-Second Recap of 5.1
* **Transaction ($T$):** Logical unit of work (`read_item(X)`, `write_item(X)`).
* **4 Problems of Uncontrolled Concurrency:**
  1. **Lost Update:** $T_2$ overwrites $T_1$'s write ($W-W$).
  2. **Dirty Read (Temporary Update):** $T_2$ reads $T_1$'s uncommitted write, then $T_1$ aborts ($W-R$).
  3. **Incorrect Summary:** Aggregate `SUM` reads some items before transfer and some after transfer.
  4. **Unrepeatable Read:** $T_1$ reads $X$ twice; $T_2$ changes $X$ in between ($R-W$).
