## PART A: Significance of Concurrency Control and Recovery

Whenever a transaction is submitted to a DBMS, two critical subsystems work together to protect the database:

1. **Significance of the Concurrency Control Subsystem:**
   * Ensures that when hundreds of users run transactions simultaneously, their interleaved operations do **not** cause Lost Updates, Dirty Reads, or Incorrect Summaries (enforces **Isolation**).
2. **Significance of the Recovery Subsystem:**
   * Ensures that the database always remains accurate even if the transaction crashes halfway through or the server loses power (enforces **Atomicity** and **Durability**).

### Why Do Transactions FailMid-Execution? (5 Major Causes of Failure)
1. **Computer Failure (System Crash):** A hardware, operating system, or power failure occurs during transaction execution, wiping out the contents of volatile main memory (RAM).
2. **Transaction or System Error:** An internal programming error occurs inside the transaction, such as **division by zero**, integer overflow, or invalid user input.
3. **Local Exception Conditions Detected by the Transaction:** The transaction itself detects a business-rule failure—for example, *"Insufficient balance in Account $X$"* during an ATM withdrawal—and intentionally aborts itself.
4. **Concurrency Control Enforcement:** The Concurrency Control manager forcibly aborts a transaction to break a **Deadlock** or prevent a serializability violation.
5. **Disk Failure / Physical Catastrophe:** A disk head crash or physical damage destroys disk blocks (recovered using archival backups and the System Log).

### Detailed Explanation of Each Transaction State

#### 1. Active State
* **When it enters:** This is the **initial state**—a transaction enters the Active state immediately after `BEGIN_TRANSACTION` starts.
* **What happens here:** The transaction stays in the **Active** state as long as its `READ` and `WRITE` operations are executing normally in main memory (RAM).
* **Where it goes next:**
  * If all `READ`/`WRITE` statements finish without error $\rightarrow$ moves to **Partially Committed**.
  * If an error or crash occurs mid-execution $\rightarrow$ moves to **Failed**.

#### 2. Partially Committed State
* **When it enters:** Immediately after the **final statement** of the transaction has been executed!
* **Why is it only "Partially" Committed and not "Committed" yet?**
  1. Because the modified data blocks updated by the transaction may still be sitting inside **volatile Main Memory (RAM) buffers** and have **not yet been written out to the hard disk**!
  2. The Concurrency Control and Integrity subsystems may still need to perform final checks before allowing the commit.
* **Where it goes next:**
  * Once the Recovery Manager writes the `[commit, T]` record safely to the **System Log on disk** $\rightarrow$ moves to **Committed**.
  * If the power fails or a final check fails before the log reaches disk $\rightarrow$ moves to **Failed**!

#### 3. Failed State
* **When it enters:** A transaction enters the **Failed** state as soon as the system discovers that **normal execution can no longer proceed** (either from the *Active* state due to a program error/abort, or from the *Partially Committed* state due to a crash before commit).
* **What happens next:** A failed transaction cannot stay half-done! The Recovery Manager must immediately **roll back (undo)** any changes it made.

#### 4. Aborted State
* **When it enters:** The transaction enters the **Aborted** state **after** it has been rolled back and the database has been completely restored to its original state prior to the start of the transaction.
* **Two Actions Taken After a Transaction is Aborted:**
  1. **Restart the Transaction:** Done automatically if the transaction failed due to an external hardware/software crash or deadlock (not its own fault).
  2. **Kill the Transaction:** Done if the failure was caused by an internal logic bug in the program or bad user input (e.g., insufficient balance).

#### 5. Committed State
* **When it enters:** Reached from the *Partially Committed* state once all changes have been permanently recorded in the System Log on disk.
* **Key Rule:** Once a transaction enters the **Committed** state, it has concluded its execution successfully and **can NEVER be rolled back/undone** (even if the system crashes 1 millisecond later!).

#### 6. Terminated State
* **When it enters:** Reached from either the **Committed** state or the **Aborted** state when the transaction completely leaves the system and its transaction table entry is cleared.

## PART C: The System Log (Write-Ahead Log)

How does the Recovery Manager know *what* to undo when a transaction enters the **Failed** state, or *what* to redo if power fails right after a transaction enters the **Committed** state?
It uses a special file called the **System Log**!

### 1. What is the System Log?
* **Definition:** The **System Log** (or *Transaction Log* / *Journal*) is a sequential, append-only file maintained on **non-volatile disk storage** that keeps track of **all transaction operations that affect the values of database items**.
* Because it is stored on stable disk (and periodically backed up), the System Log survives power failures and system crashes!

📸 **[Click here to view System Log Records in DBMS Recovery Diagrams on Google Images](https://www.google.com/search?q=system+log+records+in+dbms+write_item+old_value+new_value+diagram&udm=2)**

---

### 2. The 5 Types of Log Records Stored in the System Log

Every time a transaction $T$ starts, modifies data, commits, or aborts, the DBMS appends a **Log Record** to the end of the System Log:

| Log Record Format | Exact Meaning & Purpose in Recovery |
| :--- | :--- |
| **1. `[start_transaction, T]`** *(or `<T, start>`)* | Records that transaction $T$ has started execution (entered **Active** state). |
| **2. `[write_item, T, X, old_value, new_value]`** *(or `<T, X, V_old, V_new>`)* | Records that transaction $T$ has changed the value of database item $X$ from **`old_value`** *(Before-Image / BFIM)* to **`new_value`** *(After-Image / AFIM)*. |
| **3. `[read_item, T, X]`** | Records that transaction $T$ has read database item $X$ *(often omitted in modern logs since reads do not change data)*. |
| **4. `[commit, T]`** *(or `<T, commit>`)* | Records that transaction $T$ has completed all accesses successfully and its changes are **permanently committed**. |
| **5. `[abort, T]`** *(or `<T, abort>`)* | Records that transaction $T$ has been **aborted / rolled back**. |

---

### 3. Why Does `[write_item, T, X, old_value, new_value]` Store BOTH Old and New Values?

Look at that second log record: `[write_item, T1, X, 5000, 4000]`. Why does it store **both `5000` (`old_value`) and `4000` (`new_value`)**?

1. **Why we need `old_value` (For `UNDO` / Rollback):**
   * Suppose $T_1$ changes $X$ from `5000` to `4000`, and then **crashes before writing `[commit, T1]`**!
   * When the system reboots, the Recovery Manager looks at the log, sees `[start_transaction, T1]` with **NO `[commit, T1]`**, and performs an **`UNDO`**: it sets $X$ back to its **`old_value` (`5000`)**!
2. **Why we need `new_value` (For `REDO` / Roll-Forward):**
   * Suppose $T_1$ changes $X$ from `5000` to `4000` and writes **`[commit, T1]`** to the log on disk, **but the power fails 1 millisecond later** before the RAM buffer flushed `4000` to the main database file!
   * When the system reboots, the Recovery Manager sees **`[commit, T1]`** in the log and performs a **`REDO`**: it sets $X$ to its **`new_value` (`4000`)** so the committed update is not lost!

## PART D: Desirable Properties of Transactions – The ACID Properties

To ensure data integrity despite concurrent access and system failures, every transaction in a DBMS must possess four fundamental properties, universally known by the acronym **ACID**:

📸 **[Click here to view ACID Properties in DBMS Summary Diagrams on Google Images](https://www.google.com/search?q=ACID+properties+in+dbms+diagram+with+example&udm=2)**

```text

                |       ACID PROPERTIES OF TRANSACTIONS     |
                +---------------------+---------------------+
                                      |
     +----------------+---------------+---------------+----------------+
     |                |                               |                |
     v                v                               v                v
[ A: Atomicity ] [ C: Consistency ]           [ I: Isolation ]  [ D: Durability ]
 "All or Nothing"  "Valid State -> Valid State" "No Interference" "Permanent Commit"
 (Enforced by:     (Enforced by: App Code &      (Enforced by:     (Enforced by:
  Recovery Mgr)     Integrity Constraints)        Concurrency Mgr)  Recovery Mgr)
```

Let's explain each property using our bank transfer example (**Transaction $T_1$ transferring ₹1,000 from Account $X$ [₹5,000] to Account $Y$ [₹2,000]**):

---

### 1. A – Atomicity ("All or Nothing")
* **Definition:** The **Atomicity** property requires that a transaction is an **indivisible ("atomic") unit of execution**: either **ALL** of its database operations are performed in their entirety, or **NONE** of them are performed at all. There is no such thing as a "half-completed" transaction!
* **Bank Example:**
  * $T_1$ deducts ₹1,000 from $X$ ($X = 4000$) and adds ₹1,000 to $Y$ ($Y = 3000$).
  * If a crash occurs right after ₹1,000 is deducted from $X$ (before it is added to $Y$), **Atomicity** guarantees that the DBMS will automatically **undo** the deduction and restore $X$ back to ₹5,000!
* **Which DBMS Subsystem Enforces Atomicity?**
  * Enforced by the **Transaction Recovery Subsystem** (using the `UNDO` operation on the System Log).

---

### 2. C – Consistency (Preservation of Database Consistency)
* **Definition:** The **Consistency** property requires that the complete execution of a transaction in isolation (without interference from other transactions) must take the database from **one consistent state to another consistent state**, preserving all database integrity constraints and business rules.
* **Bank Example:**
  * Before $T_1$ runs, the total money across Account $X$ and Account $Y$ is:
    $$X + Y = 5000 + 2000 = \mathbf{₹7,000}$$
  * After $T_1$ finishes transferring ₹1,000, the total money must **still be ₹7,000**:
    $$X + Y = 4000 + 3000 = \mathbf{₹7,000}$$
  * Money is neither created out of thin air nor destroyed, and no constraint (like `Balance >= 0`) is violated.
* **Who Enforces Consistency?**
  * Enforced by **Application Programmers** (who write correct transaction logic) and the **DBMS Integrity Constraint Checker** (which checks Primary Key, Foreign Key, and `CHECK` constraints).

---

### 3. I – Isolation (Independence from Concurrent Transactions)
* **Definition:** The **Isolation** property requires that even though multiple transactions execute concurrently at the same time, the execution of each transaction must **not be interfered with** by any other concurrent transaction.
* **Key Rule:** The intermediate (uncommitted) updates of a transaction $T_1$ must remain **invisible** to all other concurrent transactions $T_2$ until $T_1$ commits! To every transaction, it should feel as if it is the **only transaction** running on the system.
* **Bank Example:**
  * While $T_1$ has deducted ₹1,000 from $X$ ($X=4000$) and has **not yet** added ₹1,000 to $Y$ ($Y=2000$), another transaction $T_3$ computing `X + Y` must **not** be allowed to see this temporary half-updated state (otherwise $T_3$ would see $4000 + 2000 = ₹6,000$!).
* **Which DBMS Subsystem Enforces Isolation?**
  * Enforced by the **Concurrency Control Subsystem** (using **Locks / Two-Phase Locking [2PL]**).

---

### 4. D – Durability (Permanence)
* **Definition:** The **Durability** property requires that once a transaction successfully **commits (`COMMIT`)** and the user is notified of success, the changes it applied to the database **must persist permanently** in the database and **must NEVER be lost** because of any subsequent power failure or system crash!
* **Bank Example:**
  * Once the UPI app shows `"₹1,000 Transferred Successfully (Committed)"`, even if the bank's server loses power 1 second later, Rahul's account balance **will still be ₹3,000** when the server restarts!
* **Which DBMS Subsystem Enforces Durability?**
  * Enforced by the **Recovery Subsystem** (using the **System Log** and the `REDO` operation).

---

### Quick Summary Table of ACID Properties (Great for Exam Answers!)

| Property | One-Line Meaning | Enforced By Which Component? |
| :--- | :--- | :--- |
| **A – Atomicity** | **All or Nothing** (either all steps happen, or none happen). | **Recovery Manager** (`UNDO` using System Log) |
| **C – Consistency** | **Valid State $\rightarrow$ Valid State** (preserves all constraints & sums). | **Application Code & Integrity Checker** |
| **I – Isolation** | **No Interference** between concurrent transactions. | **Concurrency Control Manager** (Locking / 2PL) |
| **D – Durability** | **Permanent Changes** once committed (survives crashes). | **Recovery Manager** (`REDO` using System Log) |

### Model Question 1 [5 Marks]:
> *"Explain the different states of a transaction with a neat state transition diagram. Also explain the role of the System Log."*

#### ✅ Model Exam Answer:

**1. Transaction States:**
*(Draw the 6-box State Transition Diagram from Part B here)*

During its execution, a transaction passes through the following states:
1. **Active State:** The initial state entered when the transaction starts (`BEGIN_TRANSACTION`). The transaction remains in this state while executing its `READ` and `WRITE` operations.
2. **Partially Committed State:** Entered right after the final statement of the transaction has been executed. At this point, changes may still reside in main memory buffers and must be flushed to the disk log before final commit.
3. **Failed State:** Entered from either the *Active* or *Partially Committed* state when the system discovers that normal execution can no longer proceed (due to hardware crash, logical error, or concurrency abort).
4. **Aborted State:** Entered after a failed transaction has been completely rolled back (`UNDO`) and the database has been restored to its state prior to the start of the transaction. The transaction may then be **restarted** or **killed**.
5. **Committed State:** Entered from the *Partially Committed* state once all updates and the `[commit, T]` record are permanently written to the System Log on disk.
6. **Terminated State:** Entered when the transaction leaves the system after committing or aborting.

**2. Role of the System Log:**
* The **System Log** is a sequential, append-only file stored on non-volatile disk that records all transaction operations affecting database items:
  * `[start_transaction, T]`
  * `[write_item, T, X, old_value, new_value]`
  * `[commit, T]` and `[abort, T]`
* In the event of a failure, the Recovery Manager uses `old_value` to **UNDO** uncommitted transactions (enforcing Atomicity) and `new_value` to **REDO** committed transactions (enforcing Durability).

### Quick 30-Second Recap of 5.2
* **Transaction States:** `Active` $\rightarrow$ `Partially Committed` $\rightarrow$ `Committed` $\rightarrow$ `Terminated` *(or on error: `Active / Partially Committed` $\rightarrow$ `Failed` $\rightarrow$ `Aborted` $\rightarrow$ `Terminated`)*.
* **System Log Records:** `[start_transaction, T]`, `[write_item, T, X, old_val, new_val]`, `[commit, T]`, `[abort, T]`.
  * `old_val` is used for **UNDO**; `new_val` is used for **REDO**.
* **ACID Properties:**
  * **A**tomicity = All or Nothing *(Recovery Manager - UNDO)*
  * **C**onsistency = Valid state to valid state *(App + Constraints)*
  * **I**solation = Concurrent transactions don't interfere *(Concurrency Control)*
  * **D**urability = Committed changes survive crashes *(Recovery Manager - REDO)*
