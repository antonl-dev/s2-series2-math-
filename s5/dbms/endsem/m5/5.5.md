## PART A: What is a Lock? Types of Locks in DBMS

To prevent the concurrency problems we saw in Module 5.1 (Lost Update, Dirty Read, Incorrect Summary) and ensure schedules are **Conflict Serializable**, commercial DBMSs use **Lock-Based Concurrency Control Protocols**.

* **Definition of a Lock:** A **Lock** is a system variable associated with a database item $X$ that describes the current status of item $X$ with respect to operations that can be applied to it.
* **Who Manages Locks?** A subsystem of the DBMS called the **Lock Manager** grants and releases locks using a **Lock Table**.

There are **two main types of locks** used in database systems:
1. **Binary Locks**
2. **Shared / Exclusive (or Read / Write) Locks**

---

### 1. Binary Locks
* **Definition:** A **Binary Lock** on a data item $X$ can have only **two states (values)**:
  1. **`LOCK(X) = 1` (Locked):** Item $X$ is currently locked by a transaction and **cannot** be accessed by any other transaction.
  2. **`LOCK(X) = 0` (Unlocked):** Item $X$ is free and can be locked when requested by a transaction.
* **Two Operations Used:**
  * **`lock_item(X)`:** If `LOCK(X) == 0`, sets `LOCK(X) = 1` and lets the transaction proceed. If `LOCK(X) == 1`, forces the requesting transaction to **wait** in a queue until `LOCK(X)` becomes `0`.
  * **`unlock_item(X)`:** Sets `LOCK(X) = 0` and wakes up the next waiting transaction.
* **Why Binary Locks Are Too Restrictive in Real Databases:**
  * Suppose Transaction $T_1$ and Transaction $T_2$ **both only want to READ item $X$** (neither wants to modify $X$).
  * Remember from Module 5.3 that **two `READ` operations NEVER conflict**!
  * Yet with a Binary Lock, once $T_1$ locks $X$ to read it, $T_2$ is **blocked from reading $X$** until $T_1$ unlocks it! This kills read concurrency.

---

### 2. Shared / Exclusive (or Read / Write) Locks *(Used in All Real DBMSs!)*

To allow multiple transactions to **read** the same item $X$ simultaneously while still giving exclusive protection when a transaction wants to **write** $X$, DBMSs use **Shared / Exclusive Locks** (also called **Multiple-Mode Locks**).

📸 **[Click here to view Shared vs Exclusive Lock Compatibility Matrix Diagrams on Google Images](https://www.google.com/search?q=shared+and+exclusive+locks+compatibility+matrix+in+dbms+diagram&udm=2)**

#### The 3 States of a Shared/Exclusive Lock on Item $X$:

1. **Read-Locked / Shared-Locked (`S-Lock`):**
   * Requested via **`read_lock(X)`** (or **`lock-S(X)`**) before reading $X$.
   * **Rule:** Because reading does not modify data, **MULTIPLE transactions are allowed to hold a Shared (`S`) lock on the same item $X$ at the exact same time!**
2. **Write-Locked / Exclusive-Locked (`X-Lock`):**
   * Requested via **`write_lock(X)`** (or **`lock-X(X)`**) before reading or writing $X$.
   * **Rule:** A Write lock is **strictly exclusive**—**ONLY ONE single transaction** can hold an Exclusive (`X`) lock on item $X$ at a time, and **no other transaction** is allowed to hold even a Shared (`S`) lock on $X$ at the same time!
3. **Unlocked:**
   * Released via **`unlock(X)`**.

---

#### Lock Compatibility Matrix *(Always Draw This 2×2 Table in Locking Questions!)*

Suppose Transaction $T_i$ already holds a lock on item $X$, and another Transaction $T_j$ requests a lock on $X$. Does the Lock Manager grant $T_j$'s request immediately, or force $T_j$ to wait?

| Lock Currently Held by $T_i$ on $X$ $\downarrow$ \ Lock Requested by $T_j$ $\rightarrow$ | **Shared Lock (`S` / `read_lock`)** | **Exclusive Lock (`X` / `write_lock`)** |
| :--- | :--- | :--- |
| **Shared Lock (`S` / `read_lock`)** | ✅ **YES (Compatible!)**<br>*(Multiple readers allowed together!)* | ❌ **NO (Conflict – $T_j$ Must Wait!)**<br>*(Cannot write while someone is reading)* |
| **Exclusive Lock (`X` / `write_lock`)** | ❌ **NO (Conflict – $T_j$ Must Wait!)**<br>*(Cannot read while someone is writing)* | ❌ **NO (Conflict – $T_j$ Must Wait!)**<br>*(Only 1 writer allowed at a time)* |

---

### 3. Lock Conversion (Upgrading and Downgrading Locks)
What if a transaction $T_1$ first reads item $X$ (using an `S-lock`) and then later decides it needs to update $X$ (needing an `X-lock`)?
Instead of unlocking $X$ and re-locking it, modern DBMSs allow **Lock Conversion**:

1. **Lock Upgrade (`S-lock` $\rightarrow$ `X-lock`):**
   * Converting a held Shared lock (`read_lock(X)`) into an Exclusive lock (`write_lock(X)`).
   * If $T_1$ is the **only** transaction currently holding a `read_lock` on $X$, the upgrade happens immediately; otherwise, $T_1$ waits until other readers unlock $X$.
2. **Lock Downgrade (`X-lock` $\rightarrow$ `S-lock`):**
   * Converting a held Exclusive lock (`write_lock(X)`) down into a Shared lock (`read_lock(X)`) once writing is finished.

## PART B: The Two-Phase Locking (2PL) Protocol

> ⚠️ **Important Question:** Does simply putting `read_lock(X)` before `read(X)` and `unlock(X)` right after `read(X)` guarantee a Serializable Schedule?
> **NO!** If Transaction $T_1$ unlocks item $X$ **too early** and then goes on to lock item $Y$ later, another transaction $T_2$ can jump in between, modify both $X$ and $Y$, and create a **non-serializable cycle**!

To **guarantee 100% Conflict Serializability**, transactions must obey a simple rule on *when* they are allowed to lock and unlock items. This rule is called the **Two-Phase Locking (2PL) Protocol**!

---

### 1. Definition of Two-Phase Locking (2PL)
* **Formal Rule:** A transaction is said to follow the **Two-Phase Locking (2PL) Protocol** if **all locking operations (`read_lock`, `write_lock`, and lock upgrades) precede the FIRST `unlock` operation** in the transaction!
* **In Simple Words:** **"Once a transaction unlocks even ONE single item, it is NEVER allowed to acquire any new locks again!"**

This divides the execution of every transaction into **two distinct phases**:

```text

      ^

      |                      * | *
      |                    *   |   *

      |        *   GROWING     |  SHRINKING    *
      |      *     PHASE       |  PHASE          *
      |    *   (Acquire Locks; | (Release Locks;   *
      |  *      NO Unlocks!)   |  NO New Locks!)     *
      +------------------------+-----------------------*---> Time
     Begin                  First                    End of
   Transaction              Unlock                 Transaction
```

---

### 2. Detailed Explanation of the Two Phases

#### Phase 1: Expanding (or Growing) Phase
* **What happens here:** The transaction can **acquire new locks** (`read_lock` or `write_lock`) on any data items it needs, and can **upgrade** existing locks (`S-lock` $\rightarrow$ `X-lock`).
* **Strict Restriction:** During the Growing Phase, the transaction **CANNOT release (unlock) or downgrade ANY lock**!
* **What is the "Lock Point"?**
  * The exact instant at the end of the Growing Phase when the transaction has acquired its **final lock** (just before its first unlock) is called the **Lock Point** of the transaction!
  * *(Fun Fact: If every transaction follows 2PL, the equivalent Serial Schedule order is simply the chronological order of their **Lock Points**!)*

#### Phase 2: Shrinking (or Contracting) Phase
* **What happens here:** The transaction **releases (`unlock`)** its held locks one by one (or all at once), and may **downgrade** existing locks (`X-lock` $\rightarrow$ `S-lock`).
* **Strict Restriction:** Once the Shrinking Phase starts (i.e., once the very first `unlock` is executed), the transaction **CANNOT acquire any new locks** and **CANNOT upgrade** any lock!

### 3. Main Theorem of 2PL
> **Theorem:** If **every transaction** in a schedule obeys the **Two-Phase Locking (2PL) protocol**, then the schedule is **guaranteed to be Conflict Serializable** (its Precedence Graph will never have a cycle)!

## PART C: Variations of Two-Phase Locking (Basic, Conservative, Strict & Rigorous 2PL)

> ⭐ **DIRECT SYLLABUS TOPIC:** *"Two-phase locking and its variations"*

While Basic 2PL guarantees Conflict Serializability, it still has two practical drawbacks:
1. Because Basic 2PL releases locks during the Shrinking Phase *before* the transaction commits, another transaction $T_2$ can read an uncommitted item unlocked by $T_1$, leading to **Dirty Reads and Cascading Rollbacks**!
2. Basic 2PL can suffer from **Deadlocks**!

To fix these issues, there are **4 standard variations of Two-Phase Locking**:

📸 **[Click here to view Variations of 2PL (Basic, Conservative, Strict, Rigorous) Diagrams on Google Images](https://www.google.com/search?q=strict+2PL+rigorous+2PL+conservative+2PL+in+dbms+diagram&udm=2)**

---

### 1. Basic 2PL
* **Rule:** The standard two-phase locking protocol described above: a transaction locks data items incrementally during the **Growing Phase**, and unlocks them incrementally during the **Shrinking Phase** (even *before* the transaction commits).
* **Properties:**
  * ✅ Guarantees **Conflict Serializability**.
  * ❌ **NOT Deadlock-free** (two transactions can wait on each other).
  * ❌ **NOT Cascadeless / NOT Strict** (since locks can be released before commit, dirty reads and cascading rollbacks can occur).

---

### 2. Conservative 2PL (or Static 2PL)
* **Rule:** Requires a transaction to **lock ALL the data items it will ever need BEFORE the transaction begins execution** (by predeclaring its entire *Read-Set* and *Write-Set* upfront)!
* **How it works:** Before starting, the transaction tries to acquire every lock it needs at once. If **even one** of the requested items is already locked by another transaction, the transaction **locks NOTHING** and waits until *all* its items are available for locking simultaneously!
* **Properties:**
  * ✅ Guarantees **Conflict Serializability**.
  * ✅ **100% DEADLOCK-FREE!** *(Because a transaction never holds some locks while waiting for others!)*
  * ❌ **Difficult to use in practice:** In real SQL applications, it is often impossible to know every single row a transaction will need to lock before the transaction even starts running!

---

### 3. Strict 2PL *(The Most Widely Used Protocol in Commercial DBMSs!)*
* **Rule:** A transaction obeys Basic 2PL, **PLUS one crucial extra rule**:
  > *"The transaction **does NOT release any of its Exclusive (`X` / Write) locks until AFTER it COMMITS or ABORTS**!"*
  *(Note: Shared `S` / Read locks CAN still be released early during the shrinking phase).*
* **Why is it called "Strict" 2PL?**
  * Because holding all Write (`X`) locks until after `COMMIT` or `ABORT` guarantees that no other transaction can ever read or overwrite an uncommitted item written by $T$!
  * Therefore, Strict 2PL guarantees **Strict Schedules** (Module 5.4)!
* **Properties:**
  * ✅ Guarantees **Conflict Serializability**.
  * ✅ Guarantees **Strict Schedules** (which are automatically **Recoverable** and **Cascadeless**—zero dirty reads!).
  * ❌ **NOT Deadlock-free**.

---

### 4. Rigorous 2PL *(Simplest to Implement!)*
* **Rule:** An even stricter version of Strict 2PL:
  > *"A transaction **does NOT release ANY of its locks—neither Exclusive (`X` / Write) locks NOR Shared (`S` / Read) locks—until AFTER it COMMITS or ABORTS**!"*
* **How the Graph of Rigorous 2PL Looks:**
  * The transaction stays in its **Growing Phase** for its entire execution until it hits `COMMIT` (or `ABORT`), and then releases **100% of its locks all at once**! (There is no gradual shrinking phase).

```text
  BASIC 2PL:            STRICT 2PL:                RIGOROUS 2PL:
  Locks  /\             Locks   /------\           Locks   /---------\
        /  \                   / (Drops \                 / (Holds    |
       /    \                 /   S-locks|               /   ALL locks|
      /      \               /    only;  |              /    until    |
     /        \             /  keeps X!) |             /     COMMIT!) |
    +----------+-->        +-------------+-->         +---------------+-->
                 Commit                    Commit                       Commit
```

* **Properties:**
  * ✅ Guarantees **Conflict Serializability**.
  * ✅ Guarantees **Strict Schedules** (Recoverable & Cascadeless).
  * ✅ **Easiest to implement:** The DBMS never needs to figure out when a transaction is "done" with a lock—it simply unlocks everything at `COMMIT`!
  * ❌ **NOT Deadlock-free**.

---

## PART D: Deadlock and Starvation in Locking (Brief Overview)

Because Basic, Strict, and Rigorous 2PL are **not deadlock-free**, two problems can arise when transactions wait for locks:

### 1. Deadlock
* **Definition:** A **Deadlock** occurs when each transaction $T$ in a set of two or more transactions is waiting for a lock on an item that is currently held by some other transaction $T'$ in the set! Neither can proceed, and both wait forever.
* **Classic Example:**
  * $T_1$ holds `write_lock(X)` and requests `write_lock(Y)` *(waits for $T_2$)*.
  * $T_2$ holds `write_lock(Y)` and requests `write_lock(X)` *(waits for $T_1$)*.
* **How DBMS Handles Deadlock:**
  1. **Deadlock Detection (Wait-For Graph):** The DBMS draws a directed graph with an edge $T_i \rightarrow T_j$ if $T_i$ is waiting for $T_j$ to unlock an item. **If the Wait-For Graph has a cycle, there is a Deadlock!** The DBMS chooses one transaction as a **victim**, aborts/rolls it back, and releases its locks.
  2. **Deadlock Prevention:** Using **Conservative 2PL**, **Timeouts**, or timestamp rules (**Wait-Die** and **Wound-Wait**).

### 2. Starvation (Livelock)
* **Definition:** **Starvation** occurs when a transaction cannot proceed for an indefinite period of time while other transactions in the system continue normally (e.g., because an unfair lock queue keeps granting locks to newer transactions, or the same transaction is repeatedly chosen as the deadlock victim).
* **Solution:** Use a fair **First-Come, First-Served (FCFS / FIFO)** lock queue and prioritize older transactions.

#### ✅ Model Exam Answer (Write this verbatim for 8 / 8 Marks):

**1. Locks and Shared vs. Exclusive Locks:**
* A **Lock** is a variable associated with a database item that controls concurrent access to that item.
* In a **Shared/Exclusive (Read/Write) locking scheme**, an item $X$ can be locked in two modes:
  1. **Shared Lock (`S-Lock` / `read_lock(X)`):** Acquired before reading $X$. Since reading does not modify data, **multiple transactions can hold a Shared lock on $X$ simultaneously**.
  2. **Exclusive Lock (`X-Lock` / `write_lock(X)`):** Acquired before writing $X$. **Only one transaction can hold an Exclusive lock on $X$ at any time**, and no other transaction can hold a Shared or Exclusive lock on $X$ simultaneously.

*(Draw the $2 \times 2$ Lock Compatibility Matrix from Part A here)*

**2. Two-Phase Locking (2PL) Protocol:**
* A transaction follows the **Two-Phase Locking (2PL) protocol** if **all locking operations (`read_lock`, `write_lock`, and lock upgrades) precede the first `unlock` operation** in the transaction.
* Every schedule in which all transactions obey 2PL is **guaranteed to be Conflict Serializable**.

*(Draw the Growing Phase & Shrinking Phase Graph from Part B here)*

The execution of a 2PL transaction is divided into two phases:
1. **Growing (Expanding) Phase:** The transaction can acquire new locks on items (and upgrade `S-locks` to `X-locks`), **but cannot release (unlock) any lock**. The end of this phase (when the final lock is acquired) is called the **Lock Point**.
2. **Shrinking (Contracting) Phase:** The transaction can release (`unlock`) its held locks (or downgrade `X-locks` to `S-locks`), **but cannot acquire any new locks**.

**3. Variations of Two-Phase Locking (2PL):**
1. **Basic 2PL:** Locks are acquired incrementally in the growing phase and released incrementally in the shrinking phase before commit. Guarantees conflict serializability, but suffers from deadlocks and cascading rollbacks.
2. **Conservative (Static) 2PL:** Requires a transaction to **predeclare and lock all items it needs before execution begins**. If any item is unavailable, it locks nothing and waits. It is **100% Deadlock-Free**.
3. **Strict 2PL:** In addition to Basic 2PL, a transaction **does not release any Exclusive (Write / `X`) locks until after it commits or aborts**. This guarantees **Strict (and Cascadeless) schedules**.
4. **Rigorous 2PL:** A transaction **does not release ANY locks (neither Shared `S` nor Exclusive `X` locks) until after it commits or aborts**. It guarantees Strict schedules and is the easiest to implement in commercial DBMSs.

### Quick 30-Second Recap of 5.5
* **Shared Lock (`S`):** For reading. Compatible with other `S` locks (`S + S = YES`).
* **Exclusive Lock (`X`):** For writing. Compatible with **nothing** (`X + S = NO`, `X + X = NO`).
* **2PL Rule:** All locks must happen **before** the first unlock:
  * **Growing Phase:** Acquire locks only (no unlocks). Ends at the **Lock Point**.
  * **Shrinking Phase:** Release locks only (no new locks).
* **4 Variations of 2PL:**
  1. **Basic 2PL:** Standard growing + shrinking phase.
  2. **Conservative 2PL:** Lock **everything before starting** $\rightarrow$ **Deadlock-Free!**
  3. **Strict 2PL:** Hold all **Write (`X`) locks** until after `COMMIT` $\rightarrow$ **Strict & Cascadeless!**
  4. **Rigorous 2PL:** Hold **ALL (`S` & `X`) locks** until after `COMMIT` $\rightarrow$ **Strict & Easiest!**
