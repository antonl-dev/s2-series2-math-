## PART A: Fundamentals of Log-Based Recovery & Write-Ahead Logging (WAL)

When a system crash (power failure or OS crash) occurs, the contents of **Main Memory (RAM)** are wiped out completely, while the **Hard Disk / SSD** survives.
To recover the database to a consistent state after a crash, the Recovery Manager relies on the **System Log** stored on non-volatile disk.

### 1. The Two Basic Recovery Operations: `UNDO` and `REDO`

Recall from Module 5.2 that a write log record has the format:
$$\texttt{[write\_item, } T, \; X, \; \texttt{old\_value}, \; \texttt{new\_value]}$$

Using this log record, the Recovery Manager can perform two opposite operations:
1. **`UNDO(T)` (Rollback an Uncommitted Transaction):**
   * Restores every database item $X$ updated by transaction $T$ back to its **`old_value`** *(Before-Image / BFIM)*.
   * Performed scanning **backward** through the log (from newest change to oldest change).
2. **`REDO(T)` (Roll-Forward a Committed Transaction):**
   * Sets every database item $X$ updated by transaction $T$ to its **`new_value`** *(After-Image / AFIM)*.
   * Performed scanning **forward** through the log (from oldest change to newest change).

---

### 2. The Write-Ahead Logging (WAL) Rule *(Crucial 2-Mark Concept!)*

For Log-Based Recovery to work, the DBMS must **always write the Log Record to disk BEFORE modifying the actual Database on disk**! This rule is called **Write-Ahead Logging (WAL)**:

1. **WAL Rule for `UNDO`:** Before a database item $X$ on disk is overwritten by an uncommitted transaction, the log record containing its **`old_value` MUST be flushed to the System Log on disk first** *(otherwise, if a crash happens mid-write, we wouldn't know what `old_value` to restore!)*.
2. **WAL Rule for `REDO`:** Before a transaction $T$ is allowed to enter the **Committed** state, all of its **`new_value` log records and `[commit, T]` MUST be flushed to the System Log on disk first** *(so its committed updates can be redone if power fails right after commit!)*.

---

### 3. Two Techniques of Log-Based Recovery
Depending on **WHEN** the DBMS writes modified data blocks from RAM to the physical Database on disk, there are **two standard Log-Based Recovery schemes**:
1. **Deferred Database Modification (`NO-UNDO / REDO` Algorithm)** — *Updates to disk are postponed until AFTER commit!*
2. **Immediate Database Modification (`UNDO / REDO` Algorithm)** — *Updates can be written to disk BEFORE commit!*

## PART B: Deferred Database Modification (`NO-UNDO / REDO`)

> ⭐ **DIRECTLY NAMED IN YOUR SYLLABUS (5.6):** *"Log-based recovery, Deferred Database Modification"*

### 1. Core Concept of Deferred Database Modification
* **What "Deferred" Means:** The word *deferred* means **postponed / delayed**.
* **Rule:** The Deferred Database Modification technique **postpones (defers) all physical updates to the actual Database on disk until AFTER the transaction reaches its Commit Point** and writes `[commit, T]` to the System Log!
* **What happens while Transaction $T$ is still Active (Uncommitted)?**
  * All `write_item(X)` operations performed by $T$ are recorded **ONLY in the System Log** (and kept in local RAM buffers).
  * **Zero changes are written to the actual Database on disk while $T$ is still running!**
* **Once Transaction $T$ reaches its Commit Point:**
  1. First, `[commit, T]` is force-written to the **System Log on disk**.
  2. Only **after** `[commit, T]` is safely on disk does the DBMS write the updated data blocks to the **actual Database on disk**!

📸 **[Click here to view Deferred Database Modification Log Recovery Diagrams on Google Images](https://www.google.com/search?q=deferred+database+modification+log+based+recovery+in+dbms+diagram&udm=2)**

```text
DEFERRED DATABASE MODIFICATION (Database Disk is NEVER touched before Commit!):

  While T1 is ACTIVE:     [ Trans T1 ] ---> Writes ONLY to System Log (<T1, X, new_val>)
                                       ---> Actual Database on Disk stays UNCHANGED!

  Once T1 COMMITS:        1. Write <T1, commit> to System Log on Disk.
                          2. Now flush X = new_val to Actual Database on Disk!
```

---

### 2. Why is Deferred Modification Called the "`NO-UNDO / REDO`" Algorithm?

Imagine the power suddenly fails and the system crashes! When the server reboots, what does the Recovery Manager have to do under **Deferred Database Modification**?

#### Case 1: Transaction $T$ had NOT Committed Before the Crash
*(Log has `[start_transaction, T]`, **but NO `[commit, T]`**)*
* **Recovery Action:** **DO NOTHING (`NO-UNDO`)!**
* **Why is `UNDO` never needed?!**
  * Because under Deferred Modification, an uncommitted transaction **never wrote anything to the actual Database on disk in the first place**! The database on disk still has the original untouched values!
  * *(In fact, because `UNDO` is never needed, log records in Deferred Modification don't even need to store `old_value`—they only store **`[write_item, T, X, new_value]`**!)*

#### Case 2: Transaction $T$ HAD Committed Before the Crash
*(Log has **BOTH `[start_transaction, T]` AND `[commit, T]`**)*
* **Recovery Action:** **Perform `REDO(T)`!**
* **Why is `REDO` needed?**
  * Even though $T$ wrote `[commit, T]` to the log, the power might have failed 1 millisecond later before the RAM buffer finished copying the new values to the Database disk!
  * Therefore, the Recovery Manager scans the log forward and sets every item $X$ updated by $T$ to its **`new_value`**.

---

### 3. Step-by-Step Worked Example of Deferred Database Modification

Suppose initially on disk: **$A = 1000$**, **$B = 2000$**, and **$C = 700$**.
* **Transaction $T_1$** transfers $100$ from $A$ to $B$ (so $A$ becomes $900$, $B$ becomes $2100$).
* **Transaction $T_2$** subtracts $100$ from $C$ (so $C$ becomes $600$).

Look at the **System Log** at the exact moment a **System Crash** occurs:

```text
SYSTEM LOG ON DISK AT THE TIME OF CRASH:
+----------------------------------------+
| [start_transaction, T1]                |
| [write_item, T1, A, 900]               |  <-- Notice: Only new_value stored!
| [write_item, T1, B, 2100]              |
| [commit, T1]                           |  <-- T1 COMMITTED before crash!
| [start_transaction, T2]                |
| [write_item, T2, C, 600]               |
+----------------------------------------+  <=== 💥 SYSTEM CRASH HAPPENS HERE!
                                                 (Notice: NO [commit, T2] in log!)
```

#### What Does the Recovery Manager Do Upon Reboot?
1. **Check $T_1$:** Since the log contains **both** `[start_transaction, T1]` and **`[commit, T1]`**, we perform **`REDO(T1)`**:
   * Set **$A = 900$** and **$B = 2100$** on disk!
2. **Check $T_2$:** Since the log contains `[start_transaction, T2]` **without** `[commit, T2]`, **$T_2$ is ignored completely (`NO-UNDO`)**!
   * Item **$C$ remains at its original disk value $700$**!

## PART C: Immediate Database Modification (`UNDO / REDO`)

To give a complete answer in exams, you should also know the contrast scheme: **Immediate Database Modification**.

* **Core Rule:** Under **Immediate Database Modification**, the database on disk **CAN be updated immediately by an active transaction EVEN BEFORE the transaction reaches its commit point**—provided that the log record `[write_item, T, X, old_value, new_value]` is written to the System Log on disk first (Write-Ahead Logging).
* **Why is it called the "`UNDO / REDO`" Algorithm?**
  Because an uncommitted transaction might have *already* written dirty values to the database disk before crashing! Therefore, after a crash:
  1. **If $T$ has `[start_transaction, T]` with NO `[commit, T]`:** We **MUST perform `UNDO(T)`** (restore `old_value` scanning backward)!
  2. **If $T$ has BOTH `[start_transaction, T]` AND `[commit, T]`:** We **perform `REDO(T)`** (apply `new_value` scanning forward)!

---

### Side-by-Side Comparison: Deferred vs. Immediate Database Modification

*(Memorize this table—it is a classic 4-mark exam comparison!)*

| Feature | Deferred Database Modification | Immediate Database Modification |
| :--- | :--- | :--- |
| **1. When is Database Disk Updated?** | **Only AFTER** the transaction reaches its **Commit** point. | **Immediately** during execution (even **BEFORE** the transaction commits). |
| **2. Algorithm Name** | **`NO-UNDO / REDO` Algorithm** | **`UNDO / REDO` Algorithm** |
| **3. Log Record Format** | Needs only **`new_value`**: `<T, X, new_value>` | Needs **BOTH `old_value` and `new_value`**: `<T, X, old_val, new_val>` |
| **4. If Uncommitted $T$ Crashes** | **Do Nothing (`NO-UNDO`)** *(disk was never touched!)*. | **Perform `UNDO(T)`** *(restore `old_value` on disk)*. |
| **5. If Committed $T$ Crashes** | **Perform `REDO(T)`** *(write `new_value` to disk)*. | **Perform `REDO(T)`** *(write `new_value` to disk)*. |
| **6. Buffer Space Issue** | Requires large RAM buffers if a transaction modifies many items before committing. | Can flush dirty RAM buffers to disk at any time (after logging). |

## PART D: Checkpoints (Checkpointing in Log-Based Recovery)

> ⭐ **DIRECTLY NAMED IN YOUR SYLLABUS (5.6):** *"Checkpoints"*

### 1. Why Do We Need Checkpoints? (The Problem With Scanning the Entire Log!)
Think about what happens if a bank's database server runs continuously for **30 days** (executing 10 million transactions) and then suddenly crashes on Day 30:
* Without Checkpoints, the Recovery Manager would have to go all the way back to **Day 1** of the System Log and **`REDO` all 10 million committed transactions**—even though 9,999,900 of those transactions already had their changes safely written to the hard disk weeks ago!
* Recovery would take **several hours** of downtime!

To make crash recovery take **seconds instead of hours**, the DBMS periodically performs a **Checkpoint**!

---

### 2. What is a Checkpoint? (And the 4 Exact Steps of Taking a Checkpoint!)

* **Definition:** A **Checkpoint** is a periodic synchronization operation in which the DBMS writes all modified main-memory buffers out to the physical database disk and records a special **`[checkpoint]`** marker in the System Log.
* **Why is a Checkpoint so powerful?** Because the `[checkpoint]` record in the log is a **100% guarantee** that **every single transaction that committed BEFORE the `[checkpoint]` already has all of its updates permanently saved on the database disk**!

#### The 4 Steps Performed by the DBMS During a Checkpoint:
*(Always write these 4 numbered steps when an exam asks "Explain Checkpointing"!)*

1. **Step 1:** Temporarily **suspend** the execution of active transactions briefly.
2. **Step 2:** **Force-write (flush) all modified database buffers** from main memory (RAM) out to the physical database disk.
3. **Step 3:** Write a **`[checkpoint, L]`** record into the System Log (where $L$ is the list of transactions currently active at the time of the checkpoint) and force-write the log to disk.
4. **Step 4:** **Resume** executing transactions normally.

---

Look at the 4 transactions ($T_1, T_2, T_3, T_4$) in the timeline above when the crash happens:

| Transaction | When Did It Start & Finish? | What Does the Recovery Manager Do After the Crash? |
| :--- | :--- | :--- |
| **1. Transaction $T_1$** | Committed **BEFORE** the `[checkpoint]`. | ✅ **DO NOTHING (Ignore $T_1$ completely)!**<br>*(Why? Because Step 2 of the Checkpoint already forced all of $T_1$'s updates to the physical disk! No `REDO` needed!)* |
| **2. Transaction $T_2$** | Started before (or after) the Checkpoint, and **Committed AFTER the `[checkpoint]`** (before the Crash). | 🔄 **Perform `REDO(T2)`!**<br>*(Why? Because $T_2$ committed after the checkpoint, so its updates might still have been in RAM when the crash happened!)* |
| **3. Transaction $T_3$** | Started before the Checkpoint, and was **still active (uncommitted)** at the time of the Crash. | ⏪ **Perform `UNDO(T3)`!** *(under Immediate Modification)*<br>*(Or ignore `NO-UNDO` under Deferred Modification).* |
| **4. Transaction $T_4$** | Started after the Checkpoint, and was **still active (uncommitted)** at the time of the Crash. | ⏪ **Perform `UNDO(T4)`!** *(under Immediate Modification)*<br>*(Or ignore `NO-UNDO` under Deferred Modification).* |

### Summary of Advantages of Checkpointing:
1. **Drastically Reduces Recovery Time:** Eliminates the need to `REDO` thousands of old transactions that committed before the last checkpoint.
2. **Allows Log Truncation:** Once a checkpoint completes and old transactions finish, old log records before the checkpoint can be archived or deleted to free disk space.
3. **Guarantees Bounded Dirty Pages:** Ensures modified RAM buffers are flushed to disk at regular intervals (e.g., every 5 minutes or every $N$ log records).

## PART E: Model Exam Questions & Full Word-for-Word Answers for 5.6

### Model Question 1 [8 Marks]:
> *"Explain Log-based recovery and the Deferred Database Modification technique with a suitable example. What is the purpose of Checkpoints in recovery?"*

#### ✅ Model Exam Answer (Write this verbatim for 8 / 8 Marks):

**1. Log-Based Recovery:**
* In Log-Based Recovery, the DBMS maintains a sequential **System Log** on stable disk storage that records every transaction operation affecting database items (`[start_transaction, T]`, `[write_item, T, X, old_value, new_value]`, `[commit, T]`, `[abort, T]`).
* It follows the **Write-Ahead Logging (WAL)** protocol, which ensures that log records are always written to disk *before* the corresponding database items are modified on disk.

**2. Deferred Database Modification (`NO-UNDO / REDO` Technique):**
* **Concept:** The Deferred Database Modification technique **postpones (defers) all physical updates to the actual database on disk until AFTER the transaction reaches its Commit Point** and writes `[commit, T]` to the System Log.
* While a transaction $T$ is still active (uncommitted), all of its `write_item` operations are recorded **only in the System Log** (and local RAM buffers); the physical database on disk is never modified before commit.
* **Recovery Procedure After a Crash (`NO-UNDO / REDO`):**
  1. **Uncommitted Transactions (`[start_transaction, T]` in log, but NO `[commit, T]`):**
     * **Action: `NO-UNDO` (Do Nothing)!** Since updates were deferred until commit, an uncommitted transaction never modified the database on disk. Thus, no `UNDO` operation is ever required.
  2. **Committed Transactions (`BOTH [start_transaction, T]` AND `[commit, T]` in log):**
     * **Action: `REDO(T)`!** The Recovery Manager scans the log forward and sets every item $X$ updated by $T$ to its **`new_value`**.

* **Example:**
  Suppose initially $A = 1000$ and $C = 700$. Transaction $T_1$ updates $A = 900$ and **commits**, while Transaction $T_2$ updates $C = 600$ and **crashes before committing**:
  * Log before crash: `[start, T1], [write, T1, A, 900], [commit, T1], [start, T2], [write, T2, C, 600] <--- CRASH!`
  * Upon recovery: **$T_1$ is redone (`REDO(T1)` sets $A = 900$)** because `[commit, T1]` is present in the log, whereas **$T_2$ is ignored (`NO-UNDO`)** and $C$ remains $700$ on disk.

**3. Purpose and Working of Checkpoints:**
* **Purpose:** Without checkpoints, crash recovery would have to scan the entire System Log from the very beginning and unnecessarily `REDO` thousands of transactions whose changes were already written to disk long ago. **Checkpoints drastically reduce recovery time.**
* **Steps in a Checkpoint:**
  1. Suspend execution of active transactions briefly.
  2. Force-write (flush) all modified main-memory buffers to the physical database disk.
  3. Write a **`[checkpoint]`** record to the System Log on disk.
  4. Resume transaction execution.
* **Effect on Recovery:**
  *(Draw the $T_1, T_2, T_3, T_4$ Checkpoint Timeline Diagram from Part D here)*
  * Any transaction **$T_1$ that committed BEFORE the `[checkpoint]` requires NO `REDO`**, because its updates were guaranteed to be flushed to disk during the checkpoint!
  * Only transactions like **$T_2$ that committed AFTER the `[checkpoint]`** need to be **redone (`REDO`)**, and transactions active at the time of the crash ($T_3, T_4$) are rolled back (`UNDO`).

* **Deferred Database Modification (`NO-UNDO / REDO`):**
  * Delays writing to the database disk until **after `COMMIT`**.
  * If $T$ committed before crash $\rightarrow$ **`REDO(T)`**.
  * If $T$ did NOT commit before crash $\rightarrow$ **Do Nothing (`NO-UNDO`)** (disk was never touched!).
* **Immediate Database Modification (`UNDO / REDO`):**
  * Writes to database disk **even before `COMMIT`** (after writing to log).
  * If $T$ committed $\rightarrow$ **`REDO(T)`**. If $T$ did NOT commit $\rightarrow$ **`UNDO(T)`**.
* **Checkpoint:** Flushes all dirty RAM buffers to disk and writes `[checkpoint]` to the log.
  * Committed **before** Checkpoint ($T_1$) $\rightarrow$ **Ignore!**
  * Committed **after** Checkpoint ($T_2$) $\rightarrow$ **`REDO`!**
  * Still active at Crash ($T_3, T_4$) $\rightarrow$ **`UNDO`!**
