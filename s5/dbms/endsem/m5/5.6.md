## PART A: Fundamentals of Log-Based Recovery

When a system crash (like a power failure) occurs, the contents of **Main Memory (RAM) buffers are completely wiped out**, while the **System Log** on non-volatile disk survives.
**Log-Based Recovery** is the technique where the Recovery Manager reads the System Log after a crash to restore the database to a consistent state.

### 1. The Two Fundamental Recovery Operations: `UNDO` and `REDO`

1. **`UNDO(T)` (Rollback an Uncommitted Transaction):**
   * **Used for:** Any transaction $T$ that started before the crash (`[start_transaction, T]` is in the log) **but DID NOT commit** (`[commit, T]` is **NOT** in the log).
   * **What it does:** Scans the System Log **backward** (from newest to oldest) and restores every item $X$ modified by $T$ back to its **`old_value` (Before-Image / BFIM)**.
   * **Which ACID property it enforces:** **Atomicity** ("All or Nothing").

2. **`REDO(T)` (Roll-Forward a Committed Transaction):**
   * **Used for:** Any transaction $T$ that **DID commit** before the crash (**both** `[start_transaction, T]` **AND** `[commit, T]` are present in the log), because its updated RAM buffers might not have been flushed to the database disk before the power went out.
   * **What it does:** Scans the System Log **forward** (from oldest to newest) and sets every item $X$ modified by $T$ to its **`new_value` (After-Image / AFIM)**.
   * **Which ACID property it enforces:** **Durability** (Permanent changes).

---

### 2. The Write-Ahead Logging (WAL) Rule *(Crucial 2-Mark Concept!)*
For Log-Based Recovery to work, the DBMS must obey one golden rule called **Write-Ahead Logging (WAL)**:
1. **Before** a database item $X$ on disk can be overwritten by an uncommitted transaction, the log record **`[write_item, T, X, old_value, new_value]` MUST be written to the System Log on disk FIRST!** *(Why? Because if the system crashes right after overwriting $X$ on disk, we need `old_value` in the disk log to `UNDO` it!)*
2. **Before** a transaction $T$ is allowed to enter the **Committed** state, all of its log records (including `[commit, T]`) **MUST be flushed to the System Log on disk FIRST!**

## PART B: Deferred Database Modification (`NO-UNDO / REDO` Algorithm)

> ⭐ **EXPLICITLY NAMED IN YOUR SYLLABUS (`5.6`):** *"Log-based recovery, Deferred Database Modification..."*

Depending on *when* the DBMS writes a transaction's updates to the actual database on disk, there are two log-based recovery techniques:
1. **Deferred Database Modification** *(Postpones disk updates until AFTER Commit)*
2. **Immediate Database Modification** *(Writes disk updates IMMEDIATELY, even before Commit)*

📸 **[Click here to view Deferred vs Immediate Database Modification Diagrams on Google Images](https://www.google.com/search?q=deferred+database+modification+vs+immediate+database+modification+in+dbms+diagram&udm=2)**

---

### 1. How Deferred Database Modification Works
* **What does "Deferred" mean?** It means **"Postponed / Delayed until Commit"**!
* **Core Rule:**
  1. While a transaction $T$ is in the **Active** state, it **NEVER writes any changes to the physical database on disk**!
  2. Instead, whenever $T$ executes `write_item(X)`, it **defers (postpones)** updating the database on disk and only records the update inside the **System Log** (and local RAM workspace).
  3. Only **AFTER** transaction $T$ reaches its commit point and **`[commit, T]` is safely written to the System Log on disk** does the DBMS actually write the new values to the physical database on disk!

```text
DEFERRED DATABASE MODIFICATION (Database Disk is NOT touched until AFTER Commit!):

  While T is ACTIVE:       [ Transaction T ] ===> Writes ONLY to [ System Log ] ( & local RAM )
                                                  (Physical Database on Disk is UNTOUCHED!)

  After [commit, T] in Log: [ System Log / RAM ] ===> Now updates [ Physical Database on Disk ]!
```

---

### 2. Why is Deferred Modification Called the `NO-UNDO / REDO` Algorithm?
*(Always write this exact heading in your exam—evaluators love seeing the term **`NO-UNDO / REDO`**!)*

1. **Why `NO-UNDO` is Ever Needed (Zero Rollbacks on Disk!):**
   * Suppose Transaction $T_2$ is halfway through its execution and the system suddenly crashes **before** $T_2$ commits.
   * Because updates are **deferred until commit**, $T_2$ **never modified a single byte of the physical database on disk**!
   * Since the database on disk still has the original clean values, **NO `UNDO` operation is ever required** for uncommitted/failed transactions!
   * *(In fact, in pure Deferred Modification, log records don't even need to store `old_value`—they only need to store **`[write_item, T, X, new_value]`**!)*

2. **Why `REDO` IS Needed:**
   * Suppose Transaction $T_1$ finished and wrote **`[commit, T1]`** to the System Log on disk, and then the power failed **while** its deferred updates were being copied to the physical database on disk.
   * When the system reboots, the Recovery Manager sees both **`[start_transaction, T1]`** and **`[commit, T1]`** in the log, so it executes **`REDO(T1)`** (setting $X$ to `new_value`) to ensure $T_1$'s committed changes are saved on disk!

---

### 3. Worked Example of Crash Recovery Using Deferred Database Modification

Suppose Transaction $T_1$ transfers ₹1,000 from $A$ (initial $5000$) to $B$ (initial $2000$), and Transaction $T_2$ withdraws ₹500 from $C$ (initial $3000$).
Look at the **System Log** at the exact moment a **System Crash** happens:

```text
SYSTEM LOG ON DISK AT THE MOMENT OF CRASH:
+------------------------------------------+
| [start_transaction, T1]                  |
| [write_item, T1, A, 4000]                |
| [write_item, T1, B, 3000]                |
| [commit, T1]                             |  <-- T1 COMMITTED before crash!
| [start_transaction, T2]                  |
| [write_item, T2, C, 2500]                |
+------------------------------------------+
                  ⚡ <--- SYSTEM CRASH HAPPENS HERE! (Before [commit, T2]!)
```

#### What Does the Recovery Manager Do When the System Reboots?
1. **For Transaction $T_1$:**
   * The log contains **both `[start_transaction, T1]` AND `[commit, T1]`**.
   * **Action:** Execute **`REDO(T1)`**! Set $A = 4000$ and $B = 3000$ on the database disk.
2. **For Transaction $T_2$:**
   * The log contains `[start_transaction, T2]`, **but NO `[commit, T2]`**.
   * **Action:** **Do NOTHING (`NO-UNDO`)!** Ignore $T_2$'s log records completely because $T_2$'s change ($C = 2500$) was never written to the database disk ($C$ is still $3000$ on disk!).

## PART C: Immediate Database Modification (`UNDO / REDO` Algorithm) & Comparison

### 1. How Immediate Database Modification Works
* **Core Rule:** Under **Immediate Database Modification**, the database on disk can be updated by `write_item(X)` operations of a transaction **IMMEDIATELY** during its **Active** state—**even BEFORE the transaction reaches its commit point**!
* **Mandatory Condition (Write-Ahead Logging):** Before any uncommitted change is written to the database disk, the log record **`[write_item, T, X, old_value, new_value]`** (containing both `old_value` and `new_value`) **must be written to the System Log on disk first**.

### 2. Why It is Called the `UNDO / REDO` Algorithm:
When a crash occurs:
1. **If Transaction $T_2$ has `[start_transaction, T2]` with NO `[commit, T2]`:**
   * Because $T_2$'s uncommitted update ($C = 2500$) might have **already been written to the database disk**, the Recovery Manager **MUST execute `UNDO(T2)`** (restoring $C$ back to its `old_value = 3000`)!
2. **If Transaction $T_1$ has BOTH `[start_transaction, T1]` AND `[commit, T1]`:**
   * The Recovery Manager executes **`REDO(T1)`** (setting $A = 4000, B = 3000$ using `new_value`).

---

### Side-by-Side Comparison: Deferred vs. Immediate Database Modification

*(Memorize this table—it gets you full marks on any Log-Based Recovery question!)*

| Feature | Deferred Database Modification | Immediate Database Modification |
| :--- | :--- | :--- |
| **1. When is the Physical Database Updated?** | **Deferred (Postponed)** until **AFTER** the transaction commits (`[commit, T]`). | **Immediately** while the transaction is still Active (even **BEFORE** commit). |
| **2. Algorithm Name** | **`NO-UNDO / REDO` Algorithm** | **`UNDO / REDO` Algorithm** |
| **3. Action for Uncommitted Transactions on Crash** | **No `UNDO` needed!** (Simply ignore them since disk was never touched). | **Must perform `UNDO(T)`** (restore `old_value` since disk may have dirty writes). |
| **4. Action for Committed Transactions on Crash** | **Perform `REDO(T)`** (apply `new_value` in forward order). | **Perform `REDO(T)`** (apply `new_value` in forward order). |
| **5. What Must Be Stored in `write_item` Log Record?** | Only **`new_value` (After-Image)** is strictly required (`[write_item, T, X, new_val]`). | **BOTH `old_value` AND `new_value`** are required (`[write_item, T, X, old_val, new_val]`). |

## PART D: Checkpoints (Checkpointing in Log-Based Recovery)

> ⭐ **EXPLICITLY NAMED IN YOUR SYLLABUS (`5.6`):** *"...Checkpoints"*

### 1. Why Do We Need Checkpoints?
Suppose a bank database server has been running continuously for 12 hours, and 50,000 transactions have already committed since morning.
If a power failure occurs at 9:00 PM and we do **not** use checkpoints:
* The Recovery Manager has to scan the **entire System Log all the way back to 9:00 AM**!
* It would waste hours running `REDO(T)` on all 50,000 committed transactions—even though 49,990 of those transactions had already flushed their changes from RAM to the hard disk hours ago!

To avoid scanning the entire log from the beginning and avoid redoing transactions whose updates are already safely on disk, the DBMS periodically performs a **Checkpoint**!

---

### 2. What is a Checkpoint & The 4 Steps of Taking a Checkpoint

* **Definition:** A **Checkpoint** is a synchronization point between the database on disk and the System Log, where all committed updates currently sitting in main-memory (RAM) buffers are forcibly flushed out to the physical database on disk.

#### The 4 Exact Steps Performed by the DBMS During a Checkpoint:
*(Memorize these 4 numbered steps for the exam!)*

1. **Step 1:** **Suspend** the execution of transactions temporarily.
2. **Step 2:** **Force-write (flush) all modified main-memory database buffers** out to the physical database on disk.
3. **Step 3:** **Write a `[checkpoint]` record** (along with a list of all currently active transaction IDs) into the System Log and flush the log to disk.
4. **Step 4:** **Resume** normal execution of transactions.

---

### 3. How a Checkpoint Speeds Up Crash Recovery (The 4 Transaction Cases!)

📸 **[Click here to view Checkpoint in DBMS Recovery Timeline (T1, T2, T3, T4) Diagram on Google Images](https://www.google.com/search?q=checkpoint+in+dbms+recovery+T1+T2+T3+T4+diagram&udm=2)**

### Diagram to Draw in Exam: Recovery Using a Checkpoint ($T_1, T_2, T_3, T_4$)
*(Draw this timeline diagram in any Checkpoint question—it makes the explanation 100% visual and effortless!)*

```text
                     [CHECKPOINT]                         ⚡ SYSTEM CRASH!
                          |                                      |
  Time -------------------+--------------------------------------+--->
                          |                                      |
  T1:  [------ T1 ------] |                                      |   --> Case 1: Committed BEFORE Checkpoint
                     Commit                                      |       (Already on disk! DO NOTHING!)
                          |                                      |
  T2:        [----------- | ------------ T2 -----------]         |   --> Case 2: Committed AFTER Checkpoint
                          |                         Commit       |       (Must REDO(T2)!)
                          |                                      |
  T3:              [----- | -------------------- T3 -------------|   --> Case 3: Active at Crash (Not Committed)
                          |                                      |       (Must UNDO(T3)! [or ignore in Deferred])
                          |                                      |
  T4:                     |       [------ T4 ------]             |   --> Case 4: Started & Committed AFTER Ckpt
                          |                    Commit            |       (Must REDO(T4)!)
```

When a crash occurs, the Recovery Manager finds the **most recent `[checkpoint]` record** in the log and classifies transactions into **4 cases**:

1. **Case 1 – Transaction $T_1$ (Committed BEFORE the Checkpoint):**
   * Because $T_1$ committed *before* the checkpoint, Step 2 of the checkpoint **already forced all of $T_1$'s updates out to the physical hard disk**!
   * ✅ **Action:** **Do NOTHING!** ($T_1$ does **not** need to be redone! This saves massive recovery time).
2. **Case 2 – Transaction $T_2$ (Started before Checkpoint, Committed AFTER the Checkpoint before Crash):**
   * Since $T_2$ committed *after* the checkpoint, its updates might still have been in RAM when the crash occurred.
   * ✅ **Action:** **Perform `REDO(T2)`!**
3. **Case 3 – Transaction $T_3$ (Still Active at the Time of Crash – Did NOT Commit):**
   * $T_3$ never reached its commit point before the crash.
   * ✅ **Action:** **Perform `UNDO(T3)`** *(under Immediate Modification)*, or **Do Nothing (`NO-UNDO`)** *(under Deferred Modification)*!
4. **Case 4 – Transaction $T_4$ (Started AND Committed AFTER the Checkpoint before Crash):**
   * Just like $T_2$, $T_4$ committed *after* the checkpoint, so its changes might not have reached the database disk yet.
   * ✅ **Action:** **Perform `REDO(T4)`!**

## PART E: Model Exam Questions & Full Word-for-Word Answers for 5.6

### Model Question 1 [8 Marks]:
> *"Explain Log-based recovery and the Deferred Database Modification technique. Also explain what a Checkpoint is and how it helps during recovery."*

#### ✅ Model Exam Answer (Write this verbatim for 8 / 8 Marks):

**1. Log-Based Recovery & Write-Ahead Logging:**
* **Log-Based Recovery** maintains a sequential **System Log** on stable disk storage that records every transaction operation (`[start_transaction, T]`, `[write_item, T, X, old_value, new_value]`, `[commit, T]`, `[abort, T]`).
* Following the **Write-Ahead Logging (WAL)** protocol, log records must be flushed to stable disk *before* the corresponding database items are modified on disk or the transaction commits.
* During recovery, the DBMS uses two operations:
  * **`UNDO(T)`:** Restores items modified by uncommitted transactions back to `old_value`.
  * **`REDO(T)`:** Sets items modified by committed transactions to `new_value`.

**2. Deferred Database Modification (`NO-UNDO / REDO` Technique):**
* Under the **Deferred Database Modification** technique, all physical database modifications are **deferred (postponed)** until after the transaction reaches its **Commit** point:
  1. During execution (**Active** state), a transaction records all `write_item` updates **only in the System Log** (and local memory buffers) without modifying the physical database on disk.
  2. Only after **`[commit, T]`** is written to the System Log on disk are the updates written out to the database on disk.
* **Recovery Procedure (`NO-UNDO / REDO`):**
  * **`NO-UNDO` for Uncommitted Transactions:** If a transaction fails or crashes before `[commit, T]` is written to the log, it has never modified the physical database on disk. Hence, **no `UNDO` operation is ever needed**; its log entries are simply ignored.
  * **`REDO` for Committed Transactions:** If a transaction has both `[start_transaction, T]` and `[commit, T]` in the log before the crash, the Recovery Manager performs **`REDO(T)`** by setting all items it updated to their `new_value`.

**3. Checkpoints and Their Role in Recovery:**
* Without checkpoints, the Recovery Manager must scan the entire System Log from the very beginning after a crash and redo every committed transaction, which is very slow.
* A **Checkpoint** is a periodic operation in which the DBMS:
  1. Temporarily suspends transaction execution,
  2. Force-writes (flushes) all modified main-memory buffers to the physical database disk,
  3. Writes a **`[checkpoint]`** record to the System Log on disk, and
  4. Resumes transaction execution.

*(Draw the $T_1, T_2, T_3, T_4$ Checkpoint Timeline Diagram from Part D here)*

* **How Checkpoints Speed Up Recovery:**
  * Any transaction (like **$T_1$**) that committed **before** the `[checkpoint]` record already has its changes safely written to disk during the checkpoint, so it **does not need to be redone**.
  * Transactions (like **$T_2$ and $T_4$**) that committed **after** the `[checkpoint]` record before the crash are **REDONE (`REDO`)**.
  * Transactions (like **$T_3$**) that did **not commit** before the crash are **UNDONE (`UNDO`)** (or ignored in Deferred Modification).

---

### Quick 30-Second Recap of 5.6
* **Deferred Database Modification (`NO-UNDO / REDO`):**
  * Postpones all disk writes until **AFTER `[commit, T]`**.
  * If $T$ crashed before commit $\rightarrow$ **Do Nothing (`NO-UNDO`)**!
  * If $T$ committed before crash $\rightarrow$ **`REDO(T)`**!
* **Immediate Database Modification (`UNDO / REDO`):**
  * Writes to disk **before commit** (after writing WAL log record).
  * If $T$ crashed before commit $\rightarrow$ **`UNDO(T)`** (restore `old_value`)!
  * If $T$ committed before crash $\rightarrow$ **`REDO(T)`** (apply `new_value`)!
* **Checkpoint:** Flushes all RAM buffers to disk and writes `[checkpoint]` to the log.
  * Committed **before** checkpoint ($T_1$) $\rightarrow$ **Ignore (already on disk!)**.
  * Committed **after** checkpoint ($T_2, T_4$) $\rightarrow$ **`REDO`**.
  * Not committed at crash ($T_3$) $\rightarrow$ **`UNDO`** (or ignore in Deferred).
