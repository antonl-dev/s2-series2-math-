# 1.1 Introduction to Operating Systems: Virtualizing the CPU & Virtualizing the Memory

---

## 1. What is an Operating System (OS)?

An **Operating System (OS)** is a layer of system software that sits between the computer hardware and the user/application programs. Its primary job is to make the computer system **easy to use**, **safe**, and **efficient** by managing all hardware resources and providing clean abstractions to running programs.

[Click here to see the diagram for Operating System layered view between hardware and users](https://www.google.com/search?q=operating+system+abstract+view+hardware+kernel+user+applications+diagram&udm=2)

### What Happens When a Program Runs?
At the hardware level, a running program follows a simple **Fetch–Decode–Execute cycle**:
1. **Fetch:** The CPU fetches an instruction from memory (using the Program Counter).
2. **Decode:** The CPU decodes the instruction to understand what operation to perform.
3. **Execute:** The CPU executes the operation (e.g., adding two numbers, reading memory, jumping to another instruction) and moves to the next instruction.

However, modern computers run dozens or hundreds of programs simultaneously, all needing the CPU, RAM, disk, keyboard, and display. Without an OS, programs would overwrite each other's memory, hog the CPU forever, and have to write complex hardware-specific code just to print a character or save a file.

### Dual Role of an Operating System
From a system perspective, the OS serves two main roles:
1. **Resource Manager (Virtualizer):** It takes physical resources (CPU, Memory, Disk) and transforms them into more general, powerful, and easy-to-use **virtual** forms. It decides *who* gets *which* resource, *when*, and *for how long*, ensuring fairness, efficiency, and isolation.
2. **Control Program & Standard Library (Provider of Interfaces):** It prevents errors and improper use of the computer (e.g., stopping one program from crashing another) and provides **system calls** (APIs) so programs can request services like creating processes, allocating memory, or reading files.

### The "Three Easy Pieces" of an Operating System
Modern OS design revolves around three core themes (covered across Modules 1–5):
1. **Virtualization:** Creating the illusion that each program has its own dedicated CPU and its own dedicated private memory.
2. **Concurrency:** Handling multiple tasks or threads executing simultaneously and sharing data safely without corruption.
3. **Persistence:** Storing data reliably on non-volatile storage (HDDs/SSDs) so it survives power loss and crashes.

## 2. Virtualizing the CPU

### The Problem
A computer typically has only a limited number of physical CPUs (or cores)—for example, 1, 4, or 8 cores. Yet a user may simultaneously run a web browser, a music player, a code editor, a compiler, and dozens of background services.

### The Core Idea: Virtualization via Time-Sharing
**CPU Virtualization** is the technique by which the OS creates the **illusion of an infinite (or very large) number of CPUs**, making every running program believe it has its own dedicated processor.

The OS achieves this illusion through **time-sharing**:
- Run Process A for a short period of time (a **time slice** or **quantum**, typically a few milliseconds).
- Stop Process A and save its exact state.
- Run Process B for a short period of time.
- Stop Process B, save its state, and switch to Process C (or back to A).

Because the CPU executes billions of instructions per second and switches between processes hundreds of times per second, human users perceive all programs as running **simultaneously** (in parallel), even on a single-core CPU.

> **Trade-off of Time-Sharing:**
> Time-sharing improves interactivity and responsiveness, but comes at a slight cost to **performance**:
> 1. Each individual program runs slower than if it owned the CPU exclusively.
> 2. Switching between programs incurs overhead (CPU cycles spent switching instead of doing useful program work).

[Click here to see the diagram for CPU virtualization and time sharing between processes](https://www.google.com/search?q=CPU+virtualization+time+sharing+processes+OS+diagram&udm=2)

### Mechanisms vs. Policies in CPU Virtualization
To virtualize the CPU cleanly, the OS separates **how** to do something from **which** decision to make:
- **Mechanisms (The "How"):** Low-level methods or protocols that implement a needed piece of functionality.
  - *Example:* **Context switching** (saving and restoring registers) and **timer interrupts** (regaining CPU control).
- **Policies (The "Which"):** High-level algorithms used to make decisions inside the OS.
  - *Example:* **CPU Scheduling policies** (FCFS, Shortest Job First, Round Robin) that decide *which* ready process should run next.

### Key Components That Enable CPU Virtualization

#### 1. Context Switching
A **context switch** is the low-level mechanism by which the OS stops executing one process and starts executing another.
- Every process has a **context** (its execution state), stored in a kernel data structure called the **Process Control Block (PCB)**. This context includes:
  - General-purpose CPU registers
  - Program Counter (PC) – the address of the next instruction to execute
  - Stack Pointer (SP) – the current top of the process's stack
  - CPU status flags and memory management info
- **Steps in a Context Switch:**
  1. Pause Process A.
  2. Save Process A's current CPU registers (PC, SP, etc.) into Process A's PCB (or kernel stack).
  3. Load Process B's saved CPU registers from Process B's PCB into the physical CPU registers.
  4. Jump to Process B's saved Program Counter so it resumes execution seamlessly as if it were never interrupted.

[Click here to see the diagram for Context Switching between two processes](https://www.google.com/search?q=context+switch+between+process+P0+and+P1+PCB+diagram&udm=2)

#### 2. Timer Interrupts (Regaining Control)
A major challenge in CPU virtualization is: **If a user process is running directly on the CPU, how does the OS regain control?**
- If a process enters an infinite loop (e.g., `while(1);`) and never makes a system call, a cooperative OS would hang forever.
- **Solution — Hardware Timer Interrupt:**
  - During system boot, the OS configures a hardware timer chip to raise a **timer interrupt** every few milliseconds (e.g., every 10 ms).
  - When the timer fires, the hardware automatically halts the currently running user process, switches the CPU from **User Mode** to **Kernel Mode**, and jumps to a pre-registered **interrupt handler** inside the OS kernel.
  - Now the OS is back in control! It can decide to let the current process continue, or preempt it and switch to another process.

#### 3. Scheduling
Once the OS regains control (via a timer interrupt, an I/O request, or process termination), the **CPU Scheduler** executes a **scheduling policy** to decide which process in the **ready queue** should run next.
- Good scheduling balances multiple goals:
  - **Fairness:** Every process gets a fair share of CPU time (preventing starvation).
  - **Responsiveness:** Interactive tasks respond quickly to user input.
  - **Throughput & Efficiency:** Maximize work completed per unit time and keep the CPU busy (e.g., when one process waits for slow disk I/O, immediately schedule another ready process).

#### 4. Privilege Modes (User Mode vs. Kernel Mode)
To protect the OS and other processes while running user code directly on the CPU, hardware provides at least two execution modes:
- **User Mode:** Restricted mode where user applications run. They cannot directly access hardware, disable interrupts, or modify other processes' memory.
- **Kernel Mode (Supervisor Mode):** Privileged mode where the OS runs. It has full access to all hardware instructions, memory, and I/O devices.

## 3. Virtualizing the Memory

### The Physical Reality
Physical main memory (RAM) is simply a single, large, linear array of bytes indexed from address `0` to `MAX_RAM - 1`. To read or write data, the CPU specifies a physical address on the memory bus.

If multiple processes shared physical RAM directly without virtualization, several severe problems would arise:
1. **Lack of Isolation / Protection:** Process A could accidentally (or maliciously) overwrite Process B's variables or even the OS kernel's code.
2. **Address Conflicts:** If two programs are compiled expecting to use address `0x1000`, they cannot run at the same time.
3. **Difficult Programming:** Programmers would have to manually figure out where free physical RAM exists at runtime.

### The Core Idea: Virtual Address Spaces
**Memory Virtualization** creates the illusion that **every running process has its own large, private, contiguous memory**, called its **Virtual Address Space** (starting from address `0` up to a maximum virtual address).

- Even though Process A and Process B both think they have data stored at virtual address `0x2000`, the OS and CPU hardware map those identical virtual addresses to **completely different physical addresses** in RAM.
- Thus, memory operations in Process A have **zero effect** on Process B's memory.

[Click here to see the diagram for Memory Virtualization mapping virtual address spaces to physical RAM](https://www.google.com/search?q=memory+virtualization+multiple+virtual+address+spaces+mapped+to+physical+memory+diagram&udm=2)

### Classic Demonstration (Why Virtual Addresses Can Be Identical)
Suppose you run two instances of a C program at the same time that allocates an integer `p`, prints its memory address `p`, and increments `*p` every second:
- Instance 1 prints: `address of p: 0x00200000`, value: `1, 2, 3, ...`
- Instance 2 prints: `address of p: 0x00200000`, value: `1, 2, 3, ...`

Both processes see the **exact same virtual address** (`0x00200000`), yet each updates its own independent value! This proves that the address printed by a user program is a **virtual address**, not a physical RAM address.

### How Memory Virtualization Works (High-Level Mechanism)
Memory virtualization is achieved through cooperation between the **OS** and a hardware component inside the CPU called the **MMU (Memory Management Unit)**:
1. **Virtual Address Generation:** The running process (CPU) always generates **virtual addresses** (logical addresses).
2. **Address Translation (Hardware):** On every memory access (instruction fetch, load, or store), the MMU intercepts the virtual address and translates it on-the-fly into a **physical address** in actual RAM using OS-managed structures (such as Base & Bounds registers, Segment Tables, or Page Tables — studied in detail in Module 4).
3. **Protection Check:** If a process attempts to access an address outside its own virtual address space (or writes to read-only memory), the MMU raises a hardware exception (e.g., segmentation fault / protection fault), and the OS terminates the offending process.
4. **Transparency & Efficiency:** Programs do not need to know where they physically reside in RAM, and hardware support (like MMU and TLB) makes translation extremely fast.

### Structure of a Process's Virtual Address Space
Inside its private virtual address space, a process sees a clean, standardized layout:
- **Code (Text) Segment:** Stores the compiled machine instructions of the program (typically read-only).
- **Data Segment:** Stores global and static variables.
- **Heap:** Dynamically allocated memory (via `malloc()` / `new`), typically grows **downward/upward** toward higher addresses.
- **Stack:** Stores local variables, function parameters, and return addresses, typically grows in the **opposite direction** toward the heap.

[Click here to see the diagram for Process Virtual Address Space layout Code Data Heap Stack](https://www.google.com/search?q=process+virtual+address+space+layout+code+heap+stack+OSTEP+diagram&udm=2)

### Benefits of Virtualizing Memory
1. **Transparency:** The OS hides the complexity of physical memory allocation from the programmer; programs behave as if they have private RAM.
2. **Efficiency:** Memory is managed with minimal time and space overhead using hardware support (MMU).
3. **Protection / Isolation:** Processes are isolated from one another and from the OS kernel; a bug in one program cannot corrupt another program or crash the OS.
4. **Running Larger Programs (Virtual Memory):** Combined with disk storage (demand paging), the OS can even allow programs to use more virtual memory than the physical RAM installed on the machine.

## 4. Comparison: CPU Virtualization vs. Memory Virtualization

| Feature | CPU Virtualization | Memory Virtualization |
| :--- | :--- | :--- |
| **Physical Resource** | Limited number of physical CPU cores | Limited, shared physical RAM (linear byte array) |
| **Illusion Created** | Every process has its own dedicated CPU | Every process has its own private, contiguous address space |
| **Core Technique** | **Time-sharing** (multiplexing CPU across time) | **Space-sharing** & **Address Translation** (plus time-sharing via paging/swapping) |
| **Hardware Support** | Timer interrupts, User/Kernel privilege modes, Trap instructions | Memory Management Unit (MMU), Base/Bounds registers, Page Tables, TLB |
| **OS Mechanisms** | Context switching, Process Control Block (PCB), Schedulers | Address space allocation, Page table management, Free-space management |
| **Primary Goal** | Fairness, high CPU utilization, responsiveness, controlled execution | Transparency, isolation/protection, efficient memory usage |

### Question 1
**Source:** *End Semester Examination – November 2025 (Module 1, Q2 – 8 Marks, CO1)*

**Question:**
*Explain how the operating system virtualizes the CPU. Include the roles of context switching, scheduling, and timer interrupts.*

**Answer:**

**1. Concept of CPU Virtualization (2 Marks):**
A computer system has only a small number of physical CPUs (or cores), yet users need to run many programs simultaneously. The operating system creates the illusion of having many virtual CPUs through **CPU virtualization**, making each running process feel as though it owns the processor exclusively.

This illusion is achieved via **time-sharing**: the OS runs one process for a brief period (a time slice), pauses it, switches to another process, and repeats this cycle rapidly. Because switching occurs hundreds of times per second, all processes appear to run concurrently. To do this safely and efficiently, the OS uses **Limited Direct Execution**, running user programs directly on the CPU in **User Mode**, while reserving privileged operations for the OS in **Kernel Mode**.

**2. Role of Timer Interrupts (2 Marks):**
When a user process is executing directly on the CPU, the OS itself is not running. If a process enters an infinite loop or refuses to yield the CPU, the OS could lose control permanently.
- To solve this, the OS configures a **hardware timer** during boot to fire an interrupt periodically (every few milliseconds).
- When the timer expires, a **timer interrupt** occurs: the hardware automatically suspends the current user process, saves minimal hardware state, switches the CPU from **User Mode to Kernel Mode**, and transfers control to the OS's **interrupt handler**.
- This guarantees **preemption**—the OS forcefully regains control of the CPU regardless of what the user process is doing.

**3. Role of Scheduling (2 Marks):**
Once the OS regains control (due to a timer interrupt, an I/O block, or process completion), it must decide **which process should run next**.
- This decision is made by the **CPU Scheduler** using a **scheduling policy** (such as First-Come First-Served, Shortest Job First, Priority Scheduling, or Round Robin).
- The scheduler inspects all runnable processes in the **ready queue** and selects the next process based on system objectives such as fairness (preventing starvation), low turnaround time, fast response time for interactive users, and maximum CPU utilization.
- Scheduling represents the **policy** ("which process to run"), whereas context switching and interrupts represent the **mechanisms** ("how to switch").

**4. Role of Context Switching (2 Marks):**
After the scheduler picks the next process (say, switching from Process A to Process B), the OS executes a **context switch** to hand the CPU over cleanly:
1. The OS saves the execution context of Process A—including its general-purpose registers, **Program Counter (PC)**, **Stack Pointer (SP)**, and status flags—into Process A's **Process Control Block (PCB)** / kernel stack.
2. The OS updates Process A's state (e.g., from *Running* to *Ready* or *Blocked*).
3. The OS restores Process B's previously saved registers, PC, and SP from Process B's PCB into the physical CPU registers and marks Process B as *Running*.
4. Finally, the OS executes a return-from-trap instruction, switching back to **User Mode** and jumping to Process B's saved Program Counter so Process B resumes right where it left off.

[Click here to see the diagram for Limited Direct Execution timeline with timer interrupt and context switch](https://www.google.com/search?q=limited+direct+execution+timer+interrupt+context+switch+timeline+OSTEP+diagram&udm=2)

**Summary:**
Together, **timer interrupts** ensure the OS never loses control of the CPU, **scheduling** fairly and efficiently chooses the next process to run, and **context switching** transparently saves and restores process states—seamlessly virtualizing a single physical CPU into many virtual CPUs.
