# 1.5 Modules and Generalized View of System Calls

---

## 1. Modules (Loadable Kernel Modules)

### What are Kernel Modules?
While early operating systems were strictly monolithic (fast but hard to maintain) or microkernel-based (highly modular but slow), modern operating systems (like Linux, macOS, and Windows) use a **hybrid** approach to get the best of both worlds. They use **Loadable Kernel Modules (LKMs)**.

In a modular OS structure, the kernel has a set of core components built-in, but it can **dynamically link and load additional services at boot time or run time**.
- Instead of recompiling the entire OS kernel just to add a new USB driver, you compile the driver as a module.
- When you plug in the USB device, the OS dynamically loads that module into kernel memory. When the device is removed, the module can be unloaded, freeing up memory.

### Characteristics of the Modular Approach
- **Object-Oriented Concept:** Each core component is separate and communicates with others over known interfaces.
- **Runs in Kernel Space:** Unlike the Microkernel approach (where services run in User Space and communicate via slow Message Passing), kernel modules are loaded directly into **Kernel Space**.
- **High Performance + Modularity:** Because modules run in kernel space, there is **no message-passing overhead**—they can call other kernel functions directly, making them as fast as a monolithic kernel, while remaining as flexible as a microkernel.

## 2. Generalized View of System Calls

### What is a System Call?
A **System Call** provides the fundamental interface between a running user program and the Operating System. Since user applications run in a restricted **User Mode**, they cannot directly access hardware, write to a file, or create a new process. 

To perform any privileged operation, the application must ask the OS to do it on its behalf. The method used to ask the OS is the **system call**.

### System Calls vs. APIs
Programmers rarely write raw system calls directly in Assembly language. Instead, they use an **Application Programming Interface (API)** provided by high-level languages (like C, C++, or Java standard libraries).
- **POSIX API:** Used in UNIX/Linux/macOS systems.
- **Win32 API:** Used in Windows systems.
- **Java API:** Used by programs running on the JVM.

*Example:* When you write `printf("Hello");` in C, the C standard library intercepts this API call and internally triggers the `write()` system call to ask the OS to output text to the screen.

### Why Use APIs Instead of Direct System Calls?
1. **Portability:** An API program can compile and run on any system supporting that API, whereas system calls differ drastically between Windows and Linux.
2. **Simplicity:** APIs hide the complex low-level register setups required to trigger a hardware trap.

## 3. How a System Call Works: The Execution Steps

Executing a system call involves hardware and software working together to safely switch privileges. The OS maintains a **System Call Interface** that intercepts API function calls and invokes the necessary OS kernel routines.

### Steps in Handling a System Call
1. **Application Calls API:** The user application invokes an API function (e.g., `open()` to open a file).
2. **Setup and Trap Instruction:** The C library (or equivalent wrapper) places the **System Call Number** corresponding to `open()` (e.g., syscall #5) into a specific CPU register. It then executes a special hardware instruction called a **trap** (or software interrupt).
3. **Mode Switch (User to Kernel):** 
   - The hardware immediately suspends the user program.
   - It changes the CPU privilege mode from **User Mode to Kernel Mode**.
   - It jumps to a predefined memory location inside the OS kernel called the **trap handler**.
4. **System Call Dispatch:** The OS trap handler reads the system call number from the register. It looks up this number in a **System Call Table** to find the memory address of the actual kernel function that implements `open()`.
5. **Execution:** The OS executes the requested privileged operation (e.g., accessing the disk to open the file).
6. **Return and Mode Switch (Kernel to User):** Once the operation is complete, the OS places the result (e.g., a file descriptor or an error code) into a register. It executes a **return-from-trap** instruction, which switches the CPU back to **User Mode** and hands control back to the user application exactly where it left off.

## 4. Parameter Passing Methods for System Calls
When a system call is made, the OS needs to know exactly what the application wants (e.g., if the call is `read()`, the OS needs to know *which* file to read, *where* in memory to put the data, and *how many* bytes to read). These are the parameters.

The OS provides three general methods to pass parameters to system calls:
1. **Pass in Registers:** The simplest method. The parameters are loaded directly into CPU registers. *Problem:* There may be more parameters than available registers.
2. **Pass via Block/Table in Memory:** The parameters are stored in a block or table in main memory, and the **memory address** of that block is passed to the OS in a single register. (This is the most common approach in Linux/UNIX).
3. **Push to Stack:** Parameters are pushed onto the process's stack by the user program and popped off the stack by the OS kernel.

## 5. Exam Questions & Answers (From Provided Question Papers)

### Question 1
**Source:** *End Semester Examination – November 2025 (Module 1, Q1a – 5 Marks, CO1)*

**Question:**
*Define system call? Explain the different steps in handling a system call.*

**Answer:**
**Definition (1.5 Marks):**
A **system call** is the programmable interface provided by the operating system. It acts as the mechanism by which a user-level program requests privileged services (such as accessing hardware, creating processes, or reading files) from the Operating System kernel.

**Steps in Handling a System Call (3.5 Marks):**
Handling a system call involves a safe transition from User Mode to Kernel Mode. The steps are:
1. **API Invocation:** A user application calls a standard library API (like `open()` or `read()`), passing the required arguments.
2. **Preparation & Trap:** The library wrapper function places the unique **system call number** into a specific CPU register. It then executes a hardware **trap** (software interrupt) instruction.
3. **Mode Switch:** The CPU hardware pauses the user process, saves its state, switches from **User Mode to Kernel Mode**, and jumps to the kernel's trap handler.
4. **Table Lookup:** The OS reads the system call number from the register and indexes into the **System Call Table** to locate the exact address of the kernel routine that handles this request.
5. **Execution:** The OS kernel safely executes the privileged operation.
6. **Return to User:** After execution, the OS stores the return status (success or error code) in a register and executes a **return-from-trap** instruction. This switches the CPU back to **User Mode** and resumes the user application just after the trap instruction.

### Question 2
**Source:** *Internal Test – I, August 2026 (Q2b – 5 Marks, BL-2, CO1)*

**Question:**
*Explain how a system call enables a user program to access operating-system services. Illustrate how the system switches between user mode and kernel mode during a system call.*

**Answer:**
**How a System Call Enables Access (2 Marks):**
User programs execute in **User Mode**, a restricted state where they cannot directly access hardware, memory outside their address space, or I/O devices. To perform a privileged task (like reading a file from disk), the user program must ask the OS to perform the action on its behalf. The **system call** provides this secure gateway. Instead of accessing hardware directly, the program invokes the system call, yielding control to the OS, which validates the request and executes it securely.

**Illustration of Mode Switching During a System Call (3 Marks):**
The safety of the system relies on hardware-supported dual-mode operation:
1. **User Mode Execution:** The application runs normally. When it needs an OS service, it triggers a **trap** instruction.
2. **Switch to Kernel Mode:** The trap instruction forces the CPU hardware to flip a mode bit (from User to Kernel/Supervisor). The CPU transfers control to a pre-defined OS memory location (trap vector). The OS is now in full control and operates in **Kernel Mode**, granting it unrestricted access to all hardware and memory.
3. **Kernel Execution:** The OS processes the system call (e.g., sending commands to the disk controller).
4. **Switch to User Mode:** Once the OS finishes the service, it issues a **return-from-interrupt** instruction. The hardware flips the mode bit back to **User Mode** and hands the CPU execution back to the user program. 
This strict boundary ensures that buggy or malicious programs cannot bypass OS security protocols.
