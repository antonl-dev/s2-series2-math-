# 1.2 Concurrency, Persistence, and Design Goals

---

## 1. Concurrency

### What is Concurrency?
**Concurrency** refers to the set of problems and techniques that arise when **working on many things at once** within the same system or within the same program.

Concurrency occurs at two major levels in a computer system:
1. **Inside the Operating System:** The OS juggles multiple processes, handles hardware interrupts at unpredictable times, and services multiple system calls simultaneously. It must manage its own internal shared data structures (like ready queues, memory tables, and open-file lists) safely.
2. **Inside Multithreaded Applications:** Modern programs create multiple **threads** of execution that run simultaneously inside the **same virtual address space** (sharing the same global variables and heap memory) to take advantage of multi-core CPUs or perform background tasks without freezing the UI.

[Click here to see the diagram for Concurrency and multithreaded execution sharing memory](https://www.google.com/search?q=multithreaded+process+shared+memory+concurrency+OS+diagram&udm=2)

### Why is Concurrency Hard? (The Non-Atomic Operation Problem)
Even a seemingly simple line of code in a high-level language like C—such as incrementing a shared global counter:

> `counter = counter + 1;`

is **not executed atomically** (as a single indivisible step) by the CPU. Instead, the compiler translates it into **three separate machine instructions**:
1. **Load:** Fetch the value of `counter` from memory into a CPU register (`mov 0x8049a1c, %eax`).
2. **Increment:** Add 1 to the value inside the register (`add $0x1, %eax`).
3. **Store:** Write the updated register value back into memory (`mov %eax, 0x8049a1c`).

#### What Goes Wrong (Race Condition Example)
Suppose `counter` initially equals `50`, and **Thread 1** and **Thread 2** both try to execute `counter++`:

| Step | Event / Instruction Executed | Thread 1 Register | Thread 2 Register | Memory (`counter`) |
| :---: | :--- | :---: | :---: | :---: |
| 1 | Thread 1 executes **Load** | `50` | — | `50` |
| 2 | Thread 1 executes **Increment** | `51` | — | `50` |
| 3 | **Timer Interrupt!** Context switch from Thread 1 to Thread 2 | `51` (saved) | — | `50` |
| 4 | Thread 2 executes **Load** | `51` (saved) | `50` | `50` |
| 5 | Thread 2 executes **Increment** | `51` (saved) | `51` | `50` |
| 6 | Thread 2 executes **Store** | `51` (saved) | `51` | **`51`** |
| 7 | Context switch back to Thread 1 | `51` (restored) | `51` | `51` |
| 8 | Thread 1 executes **Store** | `51` | `51` | **`51`** |

- **Expected result:** `52` (two increments).
- **Actual result:** `51` (one update was completely lost!).

This bug is called a **Race Condition**—the final result depends unpredictably on the exact timing of thread interleaving and interrupts. If two threads increment `counter` 100,000 times each without protection, the final value will rarely be `200,000` and will change randomly on every run!

[Click here to see the diagram for Race Condition in counter increment across two threads](https://www.google.com/search?q=race+condition+two+threads+increment+counter+load+add+store+diagram&udm=2)

### How the OS Solves Concurrency Problems
To build correct concurrent programs, the OS and hardware work together to provide **synchronization primitives**:
- **Atomic Hardware Instructions:** Special CPU instructions (e.g., Test-and-Set, Compare-and-Swap) that execute indivisibly.
- **Locks / Mutexes:** Ensure **mutual exclusion** so only one thread can enter a *critical section* (code accessing shared data) at a time.
- **Semaphores & Condition Variables / Monitors:** Allow threads to coordinate and wait safely for specific events (e.g., Producer–Consumer coordination).

## 2. Persistence

### The Problem: Memory is Volatile
Main memory (DRAM) is **volatile**—the moment power is lost or the system crashes, every single bit stored in RAM vanishes. Users and applications need a way to store important data (documents, source code, databases, OS files) **persistently** so it survives reboots and power failures.

### Hardware & Software for Persistence
Persistence requires two layers working together:
1. **Hardware (Non-Volatile Storage Devices):**
   - **Hard Disk Drives (HDDs):** Magnetic spinning platters.
   - **Solid-State Drives (SSDs):** Flash memory (NAND) with no moving parts.
   - I/O devices and disk controllers connect these drives to the CPU/memory bus.
2. **Software (The File System):**
   - The part of the OS responsible for managing persistent storage is called the **File System**.
   - Unlike the CPU and RAM—where the OS creates a **private, virtualized copy** for each process—the OS usually does **not** create a completely private disk for every process. Instead, **users want to share files** across programs (e.g., writing a `.c` file in an editor, compiling it with `gcc`, and running the resulting binary).

[Click here to see the diagram for File System sitting between User Applications and Storage Hardware](https://www.google.com/search?q=operating+system+file+system+architecture+virtual+file+system+disk+diagram&udm=2)

### What the OS Does to Provide Persistence
When a program creates and writes to a file (using standard system calls such as `open()`, `write()`, and `close()`), the OS performs a large amount of complex work behind the scenes:
1. **Mapping & Allocation:** Decides *where* on the physical disk blocks the new data will reside and updates on-disk metadata (inodes, directory entries, free-space bitmaps).
2. **Issuing I/O Requests:** Communicates with the underlying storage device via **device drivers** (low-level OS code that knows the exact hardware protocols for SATA, NVMe, USB, etc.).
3. **Performance Optimization:** Because disks are orders of magnitude slower than RAM, the OS uses **caching/buffering** (holding recently accessed disk blocks in RAM, delaying writes slightly to batch them together) and **disk scheduling** (reordering requests to reduce seek time).
4. **Crash Consistency (Reliability):**
   - Updating a file often requires writing to multiple places on disk (data blocks + metadata/inode + free-space map).
   - What if the power fails halfway through these writes? The file system could be left in a corrupted, inconsistent state!
   - To guard against crashes, modern file systems use sophisticated protocols like **Journaling (Write-Ahead Logging)** or **Copy-on-Write (CoW)** so that either the entire update succeeds or the file system safely recovers to its previous consistent state upon reboot.

## 3. Design Goals of an Operating System

When OS engineers design an operating system, they must balance several competing **design goals**. Every mechanism and policy in an OS exists to satisfy one or more of these goals:

### 1. Building Useful Abstractions
- **Goal:** Make the computer system **convenient and easy to use** for programmers and users by hiding messy, ugly hardware details.
- **Examples:**
  - Instead of manually managing CPU registers and interrupts, programmers work with **Processes** and **Threads**.
  - Instead of raw physical RAM addresses, programmers work with clean **Virtual Address Spaces** (`malloc()`).
  - Instead of raw disk sectors and tracks, users work with **Files and Directories**.
- Abstractions make it possible to write huge, complex applications cleanly and portably across different hardware.

### 2. High Performance (Minimizing Overhead)
- **Goal:** Provide virtualization and abstractions with **minimal overhead** in both **time** (extra CPU instructions) and **space** (extra RAM or disk space used by OS tables/structures).
- **Why it matters:** Every extra microsecond spent inside the OS kernel (e.g., slow context switches, inefficient page tables, excessive memory copying) is time stolen from actual user applications.
- **Example:** Allowing user code to execute *directly* on the physical CPU (Limited Direct Execution) rather than interpreting every instruction in software.

### 3. Protection and Isolation
- **Goal:** Ensure that **errant or malicious programs cannot harm other programs or the OS itself**.
- **Isolation** is the fundamental principle behind protection: each process runs in its own sandbox (its own virtual address space, restricted to User Mode).
- If one application crashes (e.g., divides by zero or accesses an invalid pointer), only *that* process dies—the OS and all other applications continue running unharmed.

### 4. Reliability (Fault Tolerance & Availability)
- **Goal:** The OS must run **non-stop** for days, months, or years without crashing.
- If the OS crashes, *every* single application running on the machine fails immediately.
- Reliability is especially critical in servers, banking systems, medical equipment, and aerospace systems. Techniques like crash-consistent file systems (journaling), strict kernel verification, and modular isolation support reliability.

### 5. Security
- **Goal:** Protect user data and system resources from **unauthorized access, tampering, and attacks** (both local multi-user threats and network/remote threats).
- Includes **Authentication** (verifying user identity), **Access Control / Permissions** (who can read/write/execute which files), and **Encryption**.

### 6. Energy Efficiency
- **Goal:** Minimize power consumption—critical both for **battery-powered mobile/embedded devices** (smartphones, laptops, IoT sensors) and for **massive data centers** (where electricity and cooling cost millions of dollars).
- Examples: CPU frequency scaling (DVFS), putting idle CPU cores into deep sleep states, and spinning down idle disks.

### 7. Mobility and Portability
- **Goal:** Support diverse form factors (from tiny wearables to massive cloud servers) and allow the OS itself to be **ported** easily across different CPU architectures (e.g., x86, ARM, RISC-V) by keeping hardware-specific code cleanly separated from hardware-independent code.

### Summary Table of OS Design Goals

| Design Goal | Core Question Answered | Key OS Mechanism / Example |
| :--- | :--- | :--- |
| **Abstraction** | Is the system easy to program and use? | Processes, Virtual Memory, Files/Directories |
| **High Performance** | Is OS overhead (time & space) kept low? | Direct execution, Caching, TLB, Fast scheduling |
| **Protection / Isolation** | Can one buggy app crash another or the OS? | User/Kernel modes, MMU, Virtual Address Spaces |
| **Reliability** | Does the OS run continuously without losing data? | Crash recovery, Journaling file systems |
| **Security** | Is data safe from unauthorized users/attackers? | File permissions, Authentication, Sandboxing |
| **Energy Efficiency** | Does it conserve battery and power? | CPU sleep states, Dynamic voltage/frequency scaling |
| **Mobility / Portability** | Can it run on diverse/mobile hardware? | Hardware Abstraction Layer (HAL), modular drivers |

### Expected Question 1 (Short/Medium Answer – 4 to 5 Marks)
**Question:**
*What is concurrency in operating systems? Explain with a suitable example how a race condition can occur when two threads update a shared variable.*

**Answer:**
- **Concurrency** refers to multiple tasks or threads making progress simultaneously—either interleaved on a single CPU core via time-sharing or truly executing in parallel on multi-core processors.
- **Why Race Conditions Occur:** High-level operations on shared data are not atomic at the hardware level. For example, `counter = counter + 1` compiles into three machine instructions:
  1. `Load` the value of `counter` from memory into a register.
  2. `Increment` the register by 1.
  3. `Store` the register value back to memory.
- **Scenario:** Suppose `counter = 50`. Thread 1 loads `50` and increments its register to `51`. Before Thread 1 stores `51` back, a **timer interrupt** switches the CPU to Thread 2. Thread 2 loads the still-unchanged `50` from memory, increments it to `51`, and stores `51`. Later, Thread 1 resumes and stores its saved `51`, overwriting Thread 2's update.
- **Result:** Despite two increments, `counter` becomes `51` instead of `52`. Because the outcome depends on unpredictable execution timing, this is a **race condition**. OS synchronization tools (locks, semaphores, atomic instructions) are needed to prevent it.

### Expected Question 2 (Short/Medium Answer – 4 to 5 Marks)
**Question:**
*Explain the concept of Persistence in an Operating System. What role does the file system play, and why is crash consistency important?*

**Answer:**
- **Persistence** is the ability of a computer system to retain data permanently even after power is turned off or the system crashes. Since main memory (DRAM) is volatile, persistent storage relies on non-volatile hardware such as **HDDs** and **SSDs**.
- **Role of the File System:** The OS manages persistent storage through a software layer called the **File System**. Unlike CPU and memory virtualization (which give each process private resources), the file system generally allows **controlled sharing of files** across processes. It handles:
  1. Mapping logical files/directories to physical disk blocks.
  2. Managing low-level I/O through device drivers.
  3. Improving performance via disk caching, write buffering, and disk scheduling.
- **Importance of Crash Consistency:** Writing data often updates multiple on-disk structures (data blocks, inodes, free-space maps). If power fails mid-operation, the disk can end up in a corrupted state. File systems use **journaling (write-ahead logging)** or **copy-on-write** techniques to ensure updates happen atomically and the file system can recover safely after a crash.

### Expected Question 3 (Short/Medium Answer – 4 to 5 Marks)
**Question:**
*Discuss the major design goals of an Operating System.*

**Answer:**
An Operating System is designed to achieve the following primary goals:
1. **Abstraction:** Hide complex hardware details behind simple, clean interfaces (processes, virtual memory, files) so applications are easier to build and maintain.
2. **High Performance (Low Overhead):** Provide virtualization and OS services while minimizing extra CPU time and memory space consumed by the OS itself.
3. **Protection and Isolation:** Prevent buggy or malicious applications from corrupting other applications or the OS kernel using hardware privilege modes and isolated virtual address spaces.
4. **Reliability:** Ensure the OS runs continuously without crashing, and protect stored data against power failures or hardware faults.
5. **Security:** Guard system resources and user data against unauthorized access through authentication and access-control policies.
6. **Energy Efficiency & Mobility:** Conserve power (crucial for mobile devices and data centers) and remain portable across diverse hardware architectures.
