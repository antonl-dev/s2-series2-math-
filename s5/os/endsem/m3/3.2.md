# 3.2 Process Synchronization: Critical-Section Problem, Synchronization Hardware, and Mutex Locks

---

## 1. Introduction: The Need for Synchronization

In a multithreaded (or multiprogrammed) environment, multiple threads (or processes) share the same address space. They often need to read and update the same shared variables, files, or data structures. 

If two threads execute concurrently and try to modify a shared variable at the exact same time, the outcome depends on the unpredictable order in which their machine instructions are interleaved by the CPU scheduler. 
- This situation is called a **Race Condition**. (As discussed in Module 1, an operation like `count++` takes 3 machine instructions: Load, Add, Store. If a context switch happens in the middle, the data becomes corrupted).

To prevent race conditions, we need **Process Synchronization**: a way to coordinate the execution of threads so that shared data remains consistent.

---

## 2. The Critical-Section Problem

To model the synchronization problem, we divide a thread's code into different sections. The most important is the **Critical Section**.

### What is a Critical Section?
A **Critical Section** is a segment of code where a process accesses and modifies shared resources (such as updating a global variable, modifying a database, or writing to a shared file).
- **The Rule:** Only **one** process/thread is allowed to execute inside its critical section at a time. This concept is called **Mutual Exclusion**.

### General Structure of a Process
To enforce mutual exclusion, a process must ask for permission before entering the critical section. 
```c
do {
    // 1. ENTRY SECTION: Request permission to enter
    
    // 2. CRITICAL SECTION: Modify shared data here
    
    // 3. EXIT SECTION: Release permission so others can enter
    
    // 4. REMAINDER SECTION: Non-shared code (safe)
} while (true);
```

### The Three Requirements for a Valid Solution
Any valid solution to the Critical-Section problem *must* satisfy three strict requirements:

1. **Mutual Exclusion:** If process $P_1$ is executing in its critical section, then no other process is allowed to execute in their critical sections. 
2. **Progress:** If no process is in its critical section, and some processes wish to enter, only those processes waiting in their Entry Sections can participate in deciding who goes next. The decision cannot be postponed indefinitely (no deadlock).
3. **Bounded Waiting:** There must exist a bound (limit) on the number of times that other processes are allowed to enter their critical sections after a process has made a request to enter its own, and before that request is granted (no starvation).

## 3. Synchronization Hardware (Low-Level Solutions)

Software-only solutions (like Peterson's Algorithm) are complex and don't scale well to modern multi-core processors. Therefore, modern systems rely on **hardware support** to implement synchronization safely.

### The Problem with Disabling Interrupts
On a single-core machine, the simplest way to prevent race conditions is to **disable timer interrupts** right before entering the critical section, and re-enable them upon exiting. 
- *Why it works:* If interrupts are off, no context switch can occur. 
- *Why it's bad:* 
  1. Giving a user program the power to disable interrupts is dangerous (if it enters an infinite loop, the system dies).
  2. It does not work on multi-core processors (disabling interrupts on Core 1 does not stop a thread running on Core 2 from accessing the shared memory).

### Atomic Hardware Instructions
To solve this on multi-core systems, CPU designers introduced special **atomic** hardware instructions. 
- **Atomic** means the instruction executes as one single, indivisible, uninterruptible unit of operation.
- The two most famous atomic instructions are **Test-and-Set (`test_and_set()`)** and **Compare-and-Swap (`compare_and_swap()`)**.

### How `Test-and-Set` works:
Imagine a boolean variable called `lock`, initially set to `false`.
The `test_and_set()` instruction does two things in one uninterruptible CPU cycle:
1. It returns the current value of the `lock`.
2. It sets the `lock` to `true`.

**Using Test-and-Set to solve the Critical Section:**
```c
boolean lock = false; // Shared variable

do {
    // ENTRY SECTION
    // If lock is false, it becomes true, and while loop breaks (Process enters).
    // If lock is true, it stays true, and while loop spins (Process waits).
    while (test_and_set(&lock)) {
        ; // do nothing (spin wait)
    }

    // CRITICAL SECTION

    // EXIT SECTION
    lock = false; // Release the lock
    
} while (true);
```

## 4. Mutex Locks (High-Level OS Solution)

While hardware instructions like `test_and_set` work, they are too complicated for average programmers to use directly. Operating system designers use these hardware instructions to build higher-level software tools. 

The simplest and most fundamental synchronization tool provided by an OS is the **Mutex Lock** (short for **Mut**ual **Ex**clusion).

### How a Mutex Works
A Mutex is a lock that protects a critical section. A process must `acquire()` the lock before entering the critical section, and `release()` the lock when exiting.

- The `acquire()` function checks if the lock is available. If it is, it takes the lock. If it is not, it blocks (waits) until the lock is available.
- The `release()` function frees the lock so another waiting thread can take it.

```c
// Example using POSIX Pthreads Mutex
pthread_mutex_t lock;

// ENTRY SECTION
pthread_mutex_lock(&lock);

// CRITICAL SECTION
counter = counter + 1; // Safe from race conditions!

// EXIT SECTION
pthread_mutex_unlock(&lock);
```

### Spinlocks vs. Yielding Locks
How exactly does a thread "wait" inside the `acquire()` function if the lock is already taken?
1. **Spinlock (Busy Waiting):** 
   - The thread sits in a `while(lock == true)` loop, constantly checking the lock and burning CPU cycles.
   - *Good for:* Multi-core systems where the critical section is very short. The thread wastes a little CPU time spinning, but avoids the heavy overhead of a context switch.
2. **Yielding Lock (Blocking / Sleep):** 
   - Instead of spinning, the thread calls the OS and puts itself to sleep (moves to the Blocked Queue). The OS schedules another thread to run on the CPU. When the lock is released, the OS wakes the sleeping thread up.
   - *Good for:* Single-core systems or when critical sections are long (like waiting for disk I/O).

### Question 1
**Source:** *Internal Test – II, October 2026 (Q1b – 5 Marks, BL-2, CO3)*

**Question:**
*What is a critical section? (2 marks) List and explain the requirements that any solution to the critical-section problem must meet (3 marks).*

**Answer:**

**1. What is a critical section? (2 Marks):**
A critical section is a specific segment of code within a process or thread where it accesses and modifies shared resources (such as updating shared variables, writing to shared files, or updating a database). To prevent data corruption and race conditions, the execution of critical sections must be strictly controlled so that only **one** process is allowed to execute inside its critical section at any given time (Mutual Exclusion).

**2. Requirements for a valid solution (3 Marks):**
Any valid algorithm or mechanism solving the critical-section problem must satisfy the following three requirements:
1. **Mutual Exclusion:** If a process $P_i$ is executing inside its critical section, then no other process is allowed to enter their respective critical sections. This ensures that shared data is never accessed concurrently.
2. **Progress:** If no process is currently executing in its critical section, and one or more processes wish to enter, only those processes not executing in their remainder sections can participate in deciding which process will enter next. This decision cannot be postponed indefinitely, preventing system deadlock.
3. **Bounded Waiting:** There must be a strict limit (or bound) on the number of times that other processes are allowed to enter their critical sections after a process has made a request to enter its critical section, and before that request is granted. This ensures that no process suffers from starvation (waiting forever).

### Expected Question 2 (Short Answer – 4 Marks)
**Question:**
*Explain how a Mutex lock is used to solve the critical section problem. What is the difference between a spinlock and a blocking mutex?*

**Answer:**
**Mutex Lock Usage (2 Marks):**
A Mutex (Mutual Exclusion) lock is a high-level synchronization tool provided by the OS. It is a boolean variable indicating if a lock is available or owned. A process solves the critical section problem by calling `acquire()` in the Entry Section to take the lock. If another process holds the lock, the caller must wait. Once the critical section is finished, the process calls `release()` in the Exit Section to free the lock, allowing another process to enter safely.

**Spinlock vs. Blocking Mutex (2 Marks):**
- **Spinlock (Busy Waiting):** When a thread tries to acquire an unavailable lock, it continuously loops (`while(lock == true);`), checking the lock condition. It burns active CPU cycles while waiting. It is efficient only for very short critical sections on multi-core systems, as it avoids context-switch overhead.
- **Blocking Mutex:** When a thread tries to acquire an unavailable lock, it yields the CPU, puts itself to sleep, and is placed in a Wait Queue by the OS. It uses zero CPU cycles while waiting. When the lock is released, the OS wakes the thread. This is efficient for long critical sections.

### Quick Self-Check Key Points for Revision
- **Critical Section:** Code that touches shared variables.
- **Race Condition:** Outcome depends on unpredictable thread scheduling order.
- **The 3 Rules of Critical Section:** 
  1. Mutual Exclusion (Only one allowed). 
  2. Progress (Someone must be chosen, no deadlocks). 
  3. Bounded Waiting (No starvation).
- **Atomic Hardware:** `Test-and-Set`. Uninterruptible hardware instructions to build locks.
- **Mutex Lock:** Software tool. `acquire()` before entering, `release()` after leaving.
