# 3.4 Synchronization Problem Examples (Classical Problems)

---

## 1. Introduction to Classical Problems

To test and compare different synchronization mechanisms (like Semaphores and Monitors), computer scientists developed a set of standard **classical synchronization problems**. These problems model real-world concurrency scenarios where multiple processes compete for limited resources or share data.

The three most famous classical problems are:
1. **The Bounded-Buffer (Producer-Consumer) Problem**
2. **The Readers-Writers Problem**
3. **The Dining-Philosophers Problem**

*(Additionally, practical real-world problems like Bank Account Race Conditions are commonly used in exams to test your applied knowledge).*

---

## 2. The Bounded-Buffer (Producer-Consumer) Problem

### The Problem
Imagine a system with two types of processes:
- **Producer:** Generates data (e.g., a web server receiving user uploads) and puts it into a buffer.
- **Consumer:** Takes data out of the buffer and processes it (e.g., a database writing the upload to disk).
- **The Buffer:** A shared array of a fixed size $N$ (Bounded Buffer).

**The Synchronization Constraints:**
1. **Mutual Exclusion:** The Producer and Consumer cannot access the buffer array at the exact same time, or data could be overwritten or read incorrectly.
2. **Condition 1 (Buffer Full):** The Producer must go to sleep if the buffer is completely full.
3. **Condition 2 (Buffer Empty):** The Consumer must go to sleep if the buffer is completely empty.

### The Semaphore Solution
This problem is solved using three semaphores:
- `mutex` (Binary Semaphore, initialized to 1): Ensures mutual exclusion for accessing the buffer.
- `empty` (Counting Semaphore, initialized to $N$): Tracks how many empty slots are left.
- `full` (Counting Semaphore, initialized to 0): Tracks how many full slots are available to consume.

## 3. The Readers-Writers Problem

### The Problem
Imagine a database shared among several processes.
- **Readers:** Only want to read the database. (They don't modify anything).
- **Writers:** Want to update (read and write) the database.

**The Synchronization Constraints:**
1. **Concurrent Reads:** Multiple Readers can safely read the database at the exact same time (since no data is changing).
2. **Exclusive Writes:** If a Writer is writing to the database, NO OTHER process (neither Reader nor Writer) can access the database at that time.

*(Note: If not implemented carefully, this problem easily leads to **Starvation**, where a constant stream of Readers prevents a Writer from ever getting access).*

## 4. The Dining-Philosophers Problem

### The Problem Description
Consider five philosophers sitting around a circular table. 
- They spend their lives alternating between two activities: **Thinking** and **Eating**.
- In the center of the table is a bowl of rice. Between each philosopher is a single chopstick (5 chopsticks in total).
- **The Rule:** A philosopher needs exactly **two chopsticks** (the one on their left and the one on their right) to eat the rice.
- A philosopher can only pick up one chopstick at a time. After eating, they put both chopsticks down and go back to thinking.

### Why is this problem important?
It represents a classic **resource allocation problem** where multiple processes compete for limited resources (chopsticks/locks) and can easily fall into a **Deadlock**.

### The Deadlock Scenario
Suppose we use a simple Semaphore for each chopstick (`chopstick[5]`).
- Philosopher $i$ executes: `wait(chopstick[i]); wait(chopstick[(i+1)%5]); eat();`
- **Deadlock:** What if all 5 philosophers become hungry at the exact same time? Every philosopher reaches to their left and grabs their left chopstick. Now, every philosopher turns to their right, but the right chopstick is already taken! They all wait forever. The system is deadlocked.

## 5. Exam Questions & Answers (From Provided Question Papers)

### Question 1 (Dining Philosophers & Monitor Solution)
**Source:** *Internal Test – II, October 2026 (Q5a – 5 Marks, BL-2, CO3)*

**Question:**
*Describe the Dining Philosophers problem. Give a solution to it using monitors.*

**Answer:**

**1. Description of the Problem (1.5 Marks):**
The Dining Philosophers problem models a scenario where 5 philosophers sit around a circular table. There is one chopstick between each philosopher (5 total). A philosopher alternates between thinking and eating. To eat, a philosopher must acquire exactly two chopsticks (the left one and the right one). This problem highlights the complexities of concurrency: if every philosopher picks up their left chopstick simultaneously, they will all wait forever for their right chopstick, resulting in a **Deadlock**. The challenge is to design a protocol where no philosopher starves and no deadlock occurs.

**2. Solution using Monitors (3.5 Marks):**
To ensure a deadlock-free solution, we use a Monitor. The strategy is: A philosopher may only pick up their chopsticks if **both** the left and right chopsticks are available at the same time.

We define a monitor with:
- An array `state[5]` which tracks if a philosopher is `THINKING`, `HUNGRY`, or `EATING`.
- An array of condition variables `self[5]` where a philosopher can go to sleep if they are hungry but their neighbors are eating.

**Monitor Code (Pseudocode):**
```pascal
monitor DiningPhilosophers {
    
    enum {THINKING, HUNGRY, EATING} state[5];
    condition self[5];

    // Helper function to check if neighbors are eating
    void test(int i) {
        if ((state[(i + 4) % 5] != EATING) && 
            (state[i] == HUNGRY) && 
            (state[(i + 1) % 5] != EATING)) {
                state[i] = EATING;
                signal(self[i]); // Wake up philosopher i if they were sleeping
        }
    }

    // Called by a philosopher when they want to eat
    void pickup(int i) {
        state[i] = HUNGRY;
        test(i); // Try to eat
        if (state[i] != EATING) {
            wait(self[i]); // If couldn't eat, go to sleep
        }
    }

    // Called by a philosopher when they finish eating
    void putdown(int i) {
        state[i] = THINKING;
        // Check if left and right neighbors are hungry and can now eat
        test((i + 4) % 5); // Check Left neighbor
        test((i + 1) % 5); // Check Right neighbor
    }
    
    // Initialization
    init() {
        for (int i = 0; i < 5; i++)
            state[i] = THINKING;
    }
}
```
*How it prevents deadlock:* Because `pickup` and `putdown` are Monitor methods, they are **mutually exclusive**. A philosopher safely checks both chopsticks simultaneously. They either get both or go to sleep, completely eliminating the circular wait condition that causes deadlocks.

### Question 2 (Banking System Race Condition)
**Source:** *End Semester Examination – November 2025 (Module 2/3, Q6 – 8 Marks, CO3)*
*(Note: Though placed under Module 2 in the exam paper numbering, this is purely a Module 3 Synchronization / Race Condition question).*

**Question:**
*Consider a banking system that maintains an account balance with two functions: `deposit(amount)` and `withdraw(amount)`. These two functions are passed the amount that is to be deposited or withdrawn from the bank account balance. Assume that a husband and wife share a bank account. Concurrently, the husband calls the `withdraw()` function and the wife calls `deposit()`. Describe how a race condition is possible and what might be done to prevent the race condition from occurring.*

**Answer:**

**1. Description of the Race Condition (4 Marks):**
A race condition occurs when multiple threads (or processes) access and manipulate shared data concurrently, and the final outcome depends on the unpredictable execution order (interleaving) of their instructions.

In this scenario, the shared variable is `balance`. 
Both `deposit(amount)` and `withdraw(amount)` involve a sequence of three machine-level operations:
1. **Read** the current `balance` from memory into a local CPU register.
2. **Modify** the value in the register (Add for deposit, Subtract for withdraw).
3. **Write** the new value from the register back into the shared `balance` memory.

*Example Scenario:*
Let the initial `balance` = ₹10,000. 
- The Wife calls `deposit(2000)`. 
- The Husband calls `withdraw(5000)`.

If the OS context-switches them improperly, the following interleaving can occur:
1. **Wife's thread** reads `balance` (₹10,000) into Register A.
2. **Wife's thread** adds 2,000 (Register A is now ₹12,000).
3. *[Context Switch! Timer interrupt suspends Wife before she can write back]*
4. **Husband's thread** reads `balance` (still ₹10,000 in memory!) into Register B.
5. **Husband's thread** subtracts 5,000 (Register B is now ₹5,000).
6. **Husband's thread** writes Register B (₹5,000) back to memory. (New `balance` = ₹5,000).
7. *[Context Switch back to Wife]*
8. **Wife's thread** resumes and writes Register A (₹12,000) back to memory. (New `balance` overwrites to ₹12,000).

**Result:** The husband successfully withdrew ₹5,000, but the bank's system completely lost the record of that withdrawal because the wife's thread overwrote the memory. The final balance is wrong (Should be ₹7,000, but is ₹12,000).

**2. How to Prevent the Race Condition (4 Marks):**
To prevent this, the banking system must treat the `deposit()` and `withdraw()` operations as **Critical Sections** and enforce **Mutual Exclusion**. Only one thread must be allowed to read and update the `balance` at a time.

This can be done using a **Mutex Lock** (or a Binary Semaphore). 
- A shared `account_lock` is initialized to unlocked.
- Before executing the read/modify/write operations, a thread must call `acquire(account_lock)`. 
- After writing the final value back to memory, it calls `release(account_lock)`.

*Safe Code Implementation:*
```c
// Wife's Thread
deposit(amount) {
    acquire(account_lock);    // ENTER CRITICAL SECTION
    balance = balance + amount; 
    release(account_lock);    // EXIT CRITICAL SECTION
}

// Husband's Thread
withdraw(amount) {
    acquire(account_lock);    // ENTER CRITICAL SECTION
    balance = balance - amount;
    release(account_lock);    // EXIT CRITICAL SECTION
}
```
If the wife's thread acquires the lock first, the husband's thread will be blocked at `acquire()` and must wait until the wife finishes the entire transaction, guaranteeing data integrity.

### Quick Self-Check Key Points for Revision
- **Producer-Consumer:** Requires `mutex` + `empty` semaphore + `full` semaphore.
- **Readers-Writers:** Multiple readers OK, Writer must be totally isolated. Watch out for starvation.
- **Dining Philosophers:** Circular table, 5 philosophers. Grabbing left then right causes Deadlock. Solve by grabbing both simultaneously (via Monitor) or breaking the circular wait.
- **Bank Race Condition:** Read $\rightarrow$ Modify $\rightarrow$ Context Switch $\rightarrow$ Overwrite. Solve using **Mutex Locks** around the Critical Section.
