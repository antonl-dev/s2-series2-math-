# 3.5 Deadlock: System Model, Deadlock Characterization, and Methods for Handling Deadlocks

---

## 1. Introduction: What is a Deadlock?

In a multiprogramming environment, multiple processes compete for a finite number of resources (like CPUs, memory space, files, or hardware devices like printers). A process requests resources, and if they are not available, it enters a waiting state.

A **Deadlock** is a situation where a set of processes are **permanently blocked** because each process is holding a resource and waiting for another resource that is held by another process in the set.

- **Classic Analogy:** Traffic gridlock at a four-way intersection. Car A cannot move until Car B moves. Car B cannot move until Car C moves. Car C cannot move until Car D moves. Car D cannot move until Car A moves. No one can move, and they will wait forever.

---

## 2. System Model

To understand how deadlocks occur, the OS models the system as a collection of **Processes** ($P_1, P_2, \dots, P_n$) and **Resource Types** ($R_1, R_2, \dots, R_m$).
- A resource type can have multiple **instances** (e.g., Resource Type "Printer" might have 3 instances).

Under the normal mode of operation, a process may utilize a resource in only the following sequence:
1. **Request:** The process requests the resource. If the resource is in use by another process, the requesting process waits.
2. **Use:** The process can operate on the resource.
3. **Release:** The process releases the resource back to the OS pool.

---

## 3. Deadlock Characterization (The Four Necessary Conditions)

For a deadlock to occur, **four specific conditions must hold simultaneously** in a system. This is a very important theoretical concept. If even *one* of these conditions is broken, a deadlock cannot happen.

1. **Mutual Exclusion:**
   - At least one resource must be held in a non-sharable mode. This means only one process can use the resource at a time. If another process requests that resource, it must be delayed until the resource is released.
2. **Hold and Wait:**
   - A process must be currently holding at least one resource and at the same time waiting to acquire additional resources that are currently being held by other processes.
3. **No Preemption:**
   - Resources cannot be preempted (forcibly taken away). A resource can only be released voluntarily by the process holding it, after that process has completed its task. The OS cannot force a process to give up its lock.
4. **Circular Wait:**
   - There must exist a set of waiting processes $\{P_0, P_1, \dots, P_n\}$ such that $P_0$ is waiting for a resource held by $P_1$, $P_1$ is waiting for a resource held by $P_2$, $\dots$, and $P_n$ is waiting for a resource held by $P_0$.

## 4. Resource-Allocation Graph

Deadlocks can be described more precisely using a directed graph called a **Resource-Allocation Graph**. 

### Graph Components
- **Vertices (Nodes):**
  - **Processes (Circles):** $P_1, P_2, \dots$
  - **Resource Types (Squares):** $R_1, R_2, \dots$ (Inside the square, small dots represent the number of instances).
- **Edges (Lines):**
  - **Request Edge ($P_i \rightarrow R_j$):** A directed arrow from a Process to a Resource type. It means the process has requested the resource and is waiting for it.
  - **Assignment Edge ($R_j \rightarrow P_i$):** A directed arrow from a dot inside the Resource square to a Process. It means the resource has been allocated to the process.

### Analyzing the Graph for Deadlocks
- If a graph contains **no cycles**, then **no deadlock** exists.
- If a graph **does contain a cycle**:
  1. **Single Instance Resources:** If every resource type has only exactly one instance, then a cycle implies that a **deadlock has definitely occurred**.
  2. **Multiple Instance Resources:** If resource types have multiple instances, a cycle does **not** necessarily mean a deadlock has occurred. (Another process holding an instance of the resource outside the cycle might release it, breaking the cycle).

## 5. Methods for Handling Deadlocks

Broadly speaking, an operating system can handle the problem of deadlocks in one of three ways:

### 1. Deadlock Prevention or Avoidance (Proactive)
Ensure that the system will *never* enter a deadlocked state.
- **Deadlock Prevention:** Structuring the system strictly so that at least one of the four necessary conditions (Mutual Exclusion, Hold and Wait, No Preemption, Circular Wait) cannot possibly hold. (Covered deeply in `3.6`).
- **Deadlock Avoidance:** The OS requires the processes to declare in advance how many resources they will need. The OS dynamically checks every resource request (using algorithms like the **Banker's Algorithm**) to ensure granting it will not lead the system into an unsafe state. (Covered deeply in `3.6`).

### 2. Deadlock Detection and Recovery (Reactive)
Allow the system to enter a deadlocked state, detect that it has happened, and then recover from it.
- **Detection:** The OS periodically runs an algorithm that examines the state of resources to see if a circular wait has occurred.
- **Recovery:** Once detected, the OS forces a recovery by aborting a process or forcibly preempting resources from processes to break the cycle. (Covered deeply in `3.7`).

### 3. Ignorance (The Ostrich Algorithm)
Ignore the problem altogether and pretend that deadlocks never occur in the system.
- If a deadlock happens, the system will eventually freeze up, and the human user will have to manually restart the computer or kill the frozen application.
- **Surprise Fact:** This is the method used by most general-purpose modern operating systems, including **Windows, Linux, and macOS**! Why? Because deadlocks are statistically rare, and the performance overhead required to proactively prevent or avoid them (like running the Banker's algorithm on every single lock request) is far too costly.

### Expected Question 1 (Medium Answer – 6 Marks)
**Question:**
*Define deadlock. State and explain the four necessary conditions for a deadlock to occur in an operating system.*

**Answer:**
**Definition (2 Marks):**
A deadlock is a situation where a set of processes are permanently blocked because each process is currently holding a resource and waiting for another resource that is currently being held by another process within the same set.

**The Four Necessary Conditions (4 Marks):**
For a deadlock to exist, the following four conditions must occur simultaneously:
1. **Mutual Exclusion:** At least one resource in the system must be non-sharable. Only one process can use it at a time.
2. **Hold and Wait:** A process must be holding at least one resource while waiting to acquire additional resources that are currently allocated to other processes.
3. **No Preemption:** Resources cannot be forcibly taken away by the OS. A resource can only be released voluntarily by the process holding it.
4. **Circular Wait:** There must exist a closed chain (cycle) of waiting processes, where $P_0$ is waiting for a resource held by $P_1$, $P_1$ is waiting for a resource held by $P_2$, ..., and $P_n$ is waiting for a resource held by $P_0$.

---

### Expected Question 2 (Short Answer – 4 Marks)
**Question:**
*Explain the purpose of a Resource-Allocation Graph. If a cycle exists in the graph, does it always mean the system is deadlocked? Justify your answer.*

**Answer:**
**Purpose of Resource-Allocation Graph (2 Marks):**
A Resource-Allocation Graph is a directed graph used by the OS to model the current state of resource allocation. It consists of process nodes (circles) and resource nodes (squares). Request edges ($P \rightarrow R$) indicate a process is waiting for a resource, and Assignment edges ($R \rightarrow P$) indicate a resource is currently held by a process. It is used to visually and algorithmically detect deadlocks.

**Cycle and Deadlock Relationship (2 Marks):**
A cycle in the graph **does not always** mean a deadlock exists. 
- If every resource type in the cycle has exactly **one instance**, then a cycle definitely implies a deadlock.
- However, if the resource types have **multiple instances**, a cycle is only a necessary condition, but not a sufficient one. Another process outside the cycle might be holding one of the instances of the resource and could release it, thereby breaking the cycle and preventing the deadlock.

### Quick Self-Check Key Points for Revision
- **Deadlock Definition:** Processes permanently blocked, waiting on each other.
- **4 Necessary Conditions:** Mutual Exclusion, Hold and Wait, No Preemption, Circular Wait. (If you break one, you cure the deadlock).
- **Resource Graph Rule:** 
  - No cycle = No deadlock. 
  - Cycle + Single Instance = Deadlock. 
  - Cycle + Multiple Instances = *Maybe* deadlock.
- **3 Handling Methods:** Prevent/Avoid (Proactive), Detect/Recover (Reactive), Ignore (Ostrich Algorithm - used by Linux/Windows).
