# 3.7 Deadlock Detection and Recovery

---

## 1. Introduction

If an operating system does not employ deadlock prevention (breaking one of the four necessary conditions) or deadlock avoidance (running the Banker's Algorithm before every request), then deadlocks may occur. 

In this environment, the OS must provide two things:
1. **An algorithm that examines the state of the system to determine whether a deadlock has occurred (Deadlock Detection).**
2. **An algorithm to recover from the deadlock (Deadlock Recovery).**

*Note:* Running detection and recovery algorithms requires significant CPU overhead, which is why many general-purpose OSes (like Windows and Linux) prefer to ignore deadlocks entirely (the Ostrich Algorithm). However, specialized systems (like databases) heavily rely on detection and recovery.

---

## 2. Deadlock Detection

The method of detection depends on whether the resource types have a single instance or multiple instances.

### A. Single Instance of Each Resource Type: The Wait-For Graph
If all resources have only a single instance, we can define a deadlock detection algorithm that uses a variant of the resource-allocation graph, called a **Wait-For Graph**.

- **How it's built:** We remove the resource nodes (squares) from the resource-allocation graph and collapse the edges. 
- An edge from $P_i \rightarrow P_j$ exists if process $P_i$ is waiting for a resource that is currently held by process $P_j$.
- **Detection Rule:** A deadlock exists in the system **if and only if the wait-for graph contains a cycle**. 
- The OS periodically maintains this graph and runs a cycle-detection algorithm (which takes $O(n^2)$ operations, where $n$ is the number of processes).

[Click here to see the diagram comparing a Resource-Allocation Graph to a Wait-For Graph](https://www.google.com/search?q=resource+allocation+graph+vs+wait-for+graph+diagram+OS&udm=2)

### B. Multiple Instances of a Resource Type
If resources have multiple instances, a wait-for graph is not sufficient. The OS must use an algorithm very similar to the Banker's Algorithm.

Instead of `Max` and `Need` matrices (since we don't know the maximum advance claims in a detection environment), we use a **Request matrix**.

**Data Structures:**
- `Available`: Vector of length $m$ (available resources).
- `Allocation`: $n \times m$ matrix (current allocations).
- `Request`: $n \times m$ matrix (current requests of each process).

**Detection Algorithm Logic:**
1. Find a process whose current `Request` can be satisfied by the `Available` resources.
2. Pretend to allocate them, let the process finish, and return its `Allocation` back to `Available`.
3. Repeat this. If you can finish all processes, there is **no deadlock**.
4. If you get stuck and some processes cannot finish, **those specific remaining processes are deadlocked**.

## 3. Recovery from Deadlock

Once the detection algorithm determines that a deadlock exists, the system must recover. There are two primary approaches to breaking a deadlock: **Process Termination** and **Resource Preemption**.

### Approach 1: Process Termination (Aborting Processes)
The OS breaks the deadlock cycle by killing processes. There are two ways to do this:
1. **Abort all deadlocked processes:**
   - *Pros:* Guaranteed to break the deadlock immediately.
   - *Cons:* Extremely costly. Processes might have computed for hours, and all that work is thrown away and must be restarted.
2. **Abort one process at a time until the deadlock cycle is eliminated:**
   - *Pros:* Wastes less work.
   - *Cons:* High overhead. After aborting one process, the OS must re-run the deadlock detection algorithm to see if the cycle still exists.

**How to choose the victim? (Victim Selection):**
If we abort one at a time, the OS must decide which process to kill based on minimum cost:
- What is the priority of the process? (Kill low priority first).
- How long has it computed, and how much longer does it need? (Kill newer processes).
- How many and what type of resources has it used?
- Is it an interactive (user-facing) or batch process?

### Approach 2: Resource Preemption
Instead of killing a process, the OS forcibly takes away resources from one or more deadlocked processes and gives them to others until the deadlock is broken.

If preemption is required, three major issues must be addressed:
1. **Selecting a Victim:** Which resources and which processes are preempted? The OS must minimize cost (e.g., preempting a printer might mean a document prints half-garbled).
2. **Rollback:** If we take a resource away from a process, what do we do with that process? It cannot continue normally. The OS must **roll back** the process to some safe state and restart it from that state. (Often, OSes just do a total rollback: abort the process and restart it from the beginning).
3. **Starvation:** How do we guarantee that resources will not always be preempted from the exact same process? If the same process is always chosen as the victim, it will never finish. 
   - *Solution:* Include the number of rollbacks in the cost factor so a process can only be a victim a finite number of times.

## 4. Exam Questions & Answers

> **Note on Provided Question Papers:** The provided exams for Module 3 focused heavily on Banker's Algorithm calculations (Avoidance) and Synchronization primitives (Monitors/Mutexes). However, Deadlock Detection and Recovery is the final core syllabus topic for this module. Below are expected standard exam questions to ensure complete preparation.

### Expected Question 1 (Medium Answer – 5 Marks)
**Question:**
*Explain how a Wait-For Graph is used for deadlock detection. What is its primary limitation?*

**Answer:**
**Wait-For Graph (3 Marks):**
A Wait-For Graph is a directed graph used by the OS to detect deadlocks in systems where every resource type has exactly **one instance**. It is constructed from the Resource-Allocation graph by removing the resource nodes and directly connecting the process nodes. A directed edge from process $P_i$ to $P_j$ indicates that $P_i$ is waiting for a resource that is currently held by $P_j$. The detection algorithm traverses this graph; **if and only if a cycle exists in the graph, a deadlock is present.**

**Limitation (2 Marks):**
The primary limitation of the Wait-For Graph is that it **fails if resources have multiple instances**. In a multiple-instance system, a cycle in the wait-for graph does not guarantee a deadlock (because an instance of the resource held by a process outside the cycle might be released). For multiple instances, the OS must use matrix-based detection algorithms (similar to Banker's Algorithm) instead of a simple graph.

---

### Expected Question 2 (Medium Answer – 5 Marks)
**Question:**
*Once a deadlock is detected, the operating system must recover from it. Discuss the two main approaches to deadlock recovery and the issues associated with them.*

**Answer:**
The two main approaches to recover from a deadlock are Process Termination and Resource Preemption:

**1. Process Termination (2.5 Marks):**
The OS breaks the deadlock by aborting processes. It can either:
- Abort *all* deadlocked processes: This is guaranteed to resolve the deadlock but is highly inefficient as it discards all partial computations.
- Abort *one process at a time*: The OS aborts a selected victim and re-runs the detection algorithm. 
*Issues:* The OS must smartly select a victim (based on priority, execution time, and resources held) to minimize the cost of lost work.

**2. Resource Preemption (2.5 Marks):**
The OS forcefully takes away resources from one process and allocates them to another to break the deadlock cycle.
*Issues that must be managed include:*
- **Victim Selection:** Deciding which process loses its resources based on minimum cost.
- **Rollback:** The preempted process must be rolled back to a safe state or completely restarted, as its current execution is disrupted.
- **Starvation:** The OS must ensure the same process is not repeatedly chosen as the victim (e.g., by factoring the number of rollbacks into the victim-selection algorithm).

---

### Quick Self-Check Key Points for Revision
- **Detection (Single Instance):** Use a **Wait-For Graph**. Cycle = Deadlock.
- **Detection (Multiple Instances):** Use a matrix algorithm (Available, Allocation, Request).
- **Recovery by Termination:** Kill all deadlocked, or kill one-by-one until fixed.
- **Recovery by Preemption:** Steal resources. Requires handling **Victim Selection**, **Rollback**, and preventing **Starvation**.
