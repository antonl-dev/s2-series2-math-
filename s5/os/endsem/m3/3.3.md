# 3.3 Semaphores, Critical Regions, and Monitors

---

## 1. Semaphores

While Mutex Locks are excellent for simple mutual exclusion (locking a single resource), they are somewhat limited. What if we have a pool of **5 identical printers**, and we want to allow exactly 5 threads to access them simultaneously, but block the 6th? A simple true/false Mutex cannot do this. 

To solve more complex synchronization problems, OS designers introduced the **Semaphore**.

### What is a Semaphore?
A Semaphore (`S`) is an **integer variable** that, apart from initialization, is accessed only through two standard **atomic** operations: `wait()` and `signal()`.
- Historically, these operations were named **P()** (from Dutch *proberen*, to test) for wait, and **V()** (from *verhogen*, to increment) for signal.

**The operations are defined as follows:**
```c
// Decrements the semaphore. If S becomes negative or 0, the thread blocks.
wait(S) {
    while (S <= 0) {
        // busy wait or put thread to sleep
    }
    S--;
}

// Increments the semaphore. If threads are waiting, it wakes one up.
signal(S) {
    S++;
}
```
*Crucially, the OS guarantees that testing and modifying the integer `S` is done atomically (without interruption).*

### Types of Semaphores
1. **Binary Semaphore:** The integer value can only be `0` or `1`. It functions exactly like a Mutex Lock. It is used to guarantee mutual exclusion.
2. **Counting Semaphore:** The integer value can range over an unrestricted domain (e.g., $0$ to $N$). It is used to control access to a given resource consisting of a finite number of instances.
   - *Example:* Initialize Semaphore $S = 5$ (for 5 printers).
   - Each time a thread wants a printer, it calls `wait(S)` (S becomes 4). 
   - When S hits 0, all printers are in use. If a 6th thread calls `wait(S)`, it blocks.
   - When a thread finishes, it calls `signal(S)`, increasing S back to 1 and waking up a blocked thread.

### Implementation of Semaphores (Avoiding Busy Waiting)
Just like Mutexes, if `wait()` uses a `while(S <= 0)` loop, it suffers from **busy waiting** (Spinlock), wasting CPU cycles. 
To solve this, OSes implement **Blocking Semaphores**:
- The Semaphore is structured as a struct containing an **integer value** and a **waiting queue (linked list of PCBs)**.
- If a thread calls `wait()` and the value is $\leq 0$, the thread uses a system call (`sleep()`) to put itself into the semaphore's wait queue.
- When another thread calls `signal()`, the OS checks the queue. If it is not empty, it uses `wakeup()` to move a waiting thread from the wait queue back to the Ready Queue.

## 2. Problems with Semaphores (Why we need something better)

Semaphores are incredibly powerful, but they are essentially low-level programming tools. They are **highly prone to human error**. 

If a programmer makes a tiny typo, the entire system can deadlock or suffer data corruption:
- **Error 1 (Wrong Order):** Calling `signal(mutex)` *before* the critical section, and `wait(mutex)` *after*. (Result: Multiple threads enter, causing a Race Condition).
- **Error 2 (Double Wait):** Calling `wait(mutex)` twice by accident. (Result: The thread deadlocks itself permanently).
- **Error 3 (Forgetting to Signal):** A thread calls `wait()`, enters the critical section, but an exception/error occurs before it can call `signal()`. (Result: The lock is never released, and all other threads wait forever).

To solve these human-error issues, researchers developed high-level language constructs: **Critical Regions** and **Monitors**.

---

## 3. Critical Regions

A **Critical Region** (or Conditional Critical Region) is a high-level, language-based synchronization construct. Instead of forcing the programmer to manually place `wait()` and `signal()` functions, the programming language itself enforces mutual exclusion.

- The programmer declares a variable as `shared`.
- The programmer wraps the code that accesses this variable inside a special `region` block.
```pascal
// Pseudocode example
var v: shared integer;

region v when (condition) do {
    // This is the Critical Section
    v = v + 1;
}
```
- **How it works:** The compiler automatically translates the `region` block into the appropriate `wait()` and `signal()` semaphore calls. If a thread crashes inside the region, the language runtime automatically releases the lock. 
- *Note:* While conceptually important, Critical Regions were largely superseded by Monitors in modern programming languages.

## 4. Monitors

A **Monitor** is a highly structured, object-oriented synchronization mechanism provided directly by high-level programming languages (like Java and C#). 

### How a Monitor Works
Think of a Monitor as a special **Class** or **Object** that has a built-in Mutex Lock and condition variables.
1. **Private Data:** The shared variables are hidden inside the monitor. They cannot be accessed directly by outside threads.
2. **Synchronized Methods:** The only way to modify the data is by calling the monitor's methods.
3. **Automatic Mutual Exclusion:** The monitor guarantees that **only one thread can be active inside the monitor at any given time**. 
   - If Thread A calls a monitor method, it enters the monitor. 
   - If Thread B tries to call a method while Thread A is inside, Thread B is automatically blocked and placed in the monitor's entry queue.

### Condition Variables inside Monitors
Sometimes, a thread enters a monitor, but realizes it cannot proceed (e.g., it wants to read data, but the buffer is empty). It needs to wait, but it is currently holding the monitor's lock! If it just sleeps, no other thread can enter the monitor to put data in the buffer (Deadlock).

To solve this, Monitors provide **Condition Variables** with two operations:
- **`wait(c)`:** The thread immediately suspends itself, **releases the monitor lock**, and goes to sleep in the queue for condition `c`. This allows another thread to enter the monitor.
- **`signal(c)`:** Wakes up *exactly one* thread waiting on condition `c`. (If no one is waiting, it does nothing).

**Famous Example in Java:**
Java natively implements monitors. Every object in Java has an implicit monitor lock. You access it using the `synchronized` keyword, and use `wait()` and `notify()` (which act as condition variables).

```java
class CounterMonitor {
    private int count = 0; // Protected data

    // The 'synchronized' keyword tells Java this is a Monitor method
    public synchronized void increment() {
        count++; // Automatically mutually exclusive!
    }
}
```

## 5. Comparison: Semaphores vs. Monitors

| Feature | Semaphore | Monitor |
| :--- | :--- | :--- |
| **Level of Abstraction** | Low-level OS primitive (integer variable). | High-level programming language construct (Object/Class). |
| **Ease of Use** | Difficult. High risk of programming errors (deadlocks, race conditions). | Easy. The compiler handles the mutual exclusion automatically. |
| **Mutual Exclusion** | Must be explicitly coded using `wait()` and `signal()`. | Implicitly guaranteed. Only one thread can execute a monitor method at a time. |
| **Condition Waiting** | Handled by adding more semaphores (complex). | Handled elegantly using built-in Condition Variables (`wait(c)`/`signal(c)`). |

### Expected Question 1 (Medium Answer – 6 Marks)
**Question:**
*What is a Semaphore? Explain the difference between a binary semaphore and a counting semaphore. How does a blocking semaphore avoid the busy-waiting problem?*

**Answer:**
**1. What is a Semaphore? (2 Marks):**
A semaphore is a synchronization tool used to manage concurrent access to shared resources. It consists of an integer variable that can only be accessed and modified through two indivisible (atomic) operations: `wait()` (which decrements the integer) and `signal()` (which increments the integer).

**2. Binary vs. Counting Semaphore (2 Marks):**
- **Binary Semaphore:** The integer value is restricted to either 0 or 1. It is primarily used to provide strict mutual exclusion (acting exactly like a Mutex Lock) for a single shared resource.
- **Counting Semaphore:** The integer value can range over any non-negative integer (e.g., 0 to N). It is used to control access to a pool of multiple identical resources (like 5 network connections). The semaphore is initialized to N. Each `wait()` decreases it, and each `signal()` increases it.

**3. Avoiding Busy-Waiting (2 Marks):**
If a simple `wait()` operation uses a `while(S <= 0)` loop, it continuously burns CPU cycles (busy waiting). A **blocking semaphore** avoids this by associating a Wait Queue with the semaphore integer. If a thread calls `wait()` and the value is $\leq 0$, the OS removes the thread from the CPU, puts it to sleep, and adds its PCB to the semaphore's Wait Queue. When another thread calls `signal()`, the OS wakes a sleeping thread and moves it to the Ready Queue, wasting zero CPU cycles while waiting.

### Expected Question 2 (Short Answer – 4 Marks)
**Question:**
*Why are Monitors considered superior to Semaphores for writing concurrent programs? Explain how a Monitor ensures mutual exclusion.*

**Answer:**
**Why Monitors are Superior (2 Marks):**
Semaphores are low-level tools that rely heavily on programmer discipline. A simple programming error—such as forgetting to call `signal()`, or calling `wait()` and `signal()` in the wrong order—can cause permanent deadlocks or race conditions. Monitors are superior because they are high-level, object-oriented language constructs (like in Java or C#) that abstract away the complex locking logic, significantly reducing human error.

**Ensuring Mutual Exclusion (2 Marks):**
A Monitor acts as a protective shell around shared data. The shared variables are kept private inside the monitor, and threads can only modify them by calling the monitor's synchronized methods. The monitor construct implicitly guarantees mutual exclusion: **only one thread is allowed to be active inside the monitor at any exact moment**. If a second thread tries to call a method while the first is inside, the language runtime automatically blocks the second thread and places it in an entry queue until the first thread exits.

### Quick Self-Check Key Points for Revision
- **Semaphore:** Integer `S`. `wait(S)` = S--, `signal(S)` = S++. Must be atomic.
- **Counting Semaphore:** Controls a finite pool of resources (e.g., 5 parking spots).
- **Busy-waiting vs Blocking:** Spinloops waste CPU. Blocking puts the thread to sleep in a queue.
- **Monitor:** Object-oriented safe box. Only 1 thread allowed inside its methods at a time.
- **Condition Variables:** Inside a monitor, `wait(c)` lets a thread safely go to sleep and *drop the monitor lock* so someone else can enter.
