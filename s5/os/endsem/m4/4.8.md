# 4.8 Allocation of Frames and Thrashing

---

## 1. Allocation of Frames

In a multiprogramming system, physical memory (frames) must be divided among multiple active processes. The OS must decide **how many frames to allocate to each process**.

### The Minimum Number of Frames
There is a hardware-defined minimum number of frames a process must have. If an instruction is 6 bytes long and spans across two pages, and it references a memory address that spans across another two pages, the process needs at least 4 frames just to execute that single instruction without immediately faulting.

### Allocation Algorithms
Once the minimum is met, how does the OS distribute the remaining frames?

1. **Equal Allocation:**
   - If there are 100 frames and 5 processes, give each process exactly 20 frames.
   - *Problem:* A tiny text editor gets 20 frames, while a massive 3D rendering program gets 20 frames (which is way too few for it).
2. **Proportional Allocation:**
   - Allocate frames based on the **size** of the process.
   - If Process A is 10 MB and Process B is 90 MB, out of 100 frames, Process A gets 10 frames and Process B gets 90 frames.

### Global vs. Local Allocation
When a page replacement is necessary (a process needs to swap a page out):
- **Global Replacement:** The OS allows Process A to select a replacement frame from the set of *all* frames, even if that frame is currently allocated to Process B. (Process A steals a frame from Process B). This is the most common approach because it maximizes overall system throughput.
- **Local Replacement:** Process A can only select a victim from its *own* set of allocated frames. It cannot steal from other processes.

## 2. Thrashing

Thrashing is one of the most severe performance problems that can occur in a paging system.

### What is Thrashing?
If a process does not have "enough" frames (it doesn't even have the minimum number of frames to hold its actively used pages), it will cause a page fault. It replaces a page, but because it needs all its pages actively, it will almost immediately need the replaced page back, causing another page fault.

- **Definition:** A system is **thrashing** if it is spending more time paging (swapping pages in and out of the disk) than actually executing user instructions.
- When thrashing occurs, CPU utilization completely collapses (often dropping to near 0%), and the system becomes incredibly slow and unresponsive.

[Click here to see the diagram of CPU Utilization vs Degree of Multiprogramming (The Thrashing Curve)](https://www.google.com/search?q=CPU+utilization+thrashing+degree+of+multiprogramming+diagram+OS&udm=2)

### The Cause of Thrashing
Thrashing is caused by the OS's CPU scheduler interacting poorly with the paging system (specifically under Global Replacement):
1. The CPU scheduler sees that CPU utilization is low.
2. To increase utilization, it increases the **degree of multiprogramming** by loading a new process into memory.
3. This new process needs frames, so it steals them from existing processes (Global Replacement).
4. The existing processes now don't have enough frames, so they start page faulting heavily.
5. They wait for the disk, so they drop out of the CPU.
6. CPU utilization drops even further.
7. The scheduler sees utilization drop, so it loads *even more* processes into memory.
8. **Result:** A vicious cycle where everyone is fighting for frames, the disk is running at 100%, and the CPU is doing absolutely nothing.

## 3. How to Prevent Thrashing (The Working-Set Model)

To prevent thrashing, the OS must provide each process with as many frames as it actually *needs* right now. But how does the OS know how many frames a process needs? 

It uses the principle of **Locality**.
- **Locality Model:** As a process executes, it moves from locality to locality. A locality is a set of pages that are actively used together (e.g., a function and its local variables). 
- If the OS allocates enough frames to hold the current locality, the process will not thrash.

### The Working-Set Model
The Working-Set model uses a parameter $\Delta$ (delta) to define a **working-set window** (e.g., $\Delta = 10,000$ recent memory references).
- The **Working Set ($WS$)** of a process is the set of pages referenced in the most recent $\Delta$ accesses.
- The size of the working set ($WSS_i$) is the number of frames process $i$ currently needs.
- Let $D = \sum WSS_i$ be the total demand for frames by all processes.

**The Thrashing Rule:**
- If the total demand $D$ is strictly less than the total available frames in physical memory ($D < \text{Frames}$), the system is healthy.
- If $D > \text{Frames}$, the system is heading into **Thrashing**.
- **The Fix:** The OS must suspend (swap out) one or more entire processes to the disk to reduce the degree of multiprogramming and free up frames until $D < \text{Frames}$ again.

## 4. Exam Questions & Answers

> **Note on Provided Question Papers:** The provided exams for Module 4 did not explicitly contain a standalone question on Thrashing. However, it is the capstone theory concept of Virtual Memory. Below are the standard expected questions for end-semester exams.

### Expected Question 1 (Medium Answer – 5 Marks)
**Question:**
*Define thrashing. Explain the vicious cycle that causes a system to enter a state of thrashing when using a global replacement algorithm.*

**Answer:**
**Definition (2 Marks):**
Thrashing is a severe performance degradation condition in a virtual memory system where the Operating System spends more time servicing page faults (swapping pages in and out from the disk) than executing actual process instructions. During thrashing, CPU utilization plummets dramatically.

**The Vicious Cycle (3 Marks):**
Thrashing typically occurs under a global page-replacement policy when the system is over-committed. The cycle is as follows:
1. A process page faults and steals a frame from another process.
2. The second process now lacks its actively used pages, so it also page faults and waits for the disk, yielding the CPU.
3. As more processes wait for the disk, the CPU utilization drops.
4. The OS Long-Term Scheduler monitors CPU utilization. Seeing it drop, it attempts to increase it by introducing new processes into memory (increasing the degree of multiprogramming).
5. These new processes steal even more frames from the existing processes, causing a massive explosion of page faults. The disk queue fills up, and the CPU does zero useful work.

---

### Expected Question 2 (Short Answer – 4 Marks)
**Question:**
*How does the Working-Set model help an operating system prevent thrashing?*

**Answer:**
The Working-Set model prevents thrashing by ensuring that the degree of multiprogramming is kept at a safe level based on the active memory demands of the processes (their "locality"). 

- The OS tracks the **Working Set** of each process: the set of pages it has actively accessed over the most recent time window ($\Delta$).
- The Working Set Size ($WSS$) represents the absolute minimum number of frames that process needs *right now* to avoid page faulting.
- The OS sums the $WSS$ of all active processes to find the total frame demand ($D$). 
- If $D$ exceeds the total physical frames available in RAM, the OS knows thrashing is imminent. To prevent it, the OS suspends (swaps out) one or more processes to the disk, freeing their frames to satisfy the working sets of the remaining processes.

### Quick Self-Check Key Points for Revision
- **Global Allocation:** Best performance, but processes steal frames from each other.
- **Thrashing Definition:** Paging $\gg$ Executing. 
- **Cause:** Degree of multiprogramming is too high $\rightarrow$ Processes steal frames $\rightarrow$ Endless page faults $\rightarrow$ CPU idles while waiting for disk.
- **Locality:** Code tends to use a specific cluster of pages for a period of time, then moves to another cluster.
- **Working-Set Model:** Track active pages ($\Delta$). If Total Active Demand > Physical RAM, suspend someone!
