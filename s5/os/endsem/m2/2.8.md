# 2.8 Inter-Process Communication (IPC): Shared Memory and Message Passing Systems

---

## 1. Introduction: Why do processes need to communicate?

Processes executing concurrently in an operating system can be either **independent** or **cooperating**.
- **Independent Process:** Does not share data with any other process. Its execution cannot affect or be affected by other processes.
- **Cooperating Process:** Can affect or be affected by other processes. They share data and state.

**Reasons for Process Cooperation:**
1. **Information Sharing:** Multiple users/applications may need access to the same piece of information (e.g., a shared file or database).
2. **Computation Speedup:** A large task can be broken into sub-tasks that run in parallel on multiple CPU cores.
3. **Modularity:** Dividing system functions into separate processes or threads (like the microkernel architecture).
4. **Convenience:** Even a single user may run multiple programs that need to talk to each other (e.g., copying text from a web browser and pasting it into a word processor).

To allow cooperating processes to exchange data, the operating system provides **Inter-Process Communication (IPC)** mechanisms. 

There are two primary models of IPC:
1. **Shared Memory**
2. **Message Passing**

## 2. Shared Memory Systems

### How it Works
In the shared-memory model, a region of memory is established that is **shared by multiple processes**. 
- Normally, the OS actively prevents one process from accessing another process's memory (for protection).
- To use shared memory, two or more processes must explicitly agree to remove this restriction. They ask the OS to map a specific region of physical RAM into both of their virtual address spaces.

### Execution Flow
1. **Setup:** Process A makes a system call to the OS to create a shared memory segment.
2. **Attach:** Process B makes a system call to attach that same segment to its own address space.
3. **Communication:** Once the memory is mapped, the OS is **completely out of the way**. Process A can write a variable to that memory, and Process B can instantly read it using standard pointer arithmetic.

### Advantages and Disadvantages
- **Advantages (Speed):** Shared memory is the **fastest** form of IPC. Because the OS is not involved in the actual data transfer (no system calls or context switches are needed after the initial setup), communication occurs at hardware RAM speeds.
- **Disadvantages (Synchronization):** Because both processes can read and write to the same memory simultaneously, they can easily overwrite each other's data, leading to **Race Conditions**. The programmers must manually implement complex **synchronization mechanisms** (like Mutexes and Semaphores—covered in Module 3) to ensure they don't access the memory at the exact same time.

## 3. Message Passing Systems

### How it Works
In the message-passing model, processes communicate by exchanging messages with each other **through the Operating System**. They do not share any memory.
- If Process A wants to communicate with Process B, it must send a message to the OS kernel. The OS kernel then safely delivers that message to Process B.

The IPC facility provides at least two basic system calls:
- `send(message)`
- `receive(message)`

### Characteristics of Message Passing
Message passing can be implemented in various ways:

**1. Direct vs. Indirect Communication:**
- **Direct:** Processes must explicitly name each other. 
  - `send(P, message)` – Send a message to process P.
  - `receive(Q, message)` – Receive a message from process Q.
- **Indirect:** Messages are sent to and received from **mailboxes** (or ports). Each mailbox has a unique ID. Process A writes to Mailbox X, and Process B reads from Mailbox X. This is much more flexible.

**2. Synchronization (Blocking vs. Non-blocking):**
Message passing system calls can be synchronous or asynchronous:
- **Blocking `send`:** The sending process is blocked (put to sleep) until the message is received by the receiver or the mailbox.
- **Non-blocking `send`:** The sending process hands the message to the OS and immediately resumes execution, regardless of whether the receiver has picked it up yet.
- **Blocking `receive`:** The receiver blocks until a message is available.
- **Non-blocking `receive`:** The receiver checks for a message. If one is there, it takes it; if not, it returns immediately with an "empty" flag and continues executing.

**3. Buffering:**
The OS maintains a temporary queue for messages being passed:
- **Zero capacity:** The queue length is 0. The sender *must* block until the receiver receives the message (rendezvous).
- **Bounded capacity:** The queue has a finite length $n$. If the queue is full, the sender must block.
- **Unbounded capacity:** The queue has infinite length. The sender never blocks.

### Advantages and Disadvantages
- **Advantages (Safety & Simplicity):** Message passing is extremely safe. There are no race conditions over shared variables, so explicit synchronization (locks) is not needed for the data itself. It is also the only way to communicate in **distributed systems** (over a network).
- **Disadvantages (Overhead):** It is much slower than shared memory. Every single `send` and `receive` requires a system call (a trap into the Kernel Mode), data copying from user space to kernel space, and context switching.

## 4. Comparison Table: Shared Memory vs. Message Passing

| Feature | Shared Memory | Message Passing |
| :--- | :--- | :--- |
| **Basic Mechanism** | Processes share a region of physical memory. | Processes exchange messages via the OS kernel. |
| **OS Involvement** | OS is only involved during initial setup. | OS is involved in every single data transfer. |
| **Speed** | Extremely fast (hardware RAM speed). | Slower (requires system calls & context switches). |
| **Synchronization** | Manual. Programmers must use locks/semaphores. | Automatic. Handled by the OS message queues. |
| **Best Used For** | Large amounts of data on a single machine. | Small amounts of data, or over a network (distributed). |

## 5. Exam Questions & Answers

> **Note on Provided Question Papers:** The provided exams for Module 2 heavily focused on Process Creation (C programs) and CPU Scheduling calculations. However, IPC is a fundamental theory topic in the syllabus. Below are expected standard exam questions for this topic.

### Expected Question 1 (Medium Answer – 6 Marks)
**Question:**
*Describe the two fundamental models of Inter-Process Communication (IPC). Compare them in terms of operating system overhead and synchronization.*

**Answer:**
The two fundamental models of IPC are **Shared Memory** and **Message Passing**.

**1. Shared Memory:**
- **Mechanism:** Two or more processes ask the OS to map a common region of physical RAM into their private virtual address spaces. Once mapped, they communicate by simply reading and writing to this shared memory area using standard variables/pointers.
- **OS Overhead:** Very low. The OS is only involved in the initial creation of the shared segment. Subsequent communication bypasses the OS entirely, making it extremely fast.
- **Synchronization:** The OS provides no built-in synchronization. If Process A writes while Process B reads, data corruption (race conditions) occurs. Programmers must manually implement synchronization tools (like mutex locks or semaphores) to protect the shared data.

**2. Message Passing:**
- **Mechanism:** Processes do not share any memory. Instead, they communicate by sending messages to the OS kernel, which then forwards them to the receiving process (using `send()` and `receive()` system calls).
- **OS Overhead:** High. Every single message exchange requires a system call, trapping into kernel mode, and copying data from user space to kernel space and back. 
- **Synchronization:** It is inherently synchronized by the OS. A receiver can block until a message arrives, and no race conditions occur over the data payload because the OS handles the data transfer securely.

---

### Expected Question 2 (Short Answer – 4 Marks)
**Question:**
*In a Message Passing system, explain the difference between direct and indirect communication, and define blocking vs. non-blocking synchronization.*

**Answer:**
**Direct vs. Indirect Communication (2 Marks):**
- **Direct Communication:** Processes must explicitly name the sender or receiver (e.g., `send(Process_B, msg)`). This creates a hard-coded link between two specific processes.
- **Indirect Communication:** Messages are sent to and received from an intermediary structure called a **mailbox** or **port** (e.g., `send(Mailbox_A, msg)`). This is more flexible, as multiple processes can read from or write to the same mailbox.

**Blocking vs. Non-blocking (2 Marks):**
- **Blocking (Synchronous):** The sending process halts execution until the message is received by the receiver or mailbox. A blocking receiver halts execution until a message is available.
- **Non-blocking (Asynchronous):** The sending process hands the message to the OS and immediately continues executing its next line of code. A non-blocking receiver checks for a message and retrieves it if available, or returns immediately with a "null" status if the queue is empty.

### Quick Self-Check Key Points for Revision
- **Why IPC?** Information sharing, computation speedup, modularity.
- **Shared Memory:** Setup by OS $\rightarrow$ then OS gets out of the way. **Fastest**. Requires manual synchronization (locks) to prevent Race Conditions.
- **Message Passing:** Data goes *through* the OS via `send()` and `receive()`. **Slower** (kernel traps + copying data). Naturally synchronized. Great for networks.
- **Blocking = Synchronous:** "I will wait here until you take my message."
- **Non-Blocking = Asynchronous:** "I dropped off the message, I'm going back to work now."
