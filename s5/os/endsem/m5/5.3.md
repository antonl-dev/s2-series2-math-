# 5.3 File System Implementation and Directory Implementation

---

## 1. File System Implementation

To store files permanently, the Operating System uses physical storage devices (primarily Hard Disks or SSDs). The OS must translate the logical user concept of a "file" (a named collection of bytes) into physical disk sectors.

The part of the OS responsible for this is the **File System**.

### Layered Architecture of a File System
The file system is highly complex, so it is implemented in a layered, modular structure:

1. **Application Programs:** Make logical requests like `open("file.txt")`.
2. **Logical File System:** Manages metadata (attributes, directory structures, and file control blocks). It translates a file name into a file identifier (like an inode number) and passes it down.
3. **File-Organization Module:** Knows about files and their logical blocks. It translates logical block addresses (e.g., Block 5 of the file) into physical disk block addresses (e.g., Sector 1024 on Track 5).
4. **Basic File System:** Issues generic commands to the appropriate device driver to read/write specific physical blocks on the disk.
5. **I/O Control (Device Drivers):** The lowest layer. It contains hardware-specific code that communicates directly with the physical disk controller (e.g., sending electrical signals to move a magnetic read/write head).

### On-Disk and In-Memory Structures
To manage the file system efficiently, the OS maintains data structures both on the disk (persistent) and in RAM (volatile, for speed).

**On-Disk Structures:**
- **Boot Control Block:** Contains info needed by the system to boot an OS from that specific disk volume (e.g., the MBR or partition boot sector).
- **Volume Control Block (Superblock):** Contains details about the entire partition, such as the total number of blocks, number of free blocks, block size, and free-block pointers.
- **Directory Structure:** Organizes the files (maps file names to file control blocks).
- **File Control Block (FCB):** In UNIX, this is called an **inode**. Every single file has one FCB on the disk. It contains all the file's metadata (permissions, dates, size) and pointers to the physical data blocks where the file's contents actually live.

**In-Memory Structures (Loaded into RAM when OS boots/runs):**
- **System-wide Open-File Table:** Contains a copy of the FCB of *every* file currently opened by *any* process in the system.
- **Per-process Open-File Table:** An array managed by each running process. Each entry points to a specific row in the System-wide table. (When a C program calls `open()`, it gets an integer called a file descriptor, which is just the index into this per-process table).

## 2. Directory Implementation

A directory is a symbol table that translates human-readable file names into their corresponding file identifiers (like inode numbers or FCB pointers). 

When a user types `cat report.txt`, the OS must search the directory to find the FCB for `report.txt`. Because directory searches are performed constantly, the choice of directory implementation drastically affects overall system performance.

There are two primary ways to implement a directory structure under the hood:

### 1. Linear List
The simplest method of implementing a directory is to use a linear list (an array or linked list) of file names with pointers to the data blocks.
- **How it works:** To create a new file, the OS searches the list to ensure no file with that name already exists, and then adds a new entry to the end of the list. To delete a file, it searches for the name and removes the entry.
- **Pros:** Incredibly simple to program.
- **Cons:** **Extremely slow.** Finding a file requires a linear search ($O(N)$ time complexity). If a directory contains 10,000 files, the OS must compare string names 10,000 times just to find a file.

*(Optimization: Many OSes use a sorted linked list or binary search to speed this up, but maintaining the sorted order when creating/deleting files adds overhead).*

### 2. Hash Table
To overcome the massive performance bottleneck of a linear search, modern operating systems implement directories using a **Hash Table**.
- **How it works:** A linear list stores the actual directory entries, but a hash data structure is built on top of it. The hash function takes the file name (e.g., `report.txt`), computes a mathematical hash, and instantly returns a pointer to the exact location of that file in the linear list.
- **Pros:** **Lightning fast.** Searching for a file takes $O(1)$ constant time, completely independent of how many thousands of files are in the directory.
- **Cons:**
  - **Collisions:** Two different file names might mathematically hash to the exact same index. The OS must handle this (usually by attaching a linked list to that hash index).
  - **Fixed Size:** Hash tables generally require a fixed size. If the directory grows massive and exceeds the hash table size, the OS must perform an expensive operation to resize and re-hash the entire directory.

## 3. Exam Questions & Answers

> **Note on Provided Question Papers:** The exams for Module 5 focused on File Attributes/Access (`5.1/5.2`) and Storage Hardware (`5.5`). However, File System structures and Directory implementations are highly standard end-semester theoretical questions. Below are the expected questions for this topic.

### Expected Question 1 (Medium Answer – 6 Marks)
**Question:**
*Explain the purpose of a File Control Block (FCB). Describe the difference between the System-wide open-file table and the Per-process open-file table in a file system implementation.*

**Answer:**
**Purpose of File Control Block (FCB) (2 Marks):**
A File Control Block (known as an *inode* in UNIX systems) is an on-disk data structure that contains all critical metadata associated with a specific file. While the file's actual data is stored in data blocks, the FCB contains the file's permissions, ownership, size, timestamps, and most importantly, the physical pointers indicating exactly which disk blocks contain the file's data.

**System-wide vs. Per-process Open-File Tables (4 Marks):**
To avoid constantly reading the slow hard disk, the OS brings file metadata into RAM when a file is opened using two tables:
1. **System-wide open-file table:** Maintained globally by the OS kernel. It contains a copy of the FCB for every single file currently opened by *any* process in the entire system. It also tracks how many different processes currently have that file open (the open count).
2. **Per-process open-file table:** Maintained individually for every active process. It is an array of pointers (file descriptors). When a process opens a file, an entry is added to this local table, which simply points to the corresponding entry in the global System-wide table. This structure allows processes to safely share access to a single physical file without duplicating metadata in RAM.

### Expected Question 2 (Short Answer – 4 Marks)
**Question:**
*Discuss two common methods used for Directory Implementation. What is the major performance drawback of the linear list method?*

**Answer:**
**Two Common Methods (3 Marks):**
1. **Linear List:** The directory is implemented as a simple array or linked list of file names and pointers. To create, find, or delete a file, the OS must linearly scan the list. It is very simple to implement but computationally inefficient.
2. **Hash Table:** The directory uses a mathematical hash function to map a human-readable file name directly to a specific index in a table. This allows the OS to find file pointers almost instantly in $O(1)$ time, but it requires handling hash collisions and fixed table sizes.

**Major Performance Drawback (1 Mark):**
The major drawback of the linear list method is its **slow search time ($O(N)$)**. In a large directory containing thousands of files, finding a file or verifying a new file name is unique requires the CPU to perform thousands of slow string comparisons, severely degrading file system performance.

### Quick Self-Check Key Points for Revision
- **FCB (File Control Block / inode):** The disk structure holding a file's metadata and pointers to its data blocks.
- **Open File Tables:** Keep FCB copies in RAM so the OS doesn't have to hit the slow disk for every `read/write`. 
- **System-wide table:** One global list of all open files.
- **Per-process table:** Your process's personal list of pointers (File Descriptors) pointing to the global list.
- **Directory Implementation:** 
  - **Linear List:** Slow $O(N)$ search. Easy to code.
  - **Hash Table:** Fast $O(1)$ search. Harder to code (collisions).
