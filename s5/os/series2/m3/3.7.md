# 3.7 Deadlock Detection and Recovery

If a system does not employ deadlock prevention or deadlock avoidance algorithms, then a deadlock situation may occur. In this environment, the system must provide:
1.  An algorithm that examines the state of the system to determine whether a deadlock has occurred (**Deadlock Detection**).
2.  An algorithm to recover from the deadlock (**Deadlock Recovery**).

---

## 1. Deadlock Detection
The detection method depends on whether the resource types have a single instance or multiple instances.

### A. Single Instance of Each Resource Type: The Wait-For Graph
If all resources have only a single instance, we can define a deadlock detection algorithm that uses a variant of the Resource-Allocation Graph (RAG) called a **Wait-For Graph**.
*   We obtain the wait-for graph from the RAG by removing the resource nodes and collapsing the appropriate edges.
*   An edge from $P_i \rightarrow P_j$ exists in a wait-for graph if and only if the corresponding RAG contains two edges $P_i \rightarrow R_q$ and $R_q \rightarrow P_j$. 
*   This edge $P_i \rightarrow P_j$ simply means that process $P_i$ is waiting for process $P_j$ to release a resource.
*   **Detection:** A deadlock exists in the system if and only if the wait-for graph contains a **cycle**. The OS must maintain this graph and periodically invoke an algorithm that searches for a cycle.

### B. Multiple Instances of a Resource Type: Detection Algorithm
If resources have multiple instances, the wait-for graph is not sufficient. We use an algorithm similar to Banker's Algorithm.
*   We don't use a "Max" or "Need" matrix because in this environment, processes don't declare their maximum needs in advance.
*   Instead, we use a **Request** matrix of size $n \times m$, where `Request[i][j]` indicates how many more instances of resource $R_j$ process $P_i$ is currently asking for.
*   **The Logic:** The algorithm assumes that any process that is *not* currently waiting for resources will finish its task and return its currently allocated resources to the system. It simulates this. If, at the end of the simulation, there are still processes that couldn't finish (Finish[i] == false), those processes are deadlocked.

---

## 2. Deadlock Recovery
When a detection algorithm determines that a deadlock exists, the system must break the deadlock. There are two primary approaches: **Process Termination** and **Resource Preemption**.

### A. Process Termination
To eliminate deadlocks by terminating processes, the OS uses one of two methods:
1.  **Abort all deadlocked processes:** This breaks the deadlock cycle but comes at a high cost. These processes may have computed for a long time, and the results of these partial computations must be discarded and recomputed later.
2.  **Abort one process at a time until the deadlock cycle is eliminated:** This has high overhead because, after each process is aborted, a deadlock-detection algorithm must be invoked to determine whether any processes are still deadlocked.
    *   *Which process to abort first?* We should abort the one whose termination incurs the minimum cost (e.g., process priority, how long it has computed, how many resources it holds, how many more it needs).

### B. Resource Preemption
To eliminate deadlocks using resource preemption, we successively preempt (take away) some resources from processes and give these resources to other processes until the deadlock cycle is broken. Three issues need to be addressed:
1.  **Selecting a Victim:** Which resources and which processes are to be preempted? As with process termination, we must determine the order of preemption to minimize cost.
2.  **Rollback:** If we preempt a resource from a process, what should be done with that process? It cannot continue its normal execution. We must roll back the process to some safe state and restart it from that state. (Usually, this just means completely aborting and restarting the process).
3.  **Starvation:** How do we ensure that starvation will not occur? That is, how can we guarantee that resources will not always be preempted from the *same* process? (Usually solved by including the number of rollbacks in the cost factor).

## Exam Questions & Answers for Module 3.7

### Q1. Explain how an operating system detects a deadlock. Describe the strategies used to recover from a deadlock. (Question 11)
**Answer:**
**Deadlock Detection:**
The OS detects deadlocks depending on the number of instances of resources:
1.  **Single Instance Resources:** The OS converts the Resource-Allocation Graph (RAG) into a **Wait-For Graph** by removing resource nodes and connecting a requesting process directly to the process holding the required resource. The OS periodically runs a cycle-detection algorithm (like Depth-First Search) on this graph. If a cycle is found, a deadlock exists.
2.  **Multiple Instance Resources:** The OS uses a Detection Algorithm that utilizes `Available`, `Allocation`, and `Request` matrices. It simulates the execution by finding a process whose current `Request` is less than or equal to the `Available` resources. It pretends to allocate the resources, let the process finish, and add its `Allocation` back to `Available`. If, after looping through all processes, some processes are left unable to finish, those specific processes are deadlocked.

**Recovery Strategies:**
Once a deadlock is detected, the OS can recover using two main strategies:
1.  **Process Termination:**
    *   *Abort all deadlocked processes:* Fast and definitive, but wastes all the computation done by those processes up to that point.
    *   *Abort one process at a time:* Abort a process, then run the detection algorithm again. Repeat until the cycle breaks. The OS selects a victim based on factors like priority, CPU time used, and resources held.
2.  **Resource Preemption:**
    *   Forcibly take resources away from one or more deadlocked processes and give them to others until the cycle breaks. 
    *   This requires **Selecting a victim** (minimizing cost), performing a **Rollback** (restarting the victim process from a safe state or the beginning), and preventing **Starvation** (ensuring the same process isn't constantly picked as the victim).
