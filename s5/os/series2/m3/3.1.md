# 3.1 Concurrency - Threads, Single-threaded and Multithreaded Programming, Thread API

## 1. Introduction to Threads
A **thread** is the basic unit of CPU utilization; it is sometimes called a lightweight process (LWP). 
Traditionally, a process has a single thread of control. If a process has multiple threads of control, it can perform more than one task at a time.

### What does a Thread consist of?
Each thread has its own:
1.  **Thread ID**
2.  **Program Counter (PC)** (tracks the next instruction to execute)
3.  **Register Set** (holds current working variables)
4.  **Stack** (contains local variables and function call history)

### What do Threads share within the same Process?
Threads belonging to the same process share:
1.  **Code section** (executable instructions)
2.  **Data section** (global variables)
3.  **Other OS resources** (such as open files and signals)

## 2. Single-Threaded vs. Multithreaded Programming
*   **Single-threaded process:** Can perform only one task at a time. For example, if a single-threaded word processor is formatting text, it cannot simultaneously accept user input.
*   **Multithreaded process:** Can perform multiple tasks concurrently. A web browser might have one thread display images or text while another thread retrieves data from the network.

### Benefits of Multithreading
1.  **Responsiveness:** Multithreading allows a program to continue running even if part of it is blocked or performing a lengthy operation (e.g., UI remains responsive while a background thread downloads a file).
2.  **Resource Sharing:** Threads share the memory and resources of the process to which they belong by default. This is easier and more efficient than using shared memory or message passing between separate processes.
3.  **Economy:** Allocating memory and resources for process creation is costly. Because threads share resources, it is much more economical to create and context-switch threads than processes.
4.  **Scalability:** The benefits of multithreading can be greatly increased in a multiprocessor architecture, where threads may be running in parallel on different processing cores.

## 3. Types of Threads: User-Level vs Kernel-Level

### User-Level Threads (ULT)
*   **Management:** Managed entirely by a user-level thread library (e.g., POSIX Pthreads, Mach C-threads).
*   **Kernel Knowledge:** The OS kernel is unaware of user-level threads; it only recognizes the single process containing them.
*   **Advantages:** Fast to create and manage. Context switching does not require hardware or kernel intervention.
*   **Disadvantages:** If one user-level thread performs a blocking system call (like reading a file), the kernel blocks the entire process, effectively blocking all other threads in that process.

### Kernel-Level Threads (KLT)
*   **Management:** Supported and managed directly by the Operating System.
*   **Kernel Knowledge:** The kernel creates, schedules, and manages these threads.
*   **Advantages:** If one thread blocks, the kernel can schedule another thread from the same process. True parallelism can be achieved on multiprocessor systems.
*   **Disadvantages:** Creating and managing them is slower than user-level threads because it requires a mode switch to the kernel.

---

## 4. Multithreading Models
To execute programs, a relationship must exist between user threads and kernel threads. There are three common ways of establishing this relationship:

### 1. Many-to-One Model
Maps many user-level threads to one kernel thread.
*   **Advantages:** Efficient thread management since it's done in user space.
*   **Limitations:** The entire process blocks if a thread makes a blocking system call. Multiple threads cannot run in parallel on multiprocessors because only one kernel thread can access the CPU at a time.

### 2. One-to-One Model
Maps each user thread to a kernel thread. (Used by Linux and Windows).
*   **Advantages:** Provides more concurrency. Allows another thread to run when a thread makes a blocking system call. Multiple threads can run in parallel on multiprocessors.
*   **Limitations:** Creating a user thread requires creating the corresponding kernel thread, which adds overhead. Systems usually restrict the number of threads supported.

### 3. Many-to-Many Model
Multiplexes many user-level threads to a smaller or equal number of kernel threads.
*   **Advantages:** Developers can create as many user threads as necessary. The corresponding kernel threads can run in parallel on a multiprocessor. If a thread blocks, the kernel can schedule another thread.

## 5. Thread API (POSIX Pthreads Overview)
*Pthreads* refers to the POSIX standard defining an API for thread creation and synchronization.
*   `pthread_create()`: Creates a new thread and makes it executable.
*   `pthread_join()`: Suspends the execution of the calling thread until the specified target thread terminates.
*   `pthread_exit()`: Terminates the calling thread.

### Q1. Define a thread.
**Answer:**
A thread is the basic execution unit of a CPU, often referred to as a lightweight process. It comprises a thread ID, a program counter, a register set, and a stack. Threads within the same process share the code section, data section, and operating system resources (like open files and signals). It allows a single process to perform multiple tasks concurrently.

### Q2. Compare user-level threads and kernel-level threads. (Question 1a)
**Answer:**
| Feature | User-Level Threads (ULT) | Kernel-Level Threads (KLT) |
| :--- | :--- | :--- |
| **Implementation** | Implemented and managed by user-level libraries. | Supported and managed directly by the OS kernel. |
| **OS Recognition** | The OS kernel is unaware of them. | The OS kernel recognizes and schedules them. |
| **Context Switching** | Fast, as it does not require OS intervention (no mode switch). | Slower, as it requires an OS mode switch to kernel mode. |
| **Blocking** | If one thread is blocked, the entire process and all its threads are blocked. | If one thread is blocked, the kernel can schedule another thread of the same process. |
| **Multiprocessing** | Cannot utilize multiple CPUs (true parallelism is not possible). | Can utilize multiple CPUs; different threads can run on different processors simultaneously. |

---

### Q3. How does a thread differ from a process? (Question 1b)
**Answer:**
| Feature | Process | Thread |
| :--- | :--- | :--- |
| **Definition** | An executing instance of a program (Heavyweight). | A segment/unit of a process (Lightweight). |
| **Resource Allocation** | Requires separate memory space and resources. | Shares memory space and resources with sibling threads. |
| **Context Switching** | Slow and expensive due to heavy CPU overhead. | Faster and less expensive as less state information is saved. |
| **Communication** | Requires Inter-Process Communication (IPC) like pipes, shared memory. | Easier, threads can communicate directly through shared memory/variables. |
| **Isolation** | Isolated. A crash in one process does not affect others. | Not isolated. A crash in one thread can crash the entire process. |

---

### Q4. Compare single-threaded and multithreaded processes. (Question 1c)
**Answer:**
| Feature | Single-threaded Process | Multithreaded Process |
| :--- | :--- | :--- |
| **Execution** | Contains only one sequence of execution (one thread of control). | Contains multiple execution sequences (multiple threads). |
| **Responsiveness** | If the thread blocks, the entire application becomes unresponsive. | If one thread blocks, others continue running, keeping the application responsive. |
| **Resource Utilization** | Only utilizes a single CPU core, regardless of how many are available. | Can utilize multiple CPU cores, achieving true parallelism. |
| **Performance** | Slower for complex, parallelizable tasks. | Faster for tasks that can be divided into parallel sub-tasks. |
| **Example** | Simple traditional MS-DOS programs. | Modern Web Browsers, Word Processors. |

### Q5. Compare the structure of the Many-to-One, One-to-One and Many-to-Many multithreading models. State the advantages and limitations of each. (Question 2)
**Answer:**

**1. Many-to-One Model:**
*   **Structure:** Maps many user-level threads to one single kernel thread.
*   **Advantages:** Thread management is very efficient because it is done entirely in the user space by the thread library.
*   **Limitations:** If one user thread makes a blocking system call, the whole process blocks. Also, it cannot take advantage of multiple processors because only one thread can access the kernel at a time.

**2. One-to-One Model:**
*   **Structure:** Maps exactly one user-level thread to one kernel-level thread.
*   **Advantages:** Provides high concurrency. If one thread blocks, another can run. It allows true parallel execution on multiprocessor systems.
*   **Limitations:** The overhead of creating a kernel thread for every user thread can burden the performance of the system. Operating systems often place a limit on the number of threads that can be created.

**3. Many-to-Many Model:**
*   **Structure:** Multiplexes many user-level threads to a smaller or equal number of kernel threads.
*   **Advantages:** Combines the best of both worlds. Developers can create as many user threads as they want without restricting concurrency, and the kernel can schedule them in parallel on multiple processors. Blocking one thread doesn't block the process.
*   **Limitations:** It is complex to implement and manage.
