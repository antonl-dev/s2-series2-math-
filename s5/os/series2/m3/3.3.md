# 3.3 Semaphores, Critical Regions, and Monitors

## 1. Semaphores
A **Semaphore** is a robust synchronization tool provided by the operating system that does not require busy waiting (in its optimized implementation). 
Fundamentally, a semaphore `S` is an integer variable that, apart from initialization, is accessed only through two standard **atomic** operations: `wait()` and `signal()`.

*   **wait(S):** Originally termed `P` (from the Dutch *proberen*, to test). If the semaphore value is > 0, it decrements it and proceeds. If it is 0, the process blocks/waits.
*   **signal(S):** Originally termed `V` (from the Dutch *verhogen*, to increment). It increments the semaphore value, potentially waking up a waiting process.

### Types of Semaphores
1.  **Binary Semaphore:** The integer value can range only between 0 and 1. It behaves exactly like a mutex lock and is used to solve the critical-section problem.
2.  **Counting Semaphore:** The integer value can range over an unrestricted domain. It is used to control access to a given resource consisting of a finite number of instances (e.g., controlling access to 5 printers).
    *   Initialization: Initialized to the number of available resources.
    *   When a process wants a resource, it calls `wait()` (decreases count).
    *   When a process releases a resource, it calls `signal()` (increases count).

### Semaphore Implementation (Avoiding Busy Waiting)
To overcome the waste of CPU cycles from "spinning" (busy waiting), semaphores can be implemented using block/wakeup mechanisms.
A semaphore becomes a C `struct` consisting of an integer value and a pointer to a queue of waiting processes.
*   When a process executes `wait()` and the value is $\le 0$, it adds itself to the waiting queue and invokes the `block()` OS system call to suspend itself.
*   When another process executes `signal()`, it increments the value. If there are processes in the waiting queue, it removes one and invokes the `wakeup()` system call to resume its execution.

## 2. Critical Regions (Conditional Critical Regions)
While semaphores are powerful, they are prone to programmer errors (e.g., writing `signal()` instead of `wait()`, or forgetting them altogether, leading to deadlocks or broken mutual exclusion).
A **Critical Region** is a high-level language construct that protects shared variables. 
*   Variables declared as `shared` can only be accessed within a specific `region v when B do S` statement. 
*   This ensures the compiler handles the synchronization, preventing the programmer from accidentally accessing shared data outside of a protected zone.

---

## 3. Monitors
A **Monitor** is a high-level synchronization construct (an abstract data type) that provides a convenient and effective mechanism for process synchronization.
*   **Encapsulation:** A monitor encapsulates shared data structures, initialization code, and the procedures (methods) that operate on that shared data.
*   **Automatic Mutual Exclusion:** The defining characteristic of a monitor is that **only one process can be active within the monitor at a time**. The programmer does not need to explicitly code synchronization logic (like mutexes) for the monitor's methods.

### Condition Variables in Monitors
Sometimes, a process inside a monitor realizes it cannot proceed (e.g., a buffer is empty). It needs to wait, but it must also release the monitor's lock so other processes can enter. To handle this, monitors use **Condition Variables**.
*   A condition variable `x` can only be manipulated using two operations: `x.wait()` and `x.signal()`.
*   **`x.wait()`:** The process invoking this operation is suspended until another process invokes `x.signal()`. It temporarily releases the monitor lock.
*   **`x.signal()`:** Resumes exactly one suspended process. If no process is suspended, the signal does nothing.

## Exam Questions & Answers for Module 3.3

### Q1. a. What is a semaphore? Explain how semaphores are used to synchronize processes. (Question 8a)
**Answer:**
A **semaphore** is an integer variable used by the operating system to manage concurrent processes and solve the critical section problem. It is accessed exclusively through two atomic operations: `wait()` (decrement) and `signal()` (increment).

**How they synchronize processes:**
1.  **Mutual Exclusion (Binary Semaphore):** Initialized to 1. Before entering the critical section, a process calls `wait(S)` (making it 0). If another process tries to enter, `wait(S)` will block it because the value is not > 0. When the first process finishes, it calls `signal(S)` (making it 1), allowing the next process to enter.
2.  **Execution Ordering:** If Process P2 must wait for Process P1 to execute Statement A before executing Statement B, we initialize a semaphore `sync` to 0. 
    *   In P1: Execute Statement A, then call `signal(sync)`.
    *   In P2: Call `wait(sync)`, then execute Statement B. 
    P2 is forced to wait until P1 signals.

### Q2. b. Show how a semaphore can solve the critical-section problem while meeting all its requirements. (Question 8b)
**Answer:**
We use a binary semaphore `mutex` initialized to 1.
The structure of process $P_i$ is:
```c
do {
    wait(mutex);
    
    /* Critical Section */
    
    signal(mutex);
    
    /* Remainder Section */
} while (true);
```
**Meeting the requirements:**
1.  **Mutual Exclusion:** Since `mutex` is initially 1, only the first process executing `wait(mutex)` successfully changes it to 0 and enters. Any subsequent process executing `wait(mutex)` will block because the value is 0. Thus, only one process enters at a time.
2.  **Progress:** If no process is in the critical section, `mutex` is 1. Any process wishing to enter can execute `wait(mutex)` without being blocked by processes in their remainder sections.
3.  **Bounded Waiting:** When implemented with a waiting queue (FIFO), a process that is blocked on `wait()` is added to the end of the queue. When a process leaves and calls `signal()`, the process at the front of the queue is awakened. This guarantees that no process waits indefinitely (no starvation).

### Q3. c. "Although a semaphore operation is made up of a sequence of instructions, a semaphore still guarantees mutual exclusion." Justify this statement. (Question 8c)
**Answer:**
The statement is justified because the OS guarantees that the `wait()` and `signal()` operations are **atomic** (indivisible). 
Even though `wait(S)` involves reading `S`, checking if it is $\le 0$, and decrementing `S` (which takes multiple machine instructions), the OS ensures that once a process starts executing `wait()` or `signal()`, no other process can interrupt it or access the same semaphore until the operation completes. In multiprocessor systems, this atomicity is usually enforced using hardware instructions like `test_and_set()` or `compare_and_swap()` at the kernel level to lock the semaphore's internal data structure. Because the operations themselves cannot be interleaved, race conditions on the semaphore variable are prevented, thereby guaranteeing mutual exclusion for the critical sections they protect.

### Q4. A counting semaphore was initialized to 10. Then 6 P (wait) operations and 4 V (signal) operations were completed on this semaphore. The resulting value of the semaphore is? (CO3 Assessment Question)
**Answer:**
*   Initial value of semaphore (S) = 10
*   A `P` or `wait` operation **decrements** the semaphore by 1. Therefore, 6 P operations = -6.
*   A `V` or `signal` operation **increments** the semaphore by 1. Therefore, 4 V operations = +4.
*   Resulting value = 10 - 6 + 4 = **8**.

### Q5. The following two functions P1 and P2 that share a variable B with an initial value of 2 execute concurrently. (CO3 Assessment Question)
```c
P1( ) {               P2( ) {
  C = B – 1;            D = 2 * B;
  B = 2 * C;            B = D - 1;
}                     }
```
**The number of distinct values that B can possibly take after the execution is?**
**Answer:**
Because they execute concurrently without synchronization, the instructions can be interleaved in different ways. B is initially 2.
Let's break down the assembly-level steps:
*   P1.1: Read B, Calculate C = B - 1
*   P1.2: Calculate 2 * C, Write to B
*   P2.1: Read B, Calculate D = 2 * B
*   P2.2: Calculate D - 1, Write to B

**Scenario 1: P1 executes completely, then P2**
*   P1: C = 2-1 = 1; B = 2*1 = 2. (B is now 2)
*   P2: D = 2*2 = 4; B = 4-1 = 3. (Final B = 3)

**Scenario 2: P2 executes completely, then P1**
*   P2: D = 2*2 = 4; B = 4-1 = 3. (B is now 3)
*   P1: C = 3-1 = 2; B = 2*2 = 4. (Final B = 4)

**Scenario 3: Interleaved (P1 reads, P2 reads & finishes, P1 finishes)**
*   P1.1 reads B=2. C = 1. (Context switch)
*   P2.1 reads B=2. D = 4. 
*   P2.2 writes B = 3.
*   P1.2 writes B = 2*1 = 2. (Final B = 2)

**Scenario 4: Interleaved (P2 reads, P1 reads & finishes, P2 finishes)**
*   P2.1 reads B=2. D = 4. (Context switch)
*   P1.1 reads B=2. C = 1.
*   P1.2 writes B = 2.
*   P2.2 writes B = 4 - 1 = 3. (Final B = 3)

The possible final values for B are **2, 3, and 4**. 
Therefore, the number of distinct values that B can take is **3**.
