# 3.5 Deadlocks – System Model, Deadlock Characterization, and Methods for Handling Deadlocks

## 1. Introduction to Deadlock
A **Deadlock** is a situation where a set of processes are blocked because each process is holding a resource and waiting for another resource acquired by some other process in the same set. Because every process is waiting, none of them can proceed, release their resources, or wake up.

## 2. System Model
To understand deadlocks, we model the system as a collection of **processes** ($P_1, P_2, ..., P_n$) and a collection of **resource types** ($R_1, R_2, ..., R_m$). 
*   Resource types can include CPU cycles, memory space, files, and I/O devices (like printers or mutex locks).
*   A resource type can have multiple **instances** (e.g., a system with 2 identical printers has 2 instances of the printer resource).

Under normal operation, a process may utilize a resource in the following sequence:
1.  **Request:** The process requests the resource. If it cannot be granted immediately (e.g., it is held by another process), the requesting process must wait.
2.  **Use:** The process operates on the resource.
3.  **Release:** The process releases the resource, making it available for others.

---

## 3. Deadlock Characterization (The Four Necessary Conditions)
A deadlock situation can arise if and only if the following **four conditions** hold simultaneously in a system. These are known as the Coffman conditions:

1.  **Mutual Exclusion:** At least one resource must be held in a non-sharable mode. That is, only one process at a time can use the resource. If another process requests that resource, it must be delayed until the resource is released.
2.  **Hold and Wait:** A process must be holding at least one resource and waiting to acquire additional resources that are currently being held by other processes.
3.  **No Preemption:** Resources cannot be preempted; that is, a resource can be released only voluntarily by the process holding it, after that process has completed its task. The OS cannot force the process to give it up.
4.  **Circular Wait:** There must exist a set $\{P_0, P_1, ..., P_n\}$ of waiting processes such that $P_0$ is waiting for a resource held by $P_1$, $P_1$ is waiting for a resource held by $P_2$, ..., $P_{n-1}$ is waiting for a resource held by $P_n$, and $P_n$ is waiting for a resource held by $P_0$.

*(Note: All four conditions must be present for a deadlock to occur. If we can prevent even one of these from happening, we can prevent deadlocks).*

### Resource-Allocation Graph (RAG)
Deadlocks can be described precisely using a directed graph called a system resource-allocation graph.
*   **Vertices:** Processes (represented by circles) and Resources (represented by squares, with dots inside indicating instances).
*   **Edges:** 
    *   *Request Edge:* A directed edge $P_i \rightarrow R_j$ means process $P_i$ has requested an instance of $R_j$ and is waiting.
    *   *Assignment Edge:* A directed edge $R_j \rightarrow P_i$ means an instance of $R_j$ has been allocated to $P_i$.

**Graph rules for deadlocks:**
*   If the graph contains **no cycles**, then **no deadlock** exists.
*   If the graph contains **a cycle**:
    *   If each resource type has exactly *one instance*, then a deadlock **has occurred**.
    *   If each resource type has *several instances*, then a deadlock **may or may not** exist (a cycle is a necessary but not sufficient condition here).

## 4. Methods for Handling Deadlocks
Generally, operating systems deal with the deadlock problem in one of three ways:

1.  **Deadlock Prevention & Avoidance:** Use protocols to ensure that the system will *never* enter a deadlock state. 
    *   **Prevention:** Ensures that at least one of the four necessary conditions cannot hold.
    *   **Avoidance:** Requires the OS to be given additional information in advance concerning which resources a process will request. The OS then decides whether granting a request will leave the system in a "safe state."
2.  **Deadlock Detection & Recovery:** Allow the system to enter a deadlock state, detect that a deadlock has occurred, and then recover from it (e.g., by aborting processes or preempting resources).
3.  **The Ostrich Algorithm (Ignore the problem):** Pretend that deadlocks never occur in the system. If a deadlock happens, the system might freeze, and the user must manually restart it. *(This is surprisingly the method used by most general-purpose operating systems, including Linux and Windows, because deadlocks are rare and the cost of prevention/avoidance is too high for everyday use).*

### Q1. Define Deadlock. Describe the system model for resource allocation.
**Answer:**
A **deadlock** is a state in which two or more processes are indefinitely blocked, waiting for resources held by each other, preventing any of them from completing their execution.

**System Model:**
The system is modeled as a finite number of resources distributed among a number of competing processes. 
*   Resources are partitioned into types ($R_1, R_2, ... R_m$), each with identical instances.
*   A process must request a resource before using it and must release it after use.
*   The sequence of operation is: **Request** (wait if unavailable), **Use** (operate on resource), and **Release** (make it available for others).

---

### Q2. State and explain the four necessary conditions for a deadlock to occur. (Deadlock Characterization)
**Answer:**
For a deadlock to exist in a system, the following four conditions must hold simultaneously:
1.  **Mutual Exclusion:** At least one resource must be non-sharable. Only one process can use the resource at any given moment.
2.  **Hold and Wait:** A process is holding at least one resource and is simultaneously waiting to acquire additional resources that are currently held by other processes.
3.  **No Preemption:** Resources cannot be forcibly taken away from a process. A resource can only be released voluntarily by the process holding it after its task is complete.
4.  **Circular Wait:** There exists a circular chain of processes $\{P_0, P_1, ..., P_n\}$ such that $P_0$ is waiting for a resource held by $P_1$, $P_1$ is waiting for a resource held by $P_2$, and so on, with $P_n$ waiting for a resource held by $P_0$.

---

### Q3. Briefly explain the three general strategies used by Operating Systems for handling deadlocks.
**Answer:**
Operating systems generally handle deadlocks in three ways:
1.  **Prevention or Avoidance:** The system is designed to ensure it never enters a deadlock state. *Prevention* breaks one of the four necessary conditions. *Avoidance* uses algorithms (like Banker's Algorithm) to assess resource requests dynamically and only grants them if the system remains in a safe state.
2.  **Detection and Recovery:** The OS does not restrict resource requests but periodically runs an algorithm to check for deadlocks (cycles in graphs). If detected, it recovers by aborting processes or preempting resources.
3.  **Ignore the Problem (Ostrich Algorithm):** The OS assumes deadlocks happen so rarely that it is cheaper to ignore them than to run complex prevention/avoidance algorithms. If a deadlock occurs, the user must manually kill the unresponsive processes or reboot the system. This is the approach used by Windows and Linux.
