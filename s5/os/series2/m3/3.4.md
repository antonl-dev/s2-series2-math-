# 3.4 Synchronization Problem Examples

To test our synchronization tools (like semaphores and monitors), operating system designers use classic problems that simulate common concurrency issues. The three most famous examples are the Producer-Consumer problem, the Readers-Writers problem, and the Dining-Philosophers problem.

## 1. The Readers-Writers Problem
**The Scenario:** 
Imagine a database or a shared file that is accessed by multiple concurrent processes. 
*   **Readers:** Processes that only want to read the data. They do not modify it.
*   **Writers:** Processes that want to read AND modify the data.

**The Rules:**
1.  Multiple **Readers** can read the shared data simultaneously without any problems.
2.  If a **Writer** is writing to the database, it must have **exclusive access**. No other writer and no other reader can access the shared data at the same time.

There are variations of this problem depending on priority (e.g., First readers-writers problem prioritizes readers, Second prioritizes writers). We will look at the classic first readers-writers solution.

## 2. The Dining-Philosophers Problem
**The Scenario:**
Consider five philosophers sitting around a circular table. They spend their lives alternating between two activities: **thinking** and **eating**. 
*   There is a bowl of rice in the center.
*   There are exactly **five chopsticks**, placed one between each philosopher.
*   To eat, a philosopher must pick up **two chopsticks** (the one on their immediate left and the one on their immediate right).
*   A philosopher can only pick up one chopstick at a time.
*   After eating, they put down both chopsticks and go back to thinking.

**The Complication:**
If all five philosophers become hungry at the exact same time and all pick up their left chopstick, they will all be waiting forever for their right chopstick. This creates a **Deadlock**. Furthermore, a philosopher must not starve to death waiting for chopsticks. 

The problem is a classic representation of allocating multiple resources among multiple processes in a deadlock-free and starvation-free manner.

## Exam Questions & Answers for Module 3.4

### Q1. What is the Readers–Writers problem? Show how it can be solved using semaphores. (Question 9)
**Answer:**
**The Problem:**
The Readers-Writers problem deals with a shared resource (like a database) accessed by two types of processes: readers (who only read) and writers (who read and modify). The constraints are:
1. Multiple readers can access the resource concurrently.
2. A writer must have exclusive access to the resource (no other readers or writers allowed while writing).

**Solution using Semaphores:**
We use three variables:
*   `int read_count = 0;` (Tracks how many readers are currently reading)
*   `semaphore mutex = 1;` (Protects the updating of the `read_count` variable)
*   `semaphore rw_mutex = 1;` (Ensures mutual exclusion for the writers. It is also used by the first reader that enters or the last reader that exits).

**Code for the Writer Process:**
```c
do {
    wait(rw_mutex); // Request exclusive access
    
    /* WRITING IS PERFORMED HERE */
    
    signal(rw_mutex); // Release exclusive access
} while (true);
```

**Code for the Reader Process:**
```c
do {
    // Entry Section
    wait(mutex);           // Lock to update read_count
    read_count++;          // A new reader has arrived
    if (read_count == 1)   
        wait(rw_mutex);    // If this is the FIRST reader, lock out the writers
    signal(mutex);         // Unlock read_count
    
    /* READING IS PERFORMED HERE */
    
    // Exit Section
    wait(mutex);           // Lock to update read_count
    read_count--;          // A reader is leaving
    if (read_count == 0)   
        signal(rw_mutex);  // If this is the LAST reader, let writers back in
    signal(mutex);         // Unlock read_count
} while (true);
```
**Explanation:** 
The writers request `rw_mutex`. The first reader to enter requests the same `rw_mutex`. If a writer is writing, the first reader is blocked, and subsequent readers are blocked waiting for `mutex`. If a reader is reading, `rw_mutex` is held by the readers, so any writer is blocked. As long as at least one reader is inside, other readers can enter directly without locking `rw_mutex`.

### Q2. Describe the Dining Philosophers problem. Give a solution to it using monitors. (Question 10)
**Answer:**
**The Problem:**
Five philosophers sit around a circular table with five chopsticks. A philosopher needs two chopsticks (left and right) to eat rice. If all philosophers pick up their left chopstick simultaneously, a deadlock occurs because no right chopsticks are available. A proper solution must prevent deadlocks and ensure no philosopher starves.

**Solution using Monitors:**
Instead of using semaphores for individual chopsticks, we can use a **Monitor** to govern the state of the philosophers. A philosopher can only move to the eating state if both neighbors are not eating.

We define a monitor `DiningPhilosophers`.
*   **States:** A philosopher can be `THINKING`, `HUNGRY`, or `EATING`.
*   **Condition Variables:** An array `condition self[5]` allows a philosopher to delay themselves (wait) when they are hungry but unable to get chopsticks.

**Monitor Code Structure:**
```java
monitor DiningPhilosophers {
    enum {THINKING, HUNGRY, EATING} state[5];
    condition self[5];

    // Philosopher i wants to eat
    void pickup(int i) {
        state[i] = HUNGRY;
        test(i); // Try to get chopsticks
        if (state[i] != EATING) 
            self[i].wait(); // If couldn't get them, wait
    }

    // Philosopher i is done eating
    void putdown(int i) {
        state[i] = THINKING;
        // Check if neighbors were waiting and can now eat
        test((i + 4) % 5); // Test left neighbor
        test((i + 1) % 5); // Test right neighbor
    }

    // Helper function to check if philosopher i can eat
    void test(int i) {
        if ((state[(i + 4) % 5] != EATING) && // Left neighbor is not eating
            (state[i] == HUNGRY) &&           // I am hungry
            (state[(i + 1) % 5] != EATING)) { // Right neighbor is not eating
            
            state[i] = EATING; // Take chopsticks
            self[i].signal();  // Wake up if I was waiting
        }
    }

    // Initialization
    initialization_code() {
        for (int i = 0; i < 5; i++)
            state[i] = THINKING;
    }
}
```
**How a philosopher uses this:**
Philosopher $i$ executes the following sequence:
1.  `DiningPhilosophers.pickup(i);` (Enters the monitor, tries to eat. Blocks if neighbors are eating).
2.  `eat();` (Happens outside the monitor, holding the resources safely).
3.  `DiningPhilosophers.putdown(i);` (Tells monitor they are done, which wakes up any waiting neighbors).

*Note: This solution guarantees no deadlocks, but it does not strictly prevent starvation (a philosopher could theoretically starve if neighbors perfectly alternate eating).*
