# 3.2 Process Synchronization – Critical-Section Problem, Synchronization Hardware, Mutex Locks

## 1. Background: The Race Condition
When multiple processes (or threads) execute concurrently, they often share data (like variables, memory, or files). If they access and manipulate this shared data concurrently, the final outcome depends on the particular order in which the execution takes place. 
This situation, where several processes access and manipulate shared data concurrently and the outcome depends on the execution order, is called a **Race Condition**. To prevent race conditions, concurrent processes must be **synchronized**.

## 2. The Critical-Section Problem
A **Critical Section** is a segment of code in a process where the process may be changing common variables, updating a table, writing a file, etc. 
The important feature of the system is that, when one process is executing in its critical section, no other process is allowed to execute in its critical section. 

A typical process structure has:
1.  **Entry Section:** Code that requests permission to enter the critical section.
2.  **Critical Section:** Code where shared data is accessed.
3.  **Exit Section:** Code that follows the critical section, releasing the lock.
4.  **Remainder Section:** The rest of the code.

### Three Requirements for a Solution:
Any valid solution to the critical-section problem must satisfy the following three requirements:
1.  **Mutual Exclusion:** If process Pi is executing in its critical section, then no other processes can be executing in their critical sections.
2.  **Progress:** If no process is executing in its critical section and some processes wish to enter their critical sections, then only those processes that are not executing in their remainder sections can participate in deciding which will enter its critical section next. This selection cannot be postponed indefinitely. (No deadlocks in choosing).
3.  **Bounded Waiting:** There exists a bound (or limit) on the number of times that other processes are allowed to enter their critical sections after a process has made a request to enter its critical section and before that request is granted. (No starvation).

---

## 3. Peterson's Solution
Peterson's solution is a classic software-based solution to the critical-section problem for **two processes** (P0 and P1) that alternate execution between their critical sections and remainder sections.

It requires two shared data items:
*   `int turn;` (Indicates whose turn it is to enter the critical section)
*   `boolean flag[2];` (Indicates if a process is ready to enter its critical section. `flag[i] = true` implies Pi is ready).

**Structure of Process Pi (where j is the other process):**
```c
do {
    flag[i] = true;      // Pi wants to enter
    turn = j;            // Let Pj go first if it wants to
    while (flag[j] && turn == j); // Wait if Pj wants to enter and it's Pj's turn
    
    /* CRITICAL SECTION */
    
    flag[i] = false;     // Pi leaves the critical section
    
    /* REMAINDER SECTION */
} while (true);
```

---

## 4. Synchronization Hardware
Software-based solutions like Peterson's are not guaranteed to work on modern computer architectures. Therefore, operating systems rely on hardware instructions. 
Many systems provide special hardware instructions that allow us to either test and modify the content of a word or to swap the contents of two words **atomically** (i.e., as one uninterruptible unit).

### The `test_and_set()` Instruction
It is an atomic hardware instruction. It reads the original value of a boolean variable, sets it to `true`, and returns the original value.
```c
boolean test_and_set(boolean *target) {
    boolean rv = *target;
    *target = true;
    return rv;
}
```

---

## 5. Mutex Locks
Operating systems designers build higher-level software tools to solve the critical-section problem. The simplest of these tools is the **mutex lock** (stands for **mut**ual **ex**clusion).
A process must acquire the lock before entering a critical section and release the lock when it exits.

*   `acquire()`: Acquires the lock. If the lock is unavailable, the process blocks/spins until it becomes available.
*   `release()`: Releases the lock, making it available.
A boolean variable `available` indicates if the lock is available or not.

### Spinlocks vs. Blocking Mutex
*   **Spinlock:** The process trying to acquire a lock continuously loops (spins) checking the lock's status. It wastes CPU cycles but avoids context-switching overhead. Good for multi-core systems when the lock is held for a very short time.
*   **Blocking Mutex:** If the lock is unavailable, the process puts itself to sleep (blocks) and yields the CPU to another process. It is awakened when the lock is released. Good for single-processor systems or long wait times.

## Exam Questions & Answers for Module 3.2

### Q1. a. What is a critical section? (Question 3a)
**Answer:**
A critical section is a segment of code within a process where the process accesses and modifies shared resources, such as common variables, tables, or files. To ensure data consistency, the system must guarantee that when one process is executing in its critical section, no other process is allowed to execute in its critical section simultaneously.

### Q2. With suitable examples, explain the three requirements that any solution to the critical-section problem must satisfy. (Question 3b)
**Answer:**
1.  **Mutual Exclusion:** Only one process can execute in its critical section at a time. *Example:* If Process A is updating the shared bank balance variable, Process B must wait outside its critical section until A finishes.
2.  **Progress:** If no process is in the critical section, and some wish to enter, only those processes trying to enter can decide who goes next, and this decision cannot be delayed indefinitely. *Example:* If Process A is just doing internal calculations (remainder section) and Process B wants to update the shared balance, Process A should not be able to block Process B from entering the critical section.
3.  **Bounded Waiting:** There must be a limit on how many times other processes can enter their critical sections after a process has requested entry. *Example:* If Process A requests to enter the critical section, Processes B and C cannot take turns entering it infinitely; Process A must eventually be allowed in to avoid starvation.

### Q3. A bank keeps the balance of a joint account using two functions, credit() and debit(). Two partners share this account. At the same moment, one partner calls debit() and the other calls credit(). Explain how a race condition can arise, and suggest how it can be prevented. (Question 4 / Main Exam Q6)
**Answer:**
**How a race condition arises:**
Assume the current bank account balance is Rs 10,000. 
*   Partner 1 (Husband) calls `debit(2000)`.
*   Partner 2 (Wife) calls `credit(5000)`.

Internally, updating the balance takes three machine instructions:
1. Read `balance` into a local CPU register.
2. Modify the register (add/subtract amount).
3. Write the register back to `balance`.

If the OS interleaves their execution:
1. Husband's thread reads `balance` (10,000) into Register1.
2. Wife's thread reads `balance` (10,000) into Register2.
3. Husband's thread subtracts 2000 (Register1 = 8,000).
4. Wife's thread adds 5000 (Register2 = 15,000).
5. Husband's thread writes Register1 to `balance` (`balance` becomes 8,000).
6. Wife's thread writes Register2 to `balance` (`balance` becomes 15,000).

The final balance is 15,000, but it *should* be 13,000. The husband's withdrawal was completely overwritten and lost. This data inconsistency due to concurrent execution order is a race condition.

**Prevention:**
This can be prevented by implementing **Mutual Exclusion** using synchronization tools like **Mutex Locks**. 
Before executing the `credit()` or `debit()` code (the critical section), the thread must call `acquire()` to get the lock. Once the balance update is complete, it calls `release()`. If the husband's thread has the lock, the wife's thread must wait until he finishes, ensuring atomic updates and a correct final balance of 13,000.

### Q4. a. Describe Peterson's solution to the critical-section problem. Show how it satisfies mutual exclusion, progress and bounded waiting. (Question 5a)
**Answer:**
Peterson's solution is a software-based algorithm for two processes (P0 and P1). It uses two shared variables:
*   `boolean flag[2];` (initially false. `flag[i]=true` means Pi wants to enter)
*   `int turn;` (indicates whose turn it is)

**Algorithm for Process Pi (where j is the other):**
```c
flag[i] = true; 
turn = j; 
while (flag[j] && turn == j); 
// Critical Section
flag[i] = false;
```
**Satisfying the requirements:**
1.  **Mutual Exclusion:** Pi enters the critical section only if `flag[j] == false` OR `turn == i`. If both want to enter, both set their flags to true. However, `turn` can only hold one value (either `i` or `j`). The one who sets `turn` last will have to wait in the `while` loop, allowing the other to enter. Hence, both cannot be in the critical section at the same time.
2.  **Progress:** If Pj doesn't want to enter, `flag[j]` is false. Thus, Pi's `while` loop condition (`flag[j] && turn == j`) is false, and Pi can enter immediately. A process not interested in the critical section does not block the other.
3.  **Bounded Waiting:** When Pi leaves the critical section, it sets `flag[i] = false`. This breaks Pj's `while` loop if Pj was waiting. Even if Pi immediately tries to re-enter, it will set `turn = j`, forcing itself to wait and granting Pj the next entry. Thus, a process waits at most one turn.

### Q5. Explain how the test_and_set() instruction works, with an example. (Question 6)
**Answer:**
The `test_and_set()` instruction is an atomic hardware instruction. "Atomic" means it executes completely as a single, uninterruptible unit of work.
It takes a boolean variable, returns its current value, and updates the variable to `true`.

**Syntax:**
```c
boolean test_and_set(boolean *target) {
    boolean rv = *target;
    *target = true;
    return rv;
}
```
**Example Usage for Mutual Exclusion:**
We use a shared boolean variable `lock`, initialized to `false`.
```c
do {
    // Wait here while lock is true. test_and_set returns true and keeps it true.
    // If lock is false, test_and_set returns false (breaking loop) and sets lock to true.
    while (test_and_set(&lock)); 
    
    /* CRITICAL SECTION */
    
    lock = false; // Release lock
    
    /* REMAINDER SECTION */
} while (true);
```

### Q6. a. Write the syntax of a mutex lock using acquire() and release(). (Question 7a)
**Answer:**
A mutex lock uses a boolean variable, `available`, initialized to `true`.
```c
acquire() {
    while (!available)
        ; /* busy wait (spin) */
    available = false;
}

release() {
    available = true;
}

// Usage:
acquire();
/* Critical Section */
release();
```

---

### Q7. c. What are the advantages of mutex locks? What problems arise if they are not managed properly? (Question 7c)
**Answer:**
**Advantages:**
*   They provide a simple and effective way to achieve mutual exclusion.
*   They prevent race conditions and ensure data consistency.
*   Abstracts the complexity of hardware-level synchronization from the programmer.

**Problems if poorly managed:**
*   **Deadlock:** If a process acquires a lock and forgets to release it (or crashes before releasing), other processes waiting for that lock will wait forever.
*   **Starvation:** Depending on the OS queueing implementation, a process might never acquire the lock if other processes keep acquiring it first.
*   **Performance Bottleneck:** If the critical section is too large, it serializes the execution of threads, drastically reducing the benefits of concurrency.

---

### Q8. d. Compare spinlocks with blocking mutex locks. (Question 7d)
**Answer:**
| Feature | Spinlock | Blocking Mutex Lock |
| :--- | :--- | :--- |
| **Waiting Mechanism** | Process continuously loops (busy-waits) checking the lock. | Process goes to sleep (blocks) and yields the CPU. |
| **CPU Cycles** | Wastes CPU cycles while spinning. | Does not waste CPU cycles while waiting. |
| **Context Switch Overhead**| No context switch occurs while waiting. | Incurs overhead of context switching (saving state, moving to wait queue). |
| **Best Used When...** | The lock is expected to be held for a very short duration, and on multiprocessor systems. | The lock might be held for a long time, or on single-processor systems. |
