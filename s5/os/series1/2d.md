## Module 2: Inter-Process Communication (IPC)

### 2.8 Inter-Process Communication (IPC)

Processes executing within an operating system can be either independent or cooperating:
*   **Independent Processes:** Cannot affect or be affected by the execution of another process. They do not share any data (either physical or virtual).
*   **Cooperating Processes:** Can affect or be affected by other executing processes. They share data, state, or resources.

Cooperating processes require an **Inter-Process Communication (IPC)** mechanism to exchange data and synchronization signals.

#### Reasons for Providing Cooperating Processes:
1.  **Information Sharing:** Multiple users or applications may need access to the same piece of information (e.g., a shared database).
2.  **Computation Speedup:** If a task can be broken down into subtasks running concurrently, running them across multiple CPU cores speeds up execution (requires multiprocessors).
3.  **Modularity:** Constructing the system in a modular fashion, dividing system functions into separate processes or threads.
4.  **Convenience:** Even a single user can work on multiple tasks concurrently (e.g., compiling code, editing text, and listening to music).

---

### Models of Inter-Process Communication

There are two primary models of inter-process communication: **Shared Memory** and **Message Passing**.

```
    Shared Memory Model                     Message Passing Model
+-------------------------+             +-------------------------+
|  Process A   Process B  |             |  Process A   Process B  |
|     \           /       |             |     |             ^     |
|      v         v        |             |     v             |     |
|   [ Shared Memory ]     |             |  [     Kernel OS     ]  |
|  (Direct RAM Access)    |             |  (System Calls / Copy)  |
+-------------------------+             +-------------------------+
```

---

### 2.8.1 Shared Memory Systems

In the shared memory model, communicating processes establish a shared region of physical memory.

#### Mechanism:
1.  A process (e.g., Process A) requests the OS to create a shared memory segment.
2.  The OS maps a portion of physical RAM into the address spaces of both Process A and Process B.
3.  Once the mapping is complete, both processes can read and write to this memory region as if it were part of their own local memory space.
4.  The OS is not involved in the actual data transfer; data exchange occurs at RAM speeds.

#### Advantages:
*   **High Performance:** Extremely fast. Data copies do not cross the user-kernel mode boundary after the initial setup.

#### Disadvantages:
*   **Cache Coherency and Race Conditions:** Application developers must explicitly implement synchronization mechanisms (such as mutexes or semaphores) to prevent processes from writing to the same memory locations concurrently.
*   **Complex Implementation:** Harder to program safely compared to message passing.

---

### 2.8.2 Message Passing Systems

In the message passing model, processes communicate and synchronize their actions without sharing a common address space. It is particularly useful in distributed environments where communicating processes reside on different computers connected by a network.

#### Mechanism:
Message passing requires two primary system call primitives:
*   `send(message)`
*   `receive(message)`

To communicate, processes must establish a **communication link**. This link can be implemented in several ways:

#### 1. Direct vs. Indirect Communication
*   **Direct Communication:** Each process must explicitly name the recipient or sender of the communication.
    *   `send(P, message)` — Send a message to Process `P`.
    *   `receive(Q, message)` — Receive a message from Process `Q`.
    *   *Properties:* A link is established automatically between exactly one pair of communicating processes.
*   **Indirect Communication:** Messages are sent to and received from shared mailboxes or ports.
    *   `send(mailbox_A, message)` — Send a message to mailbox `A`.
    *   `receive(mailbox_A, message)` — Receive a message from mailbox `A`.
    *   *Properties:* A link is established between a pair of processes only if they share a common mailbox. Multiple processes can share a single mailbox.

#### 2. Synchronization (Blocking vs. Non-blocking)
Communication between processes can be synchronous or asynchronous:
*   **Blocking Send (Synchronous):** The sending process blocks until the message is received by the recipient process or by the mailbox.
*   **Non-blocking Send (Asynchronous):** The sending process sends the message and immediately resumes execution.
*   **Blocking Receive (Synchronous):** The receiver blocks until a message is available.
*   **Non-blocking Receive (Asynchronous):** The receiver retrieves either a valid message or a null/empty indicator and continues execution.

#### 3. Buffering Configurations
Messages exchanged by communicating processes reside in a temporary queue managed by the link. These queues can be configured in three ways:
*   **Zero Capacity (No Buffering):** The queue has a maximum length of 0. The sender must block until the receiver performs a corresponding `receive()` operation (known as a **rendezvous**).
*   **Bounded Capacity:** The queue has a finite length $N$. If the queue is not full, the sender can write without blocking. If the queue is full, the sender must block until space becomes available.
*   **Unbounded Capacity:** The queue has an infinite length. The sender never blocks when transmitting messages.

### Comparative Analysis of IPC Models

| Feature | Shared Memory | Message Passing |
| :--- | :--- | :--- |
| **Data Location** | Shared address space mapped in RAM. | Kernel buffers or system mailboxes. |
| **System Call Overhead** | Minimal (Only during initial setup). | High (Required for every message transfer). |
| **Transfer Speed** | Very fast (Memory access speed). | Slower (Requires data copying and context switches). |
| **Synchronization** | Must be implemented manually by the application programmer. | Handled automatically by the OS kernel. |
| **Hardware Suitability** | Highly suited for single-system multi-core CPUs. | Suited for both single systems and distributed systems (networks). |
