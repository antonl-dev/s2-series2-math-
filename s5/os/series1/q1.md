### Question 1: OS Access Statements Evaluation

**Evaluate the following statements. Correct them where necessary, referring to OS services, system calls, user/kernel modes, and suitable OS organization.**
*   *Statement a:* "A user program can directly access hardware whenever required."
*   *Statement b:* "All operating-system services must always execute inside the kernel."

#### Evaluation and Correction of Statement (a):
*   **Evaluation:** This statement is **incorrect**. 
*   **Reasoning:** To prevent buggy or malicious programs from crashing the system, modern computer hardware implements **dual-mode execution** (User Mode and Kernel Mode). User programs execute in user mode, which restricts them from running privileged CPU instructions or directly accessing physical hardware addresses. 
*   **Correction:** If a user program needs to access hardware (e.g., writing a file to disk or reading from a network interface), it must request the service through a **System Call**. This triggers a software trap that switches execution to kernel mode, allowing the OS kernel to perform the requested hardware access safely on behalf of the application.

#### Evaluation and Correction of Statement (b):
*   **Evaluation:** This statement is **incorrect**.
*   **Reasoning:** The organization of operating system services depends entirely on its structural design:
    *   *Monolithic Systems:* Most services run in the kernel space.
    *   *Microkernel Systems:* The operating system is intentionally structured to be as small as possible. Only minimal services (such as low-level thread scheduling, memory address translation, and message-passing IPC) execute in the kernel. All other traditional OS services (like file systems, network stacks, and device drivers) run as independent server processes in **user space**.
*   **Correction:** Not all OS services must execute in kernel space. In a microkernel-based OS organization, most services run as user-space servers, communicating with client programs through message-passing via the microkernel.

### Question 2: Process Creation via `fork()`

**A process P creates a child P1. Both P and P1 then execute one more `fork()`.**

#### Part (a): Draw the resulting process hierarchy and determine the total number of processes.
1.  **Initial State:** We start with process `P`.
2.  **First `fork()`:** Process `P` spawns a child process `P1`.
    *   *Processes in system:* `[P, P1]`.
3.  **Second `fork()`:** Both processes (`P` and `P1`) execute one more `fork()` call.
    *   `P` creates a new child process, `P2`.
    *   `P1` creates a new child process, `P3`.
    *   *Processes in system:* `[P, P1, P2, P3]`.

#### Process Hierarchy Tree:
```
             P (Original Parent)
            / \
 (1st fork) /   \
          P     P1 (First Child)
         / \    / \
 (2nd fork)P   P2  P1  P3
```

*   **Total Number of Processes:** **4** (the original parent process $P$ and $3$ newly created child processes).

#### Part (b): Explain how the return value of `fork()` can be used to make a parent and a child execute different code.
The `fork()` system call returns different values to the parent process and the child process, despite executing the exact same line of code:
*   **To the parent process:** It returns the unique Process ID (PID) of the newly created child process (a positive integer).
*   **To the child process:** It returns exactly `0`.
*   **On Failure:** It returns `-1` to the parent, indicating the system failed to create a process.

By using an conditional branch statement (`if-else`), a developer can bifurcate the execution paths:
```c
pid_t pid = fork();

if (pid < 0) {
    // Error handling
} else if (pid == 0) {
    // This code runs strictly inside the CHILD process
    execute_child_logic();
} else {
    // This code runs strictly inside the PARENT process
    execute_parent_logic();
}
```

### Question 3: Process State Transitions

**Draw the basic process-state diagram to illustrate how its state changes during execution. Explain the conditions or events that cause the process to move from one state to another.**

#### Process-State Diagram:
```
              [Admitted]          [Scheduler Dispatch]
   ( NEW ) -------------> ( READY ) ----------------> ( RUNNING ) ----> ( TERMINATED )
                            ^                            |     [Exit]
                            |                            |
                            |       [Interrupt /         |
                            |        Time Slice]         |
                            |                            v
                            +----------------------- ( WAITING )
                             [I/O or Event Complete]  [I/O or Event Wait]
```

#### Explanation of State Transitions:
1.  **New $\to$ Ready (Admitted):** The OS allocates a Process Control Block (PCB) for a process, loads its code into memory, and moves it to the ready queue to wait for CPU scheduling.
2.  **Ready $\to$ Running (Scheduler Dispatch):** The short-term CPU scheduler selects a process from the ready queue and schedules it to execute on the CPU core.
3.  **Running $\to$ Ready (Interrupt):** A running process is preempted by the OS. This occurs when its allocated time quantum (time slice) expires, or if a higher-priority process enters the ready queue.
4.  **Running $\to$ Waiting (I/O or Event Wait):** A process transitions to the waiting (blocked) state if it requests a blocking system call (such as a disk read/write operation, waiting for user input, or waiting for a synchronization signal).
5.  **Waiting $\to$ Ready (I/O or Event Completion):** Once the hardware controller finishes servicing the I/O request or the expected event occurs, the hardware generates an interrupt. The OS then moves the waiting process back to the ready queue.
6.  **Running $\to$ Terminated (Exit):** The process completes execution (returns from `main` or executes an `exit()` call) or is forcibly terminated by the OS due to a runtime error (such as a segmentation fault).

### Question 4: Round Robin Scheduling Calculation

**A Round Robin scheduler uses a time quantum of $2$ ms. A student proposes the following execution for three processes arriving at time 0:**

| Process | CPU Burst Time |
| :---: | :---: |
| **P1** | 5 ms |
| **P2** | 3 ms |
| **P3** | 2 ms |

#### Proposed Student Gantt Chart:
`0 [P1] 2 [P1] 4 [P2] 6 [P3] 8 ...`

#### Part (a): Decide whether this schedule follows Round Robin correctly. Identify the error and continue the schedule correctly until all processes finish.

*   **Decision:** The proposed schedule **does not** follow Round Robin correctly.
*   **Error Identification:** At time $t = 2$ ms, process P1 has consumed its first $2$ ms time quantum. In a correct Round Robin schedule, P1 must be preempted and placed at the tail of the `Ready` queue. The scheduler must then allocate the CPU to the next ready process in line (P2). The student's proposed chart incorrectly ran P1 for a second consecutive time slice from $t=2 \to 4$.
*   **Correct Process Queue Tracking:**
    *   *Ready Queue at $t = 0$:* `[P1, P2, P3]`
    *   **Interval $0 \to 2$ ms:** P1 runs. Remaining: P1 = $3$ ms. Preempted and queued at tail.  
        *Queue:* `[P2, P3, P1]`
    *   **Interval $2 \to 4$ ms:** P2 runs. Remaining: P2 = $1$ ms. Preempted and queued at tail.  
        *Queue:* `[P3, P1, P2]`
    *   **Interval $4 \to 6$ ms:** P3 runs for $2$ ms and terminates.  
        *Queue:* `[P1, P2]`
    *   **Interval $6 \to 8$ ms:** P1 runs. Remaining: P1 = $1$ ms. Preempted and queued at tail.  
        *Queue:* `[P2, P1]`
    *   **Interval $8 \to 9$ ms:** P2 runs for its final $1$ ms and terminates.  
        *Queue:* `[P1]`
    *   **Interval $9 \to 10$ ms:** P1 runs for its final $1$ ms and terminates.

#### Correct Gantt Chart:
```
+-------+-------+-------+-------+---+---+
|  P1   |  P2   |  P3   |  P1   |P2 |P1 |
+-------+-------+-------+-------+---+---+
0       2       4       6       8   9   10
```

#### Part (b): Explain how increasing the time quantum would affect context switching.
*   **Effect of Increasing Time Quantum:** If the time quantum ($q$) is increased, each process is allowed to run on the CPU for a longer uninterrupted block of time.
*   **Context Switches Decrease:** Because processes are preempted less frequently, the total number of context switches required to execute the same workload **decreases**. This reduces the administrative CPU overhead of saving and restoring process states.
*   **Drawback of Large Time Quantum:** If the time quantum is made too large (e.g., greater than the burst time of any active process), the algorithm degenerates into non-preemptive First-Come, First-Served (FCFS), which significantly increases the average response time for interactive programs.
