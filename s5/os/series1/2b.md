### 2.4 The Limited Direct Execution (LDE) Model

To virtualize the CPU, the operating system must run multiple processes concurrently. This raises two critical challenges:
1.  **Performance:** How can we run programs with minimal virtualization overhead?
2.  **Control:** How can we prevent a program from running indefinitely or accessing restricted system resources?

To address these challenges, modern operating systems use a CPU virtualization protocol called **Limited Direct Execution (LDE)**.

```
+--------------------------------------------------------------------------+
| OS Boot Phase (Kernel Mode)                                             |
|                                                                          |
|   1. Initialize Trap Table ----(Registers Addresses)----> CPU Hardware    |
+--------------------------------------------------------------------------+
| Program Execution Phase (User Mode / Kernel Mode)                        |
|                                                                          |
|   2. User Process (User Mode) --[Runs Directly on CPU]--                  |
|          |                                                               |
|          v (System Call / Trap / Timer Interrupt)                        |
|   3. Hardware Trap Handler --[Switches to Kernel Mode]---                |
|          |                                                               |
|          v                                                               |
|   4. OS Kernel Executes Trap Service Routine                             |
|          |                                                               |
|          v                                                               |
|   5. Return-from-trap instruction --[Switches back to User Mode]         |
+--------------------------------------------------------------------------+
```

#### 2.4.1 LDE Execution Protocol
The LDE protocol is divided into two phases: the **boot phase** (at startup) and the **runtime phase** (during program execution).

| Phase | Executed By | Action |
| :--- | :--- | :--- |
| **Boot Phase** | OS Kernel | The OS initializes the **trap table** on the CPU hardware. The trap table specifies the memory addresses of the kernel's interrupt service routines (ISRs) for system calls, division-by-zero errors, page faults, and hardware interrupts. |
| **Boot Phase** | CPU Hardware | The CPU stores the trap table addresses in internal privileged registers. |
| **Runtime Phase** | OS Kernel | The OS sets up a kernel stack for the process, allocates a PCB, loads the program code, and executes a **return-from-trap** instruction. |
| **Runtime Phase** | CPU Hardware | The CPU switches from Kernel Mode to User Mode, restores registers from the kernel stack, updates the Program Counter to the entry point, and runs the application. |
| **Runtime Phase** | User Process | The process executes directly on the physical CPU without software emulation, maximizing execution speed. |

#### 2.4.2 Maintaining Control of the CPU
To prevent an application from running indefinitely (e.g., an infinite loop) or performing illegal operations, the OS relies on two main mechanisms:

#### 1. Cooperative Multitasking (The Passive Approach)
*   The OS assumes processes will periodically yield control back to the kernel.
*   **Yielding Events:** Processes yield control when they execute a system call (like `read()` or `write()`), trigger an exception (like division by zero), or voluntarily call `yield()`.
*   **Limitation:** If a process gets stuck in an infinite loop without performing I/O or system calls, the OS cannot regain control to schedule other tasks, causing the system to freeze.

#### 2. Non-Cooperative Multitasking (The Active Approach)
*   The OS uses a physical **Timer Interrupt** to retain control of the CPU.
*   During boot, the OS configures a physical timer chip (such as an APIC or PIC) to generate a hardware interrupt every few milliseconds.
*   When the timer ticks:
    1.  The CPU suspends execution of the running user program.
    2.  The CPU automatically switches to Kernel Mode and executes the registered timer interrupt handler.
    3.  The OS scheduler runs, assesses if the process has exceeded its time slice, and decides whether to perform a context switch.

### 2.5 Process Scheduling Concepts & Schedulers

Process scheduling is the mechanism by which the OS manages process state transitions to optimize CPU utilization.

```
       +----------------------------------------------------+
       |                   Job Queue                        |
       |  (Set of all processes residing in the system)     |
       +----------------------------------------------------+
                                |
                   (Loaded by Long-Term Scheduler)
                                v
       +----------------------------------------------------+
       |                  Ready Queue                       | <---------+
       |  (Processes in RAM, waiting for CPU dispatch)      |           |
       +----------------------------------------------------+           |
                                |                                       |
                   (Dispatched by Short-Term Scheduler)                  |
                                v                                       |
       +----------------------------------------------------+           |
       |                    CPU                             |           |
       +----------------------------------------------------+           |
            /                                           \               |
     (I/O Request)                              (Time Quantum Exceeded) |
          /                                               \             |
         v                                                 v            |
+------------------+                              +-----------------+   |
|   I/O Queue      |                              | Medium-Term     |   |
| (Waiting for I/O)|                              | Swap-out Queue  |---+
+------------------+                              +-----------------+
```

#### 2.5.1 Scheduling Queues
The OS uses queues to manage processes in different states:
1.  **Job Queue:** Contains all processes in the system.
2.  **Ready Queue:** Resides in main memory (RAM). It holds processes that are in the `Ready` state, waiting for the scheduler to allocate CPU time.
3.  **Device (I/O) Queues:** A set of queues for each physical hardware device. When a process blocks waiting for I/O (e.g., a disk read), it is placed in the corresponding device queue.

---

#### 2.5.2 Types of Schedulers
Operating systems use three main types of schedulers to manage queues: **Long-Term**, **Short-Term**, and **Medium-Term** schedulers.

```
                  +--------------------------------+
                  |      Scheduler Types           |
                  +--------------------------------+
                   /              |               \
                  /               |                \
                 /                |                 \
         [Long-Term]        [Medium-Term]       [Short-Term]
       * Job Scheduler     * Swap Controller   * CPU Scheduler
       * Disk -> RAM       * RAM <-> Disk      * RAM -> CPU
```

#### 1. Long-Term Scheduler (Job Scheduler)
*   **Role:** Selects processes from a job pool on disk and loads them into physical memory (RAM) for execution.
*   **Execution Frequency:** Runs infrequently (only when a new process is created).
*   **Key Duty:** Controls the **degree of multiprogramming** (the total number of processes kept in main memory). It aims to maintain a balanced mix of I/O-bound and CPU-bound processes to keep both the CPU and I/O devices busy.

#### 2. Short-Term Scheduler (CPU Scheduler)
*   **Role:** Selects a process from the `Ready` queue in memory and allocates CPU time to it.
*   **Execution Frequency:** Runs extremely frequently (every few milliseconds).
*   **Key Duty:** Must be fast to minimize overhead, as any scheduling latency directly reduces the CPU time available for application execution.

#### 3. Medium-Term Scheduler (Swapper)
*   **Role:** Temporarily removes processes from memory and stores them on secondary storage (the swap space on a disk), a process known as **swapping out**. It can later restore these processes to memory (**swapping in**).
*   **Key Duty:** Reduces the degree of multiprogramming when physical memory (RAM) is overcommitted, helping to resolve memory bottlenecks.

### Comparative Analysis of Schedulers

This comparison details how the three schedulers differ in their operational parameters (related to the question from page 4 of the internal test):

| Feature | Long-Term Scheduler | Medium-Term Scheduler | Short-Term Scheduler |
| :--- | :--- | :--- | :--- |
| **Alternative Name** | Job Scheduler | Swapper | CPU Scheduler |
| **Speed** | Slowest | Medium | Fastest (Scale of milliseconds) |
| **Frequency of Action** | Infrequent | Moderate | Extremely frequent |
| **Location of Processes** | Moves from Disk to RAM | Moves between RAM and Swap Disk | Resides in RAM, allocates to CPU |
| **Control Parameter** | Directly determines the *degree of multiprogramming*. | Temporarily adjusts the *degree of multiprogramming* to manage memory load. | Does not control the degree of multiprogramming; only schedules ready processes. |
| **I/O Balance Control** | Maintains a balanced mix of CPU-bound and I/O-bound jobs. | Primarily addresses physical memory allocation bottlenecks. | Dispatches ready processes to maximize CPU utilization and throughput. |
