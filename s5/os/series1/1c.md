### 1.5 System Calls and Loadable Modules

A system call provides the programmatic interface through which a running application requests services from the operating system kernel.

```
+--------------------------------------------------------------+
|                         User Space                           |
|                                                              |
|   User Program  ======(Library Call: printf)=====>  glibc    |
|        ^                                             |       |
|        |                                             |       |
|  (Resumes Exec)                                      |       |
|        |                                             v       |
|        +-----(Return)-----+                  [System Call:   |
|                           |                   write() / trap]|
+---------------------------|--------------------------|-------+
|                           |                          |       |
|  Kernel Space             |                          v       |
|                           |                  [System Call    |
|                           |                   Vector Table]  |
|                           |                          |       |
|                           |                          v       |
|                           +================== [sys_write()]  |
+--------------------------------------------------------------+
```

#### 1.5.1 The System Call Mechanism
When a program runs in user mode, it is restricted from executing privileged instructions (such as writing directly to I/O hardware or accessing kernel memory). To perform these operations, the process must temporarily hand over execution control to the kernel.

#### Step-by-Step System Call Execution Flow
1.  **Application Invocation:** The application invokes an API function (e.g., `write()` in standard C, or a wrapper in a library like `glibc`).
2.  **Trap Generation:** The library code places the system call identifier (an integer index) into a designated CPU register (e.g., `eax` or `rax` on x86 architectures) and executes a machine-specific instruction to generate a **software interrupt** or **trap** (e.g., `int 0x80` or `syscall`).
3.  **Mode Switch:** The hardware switches the execution mode from User Mode to Kernel Mode. It saves the program counter (PC) and stack pointer (SP) onto the kernel stack of the process.
4.  **Vector Table Lookup:** The CPU transfers execution to the system call handler inside the kernel. The handler reads the system call number from the register and looks up the corresponding service routine address in the **System Call Vector Table**.
5.  **Execution of Kernel Function:** The kernel executes the service routine (e.g., `sys_write()`).
6.  **Return and Mode Switch:** The kernel places the return code into a CPU register, executes a return-from-trap instruction (e.g., `iret` or `sysret`), restores the saved PC and SP, switches the mode back to User Mode, and resumes application execution.

---

#### 1.5.2 Methods for Passing Parameters to the OS
System calls often require inputs (such as file names, buffer pointers, and byte counts). Operating systems use three main techniques to pass these parameters from the user application to the kernel:

| Method | Mechanism | Pros | Cons |
| :--- | :--- | :--- | :--- |
| **Registers** | Parameters are loaded directly into designated CPU registers (e.g., `ebx`, `ecx`, `edx`). | Fastest execution speed; no memory access overhead. | Limited by the physical number of registers on the CPU architecture. |
| **Block / Table** | Parameters are written into a contiguous block of user-space memory, and a pointer to the start of this block is passed in a single register. | Can pass an unlimited number of parameters. | Requires the kernel to safely read and validate user-space memory pointers, adding validation overhead. |
| **Stack** | Parameters are pushed onto the program's user-space stack, and the kernel pops them off during execution. | Highly structured; handles complex nested function calls easily. | Slower than registers due to memory access overhead. |

#### 1.5.3 Major Categories of System Calls

Operating system services are accessed through distinct categories of system calls:

```
                  +-----------------------------+
                  |  System Call Categories     |
                  +-----------------------------+
                   /      |       |       |    \
                  /       |       |       |     \
                 /        |       |       |      \
        [Process]      [File]  [Device] [Info] [Comm]
```

1.  **Process Control:**
    *   To manage process execution, creation, and termination.
    *   *Examples:* `fork()` (create child), `exec()` (load program), `exit()` (terminate), `wait()` (block until child terminates).
2.  **File Manipulation:**
    *   To access and modify documents, logs, and bin files.
    *   *Examples:* `open()`, `read()`, `write()`, `close()`, `link()`, `unlink()`.
3.  **Device Manipulation:**
    *   To request access to and control system hardware peripherals (disks, serial terminals, video frames).
    *   *Examples:* `ioctl()` (input/output control), `read()`, `write()`.
4.  **Information Maintenance:**
    *   To query and configure system states (time, date, process structures, kernel stats).
    *   *Examples:* `getpid()` (get process ID), `alarm()`, `sleep()`, `sysinfo()`.
5.  **Communications:**
    *   To handle inter-process communication (IPC) between running tasks.
    *   *Examples:* `pipe()` (create pipeline), `shmget()` (allocate shared memory), `socket()` (create network endpoint).

### 1.6 The System Boot Process

The system boot process (or **bootstrapping**) is the multi-stage procedure of loading and initializing the operating system kernel when the hardware is powered on or reset.

```
+---------------+      +-------------------+      +------------------+
|  1. Power-On  | ---> |  2. BIOS / UEFI   | ---> |  3. Bootloader   |
|     (POST)    |      | (Locate MBR/ESP)  |      |   (GRUB / LILO)  |
+---------------+      +-------------------+      +------------------+
                                                                   |
                                                                   v
+---------------+      +-------------------+      +------------------+
| 6. Init /     | <--- | 5. Kernel Init    | <--- |  4. Load Kernel  |
| systemd (PID1)|      |  (Mount Root, etc)|      |    into RAM      |
+---------------+      +-------------------+      +------------------+
```

#### Step 1: Power-On and POST (Power-On Self-Test)
*   When power is applied to the motherboard, the CPU's hardware logic points to a hardcoded address in non-volatile Read-Only Memory (ROM) or flash memory. This is called the **reset vector**.
*   The CPU begins executing the firmware stored at this address (either BIOS or modern UEFI).
*   The firmware performs the **POST** to verify that basic hardware components (RAM, CPU registers, system clock, bus, graphics card) are present and functioning.

#### Step 2: Bootstrap/First-Stage Bootloader
*   Once hardware checks pass, the BIOS/UEFI searches for a bootable storage device based on a configured boot order.
*   *In Legacy BIOS:* The system reads the first sector (Sector 0) of the target drive, known as the **Master Boot Record (MBR)**. This sector is precisely 512 bytes in size and contains a tiny, primary bootstrap program.
*   *In UEFI:* The system reads files directly from a dedicated FAT32-formatted disk partition known as the **EFI System Partition (ESP)**, which contains standardized EFI applications (`.efi`).

#### Step 3: Second-Stage Bootloader (e.g., GRUB)
*   The primary bootstrap program (which has limited space) initializes disk access routines and locates the more sophisticated, second-stage bootloader (such as **GRUB** in Linux).
*   The bootloader presents a menu to the user to choose an operating system, loads basic filesystems drivers, and identifies the location of the compiled kernel image on the disk.

#### Step 4: Loading the Kernel and initramfs
*   The bootloader reads the kernel executable image (e.g., `vmlinuz` in Linux) from the disk and loads it into a designated space in physical RAM.
*   It also loads a temporary, RAM-based filesystem image called **initramfs** (or **initrd**). This small disk image contains essential device drivers (e.g., SATA/NVMe control or network modules) needed to locate and mount the real, permanent root filesystem.

#### Step 5: Kernel Initialization
*   The CPU transfers execution directly to the entry point of the loaded kernel image in RAM.
*   The kernel initializes core hardware parameters:
    *   Builds the virtual page tables and turns on paging (switching CPU to protected mode).
    *   Registers interrupt handlers and initializes the system clock.
    *   Loads built-in device drivers.
*   Using the drivers from `initramfs`, the kernel mounts the permanent, real root filesystem (`/`) in read-only mode, checks for storage consistency, and remounts it in read-write mode.

#### Step 6: Spawning the First User-Space Process (`init` / `systemd`)
*   With the filesystem mounted, the kernel starts its first user-space program located at `/sbin/init` or `/lib/systemd/systemd`.
*   This process runs with a Process Identifier of **PID 1**.
*   `systemd` or `init` is the parent of all subsequent processes in the operating system. It reads system configuration files, loads runtime services, spawns device daemons, starts networking, and launches login managers or terminal shells (`getty`), finalizing the system boot.

### Linux Concept Connections

*   **Inspecting Boot Details:**
    *   To inspect the system messages printed by the Linux kernel during its initialization phase, you can run the `dmesg` command or view `/var/log/boot.log`.
    *   To see the process hierarchy originating from PID 1 (`systemd`), run `pstree -p`. You will observe that every single process on your Linux machine is a direct or indirect child of `systemd` (PID 1).
