### 1.1 Introduction to Operating Systems

An **Operating System (OS)** is a critical piece of system software that acts as an intermediary between a user of a computer and the computer hardware. Its primary purposes are to provide an environment in which a user can execute programs in a convenient and efficient manner, and to allocate physical resources (such as CPU, memory, storage, and I/O devices) fairly and securely among competing processes.

Historically, computers ran one program at a time (batch processing), which led to immense resource underutilization. Modern operating systems employ **Virtualization** to transform physical resources into easy-to-use virtual representations.

The OS can be viewed through two main lenses:
1. **The OS as a Resource Manager:** It manages CPU time, memory space, file storage space, and I/O devices, resolving conflicting requests for resources to ensure efficient and fair operation.
2. **The OS as a Virtual Machine:** It abstracts away the complex, messy details of raw physical hardware, presenting clean, uniform interfaces (such as files, address spaces, and processes) to programmers and applications.

---

### 1.1.1 Virtualizing the CPU

**Virtualizing the CPU** is the technique by which the operating system makes a single physical CPU (or a limited number of cores) appear as an infinite number of virtual CPUs. This abstraction allows multiple programs to run concurrently, seemingly at the same time.

#### The Core Mechanism: Time-Sharing
The fundamental way the OS virtualizes the CPU is through **time-sharing** (or temporal multiplexing). The OS runs one process for a small window of time (a time slice or quantum), stops it, saves its state, and then switches to another process.

*   **Process Abstraction:** A process is a running program. It contains instructions, data, a program counter (PC), stack pointer (SP), and general-purpose registers.
*   **The Illusion:** By switching between processes rapidly (often on the scale of milliseconds), the OS gives each user/program the illusion that it has sole possession of the CPU.

```
Physical Timeline:
|--- Process A ---|--- OS Switch ---|--- Process B ---|--- Process A ---|
[0ms            10ms]             [12ms            22ms]             [32ms]
```

#### How Virtualization is Implemented (Mechanisms vs. Policies)
To virtualize the CPU efficiently without losing control of the machine, the OS separates **mechanisms** (how the system does something) from **policies** (which way it decides to do it).

1.  **Mechanism: Context Switching**
    *   To stop one program and start another, the OS must perform a context switch.
    *   It saves the register values of the currently running program to its **Process Control Block (PCB)** or kernel stack.
    *   It restores the saved registers of the next program from its PCB/kernel stack.
    *   It updates the Program Counter to resume execution of the new program.
2.  **Mechanism: Limited Direct Execution (LDE)**
    *   To make programs run as fast as possible, the OS lets the program execute directly on the physical CPU.
    *   However, to prevent programs from running forever or accessing restricted resources, the hardware supports at least two execution modes:
        *   **User Mode:** Restricted mode. Applications run here. They cannot directly access hardware or perform privileged instructions (like initiating I/O or modifying page tables).
        *   **Kernel Mode (Privileged Mode):** Unrestricted mode. The OS runs here. It has full access to physical hardware.
    *   **System Calls:** If a user program needs to write to disk or allocate memory, it executes a trap instruction to safely transition control to the kernel.
    *   **Timer Interrupts:** To prevent a program from monopolizing the CPU (e.g., an infinite loop), a physical timer chip is programmed to generate an interrupt every few milliseconds. This forces a transition back to the kernel, allowing the OS scheduler to regain control.
3.  **Policy: CPU Scheduling**
    *   The OS scheduler determines *which* process runs next. Common scheduling policies include First-Come First-Served (FCFS), Shortest Job First (SJF), and Round Robin (RR).

### 1.1.2 Virtualizing the Memory

A running program needs to store its instructions and data in memory. Physically, memory is simply an array of bytes, indexed from 0 to some maximum capacity. 

If multiple programs accessed physical memory directly, they could overwrite each other’s data, leading to corruption, security violations, and crashes. To prevent this, the OS **virtualizes memory**.

```
+---------------------------------------+
|          Virtual Memory Space         |
|               (Process A)             |
|   [0x0000] ----Mapped to----> [0x7FFA] | (Physical RAM Location)
+---------------------------------------+
|          Virtual Memory Space         |
|               (Process B)             |
|   [0x0000] ----Mapped to----> [0xCFF3] | (Different Physical RAM Location)
+---------------------------------------+
```

#### The Abstraction: Address Space
The OS presents each process with its own private, isolated memory layout called an **Address Space**. 
*   An address space generally consists of:
    *   **Code:** The compiled machine instructions.
    *   **Data (Static/Global):** Declared variables that exist for the lifetime of the program.
    *   **Heap:** Dynamically allocated memory (via `malloc()` in C or `new` in C++). Grows downward (or upward depending on architecture/implementation).
    *   **Stack:** Local variables, function parameters, and return addresses. Grows upward or downward (typically downward toward the heap).

#### Mechanism: Address Translation
Every address generated by a user program is a **virtual address**. The OS, in tight coordination with hardware called the **MMU (Memory Management Unit)**, translates these virtual addresses into actual **physical addresses** in real RAM.

*   **Static Relocation vs. Dynamic Relocation:**
    *   In modern systems, dynamic relocation is used. The hardware MMU uses base and bounds registers (or page tables in modern paging systems).
    *   `Physical Address = Virtual Address + Base Register`
    *   If the virtual address exceeds the `Bounds Register`, the hardware raises an exception (e.g., Segmentation Fault), and the OS terminates the offending process.
*   **Paging:** Modern systems divide the virtual address space into fixed-size units called **pages** and physical memory into **frames**. Map tables (Page Tables) translate page numbers to frame numbers.

#### Benefits of Memory Virtualization
1.  **Isolation & Protection:** Process A cannot read or write to Process B's memory because Process A's page table points strictly to physical frames allocated to Process A.
2.  **Convenience:** Every process can be compiled to assume its memory starts at virtual address `0x00000000`, making compilation and linking uniform.
3.  **Overcommitment of Memory (Swapping):** The OS can allocate more virtual memory than physical RAM exists by writing temporarily unused pages to secondary storage (such as a swap partition or file on an SSD).

### 1.2 Concurrency, Persistence, and Design Goals

---

### 1.2.1 Concurrency

While virtualizing the CPU and memory gives us the illusion of multiple independent environments, modern software often involves executing multiple tasks simultaneously within the same program or across closely coupled processes. This introduces **Concurrency**.

Concurrency refers to the execution of multiple instruction sequences at the same time. This occurs in:
*   **Multi-threaded programs:** Where a single process has multiple threads sharing the same address space but running different code sections.
*   **Multi-processor/Multi-core systems:** Where threads physically run at the exact same instant on different cores.
*   **Interleaved execution:** On a single-core CPU via context switching.

#### The Fundamental Problem: Race Conditions and Shared State
Because threads in a process share the same heap and static data, multiple threads can attempt to read and write to the same memory location simultaneously. This leads to non-deterministic behavior called **race conditions**.

Consider a classic banking transaction example where two concurrent threads try to execute a `deposit(amount)` or `withdraw(amount)` function on a shared bank account balance:

```c
// Shared variable
volatile int balance = 1000;

void deposit(int amount) {
    int temp = balance;      // Read
    temp = temp + amount;    // Modify
    balance = temp;          // Write
}
```

If Thread 1 and Thread 2 both call `deposit(100)` concurrently, the compiled assembly instructions might interleave as follows:

| Time | Thread 1 | Thread 2 | CPU Registers | Physical Balance Value |
| :--- | :--- | :--- | :--- | :--- |
| $T_1$ | `mov eax, [balance]` | | `eax` (T1) = 1000 | 1000 |
| $T_2$ | (Context switched out) | `mov eax, [balance]` | `eax` (T2) = 1000 | 1000 |
| $T_3$ | | `add eax, 100` | `eax` (T2) = 1100 | 1000 |
| $T_4$ | | `mov [balance], eax` | | 1100 (Thread 2 writes) |
| $T_5$ | `add eax, 100` | | `eax` (T1) = 1100 | 1100 |
| $T_6$ | `mov [balance], eax` | | | **1100** (Thread 1 overwrites!) |

**Result:** Two deposits of $100 were made, but the final balance is $1100 instead of $1200. One deposit was completely lost due to an uncontrolled write sequence.

#### Mitigating Concurrency Anomalies
To solve concurrency problems, the OS and hardware provide synchronization primitives:
*   **Mutual Exclusion (Mutexes / Locks):** Only one thread can enter a critical section (code that accesses shared resources) at any given time.
*   **Semaphores:** Integer variables used to control access to a common resource by multiple processes.
*   **Condition Variables:** Used to make a thread sleep until a specific condition/event occurs.

### 1.2.2 Persistence

While CPU and memory virtualization provide an elegant runtime environment, both RAM and CPU registers are **volatile**—meaning their state is completely lost when power is disconnected or the system crashes. 

**Persistence** is the ability of a system to preserve data permanently across power cycles, reboots, and crashes.

```
       [ Volatile Memory ]                 [ Persistent Memory ]
  +---------------------------+       +-----------------------------+
  | RAM, CPU Registers, Cache | ----> | HDD, SSD, NVMe, Flash Drive |
  | (Lost on power down)      |  I/O  | (Retained on power down)    |
  +---------------------------+       +-----------------------------+
```

#### The Abstraction: File Systems
To achieve persistence, the hardware provides non-volatile storage devices (Hard Disk Drives (HDDs), Solid State Drives (SSDs), NVMe drives). These are raw, block-based physical devices that store arrays of sectors.

To make this usable, the OS abstracts raw disk blocks into **Files** and **Directories**.
*   **File:** A linear array of bytes that can be read, written, or appended.
*   **Directory:** A special file that contains mapping details between human-readable names and internal system references to files (such as index nodes or *inodes*).
*   **Virtual File System (VFS):** An abstract layer within the kernel that allows applications to access different file systems (e.g., ext4, NTFS, FAT32) using standard system calls like `open()`, `read()`, `write()`, and `close()`.

#### The Crash Consistency Challenge
Writing to secondary storage takes time. If a system crashes mid-write (e.g., during a file append where the system must update the file metadata, file allocation bitmap, and write the actual data blocks), the file system can be left in an inconsistent state.

*   To solve this, modern operating systems implement **Journaling** (write-ahead logging). Before making structural changes to the disk, the file system writes a quick log (journal) of its intended changes. If a crash occurs, the OS can read the journal on reboot and either complete the interrupted transaction or roll it back safely.

### 1.2.3 OS Design Goals

Designing a modern operating system involves balancing several, often conflicting, engineering goals. 

| Design Goal | Description | Primary Mechanism |
| :--- | :--- | :--- |
| **Abstraction** | Hide physical hardware details from applications, providing clean, high-level interfaces. | System calls, APIs (POSIX), file systems, virtual address spaces. |
| **Performance** | Minimize virtualization overhead. The OS should run applications nearly as fast as if they ran directly on bare metal. | Hardware-assisted address translation (MMU), Limited Direct Execution (LDE). |
| **Protection & Isolation** | Prevent malicious or buggy applications from altering or crashing other programs or the kernel itself. | Dual-mode execution (User/Kernel space), Virtual Memory limits, Access Control Lists (ACLs). |
| **Reliability / Robustness** | Ensure the core kernel remains operational at all times. If an application crashes, the OS must recover clean. | Decoupled process memory, strict exception handling, file system journaling. |
| **Energy Efficiency** | Minimize power consumption, vital for mobile and embedded systems. | CPU idling states (C-states), dynamic frequency scaling, power-aware scheduling. |
| **Portability** | Allow the OS to run on different physical CPU architectures (e.g., x86, ARM, RISC-V) with minimal codebase changes. | High-level language implementation (primarily C), isolated architecture-dependent kernel layers. |

### Linux Concept Connections (For Practical Context)

Connecting these core principles to modern Linux environments makes these abstract concepts tangible:

1.  **CPU Virtualization in Linux:** 
    *   In Linux, every running process is tracked in the kernel as a `task_struct`. 
    *   The Linux **Completely Fair Scheduler (CFS)** manages CPU virtualization. It uses a red-black tree to schedule tasks based on how much virtual runtime (`vruntime`) they have consumed, aiming to allocate execution time fairly.
2.  **Memory Virtualization in Linux:**
    *   When you run `cat /proc/self/maps` on a Linux terminal, the kernel prints the exact virtual address layout of the current shell's address space.
    *   Functions like `malloc()` do not immediately allocate physical RAM. Instead, they use system calls like `brk` or `mmap` to request virtual memory addresses. The physical page frames are only allocated by the Linux kernel when the application actually writes to that memory (a mechanism known as **Demand Paging** via Page Faults).
3.  **Persistence in Linux:**
    *   Linux mounts physical disk partitions under a unified directory tree starting at root (`/`). 
    *   It treats everything as a file (directories, hardware devices under `/dev`, process data under `/proc`). This elegant abstraction simplifies interface interactions.
