### Question 1(a): System Calls and Handling Steps (5 Marks)

**Definition:**  
A **System Call** is the programmatic interface provided by the operating system that allows user-space applications to request privileged services from the operating system kernel (such as file I/O, process creation, or hardware access).

```
[User Space: Application] --- (Invoke read()) ---> [Trap Instruction]
                                                         | (Hardware Mode Switch)
                                                         v
[Kernel Space: OS] <--- [Lookup Vector Table] <--- [System Call Handler]
         |
         +---> Executes sys_read() ---> Returns value to User Space
```

#### Detailed Steps in Handling a System Call:
1.  **API Call:** The user application calls an API wrapper function (such as `read()` in the standard C library, `glibc`).
2.  **Trap Execution:** The library function loads the specific system call identifier number into a designated CPU register (e.g., `rax` or `eax`) and executes a software interrupt/trap instruction (e.g., `syscall` or `int 0x80`).
3.  **Hardware Mode Switch:** The CPU hardware catches the trap, saves the user program's execution state (registers, Program Counter, and Stack Pointer) on the kernel stack, switches the execution privilege level from **User Mode** to **Kernel Mode**, and jumps to the system call handler.
4.  **Vector Table Lookup:** The system call handler in the kernel reads the system call number from the CPU register and indexes into the **System Call Vector Table** to locate the starting address of the corresponding service routine (e.g., `sys_read()`).
5.  **Service Routine Execution:** The kernel executes the service routine to perform the requested operation (e.g., reading data from disk blocks).
6.  **Return to User Mode:** Once complete, the service routine places the return status/value into a CPU register. The kernel then executes a return-from-trap instruction (e.g., `sysret` or `iret`), which restores the user-space registers, switches back to **User Mode**, and resumes the application's execution.

### Question 1(b): Kernel Location After Switch-On (3 Marks)

When a computer system is switched on, the physical RAM is empty and in an uninitialized state. The hardware locates and loads the operating system kernel using a multi-stage **bootstrapping** process:

1.  **Reset Vector Execution:** When powered on, the CPU's hardware logic automatically jumps to a hardcoded address in non-volatile ROM/Flash memory containing the system firmware (BIOS or UEFI).
2.  **Power-On Self-Test (POST):** The firmware performs hardware validation checks (verifying RAM, CPU, busses, and peripherals).
3.  **Boot Device Selection:** The BIOS/UEFI checks storage devices (SSD, HDD, USB) based on a configured boot order.
    *   *Legacy BIOS:* It reads the first sector (Sector 0) of the target drive, known as the **Master Boot Record (MBR)**, which contains a tiny first-stage bootstrap program.
    *   *UEFI:* It mounts the FAT32-formatted **EFI System Partition (ESP)** and executes a standardized boot loader application (`.efi`).
4.  **Bootloader Execution:** This primary bootstrap code initializes memory and disk access routines to load the more complex, secondary bootloader (such as **GRUB**).
5.  **Kernel Loading:** The secondary bootloader reads the compiled kernel binary image (e.g., `vmlinuz`) from the filesystem and copies it into physical RAM, transferring CPU control directly to the kernel's entry point to begin OS initialization.

### Question 2: CPU Virtualization (8 Marks)

The operating system virtualizes the CPU through **Limited Direct Execution (LDE)**, running programs directly on physical hardware to maintain performance while using three key mechanisms to maintain control:

#### 1. Timer Interrupts
To prevent a user process from monopolizing the CPU (either maliciously or due to an infinite loop), the OS programs a physical hardware timer chip to generate an interrupt periodically (e.g., every few milliseconds). When the timer ticks, the CPU suspends the running user-space program, switches to kernel mode, and runs the OS timer interrupt handler, allowing the OS to regain control of the processor.

#### 2. Scheduling
When the OS regains control (via a timer interrupt or a blocking system call), the **Short-Term CPU Scheduler** executes. It evaluates the processes currently waiting in the `Ready` queue and applies a scheduling policy (such as Round Robin, FCFS, or SJF) to decide which process should be executed next.

#### 3. Context Switching
Once the scheduler selects a new process, the kernel executes a **Context Switch**:
*   It saves the physical CPU register values (Program Counter, Stack Pointer, and general-purpose registers) of the currently running process into its designated **Process Control Block (PCB)** in kernel memory.
*   It updates the process state in the PCB (e.g., from `Running` to `Ready`).
*   It loads the saved register values of the newly selected process from its PCB back into the physical CPU registers.
*   It executes a return-from-trap instruction, switching the CPU back to User Mode to resume the new process.

#### Part A: First-Come, First-Served (FCFS) Scheduling

Under FCFS, processes execute sequentially in the exact order of their arrival:

**FCFS Gantt Chart:**
```
+-------------+-------------+-------+---------+------------+
|     P0      |     P1      |  P2   |   P3    |     P4     |
+-------------+-------------+-------+---------+------------+
0             11            24      30        39           51
```

**Metric Calculations (FCFS):**

| Process | Arrival ($A$) | Burst ($B$) | Completion ($C$) | Turnaround ($TAT = C - A$) | Waiting ($WT = TAT - B$) |
| :---: | :---: | :---: | :---: | :---: | :---: |
| **P0** | 0 | 11 | 11 | $11 - 0 = 11$ | $11 - 11 = 0$ |
| **P1** | 5 | 13 | 24 | $24 - 5 = 19$ | $19 - 13 = 6$ |
| **P2** | 9 | 6 | 30 | $30 - 9 = 21$ | $21 - 6 = 15$ |
| **P3** | 13 | 9 | 39 | $39 - 13 = 26$ | $26 - 9 = 17$ |
| **P4** | 17 | 12 | 51 | $51 - 17 = 34$ | $34 - 12 = 22$ |

*   **Average Turnaround Time (FCFS):**
    $$\frac{11 + 19 + 21 + 26 + 34}{5} = \frac{111}{5} = \mathbf{22.2\text{ ms}}$$
*   **Average Waiting Time (FCFS):**
    $$\frac{0 + 6 + 15 + 17 + 22}{5} = \frac{60}{5} = \mathbf{12.0\text{ ms}}$$

### Question 4(a): Process Creation Output Tracing (4 Marks)

**Code:**
```c
void main() {
    fork();
    printf("Good Luck\n");
    fork();
    fork();
    printf("Do well\n");
}
```

#### Step-by-Step Execution Trace:
1.  **Initial Process ($P_0$):** Executes the first `fork()`. This spawns a child process, $P_1$.
    *   There are now **2 active processes** ($P_0, P_1$).
2.  **First Print Statement:** Both $P_0$ and $P_1$ execute `printf("Good Luck\n")`.
    *   **"Good Luck" is printed 2 times.**
3.  **Second `fork()`:** Both active processes ($P_0, P_1$) execute `fork()`.
    *   $P_0$ creates a new child, $P_2$.
    *   $P_1$ creates a new child, $P_3$.
    *   There are now **4 active processes** ($P_0, P_1, P_2, P_3$).
4.  **Third `fork()`:** All four active processes execute `fork()`.
    *   $P_0 \to P_4$
    *   $P_1 \to P_5$
    *   $P_2 \to P_6$
    *   $P_3 \to P_7$
    *   There are now **8 active processes** in total.
5.  **Second Print Statement:** All 8 active processes execute `printf("Do well\n")`.
    *   **"Do well" is printed 8 times.**

#### Process Creation Hierarchy:
```
                  P0 (Initial Process)
                  |
             (First fork)
             /        \
            P0         P1  -----> [Prints "Good Luck" x 2]
            |          |
         (Second fork) (Second fork)
          /    \       /    \
         P0    P2     P1     P3
         |     |      |      |
      (Third fork for all four branches)
      /  \   /  \    /  \   /  \
     P0  P4 P2  P6  P1  P5 P3  P7 ----> [All 8 Print "Do well" x 8]
```

*   **Final Output Count:** "Good Luck" is printed **2 times**, and "Do well" is printed **8 times**.

### Question 4(b): Zombie vs. Orphan Processes (4 Marks)

| Feature | Zombie Process | Orphan Process |
| :--- | :--- | :--- |
| **Definition** | A process that has finished execution but still has an entry in the OS process table. | A running child process whose parent process has already terminated. |
| **Cause** | The child process exits, but its parent has not yet called `wait()` to retrieve its exit status. | The parent process terminates (exits or crashes) while the child is still executing. |
| **Status** | It does not consume CPU or memory, but it occupies a process table entry (reserving its PID). | It continues to run normally on the system. |
| **Resolution** | Cleaned up when the parent process calls `wait()`, or automatically re-parented and reaped if the parent exits. | The OS kernel immediately re-parents the orphan process to **`init`** or **`systemd`** (PID 1), which reaps its status on exit. |

#### Code Examples:

*   **Zombie Process Example:**
    ```c
    pid_t pid = fork();
    if (pid == 0) {
        // Child exits immediately
        exit(0); 
    } else {
        // Parent sleeps without calling wait()
        sleep(60); 
    }
    ```
*   **Orphan Process Example:**
    ```c
    pid_t pid = fork();
    if (pid == 0) {
        // Child keeps executing
        sleep(60); 
    } else {
        // Parent exits immediately, leaving the child orphan
        exit(0); 
    }
    ```
