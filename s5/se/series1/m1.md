## 1. Introduction to Software Engineering

### 1.1 What is Software Engineering?
Software Engineering is defined as the systematic, disciplined, quantifiable approach to the development, operation, and maintenance of software; that is, the application of engineering principles to software development.

```
       +-------------------------------------------------------+
       |                  SOFTWARE ENGINEERING                 |
       +-------------------------------------------------------+
       |  Tools      : Automated & semi-automated support      |
       |  Methods    : Technical "how-to's" (Design, Code)     |
       |  Process    : Glue holding layers together (SDLC)     |
       |  Quality    : Focus on continuous improvement         |
       +-------------------------------------------------------+
```

* **System Engineering vs. Software Engineering (Series Test Question):**
  * **System Engineering:** Deals with all aspects of computer-based systems development, including hardware, software, human processes, and policy/organizational requirements (e.g., Designing an entire Aircraft Avionics System).
  * **Software Engineering:** A subset of system engineering focused exclusively on the software components, architectures, algorithms, data structures, and maintenance (e.g., Developing the Flight Control Software).

---

### 1.2 Professional Software Development & Ethics
Software engineers have responsibilities to their profession, clients, and society that go beyond basic technical skills.

* **IEEE-CS / ACM Code of Ethics (Core Principles):**
  1. **Public:** Software engineers shall act consistently with the public interest (safety, health, and welfare).
  2. **Client and Employer:** Act in the best interests of the client/employer, consistent with the public interest.
  3. **Product:** Ensure products and related modifications meet the highest professional standards possible.
  4. **Judgment:** Maintain integrity and independence in professional judgment.
  5. **Management:** Managers and leaders shall subscribe to and promote an ethical approach to software development.
  6. **Profession:** Advance the integrity and reputation of the profession.
  7. **Colleagues:** Be fair to and supportive of colleagues.
  8. **Self:** Participate in lifelong learning regarding practice and ethics.

## 2. Software Life Cycle Models (SDLC)

An SDLC model (Process Model) is a descriptive and diagrammatic representation of the software life cycle. It defines the workflow, entry/exit criteria, deliverables, and milestones across phases.

---

### 2.1 The Classic Waterfall Model

#### Concept & Workflow
A sequential, linear development model where each phase must be fully completed and signed off before the next phase begins.

```
  +----------------------+
  | Feasibility Study    |
  +----------+-----------+
             |
             v
  +----------------------+
  | Requirement Analysis |
  | & Specification(SRS) |
  +----------+-----------+
             |
             v
  +----------------------+
  | Design (High & Low)  |
  +----------+-----------+
             |
             v
  +----------------------+
  | Coding & Unit Testing|
  +----------+-----------+
             |
             v
  +----------------------+
  | Integration & System |
  | Testing              |
  +----------+-----------+
             |
             v
  +----------------------+
  | Maintenance          |
  +----------------------+
```
> 🔍 *Google Image Search Query:* `"classical waterfall model diagram software engineering"`

#### Key Concepts & Exam Questions:
* **Effort Distribution:** 
  * The **Maintenance** phase consumes the maximum overall effort across the complete software life cycle (often 60–70% of total life cycle costs).
  * During the active development stages (excluding maintenance), **Testing & Integration** typically consumes the maximum effort (~40–50%).
* **Phase Containment of Errors:**
  * **Definition:** The principle of detecting, isolating, and fixing defects in the exact phase where they are introduced, preventing them from propagating to subsequent phases.
  * **Why Important:** The cost to fix an error grows exponentially (1x during requirements, 10x during design, 50x–100x during testing/production).
  * **How to Achieve:** Formal technical reviews (FTR), code walkthroughs, design inspections, and rigorous phase verification.

#### Pros & Cons:
* **Strengths:** Simple, easy to manage, clear milestones, rigid stage-gate process ensures high documentation quality.
* **Weaknesses:** Inflexible to changes, late working software delivery, high risk of late-stage integration failure, poor fit for dynamic user requirements.
* **Ideal For:** Well-understood requirements, mature technologies, projects with strict regulatory/contractual needs (e.g., government/defence contracts, legacy migrations).

---

### 2.2 Iterative Waterfall Model
* **Concept:** Extends the classical waterfall model by adding **feedback paths** between adjacent phases.
* **Mechanism:** If an error is detected in a later phase (e.g., design flaw found during coding), feedback allows developers to revisit the preceding phase and adjust documentation and code.
* **Limitation:** Cannot easily accommodate brand-new requirement changes once phases are signed off; only corrects errors in existing requirements.

```
  +-----------------------+
  | Requirements Analysis |<-------+
  +-----------+-----------+        |
              |                    | (Feedback)
              v                    |
  +-----------------------+        |
  |     System Design     |--------+<-------+
  +-----------+-----------+                 |
              |                             | (Feedback)
              v                             |
  +-----------------------+                 |
  | Coding & Unit Testing |-----------------+
  +-----------------------+
```

---

### 2.3 The V-Model (Verification and Validation Model)
* **Concept:** A variation of the Waterfall model where execution of processes happens sequentially in a V-shape.
* **Key Principle:** For every development activity (left branch), there is a directly corresponding testing phase (right branch).

```
   Verification Phases                             Validation Phases
   -------------------                             -----------------
   Requirements Analysis ------------------------> System / Acceptance Testing
          \                                               /
           \                                             /
      System Design -----------------------------> Integration Testing
             \                                           /
              \                                         /
          Detailed Design ---------------------> Unit Testing
                 \                                     /
                  \                                   /
                   +-------> Coding / Implementation <+
```
> 🔍 *Google Image Search Query:* `"V model software engineering verification validation diagram"`

* **Verification:** "Are we building the product right?" (Static analysis, reviews, inspections).
* **Validation:** "Are we building the right product?" (Dynamic testing, executing tests against requirements).

---

### 2.4 Incremental Model
* **Concept:** The software requirements are broken down into multiple standalone modular builds. Each increment delivers a subset of complete functional capabilities.
* **Mechanism:**
  * Increment 1: Core product features (e.g., Basic user login and document editor).
  * Increment 2: Advanced formatting, file export.
  * Increment 3: Real-time cloud collaboration.
* **Advantages:** Early delivery of working software; prioritized core features get tested early and continuously.

```
   Requirements ----> Outline Architecture
                            |
         +------------------+------------------+
         |                                     |
         v                                     v
  [ Increment 1 ]                       [ Increment 2 ]
  - Specify Features                    - Specify Features
  - Design & Build                      - Design & Build
  - Test & Integrate                    - Test & Integrate
  - Deploy to Customer                  - Deploy to Customer
```

---

### 2.5 The Spiral Model (Boehm's Model)
* **Concept:** An evolutionary, risk-driven process model that combines the iterative nature of prototyping with the controlled, systematic aspects of the Waterfall model.
* **Structure:** Represented as a spiral with 4 quadrants. Each loop through the spiral represents one phase of development.

```
                                Quadrant 1:
                       Determine Objectives, Alternatives,
                             and Constraints
                                    |
                                    |
          Quadrant 4:               |               Quadrant 2:
      Review & Plan Next            |            Evaluate Alternatives,
            Phases                  |          Identify & Resolve Risks
   ---------------------------------+--------------------------------->
   (Cumulative Cost / Progress)     |                 |
                                    |                 | (Prototyping)
                                    |                 v
                                    |            Quadrant 3:
                                    |         Develop & Verify
                                    |         Next-Level Product
                                    |
```
> 🔍 *Google Image Search Query:* `"Boehm spiral model four quadrants software engineering"`

#### The Four Quadrants Explained:
1. **Quadrant 1 (Determine Objectives):** Identify target objectives, alternative solutions, and operational constraints (cost, schedule, performance).
2. **Quadrant 2 (Identify and Resolve Risks):** Detailed evaluation of alternatives; identify technical, resource, and schedule risks. Undertake risk mitigation (e.g., building prototypes, benchmarking, simulation).
3. **Quadrant 3 (Develop and Verify):** Implement and test the planned release (uses Waterfall or prototyping techniques based on risk evaluation).
4. **Quadrant 4 (Review and Plan Next Phase):** Customer evaluates the product; project status is reviewed; plans for the next loop are finalized.

* **Ideal For:** Large, high-budget, mission-critical projects with high technical uncertainties and financial risks.

### 2.6 The Agile Model
* **Philosophy:** Focuses on iterative, incremental development, adaptability to changing requirements, rapid feedback loops, and delivering working software in short timeboxes (called Sprints/Iterations, typically 1–4 weeks).

#### The 4 Agile Values:
1. **Individuals and interactions** over processes and tools.
2. **Working software** over comprehensive documentation.
3. **Customer collaboration** over contract negotiation.
4. **Responding to change** over following a plan.

```
   Product Backlog               Sprint Backlog                  Working Increment
  +-----------------+           +-----------------+             +------------------+
  | User Story 1    |           | Task 1.1        |             | Functional,      |
  | User Story 2    | --------> | Task 1.2        | ----------> | Tested Feature   |
  | User Story 3    |           | Task 2.1        |             | Ready for Review |
  +-----------------+           +-----------------+             +------------------+
                                        ^
                                        | (Daily Scrum)
                                   [1-4 Weeks]
```

#### Comparison: When to Use Agile vs. Traditional Models

| Parameter | Traditional (Waterfall/V-Model) | Agile (Scrum/XP/Kanban) |
| :--- | :--- | :--- |
| **Requirements** | Fixed upfront, documented in SRS. | Dynamic, evolving user stories. |
| **Delivery** | Single final release at the end. | Continuous, incremental working releases. |
| **Customer Involvement** | Limited to start and acceptance testing. | Continuous throughout every iteration. |
| **Change Tolerance** | Rigid, requires formal change request. | Embraces change even late in development. |
| **Appropriate For** | Regulated, contractual systems (e.g., Oil company legacy migration). | Web apps, startups, mobile apps, changing market domains. |
| **Inappropriate For** | Dynamic startups, exploratory projects. | Safety-critical systems with strict legal certifications (where contracts & complete specs are mandatory). |

#### Common Industry Agile Frameworks:
1. **Scrum:** Framework based on sprints, daily standups, sprint backlogs, and predefined roles (Scrum Master, Product Owner, Dev Team).
2. **Extreme Programming (XP):** Engineering-focused; emphasizes Pair Programming, Test-Driven Development (TDD), continuous integration, and refactoring.
3. **Kanban:** Visual workflow management focused on Work-In-Progress (WIP) limits.
4. **Feature-Driven Development (FDD):** Client-centric approach organized around delivering concrete, tangible features.

## 3. Quick Revision Summary Table (Module 1 Models)

| Model | Primary Distinguishing Factor | Major Strength | Major Weakness |
| :--- | :--- | :--- | :--- |
