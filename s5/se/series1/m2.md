## 1. Software Project Planning & Management

Software project planning provides a framework that enables the manager to make reasonable estimates of resources, cost, and schedule.

### 1.1 Project Planning Objectives & Software Scope
* **Planning Objective:** To define the project scope, estimate resource and effort requirements, assess potential risks, establish a realistic schedule, and outline milestones to ensure the delivery of a quality software product on time and within budget.
* **Software Scope:** Defines the project boundaries and includes:
  * **Context:** How the software fits into a larger system or business context.
  * **Information Objectives:** Visible data objects, inputs, outputs, and databases.
  * **Function and Performance:** Functional requirements, processing speeds, response times, and constraints.
* **Precedence Order of Estimation Activities (Exam Favorite):**
  Estimation must follow a strict logical pipeline because each parameter feeds directly into the next:

```
  +--------------+        +----------------+        +------------------+        +--------------+
  | 1. Size      | -----> | 2. Effort      | -----> | 3. Duration      | -----> | 4. Cost      |
  |  (KLOC / FP) |        | (Person-Months)|        | (Nominal Months) |        | (Total Funds)|
  +--------------+        +----------------+        +------------------+        +--------------+
```

---

### 1.2 Software Size Metrics: LOC vs Function Points

#### Lines of Code (LOC / KLOC)
Measures size by counting the number of source lines delivered.
* **Issues/Drawbacks of LOC (Exam Question):**
  1. **Language Dependency:** High-level languages (e.g., Python) require far fewer LOC than low-level languages (e.g., Assembly/C) to implement identical functionality.
  2. **No Quality Indicator:** Longer, poorly designed code is unfairly counted as higher productivity.
  3. **Early Estimation Difficulty:** Extremely difficult to estimate KLOC accurately during the initial requirements/planning phase before code is written.
  4. **Lack of Standardization:** Ambiguity over whether to count comments, blank lines, and data declarations.

---

### 1.3 Cost & Effort Estimation Techniques
Cost estimation techniques are broadly classified into three categories:

```
                  +-----------------------------------+
                  | Software Cost Estimation Models   |
                  +-----------------+-----------------+
                                    |
         +--------------------------+--------------------------+
         |                          |                          |
         v                          v                          v
  +--------------+           +--------------+           +--------------+
  |  Empirical   |           |  Heuristic   |           |  Analytical  |
  +--------------+           +--------------+           +--------------+
  - Historical data-driven   - Mathematical models      - Theoretical/Physics basis
  - Expert Judgement/Delphi  - Single-variable models   - Putnam's SLIM Model
  - Rule-of-thumb based      - Multi-variable (COCOMO)  - Based on manpower curves
```

1. **Empirical Estimation Techniques:** Based on human experience, historical data, and subjective evaluation.
   * *Expert Judgement:* Experienced planners estimate based on past similar projects.
   * *Delphi Technique / Wideband Delphi:* Experts anonymously estimate size/cost independently, review results, and iterate until a consensus is reached without peer pressure.
2. **Heuristic Estimation Techniques:** Assume that the relationships among key project parameters can be expressed mathematically using empirical data.
   * *Single-Variable Models:* $\text{Parameter} = f(\text{Size})$ (e.g., $\text{Effort} = a \times \text{KLOC}^b$).
   * *Multi-Variable Models:* Uses size and multiple cost driver attributes (e.g., Intermediate COCOMO).
3. **Analytical Estimation Techniques:** Based on scientific and mathematical modeling of the software development process (e.g., **Putnam’s Resource Allocation Model / SLIM**, which relates effort, time, and defect rates using the Rayleigh curve).

---

### 1.4 The COCOMO Model (Constructive Cost Model)
Developed by Barry Boehm, COCOMO is a hierarchy of software estimation models.

#### Development Modes in COCOMO:
1. **Organic Mode:** Small, experienced teams working in familiar, in-house environments with stable, well-understood requirements. Low system complexity.
2. **Semidetached Mode:** Medium-sized teams with mixed experience levels. Intermediate complexity, partially rigid requirements.
3. **Embedded Mode:** Software must operate under tight, rigid hardware and operational constraints (e.g., flight control systems, medical devices). High complexity, changing requirements are difficult to accommodate.

---

#### Basic COCOMO Equations
* **Effort ($E$):** $\text{Effort} = a_b \times (\text{KLOC})^{b_b}\ \text{[in Person-Months (PM)]}$
* **Development Time ($D$ or $T_{dev}$):** $\text{Time} = c_b \times (\text{Effort})^{d_b}\ \text{[in Months]}$

| Development Mode | $a_b$ | $b_b$ | $c_b$ | $d_b$ |
| :--- | :--- | :--- | :--- | :--- |
| **Organic** | $2.4$ | $1.05$ | $2.5$ | $0.38$ |
| **Semidetached** | $3.0$ | $1.12$ | $2.5$ | $0.35$ |
| **Embedded** | $3.6$ | $1.20$ | $2.5$ | $0.32$ |

---

### 1.5 Numerical Problem (From Series Test-I Question Paper)

> **Problem:** Suppose that a project was estimated to be **$400\text{ KLOC}$**. Calculate the effort and development time for each of the three modes (Organic, Semidetached, and Embedded) using the Basic COCOMO model.

#### Given:
$$\text{Size} = 400\text{ KLOC}$$

---

#### 1. Organic Mode
* **Effort Calculation:**
  $$E = 2.4 \times (400)^{1.05}$$
  $$400^{1.05} \approx 541.67$$
  $$E = 2.4 \times 541.67 = \mathbf{1300.01\text{ PM}}\ (\approx 1300\text{ Person-Months})$$

* **Development Time Calculation:**
  $$T_{dev} = 2.5 \times (1300.01)^{0.38}$$
  $$(1300.01)^{0.38} \approx 15.22$$
  $$T_{dev} = 2.5 \times 15.22 = \mathbf{38.05\text{ Months}}$$

---

#### 2. Semidetached Mode
* **Effort Calculation:**
  $$E = 3.0 \times (400)^{1.12}$$
  $$400^{1.12} \approx 814.73$$
  $$E = 3.0 \times 814.73 = \mathbf{2444.19\text{ PM}}\ (\approx 2444\text{ Person-Months})$$

* **Development Time Calculation:**
  $$T_{dev} = 2.5 \times (2444.19)^{0.35}$$
  $$(2444.19)^{0.35} \approx 15.42$$
  $$T_{dev} = 2.5 \times 15.42 = \mathbf{38.55\text{ Months}}$$

---

#### 3. Embedded Mode
* **Effort Calculation:**
  $$E = 3.6 \times (400)^{1.20}$$
  $$400^{1.20} \approx 1309.84$$
  $$E = 3.6 \times 1309.84 = \mathbf{4715.42\text{ PM}}\ (\approx 4715\text{ Person-Months})$$

* **Development Time Calculation:**
  $$T_{dev} = 2.5 \times (4715.42)^{0.32}$$
  $$(4715.42)^{0.32} \approx 14.93$$
  $$T_{dev} = 2.5 \times 14.93 = \mathbf{37.33\text{ Months}}$$

---

### 1.6 Staffing, Personal Planning & Brooks' Law
* **Average Staffing Size:**
  $$\text{Average Staff Size } (S) = \frac{\text{Effort}}{\text{Development Time}} = \frac{E}{T_{dev}}$$

* **Exam Scenario Analysis (Series Test Question):**
  > *"If the effort required is $50\text{ person-months}$, can you complete the project by employing $50\text{ developers}$ for $1\text{ month}$? Justify your answer."*
  * **Answer:** **No, it is impossible.**
  * **Justification (Brooks' Law & Communication Overhead):**
    1. **Non-linear Partitionability:** Software tasks have dependencies; coding cannot proceed before design, and testing cannot precede coding.
    2. **Communication Overhead:** With $n$ developers, communication channels grow as $\frac{n(n-1)}{2}$. For $50\text{ developers}$, there are $\frac{50 \times 49}{2} = 1225\text{ communication paths}$, which overwhelms actual productive work.
    3. **Brooks' Law:** *"Adding manpower to a late software project makes it later."* Time spent onboarding and training new personnel drains senior developers' productivity.

## 2. Software Design Phase

The software design phase transforms the Software Requirements Specification (SRS) into a structural blueprint for implementation.

```
       +-------------------------------------------------------------+
       |                        SRS Document                         |
       +------------------------------+------------------------------+
                                      |
                                      v
       +-------------------------------------------------------------+
       | High-Level Design (Architectural Design)                    |
       | - Decomposes system into major modules & subsystems         |
       | - Defines control and data flow relationships               |
       +------------------------------+------------------------------+
                                      |
                                      v
       +-------------------------------------------------------------+
       | Low-Level Design (Detailed Design)                          |
       | - Internal data structures & algorithms for each module     |
       +-------------------------------------------------------------+
```

---

### 2.1 Design Concepts & Principles

1. **Abstraction:** Focusing on essential qualities while hiding lower-level implementation details (Data Abstraction and Procedural Abstraction).
2. **Modularity:** Partitioning software into distinct, named, and addressable components (modules) that integrate to solve the overall problem.
3. **Information Hiding (Parnas' Principle):** Modules should be designed so that the internal details (algorithms and internal data structures) are inaccessible to modules that have no need for them.
4. **Stepwise Refinement (Wirth’s Strategy):** A top-down decomposition process where a high-level conceptual statement of a function is broken down step-by-step into successively lower-level, concrete statements until reaching source code.

```
  [ Level 0 ] : Compute Payroll
                     |
  [ Level 1 ] : Read Employee Data  -->  Calculate Taxes  -->  Generate Paycheck
                     |
  [ Level 2 ] : Fetch Base Salary, Overtime, Deductions from DB
```

---

### 2.2 Design Strategies: Top-Down vs Bottom-Up

```
           TOP-DOWN STRATEGY                         BOTTOM-UP STRATEGY
       +-----------------------+                 +-----------------------+
       |      Main System      |                 |   Subsystem Modules   |
       +-----------+-----------+                 +-----------+-----------+
                   |                                         |
         +---------+---------+                     +---------+---------+
         v                   v                     v                   v
   +-----------+       +-----------+         +-----------+       +-----------+
   | Sub-mod A |       | Sub-mod B |         | Base Libs |       | Utilities |
   +-----------+       +-----------+         +-----------+       +-----------+
  (Decompose problem downward)             (Build primitive components upward)
```

* **Top-Down Strategy:**
  * Starts at the highest conceptual level and decomposes it systematically into lower-level modules.
  * *Pros:* Clear structural flow, easy to trace requirements.
  * *Cons:* Lower-level components and data handling are identified late.
* **Bottom-Up Strategy:**
  * Starts with the basic, reusable building blocks (e.g., utility functions, DB wrappers) and combines them upward to form the complete application.
  * *Pros:* Encourages code reusability and utility-first testing.
  * *Cons:* Integration with overall system goals can become disjointed.

### 2.3 Effective Modular Design: Cohesion and Coupling (Critical Exam Topic)

The primary goal of effective modular design is: **High Cohesion and Low Coupling**.

```
    HIGH COHESION (Internal Strength)            LOW COUPLING (External Independence)
   +---------------------------------+          +------------+       +------------+
   |             MODULE              |          |  Module A  | <---> |  Module B  |
   |  [Task 1] <-> [Task 2] <-> ...  |          +------------+       +------------+
   |  (All internal operations are   |                 (Minimal data exchange,
   |   focused on a single purpose)  |                  no internal interference)
   +---------------------------------+
```
> 🔍 *Google Image Search Query:* `"cohesion vs coupling software engineering diagram"`

---

#### 1. Cohesion (Intra-module Strength)
Cohesion measures the degree of functional relatedness of elements within a single module.

* **Types of Cohesion (from Worst to Best):**
  1. **Coincidental (Worst):** Elements are grouped arbitrarily with no meaningful relationship (e.g., `MiscellaneousUtils` containing `printReport()`, `calculateTax()`, `invertMatrix()`).
  2. **Logical:** Elements perform logically similar tasks, selected by a control parameter (e.g., a single input driver handling all keyboard, mouse, and touch inputs).
  3. **Temporal:** Elements are grouped solely because they execute at the same time (e.g., an `initializeSystem()` function opening files, clearing buffers, setting global flags).
  4. **Procedural:** Elements are grouped because they follow a specific execution sequence, though they handle different data.
  5. **Communicational:** Elements operate on the exact same input/output data structure (e.g., a module that updates and prints the `StudentRecord`).
  6. **Sequential:** The output of one task serves directly as the input to the next task within the module (like an assembly line).
  7. **Functional (Best):** Every element in the module is dedicated to executing a single, well-defined mathematical or logical function (e.g., `calculateSquareRoot()`, `computeLoanInterest()`).

---

#### 2. Coupling (Inter-module Independence)
Coupling measures the degree of interdependence and interconnectedness between distinct modules.

* **Types of Coupling (from Worst to Best / Tight to Loose):**
  1. **Content Coupling (Worst / Tightest):** One module directly references or modifies the internal code or private memory/data of another module.
  2. **Common Coupling:** Multiple modules share read/write access to the exact same global variables/memory space.
  3. **Control Coupling:** One module passes a control flag to another module, explicitly directing its execution logic.
  4. **Stamp Coupling:** Modules share an entire composite data structure (e.g., a complete record/class), even though the receiving module needs only a subset of fields.
  5. **Data Coupling (Best / Loosest):** Modules communicate strictly by passing individual, basic data items as parameters (e.g., passing `radius` to compute `area`).
  6. **No Coupling:** Complete, isolated independence.

---

### 2.4 Important Conceptual Exam Questions on Cohesion & Coupling

> **Question (From Exam Paper):** *"Is it true that whenever you increase the cohesion of your design, coupling in the design would automatically decrease? Justify your answer using suitable examples."*

* **Answer:** **No, it is not automatically guaranteed.** While the overarching engineering objective is to achieve high cohesion and low coupling simultaneously, increasing cohesion does not automatically decrease coupling.
* **Justification & Counter-Example:**
  * Suppose an overly large, low-cohesion module (`OrderAndInvoiceManager`) is decomposed into two functionally cohesive modules: `OrderModule` and `InvoiceModule`.
  * Cohesion is now increased (each module has a single responsibility).
  * However, if both modules are implemented such that they communicate by directly modifying a shared global structure (e.g., a shared global database buffer or control flag), the system now introduces **Common Coupling** or **Control Coupling**.
  * Therefore, deliberate design effort is required to structure clean, minimal parameter interfaces (Data Coupling) alongside cohesive internal functionality.
