# Module III: Implementation and Testing
## 3.5 Black-box and white-box testing, validation testing, system testing, the art of debugging

### 1. White-Box Testing
White-box testing (also known as glass-box testing, clear-box testing, or structural testing) is a test case design philosophy that uses the control structure described as part of component-level design to derive test cases. 

The tester has full knowledge of the internal code, branches, and logic of the system.

**Goals of White-Box Testing:**
Using white-box testing methods, the software engineer derives test cases that:
1.  Guarantee that all independent paths within a module have been exercised at least once.
2.  Exercise all logical decisions on their true and false sides.
3.  Execute all loops at their boundaries and within their operational bounds.
4.  Exercise internal data structures to ensure their validity.

**Key Techniques:**
*   **Basis Path Testing:** A technique that enables the test designer to derive a logical complexity measure (Cyclomatic Complexity) of a procedural design and use this measure as a guide for defining a basis set of execution paths.
*   **Control Structure Testing:** Enhances basis path testing by including *Condition Testing* (exercising logical conditions), *Data Flow Testing* (selecting test paths based on variable definitions and uses), and *Loop Testing* (focusing exclusively on the validity of loop constructs).

---

### 2. Black-Box Testing
Black-box testing (also known as behavioral testing) focuses on the functional requirements of the software. It enables the software engineer to derive sets of input conditions that will fully exercise all functional requirements for a program.

The tester treats the system as a "black box," not knowing or caring about the internal code or logic, focusing purely on inputs and expected outputs.

**Goals of Black-Box Testing:**
It attempts to find errors in the following categories:
1.  Incorrect or missing functions.
2.  Interface errors.
3.  Errors in data structures or external database access.
4.  Behavior or performance errors.
5.  Initialization and termination errors.

**Key Techniques:**
*   **Equivalence Partitioning:** Divides the input domain of a program into classes of data from which test cases can be derived. (e.g., If an input requires a 3-digit number, the classes are: valid 3-digit numbers, invalid numbers > 999, and invalid numbers < 100).
*   **Boundary Value Analysis (BVA):** Errors tend to occur at the boundaries of an input domain rather than in the center. BVA leads to the selection of test cases that exercise bounding values (e.g., testing the exact min and max limits).

### 3. Validation Testing
Validation testing begins at the culmination of integration testing, when individual components have been exercised, the software is completely assembled, and interface errors have been uncovered and corrected. 
Validation testing ensures that the software satisfies the customer's expectations (tracing back to the Software Requirements Specification - SRS).

**Alpha and Beta Testing (Acceptance Testing):**
If the software is developed as a product to be used by many customers, a process of acceptance testing is used.
*   **Alpha Test:** Conducted at the developer's site by an end-user. The software is used in a natural setting with the developer "looking over the shoulder" of the user and recording errors and usage problems. It is conducted in a controlled environment.
*   **Beta Test:** Conducted at one or more end-user sites. Unlike alpha testing, the developer is generally not present. It is a "live" application of the software in an environment that cannot be controlled by the developer. The customer records all problems and reports them to the developer.

---

### 4. System Testing
System testing is actually a series of different tests whose primary purpose is to fully exercise the computer-based system (software, hardware, network, databases, people) as a whole.

**Types of System Tests:**
1.  **Recovery Testing:** Forces the software to fail in a variety of ways and verifies that recovery is properly performed (e.g., pulling the plug on a database server to see if transactions are saved).
2.  **Security Testing:** Verifies that protection mechanisms built into a system will protect it from improper penetration (hackers, unauthorized access).
3.  **Stress Testing:** Executes a system in a manner that demands resources in abnormal quantity, frequency, or volume (e.g., simulating 100,000 users logging in at the exact same second).
4.  **Performance Testing:** Tests the run-time performance of software within the context of an integrated system (e.g., measuring response time under normal conditions).

---

### 5. The Art of Debugging
**Testing** is the process that *finds* bugs. **Debugging** is the process that *removes* them. Debugging occurs as a consequence of successful testing.

**Debugging Strategies:**
When an error is found, the symptom may be located far away from the actual root cause. To find the root cause, developers use three main strategies:
1.  **Brute Force:** The most common and least efficient method. Memory dumps are taken, run-time traces are invoked, and the program is loaded with output statements (`print()` / `console.log()`) hoping the bug will reveal itself.
2.  **Backtracking:** A fairly common approach used successfully in small programs. Beginning at the site where a symptom has been uncovered, the source code is traced backward manually until the site of the cause is found.
3.  **Cause Elimination:** Uses the scientific method (induction or deduction). The developer proposes a hypothesis regarding the cause of the bug, and data is used to prove or disprove the hypothesis.

#### **Question 1: (From PDF Series Test-II, Part A, Qn 3 - 2 Marks)**
**Question:** Differentiate between Black box testing and white box testing? Apply equivalence class partitioning and boundary value analysis, and design suitable test cases for an input field that accepts marks between 0-100.

**Answer:**

**Part 1: Differentiation**
| Feature | Black-Box Testing | White-Box Testing |
| :--- | :--- | :--- |
| **Focus** | Functional requirements and external behavior. | Internal logic, control structures, and code paths. |
| **Knowledge** | Tester has no knowledge of the internal code. | Tester has full knowledge of the internal source code. |
| **Also known as** | Behavioral testing, opaque-box testing. | Structural testing, glass-box testing. |
| **Performed by** | QA Testers, End-users. | Software Developers. |

**Part 2: Applying Testing Techniques (Input: Marks between 0-100)**

**A. Equivalence Class Partitioning:**
We divide the input domain into valid and invalid classes. One test case from each class is sufficient to test the entire class.
*   *Invalid Class 1 (Below limit):* Marks < 0. **(Test Case: -15)**
*   *Valid Class (Within limit):* 0 <= Marks <= 100. **(Test Case: 75)**
*   *Invalid Class 2 (Above limit):* Marks > 100. **(Test Case: 150)**

**B. Boundary Value Analysis (BVA):**
Errors are most frequent at the extreme edges of input domains. We test the exact boundaries and just outside them.
*   *Lower Boundary Tests:* Just below minimum (**-1**), exact minimum (**0**), just above minimum (**1**).
*   *Upper Boundary Tests:* Just below maximum (**99**), exact maximum (**100**), just above maximum (**101**).
*   **Final BVA Test Cases:** `-1, 0, 1, 99, 100, 101`.

#### **Question 2: (From Syllabus CO Assessment Qn 4)**
**Question:** Explain how you would integrate both black-box and white-box testing techniques to ensure comprehensive test coverage for a complex software application. Provide specific examples.

**Answer:**
To ensure comprehensive test coverage, a hybrid approach must be used because Black-box testing ensures the software does *what the user wants*, while White-box testing ensures the software does it *safely, efficiently, and without internal errors*.

**Integration Strategy:**
1.  **Start with White-Box Testing at the Component Level:** When developers write individual modules, they use white-box testing (like Basis Path Testing). They ensure all loops terminate, all variables are declared, and every line of code executes properly.
2.  **Move to Black-Box Testing at Integration/System Level:** Once modules are integrated, QA testers take over using black-box techniques (like Equivalence Partitioning). They test the system against the user requirements.
3.  **Feedback Loop:** If a black-box test fails (e.g., clicking 'Submit' crashes the app), the bug is sent back to developers. They use white-box debugging (examining stack traces and memory) to find and fix the broken internal path.

**Specific Example: Testing a Secure Bank Login Application**
*   **White-Box Phase:** The developer writes the `authenticateUser()` module. They write test cases to ensure that the `if(password_match)` branch is tested, the `else(invalid_password)` branch is tested, and the SQL database query does not allow SQL injection. They check the internal encryption algorithm loops.
*   **Black-Box Phase:** A QA tester sits at the login UI. They don't know how the encryption works. They use *Boundary Value Analysis* on the password field (e.g., testing exactly 8 characters, 7 characters, and 9 characters if the limit is 8). They input a valid username and valid password and check if the dashboard loads (testing the functional requirement). 
By combining both, we ensure the UI works correctly for the user (Black-box) and the internal database logic is completely secure against unauthorized access (White-box).

#### **Question 3: (Standard University Exam Question)**
**Question:** "Testing finds errors, debugging removes them." Discuss the three main debugging strategies used by software engineers.

**Answer:**
Once a test case uncovers an error, debugging is the process of locating the root cause and correcting it. The three primary strategies are:
1.  **Brute Force:** This is the most common but least efficient method. The developer relies on memory dumps, runtime traces, and scattering `print()` statements throughout the code to monitor variable values. It is generally used when all other methods fail, as it is highly time-consuming.
2.  **Backtracking:** Highly effective for small to medium programs. The developer starts at the exact point where the error symptom was observed (e.g., where a `NullPointerException` was thrown) and traces the source code backward, line by line, to find where the bad data was initially introduced.
3.  **Cause Elimination:** Based on the scientific method. The developer looks at the symptom and proposes multiple hypotheses for why it might be happening. They then write specific tests or look at specific data points to disprove these hypotheses one by one, until only the actual root cause remains.
