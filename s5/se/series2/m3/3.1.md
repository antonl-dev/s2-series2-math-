# Module III: Implementation and Testing
## 3.1 Design Engineering: Design process and design quality, design concepts, the design model

### Introduction to Design Engineering
Design Engineering in software development is the critical phase where the requirements specified in the SRS (Software Requirements Specification) document are translated into a blueprint for constructing the software. It bridges the gap between what the system needs to do (requirements) and how it will do it (implementation/coding).

[Click here for a visual representation of the Software Design Engineering Process](https://www.google.com/search?q=Software+Design+Engineering+Process+Pressman&udm=2)

---

### 1. The Design Process
Software design is an iterative process through which requirements are translated into a "blueprint" for constructing the software. The design process involves:
*   **Initial Design:** Translating the requirement model into an architectural design, subsystem design, and identifying major components.
*   **Component Design:** Detailing data structures, algorithms, and interface attributes for each component.
*   **Iterative Refinement:** Continually evaluating and refining the design to improve quality, reduce complexity, and ensure all requirements are met.

**Characteristics of a good design process:**
1.  The design must implement all explicit requirements contained in the analysis model, and it must accommodate all implicit requirements desired by stakeholders.
2.  The design must be a readable, understandable guide for those who generate code and for those who test and subsequently support the software.
3.  The design should provide a complete picture of the software, addressing the data, functional, and behavioral domains from an implementation perspective.

---

### 2. Design Quality
Quality is established during the design phase. A poor design leads to an unstable, unmaintainable, and error-prone system. Assessing design quality is based on several attributes and guidelines.

**Quality Guidelines (How to achieve a good design):**
1.  **Architecture:** The design should exhibit an architecture that:
    *   Has been created using recognizable architectural styles or patterns.
    *   Is composed of components that exhibit good design characteristics (high cohesion, low coupling).
    *   Can be implemented in an evolutionary fashion, facilitating testing.
2.  **Modularity:** The design should be modular; that is, the software should be logically partitioned into elements or subsystems.
3.  **Data Structures:** Should be appropriate for the classes to be implemented and drawn from recognizable data patterns.
4.  **Interfaces:** The design should lead to interfaces that reduce the complexity of connections between components and with the external environment.

**Quality Attributes (FURPS Model):**
*   **Functionality:** Feature set, capabilities, and security.
*   **Usability:** Human factors, aesthetics, consistency, documentation.
*   **Reliability:** Frequency and severity of failure, accuracy, predictability.
*   **Performance:** Processing speed, response time, resource consumption, throughput.
*   **Supportability:** Maintainability, testability, adaptability, extensibility.

### 3. Design Concepts
These are fundamental principles that act as a foundation for all software design methods. Understanding these is highly critical for university exams.

#### A. Abstraction
Abstraction is the process of hiding the background details or complex implementations and showing only the essential features to the user.
*   **Data Abstraction:** A named collection of data that describes a data object (e.g., `Car` class hiding engine variables).
*   **Procedural Abstraction:** A sequence of instructions that have a specific and limited function (e.g., calling `calculateTax()` without knowing the complex math inside).

#### B. Architecture
The overall structure of the software, consisting of components, their properties, and relationships. It acts as the skeleton of the system.

#### C. Patterns
A design pattern describes a recurring design problem and presents a well-proven solution to it. It provides reusable structural templates.

#### D. Separation of Concerns
Any complex problem can be handled more easily if it is subdivided into pieces that can each be solved independently. A "concern" is a feature or behavior. 

#### E. Modularity
Modularity is the most common manifestation of Separation of Concerns. Software is divided into separately named and addressable components, sometimes called modules. 
*   *Note:* As the number of modules increases, the cost to integrate them increases. Therefore, an optimal number of modules must be found.

#### F. Information Hiding
Modules should be specified and designed so that information (algorithms and data) contained within a module is inaccessible to other modules that have no need for such information. It is achieved through interfaces.

#### G. Functional Independence (Crucial Concept: Cohesion and Coupling)
Functional independence is achieved by developing modules with "single-minded" function and an aversion to excessive interaction with other modules. It is measured using two qualitative criteria: **Cohesion** and **Coupling**.

[Click here for a visual representation of Cohesion vs Coupling](https://www.google.com/search?q=Cohesion+and+Coupling+in+Software+Engineering&udm=2)

*   **Cohesion:** An internal property of a module. It measures the strength of the relationship between pieces of functionality within a given module. A highly cohesive module performs a single, well-defined task. **(Aim for High Cohesion)**
*   **Coupling:** An external property. It measures the degree of interdependence/interaction between two or more modules. **(Aim for Low/Loose Coupling)**

#### H. Refinement & Refactoring
*   **Stepwise Refinement:** A top-down design strategy. You start with a macroscopic statement of function and elaborate it step-by-step until programming language statements are reached.
*   **Refactoring:** The process of changing a software system in such a way that it does not alter the external behavior of the code, yet improves its internal structure.

---

### 4. The Design Model
The Design Model can be viewed in four distinct layers (progressing from data to user):

1.  **Data / Class Design:** Transforms analysis-class models into design realization classes and the requisite data structures.
2.  **Architectural Design:** Defines the relationship between major structural elements of the software, architectural styles, and design patterns.
3.  **Interface Design:** Describes how the software communicates with systems that interoperate with it, and with humans who use it (UI/UX).
4.  **Component-Level Design:** Transforms structural elements of the software architecture into a procedural description of software components.

#### **Question 1: (From PDF Series Test-II, Part A, Qn 1 - 2 Marks / Can be extended to long answer)**
**Question:** Differentiate the terms cohesion and coupling in the context of software design? Is it true that whenever you increase the cohesion of your design, coupling in the design would automatically decrease? Justify your answer by using suitable examples.

**Answer:**

**Difference between Cohesion and Coupling:**
| Feature | Cohesion | Coupling |
| :--- | :--- | :--- |
| **Definition** | Cohesion is a measure of the degree to which the elements of a single module belong together. It measures internal dependency. | Coupling is a measure of the degree of interdependence or interaction between different modules. It measures external dependency. |
| **Focus** | Focuses on what a module does (single-mindedness). | Focuses on how modules communicate with each other. |
| **Ideal State** | **High Cohesion** is highly desired. | **Low (Loose) Coupling** is highly desired. |
| **Analogy** | Team members within one department working perfectly together on one specific project. | Different departments in a company relying on each other to get work done. |

**Is it true that whenever you increase cohesion, coupling automatically decreases?**
*   **No, it is not *automatically* true.** While high cohesion and low coupling often go hand-in-hand as signs of good design, increasing cohesion does not mathematically or automatically guarantee a decrease in coupling. 
*   **Justification & Example:** Suppose you have a massive, poorly cohesive module `CalculateEverything()` that calculates employee salary, generates tax reports, and prints ID cards. 
    *   To increase *cohesion*, you break it into three highly cohesive modules: `CalculateSalary()`, `GenerateTax()`, and `PrintID()`.
    *   However, if `GenerateTax()` heavily relies on temporary internal data structures actively used by `CalculateSalary()`, you might end up passing massive amounts of data back and forth between these new modules. 
    *   So, while you increased cohesion (each module now does exactly one thing), you accidentally *increased* coupling because they now heavily depend on each other's data structures to function. To truly decrease coupling, you must properly design interfaces and practice *Information Hiding*.

#### **Question 2: (From Syllabus CO Assessment Qn 6)**
**Question:** Discuss the concepts of cohesion and coupling in modular design. Provide examples of high and low cohesion and tight and loose coupling, and explain their impact on the modularity and maintainability of a software system.

**Answer:**

**1. Concepts of Cohesion and Coupling:**
*   **Cohesion** refers to the internal strength of a module. A cohesive module encapsulates only the attributes and operations that are closely related to one another and to the class/module's core purpose.
*   **Coupling** refers to the inter-dependency between modules. If modules share global variables or pass massive amounts of control parameters, they are tightly coupled.

**2. Examples of Cohesion:**
*   **Low Cohesion (Bad): Coincidental Cohesion.** A module named `UtilityMethods` contains functions like `printDocument()`, `calculateSquareRoot()`, and `validateUserLogin()`. These functions have absolutely no meaningful relationship to each other.
*   **High Cohesion (Good): Functional Cohesion.** A module named `AuthenticationService` contains functions like `loginUser()`, `logoutUser()`, and `verifyPassword()`. Every function contributes to exactly one well-defined task: user authentication.

**3. Examples of Coupling:**
*   **Tight Coupling (Bad): Content Coupling.** Module A modifies the local internal data of Module B directly. If the internal structure of Module B changes, Module A will immediately break.
*   **Loose Coupling (Good): Data Coupling.** Module A calls Module B and passes exactly the specific data needed via parameters (e.g., `calculateTotal(price, taxRate)`). They communicate through simple, well-defined interfaces without needing to know each other's internal workings.

**4. Impact on Modularity and Maintainability:**
*   *With High Cohesion and Low Coupling:* The system is highly modular. If a bug occurs in the authentication system, the developer knows exactly which module to check (due to cohesion). When they fix or update that module, it doesn't break the rest of the application (due to low coupling). Maintainability is incredibly high, and testing is easier.
*   *With Low Cohesion and Tight Coupling:* "Spaghetti code." Changing a variable in the payroll module might mysteriously crash the database backup module. Modularity is a complete illusion, and maintainability drops to zero because updates require rewriting large portions of interconnected code.
