## 3.3 Data design, architectural styles and patterns, architectural design, conceptual model of UML

### 1. Data Design
Data design (sometimes referred to as data architecture) is the first design activity. It translates the data objects identified in the requirement analysis phase into data structures at the software component level and into a database architecture at the application level.

**Principles of Data Design:**
1.  Systematic analysis principles applied to function and behavior should also be applied to data.
2.  All data structures and the operations to be performed on each should be identified.
3.  A data dictionary should be established and used to define both data and program design.
4.  Low-level data design decisions should be deferred until late in the design process.
5.  The representation of data structures should be known only to those modules that must make direct use of the data contained within the structure (Information Hiding).

### 2. Architectural Styles
An architectural style serves as a template for a system's structure. It defines a family of systems in terms of a pattern of structural organization. More specifically, an architectural style determines the vocabulary of components and connectors that can be used, and a set of constraints on how they can be combined.

[Click here for a visual representation of standard Architectural Styles](https://www.google.com/search?q=Software+Architectural+Styles+Pressman+diagrams&udm=2)

The standard architectural styles categorized in software engineering are:

#### A. Data-Centered Architectures
*   **Concept:** A data store (e.g., a file or database) resides at the center of this architecture and is accessed frequently by other components that update, add, delete, or modify data.
*   **Examples:** Repository architecture, Blackboard architecture.
*   **Advantage:** Integrability. Existing components can be changed, and new client components can be added to the architecture without concerning other clients (because clients operate independently on the central data).

#### B. Data-Flow Architectures
*   **Concept:** This architecture is applied when input data are to be transformed through a series of computational or manipulative components into output data.
*   **Examples:** Pipe and Filter style. The "pipes" transmit data from one component to the next, and the "filters" process the data independently.
*   **Advantage:** Promotes high reusability and simplifies system maintenance. If a data stream degenerates into a single line of transforms, it is termed batch sequential.

#### C. Call and Return Architectures
*   **Concept:** This architectural style enables a software designer to achieve a program structure that is relatively easy to modify and scale.
*   **Examples:** 
    *   *Main program/subprogram architectures:* Classical single-thread top-down structure.
    *   *Remote procedure call (RPC) architecture:* Components are distributed across multiple computers on a network.

#### D. Object-Oriented Architectures
*   **Concept:** The components of a system encapsulate data and the operations that must be applied to manipulate the data. Communication and coordination between components are accomplished via message passing.

#### E. Layered Architectures
*   **Concept:** A number of different layers are defined, each accomplishing operations that progressively become closer to the machine instruction set. At the outer layer, components service user interface operations. At the inner layer, components perform operating system interfacing.
*   **Advantage:** High security and clear separation of concerns.

### 3. Architectural Patterns
While an architectural *style* describes an overall system framework, an architectural *pattern* describes a solution to a specific architectural problem within a given context.
*   **Concurrency Patterns:** Handle multiple tasks in a manner that simulates parallelism (e.g., Operating system process management).
*   **Persistence Patterns:** Handle how data is stored and retrieved when the system crashes or shuts down (e.g., Database ORM mapping).
*   **Distribution Patterns:** Address the manner in which systems or components within systems communicate with one another in a distributed environment (e.g., **Broker Pattern**, which acts as a middleman to coordinate messages between clients and servers).

### 4. Conceptual Model of UML (Unified Modeling Language)
UML is a standard language for specifying, visualizing, constructing, and documenting the artifacts of software systems. To understand UML, you must understand its conceptual model, which consists of three major elements: **Things**, **Relationships**, and **Diagrams**.

[Click here for a visual representation of UML Diagrams classification](https://www.google.com/search?q=UML+Diagrams+types+hierarchy+diagram&udm=2)

#### A. Things in UML (The Objects)
Things are the basic building blocks of UML.
1.  **Structural Things:** The nouns of UML models. (e.g., *Classes*, *Interfaces*, *Use Cases*, *Components*, *Nodes*).
2.  **Behavioral Things:** The verbs of UML models, representing behavior over time and space. (e.g., *Interactions*, *State Machines*).
3.  **Grouping Things:** The organizational parts. (e.g., *Packages*).
4.  **Annotational Things:** Explanatory parts of UML. (e.g., *Notes*).

#### B. Relationships in UML (The Links)
1.  **Dependency:** A semantic relationship where a change in one thing (independent) may affect the semantics of the other thing (dependent). (Dashed line with arrow).
2.  **Association:** A structural relationship that describes a set of links/connections among objects. (Solid line).
    *   *Aggregation:* A "whole/part" relationship (Hollow diamond).
    *   *Composition:* A strict "whole/part" relationship where the part cannot exist without the whole (Filled diamond).
3.  **Generalization:** A "child/parent" relationship where the child shares the structure and behavior of the parent (Inheritance). (Solid line with hollow arrow).
4.  **Realization:** A semantic relationship between interfaces and the classes that implement them. (Dashed line with hollow arrow).

#### C. Diagrams in UML (The Views)
UML 2.0 defines 13 standard diagrams, broadly categorized into:
*   **Structure Diagrams:** Represent the static aspect of the system. (e.g., *Class Diagram*, *Object Diagram*, *Component Diagram*, *Deployment Diagram*).
*   **Behavior Diagrams:** Represent the dynamic aspect of the system. (e.g., *Use Case Diagram*, *Sequence Diagram*, *Activity Diagram*, *Statechart Diagram*).

#### **Question 2: (From PDF Series Test-II, Page 2, Qn 7b - OO Concepts component)**
**Question:** A short explanation of how encapsulation, inheritance, and polymorphism are used in object-oriented design. *(Context: Asked alongside an Insulin Pump system UML diagram question)*.

**Answer:**
These three concepts are the core pillars of Object-Oriented Architectural Design and Conceptual UML:

1.  **Encapsulation (Information Hiding):**
    *   **Explanation:** It is the mechanism of wrapping data (attributes) and the code acting on the data (methods) together as a single unit, known as a Class. It restricts direct access to some of the object's components, which prevents accidental modification.
    *   **UML usage:** Represented in Class diagrams using visibility modifiers like `-` (private), `+` (public), and `#` (protected). E.g., making a `bloodGlucoseLevel` attribute private in an Insulin Pump class, accessible only via a `readSensor()` method.
2.  **Inheritance (Generalization):**
    *   **Explanation:** It is the mechanism by which one class acquires the properties and behaviors of another class. It promotes code reusability and establishes a parent-child relationship.
    *   **UML usage:** Represented by a solid line with a hollow triangular arrow pointing to the parent class. E.g., `Admin` and `Doctor` classes inheriting common attributes from a base `User` class.
3.  **Polymorphism:**
    *   **Explanation:** Meaning "many forms," it allows methods to do different things based on the object it is acting upon. It permits a single interface to represent different underlying forms (data types or classes).
    *   **UML usage:** Usually implemented via method overriding or overloading. For instance, a base class `Notification` might have a method `sendAlert()`. The subclasses `SMSNotification` and `EmailNotification` will both override `sendAlert()` to implement their specific delivery mechanisms.

#### **Question 3: (Standard University Exam Question)**
**Question:** Differentiate between Data-centered and Data-flow architectural styles with suitable examples.

**Answer:**
| Feature | Data-Centered Architecture | Data-Flow Architecture |
| :--- | :--- | :--- |
| **Basic Concept** | A central data store (database/repository) is accessed and modified by multiple independent client components. | Input data is continuously passed through a series of independent transformational components to produce output data. |
| **Communication** | Components communicate indirectly by modifying the central repository. | Components communicate directly by passing data sequentially through channels. |
| **Primary Structure** | Repository/Blackboard structure. | Pipe and Filter structure. |
| **Advantage** | Highly scalable for data access; clients operate completely independently. | High reusability of filters; highly effective for linear data processing. |
| **Example** | A banking system database accessed by web interfaces, mobile apps, and ATM terminals. | A compiler system (Lexical analysis -> Syntax analysis -> Semantic analysis -> Code generation). |
