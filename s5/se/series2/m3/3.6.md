### Case Study 1: Mentcare - A Patient Information System
**System Context:**
Mentcare is a medical information system designed to manage patient information for a mental health care center. Mental health records are highly sensitive, so privacy and access control are critical non-functional requirements.

**Core Functional Requirements (from Exam PDF):**
1.  *Patient Registration:* Collecting personal and medical details.
2.  *Appointment Scheduling:* Booking/modifying appointments; doctors viewing schedules.
3.  *Medical Record Management:* Storing consultations, medications, test results, etc.
4.  *Emergency Alerts:* Alerting concerned staff for critical patients.
5.  *Access Control:* Role-based access (psychiatrists, nurses, admin).
6.  *Reports:* Generating summary reports and treatment outcomes.

### Case Study 2: An Insulin Pump Control System
**System Context:**
An embedded software system that controls a portable insulin pump for diabetic patients. It is a life-critical system; software failure could cause fatal harm to the patient.

**Core Functional Requirements (from Exam PDF):**
1.  *Continuous Monitoring:* Reads blood-glucose levels continuously via a sensor.
2.  *Computation:* Compares reading to a safe range.
3.  *Delivery:* Computes the required insulin dose and controls the pump to deliver it.
4.  *Alarm Handling:* Must safely handle abnormal conditions (low battery, sensor failure, dangerously high/low glucose) and trigger alarms.

#### **Question 1: (From PDF Series Test-II, Part B, Qn 6b - 10 Marks)**
**Question:** The MentCare system is designed to help manage patient information... Apply the principles of function-oriented design to develop a DFD-based model for the system. Your answer should include: I. Context-Level DFD, II. Level-1 DFD, III. Level-2 DFD, IV. Create Data Dictionary, V. Prepare the Structured Design (SDS).

**Answer (How to answer in the exam):**
*(Note: Use standard DFD notations: Circles/Bubbles for Processes, Parallel lines for Data Stores, Rectangles for External Entities, Arrows for Data Flow).*

**I. Context-Level DFD (Level-0):**
*   **Central Process Bubble:** `MentCare System` (Process 0).
*   **External Entities & Data Flows:**
    *   `Patient`: Sends *Personal Details*; Receives *Appointment Confirmations*.
    *   `Doctor / Psychiatrist`: Sends *Consultation Notes, Prescriptions*; Receives *Patient Records, Daily Schedule, Alerts*.
    *   `Nurse`: Sends *Vital Signs, Emergency triggers*; Receives *Alerts*.
    *   `Admin Staff`: Sends *Registration Info, Schedule Requests*; Receives *Summary Reports*.

**II. Level-1 DFD (Decomposing Process 0):**
Break the main system into major functional modules based on the prompt:
*   **Process 1.0: Manage Patient Registration:** Receives data from *Admin/Patient*, stores it in `D1: Patient Database`.
*   **Process 2.0: Schedule Appointments:** Receives requests from *Patient/Admin*, checks `D2: Schedule Database`, outputs confirmation.
*   **Process 3.0: Manage Medical Records:** Receives notes from *Doctors*, updates `D3: Medical Records`.
*   **Process 4.0: Handle Emergencies:** Receives critical triggers from *Nurses*, outputs Alerts to *Doctors*.
*   **Process 5.0: Generate Reports:** Reads from D1, D2, D3, outputs Reports to *Admin*.

**III. Level-2 DFD (Decomposing Process 3.0 - Manage Medical Records):**
*   **Process 3.1: Authenticate User:** Checks if Doctor/Nurse has valid access (Access Control).
*   **Process 3.2: Retrieve Record:** Fetches patient history from `D3: Medical Records`.
*   **Process 3.3: Update Treatment Plan:** Adds new diagnosis/prescriptions and saves back to `D3`.

**IV. Data Dictionary (Sample Entries):**
*   **Patient_Details** = `Patient_ID + Name + Age + Gender + Contact_Number + Address`
*   **Medical_Record** = `Patient_ID + Diagnosis + Assigned_Doctor + [Medication_List] + Therapy_Notes`
*   **Appointment** = `Appointment_ID + Patient_ID + Doctor_ID + Date + Time + Status`

**V. Structured Design (SDS) / Structure Chart:**
Draw a hierarchical tree. 
*   **Top level:** `MentCare Executive`.
*   **Second level (Modules):** `Registration Mod`, `Scheduling Mod`, `Records Mod`, `Alert Mod`, `Report Mod`.
*   **Third level (Under Records Mod):** `Verify Access`, `Fetch Data`, `Write Data`.

#### **Question 2: (From PDF Series Test-II, Part B, Qn 7a - 7 Marks)**
**Question:** An Insulin Pump Control System delivers insulin to diabetic patients automatically... Apply the principles of function-oriented design to develop a DFD-based model. Include: I. A Level-0 DFD, II. One Level-1 DFD decomposing "Control Insulin Delivery", III. Data dictionary.

**Answer:**

**I. Level-0 DFD (Context Diagram):**
*   **Central Process:** `Insulin Pump Control System` (Process 0).
*   **External Entities & Flows:**
    *   `Blood Sensor`: Sends *Glucose Reading*.
    *   `Insulin Pump Hardware`: Receives *Pump Control Commands* (amount to inject).
    *   `Patient / User`: Sends *Settings/Overrides*; Receives *Alarms / Display Info*.
    *   `Battery/Hardware Sensors`: Sends *Hardware Status* (battery low, blockage).

**II. Level-1 DFD (Decomposing "Control Insulin Delivery"):**
*   **Process 1.1: Analyze Glucose Level:** Takes *Glucose Reading* from sensor, compares it against `D1: Safe Range Limits`, outputs *Calculated Requirement*.
*   **Process 1.2: Compute Insulin Dose:** Takes *Calculated Requirement*, accesses `D2: Patient Dosage History`, outputs *Exact Dose Amount*.
*   **Process 1.3: Issue Pump Command:** Takes *Exact Dose Amount*, sends *Pump Control Command* to hardware.
*   **Process 1.4: Monitor System Safety:** Takes inputs from Battery/Sensor and Process 1.1 (if glucose is dangerously high/low). If abnormal, triggers *Alarm* to Patient and stops Process 1.3.

**III. Data Dictionary (Sample Entries):**
*   **Glucose_Reading** = `Timestamp + Glucose_Value_mg_dL`
*   **Safe_Range_Limits** = `Min_Threshold + Max_Threshold`
*   **Pump_Command** = `Motor_Pulses_Count + Delivery_Speed`
*   **Alarm_Signal** = `Alarm_ID + Error_Message (e.g., "Low Battery", "High Sugar") + Audio_Trigger`

#### **Question 3: (From PDF Series Test-II, Part B, Qn 7b - 8 Marks)**
**Question:** Apply object-oriented design concepts to the above question (Insulin Pump) and model the same system. Your answer should include: I. UML Use Case Diagram and Class Diagram, II. Sequence diagram for "Automatic Insulin Delivery", III. Short explanation of encapsulation, inheritance, polymorphism.

**Answer:**

**I. UML Models:**
*   **Use Case Diagram:**
    *   **Actors:** `Patient`, `Blood Sensor` (system actor), `Pump Hardware` (system actor).
    *   **Use Cases:** `View Status` (Patient), `Deliver Insulin` (System), `Trigger Alarm` (System), `Calibrate Sensor` (Patient). 
    *   *Includes:* `Deliver Insulin` *<<includes>>* `Calculate Dose` and `Read Sensor`.
*   **Class Diagram:**
    *   `Controller`: Methods: `startMonitor()`, `stopMonitor()`.
    *   `BloodSensor`: Attributes: `currentLevel`. Methods: `readGlucose()`.
    *   `Pump`: Attributes: `insulinReservoir`. Methods: `inject(amount)`.
    *   `Alarm`: Attributes: `status`. Methods: `activate(type)`.
    *   *Relationships:* `Controller` has a composition relationship (filled diamond) with `BloodSensor`, `Pump`, and `Alarm`.

**II. Sequence Diagram for "Automatic Insulin Delivery":**
*   **Lifelines (Objects at the top):** `:Timer`, `:Controller`, `:BloodSensor`, `:DoseCalculator`, `:Pump`.
*   **Sequence of Messages (Arrows moving top to bottom):**
    1.  `:Timer` sends `trigger()` to `:Controller` (e.g., every 5 minutes).
    2.  `:Controller` sends `readGlucose()` to `:BloodSensor`.
    3.  `:BloodSensor` returns `glucoseValue` to `:Controller`.
    4.  `:Controller` sends `compute(glucoseValue)` to `:DoseCalculator`.
    5.  `:DoseCalculator` returns `doseAmount` to `:Controller`.
    6.  `:Controller` sends `inject(doseAmount)` to `:Pump`.
    7.  `:Pump` returns `deliverySuccess` to `:Controller`.

**III. Explanation of OO Concepts in this Design:**
*(Refer to the detailed answer already provided in the notes for section 3.3, Question 2. Encapsulation is used to hide the internal `glucoseValue` inside the sensor class. Inheritance can be used if there are different types of Alarms (e.g., `BatteryAlarm` inherits from `BaseAlarm`). Polymorphism is used if a `trigger()` method behaves differently based on the alarm type.)*
