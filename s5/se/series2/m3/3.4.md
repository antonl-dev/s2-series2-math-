# Module III: Implementation and Testing
## 3.4 Testing Strategies: A strategic approach to software testing, test strategies for conventional software

### Introduction to Software Testing
Software testing is a critical element of software quality assurance (SQA) and represents the ultimate review of specification, design, and coding. Testing is the process of executing a program with the intent of finding errors. A successful test is one that uncovers an as-yet-undiscovered error.

---

### 1. A Strategic Approach to Software Testing
A software testing strategy integrates software test case design methods into a well-planned series of steps that result in the successful construction of software. 

#### Verification and Validation (V & V)
Software testing is part of a broader group of activities called Verification and Validation. It is a highly testable university exam question to differentiate between the two:
*   **Verification:** *"Are we building the product right?"* Ensures that the software correctly implements a specific function according to the design specifications.
*   **Validation:** *"Are we building the right product?"* Ensures that the software built traces back to and satisfies the actual customer requirements.

#### The Testing Spiral (Pressman's Model)
Testing progresses in a spiral or outward fashion:
1.  **Unit Testing:** Starts at the center, focusing on the smallest unit of software design (the module/component).
2.  **Integration Testing:** Moves outward, focusing on the design and construction of the software architecture (putting the modules together).
3.  **Validation Testing:** Moves further outward, validating that requirements established during requirement analysis are met. *(Covered in detail in 3.5)*
4.  **System Testing:** The outermost layer, where the software and other system elements (hardware, database, people) are tested as a whole. *(Covered in detail in 3.5)*

### 2. Test Strategies for Conventional Software
For conventional (non-object-oriented) software, the testing strategy focuses sequentially on Unit Testing and Integration Testing before moving to higher-level system tests.

#### A. Unit Testing
Unit testing focuses verification effort on the smallest unit of software design—the software component or module. It is heavily white-box oriented (examining internal logic).
*   **What is tested:** Module interfaces, local data structures, boundary conditions, independent paths (basis paths), and error-handling paths.
*   **Drivers and Stubs:** Because a module is not a standalone program, testing requires secondary code:
    *   **Driver:** A "main program" that accepts test case data, passes it to the module being tested, and prints the relevant results. (Simulates the calling module).
    *   **Stub:** A "dummy subprogram" that replaces modules that are called by the component being tested. (Simulates the called module).

#### B. Integration Testing
"If all the modules work individually, why wouldn't they work when put together?" 
The answer is the **Interface**. Data can be lost across an interface; one module can have an inadvertent, adverse effect on another; global data structures can present problems. Integration testing is a systematic technique for constructing the software architecture while at the same time conducting tests to uncover errors associated with interfacing.

[Click here for a visual representation of Top-down vs Bottom-up Integration](https://www.google.com/search?q=Top-down+vs+Bottom-up+Integration+Testing+Stubs+Drivers&udm=2)

There are two major approaches to Integration Testing:

1.  **Top-Down Integration:**
    *   Modules are integrated by moving downward through the control hierarchy, beginning with the main control module.
    *   Subordinate modules are incorporated either Depth-first or Breadth-first.
    *   **Requirement:** Relies heavily on **Stubs** (dummy lower-level modules) because the lower-level components have not been integrated yet.
    *   *Advantage:* Major control points and early architectural flaws are verified early.

2.  **Bottom-Up Integration:**
    *   Begins construction and testing with atomic modules (the lowest levels in the program structure).
    *   Because components are integrated from the bottom up, the processing required for components subordinate to a given level is always available.
    *   **Requirement:** Relies heavily on **Drivers** (dummy top-level modules) to coordinate test case input and output.
    *   *Advantage:* No stubs are needed; operational modules are tested thoroughly early on.

3.  **Regression Testing:**
    *   Whenever a new module is added during integration, the software changes. This change may cause problems with functions that previously worked flawlessly.
    *   Regression testing is the re-execution of some subset of tests that have already been conducted to ensure that changes have not propagated unintended side effects.

4.  **Smoke Testing:**
    *   An integration testing approach used when software is developed on a daily basis (often in Agile). 
    *   A daily build is created, and a series of quick tests (smoke tests) are run to ensure the build does not immediately crash ("catch fire") and that the most crucial functions work.

#### **Question 1: (From Syllabus CO Assessment Qn 3)**
**Question:** Explain how integration testing is approached in the Waterfall model. Discuss the potential risks associated with deferring integration testing until the later stages of development.

**Answer:**
**Integration Testing Approach in the Waterfall Model:**
In the Waterfall model, testing is a distinct phase that occurs only after the complete Implementation (coding) phase is finished. 
*   Developers first write and conduct **Unit Tests** independently on all individual modules. 
*   Once all modules are coded and unit-tested, the team moves into the testing phase where they attempt to stitch all the modules together. 
*   In a strict waterfall environment, this often results in a "Big Bang" integration approach, where all components are combined at once, and the entire system is tested as a single entity for interface errors. Alternatively, they may apply a strict Top-Down or Bottom-Up approach, but only after all coding is done.

**Risks of Deferring Integration Testing until Later Stages:**
1.  **The "Big Bang" Disaster:** If all modules are integrated at once late in the cycle, a massive number of interface errors will occur simultaneously. Isolating the exact cause of an error becomes extremely difficult because the problem could be anywhere within the hundreds of newly connected interfaces.
2.  **Late Discovery of Architectural Flaws:** Integration testing tests the architectural design. If integration is deferred to the end, critical architectural flaws (e.g., major system bottlenecks, fundamental database connection issues) are discovered too late. Fixing them might require rewriting large portions of the system.
3.  **Schedule Overruns:** Because interface errors are complex and hard to trace in a fully assembled but untested system, debugging takes much longer than anticipated, leading to severely delayed release schedules.
4.  **Accumulation of Technical Debt:** Minor misunderstandings between developers regarding data formats passed between modules accumulate. What could have been fixed in minutes if integrated iteratively becomes a massive restructuring task.

#### **Question 2: (Standard University Exam Question)**
**Question:** Differentiate between Verification and Validation in software testing.

**Answer:**
| Feature | Verification | Validation |
| :--- | :--- | :--- |
| **Definition** | The process of evaluating software to determine whether the products of a given development phase satisfy the conditions imposed at the start of that phase. | The process of evaluating software during or at the end of the development process to determine whether it satisfies specified business requirements. |
| **Key Question** | "Are we building the product *right*?" (Is the code technically correct based on the design?) | "Are we building the *right* product?" (Does it solve the customer's actual problem?) |
| **Focus** | Focuses on internal processes, architecture, and code. | Focuses on external user expectations and final output. |
| **Execution** | Done via reviews, walkthroughs, inspections, and unit testing. | Done via acceptance testing, beta testing, and system testing. |

#### **Question 3: (Standard University Exam Question)**
**Question:** Why are Stubs and Drivers required in software testing? Explain with context to Top-down and Bottom-up integration.

**Answer:**
During testing, a single module is rarely a standalone executable program. It either receives data from a higher-level module or passes data to a lower-level module. To test a module in isolation, these missing environments must be simulated.
*   **Drivers (The "Calling" Simulator):** A driver is a dummy main program that takes test data, passes it to the module being tested, and prints the result. 
    *   *Context in Integration:* In **Bottom-up integration**, we build from the lowest level. Because the upper-level control modules don't exist yet, we write Drivers to simulate the upper levels and call the lower levels to test them.
*   **Stubs (The "Called" Simulator):** A stub is a dummy subprogram that replaces a module called by the module currently being tested. It usually just returns a hardcoded value to simulate a successful execution.
    *   *Context in Integration:* In **Top-down integration**, we build from the top-most main control module. Because the lower-level helper modules don't exist yet, we write Stubs to simulate them so the main module can be tested without crashing.
