# Module IV: Maintenance and Project Scheduling
## 4.5 Defining task set for the software project - selecting software engineering task

### Introduction to Task Sets
No single software engineering process or project plan is appropriate for all software projects. A small web app developed by two people requires a completely different approach than a mission-critical air traffic control system built by a team of fifty. 

To accommodate these differences, the project manager must define a **Task Set**. A task set is a collection of software engineering work tasks, project milestones, work products (deliverables), and quality assurance filters that must be accomplished to complete a particular project.

---

### 1. Defining the Task Set (Types of Projects)
Before selecting tasks, the project manager must understand the type of project being undertaken. Software projects generally fall into one of the following categories:

1.  **Concept Development Projects:** Initiated to explore some new business concept or application of a new technology.
2.  **New Application Development Projects:** Undertaken as a consequence of a specific customer request (building a software product from scratch).
3.  **Application Enhancement Projects:** Occur when existing software is modified to provide new functions or better performance (Perfective Maintenance).
4.  **Application Maintenance Projects:** Correct, adapt, or extend existing software in ways that may not be immediately obvious to the end user (Corrective/Adaptive Maintenance).
5.  **Re-engineering Projects:** Undertaken with the intent of rebuilding an existing (legacy) system in whole or in part.

---

### 2. Selecting the Software Engineering Task Set
Once the project type is identified, the project manager must determine the degree of **rigor** required. 
*   A small, low-risk project might use a *casual* or *agile* task set (minimal documentation, daily stand-ups).
*   A high-risk, life-critical system must use a *strict* task set (heavy documentation, formal technical reviews, rigorous testing).

**Steps for Selecting Tasks:**
1.  **Evaluate Project Characteristics:** Assess the project's size, business criticality, longevity, stability of requirements, and team experience.
2.  **Define the Work Breakdown Structure (WBS):** The project is broken down into macroscopic activities (e.g., "Requirement Analysis", "Design", "Coding"). Then, each activity is broken down into specific tasks (e.g., "Design" is broken down into "Data Design", "Architectural Design", "UI Design").
3.  **Assign Work Products:** Decide what document or code artifact must be produced at the end of each task.
4.  **Establish Milestones:** Define specific points in time where the team and customer can review the completed tasks.

---

### 3. Task Networks (Activity Networks)
Once the task set is defined and selected, the manager must define the sequence in which the tasks will be executed. This is represented using a **Task Network**.

*   A task network is a graphic representation of the task flow for a project. 
*   It shows the **precedence ordering** of tasks (which tasks must happen before others).
*   It helps distinguish between **Sequential tasks** (must happen one after another) and **Concurrent/Parallel tasks** (can be worked on at the same time by different developers).
*   *Critical Path:* The longest sequence of dependent tasks in the network. It dictates the minimum time required to complete the project.

#### **Question 1: (From PDF Series Test-I, Page 4, Qn 8a - 5 Marks)**
**Question:** What is the order in which the following are estimated - cost, effort, duration, size? Represent the precedence ordering among these activities using a task network diagram.

**Answer:**

**Order of Estimation:**
In software project planning, estimations cannot be done randomly; they follow a strict logical dependency. The correct chronological order is:
1.  **Size Estimation:** First, you must estimate the size of the product (e.g., Lines of Code (LOC) or Function Points). You cannot estimate effort without knowing how big the software is.
2.  **Effort Estimation:** Once the size is known, you calculate the effort required (usually in Person-Months) using models like COCOMO.
3.  **Duration (Time) Estimation:** After effort is calculated, the manager looks at the available human resources and task dependencies to estimate the calendar time (duration) needed to complete the project.
4.  **Cost Estimation:** Finally, the overall cost is calculated by taking the effort (Person-Months) and duration, and multiplying it by developer salaries, hardware costs, and overhead.

**Task Network Diagram (Precedence Ordering):**
*(Note: In the exam, draw this using circles/boxes for the nodes and arrows to show the flow/dependencies).*

```text
[Start Project Planning] 
          |
          V
[Task 1: Estimate Size (LOC/FP)]
          |
          V
[Task 2: Estimate Effort (Person-Months)]
          |
          +-------------------------+
          |                         |
          V                         V
[Task 3A: Estimate Duration]   [Task 3B: Calculate Salary/Resource Rates]
          |                         |

          |

[Task 4: Estimate Total Cost]

```
*Explanation of Diagram:* Task 1 (Size) strictly precedes Task 2 (Effort). Once Effort is known, the manager can concurrently estimate the Calendar Duration (Task 3A) and evaluate resource rates (Task 3B). Both of these must be completed before the Total Cost (Task 4) can be finalized.

#### **Question 2: (Standard University Exam Question)**
**Question:** Explain the process of selecting a software engineering task set. Why is it inappropriate to use the same task set for every project?

**Answer:**
**Process of Selecting a Task Set:**
1.  The project manager identifies the **Project Type** (e.g., New Application, Maintenance, Re-engineering).
2.  The manager evaluates the **Project Characteristics** using adaptation criteria. These criteria include the size of the project, number of potential users, application criticality (will a failure cause financial/physical harm?), and the stability of the requirements.
3.  Based on these criteria, a **Degree of Rigor** is chosen (Casual, Structured, Strict, or Quick Reaction).
4.  Finally, specific tasks, milestones, and deliverables are selected to form the **Work Breakdown Structure (WBS)** tailored to that exact degree of rigor.

**Why one task set cannot fit all:**
Applying a "one-size-fits-all" approach is highly inefficient and dangerous. 
*   If a manager uses a **strict task set** (requiring massive documentation, formal mathematical proofs of correctness, and extensive reviews) for a simple, temporary promotional website, the project will be massively over-budget and delayed due to unnecessary bureaucratic overhead.
*   Conversely, if a manager uses a **casual/agile task set** (minimal documentation, no formal architecture reviews) for a life-critical medical device like an Insulin Pump, catastrophic safety risks will be missed, potentially endangering lives. The task set must map directly to the complexity and risk of the specific product.
