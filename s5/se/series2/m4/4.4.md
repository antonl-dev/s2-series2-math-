# Module IV: Maintenance and Project Scheduling
## 4.4 Project scheduling and tracking: Basic concepts, relation between people and effort

### Introduction to Project Scheduling
Software project scheduling is an activity that distributes estimated effort across the planned project duration by allocating the effort to specific software engineering tasks. 
During the early stages of a project, a macroscopic schedule is developed. As the project gets underway, each entry on the macroscopic schedule is refined into a detailed microscopic schedule.

---

### 1. Basic Concepts of Project Scheduling
To establish an objective and reliable project schedule, the project manager must adhere to several basic principles:

1.  **Compartmentalization:** The project must be compartmentalized into a number of manageable activities and tasks (Work Breakdown Structure).
2.  **Interdependency:** The dependencies of each compartmentalized activity must be determined. Some tasks must occur in sequence (e.g., you cannot test a module before it is coded), while others can occur in parallel.
3.  **Time Allocation:** Each task to be scheduled must be allocated some number of work units (e.g., person-days of effort). A start date and a completion date are assigned based on the availability of resources.
4.  **Effort Validation:** The project manager must ensure that no more than 100% of any given resource (developer) is allocated at any given time. You cannot schedule one person to do two full-time tasks simultaneously.
5.  **Defined Responsibilities:** Every task that is scheduled should be assigned to a specific team member.
6.  **Defined Outcomes & Milestones:** Every task must have a defined outcome (a deliverable, like a document or a piece of code) and should be tied to a project milestone to track progress.

### 2. The Relationship Between People and Effort
This is one of the most critical concepts in software engineering management. 

**The Fallacy of Interchangeability:**
In traditional manufacturing (like digging a ditch or picking cotton), people and time are highly interchangeable. If 1 person takes 10 days to dig a ditch, 10 people can dig it in 1 day. 

*However, software development is NOT perfectly partitionable.* 
There is a common metric used in estimation called the **Person-Month (or Man-Month)**. It is a unit of work representing the effort of one person working for one month. Managers often make the fatal mathematical assumption that:
`Time = Effort / People`

**Why this formula fails in Software Engineering:**
1.  **Sequential Tasks:** Many software tasks are strictly sequential. You cannot speed them up by adding people. *(Famous analogy by Fred Brooks: "Nine women cannot make a baby in one month.")*
2.  **Communication Overhead:** Software development requires intense collaboration. As you add more people to a team, the number of communication paths increases exponentially.
    *   *Formula for communication paths:* For `N` people, the number of paths is `N(N-1) / 2`. 
    *   If you have a team of 3 developers, there are 3 paths. If you have a team of 50 developers, there are 1,225 paths! The team will spend all their time in meetings and coordinating, rather than coding.
3.  **Training/Ramp-up Time:** New people added to a project must be educated on the requirements, architecture, and current codebase. The existing developers must stop working to train the new people, slowing the project down further.

This reality led to the creation of **Brooks' Law** (coined by Frederick P. Brooks in his book *The Mythical Man-Month*):
> *"Adding human resources to a late software project makes it later."*

### 3. Project Tracking
Once the schedule is set, it must be tracked. The project manager tracks progress by:
*   Conducting periodic project status meetings in which each team member reports progress and problems.
*   Evaluating the results of all reviews conducted throughout the software engineering process.
*   Determining if formal project milestones (e.g., "Architecture design document approved") have been accomplished by the scheduled date.
*   Comparing actual start-date to planned start-date for each project task.
*   Using Earned Value Analysis (EVA) to assess progress quantitatively.

#### **Question 1: (From PDF Series Test-I, Page 3, Qn 4 - Heavy Weight Exam Question)**
**Question:** As the manager of a software project to develop a product for business application, if you estimate the effort required for completion of the project to be 50 person-months, can you complete the project by employing 50 developers for a period of one month? Justify your answer.

**Answer:**

**Direct Answer:** No, absolutely not. It is impossible to complete a 50 person-month software project by employing 50 developers for exactly one month.

**Justification:**
This scenario highlights the classic "Mythical Man-Month" fallacy in software engineering. People and time are not perfectly interchangeable in software development due to the following reasons:

1.  **Sequential Nature of Software Development:** Software creation cannot be perfectly partitioned into 50 independent pieces. It follows a logical sequence. You cannot begin coding until the design is ready, and you cannot test until the code is written. Even with 50 developers, the project is bottlenecked by the time required to complete these sequential phases. *(As the famous adage goes: "Nine women cannot deliver a baby in one month").*
2.  **Massive Communication Overhead:** Software development is a highly collaborative engineering discipline. If a manager places 50 developers on a project, they must constantly communicate to ensure their code integrates correctly. The number of communication paths for 50 people is calculated as `N(N-1)/2`, which equals `(50 * 49)/2 = 1,225` communication channels. The team would spend the entire single month just attending meetings, coordinating interfaces, and resolving conflicts, leaving virtually no time for actual programming.
3.  **Ramp-up and Onboarding Time:** Developers cannot instantly start writing productive code on day one. They require time to understand the business application, study the requirements, and set up their environments. In a one-month timeline, this onboarding overhead would consume a massive percentage of the available time.

Therefore, while the mathematical effort is 50 person-months, the actual project duration must be stretched out over a reasonable timeline (e.g., 5 developers for 10 months, or 10 developers for 5 months) to account for task dependencies and communication coordination.

#### **Question 2: (Standard University Exam Question)**
**Question:** State and explain Brooks' Law. Why does adding manpower to a late software project often delay it further?

**Answer:**
**Brooks' Law** states: *"Adding human resources to a late software project makes it later."*

**Explanation:**
When a software project falls behind schedule, a project manager's instinct is often to hire or transfer more developers onto the team to speed things up. However, this usually causes the project to delay even further because:
1.  **The Ramp-up Penalty:** The new developers know nothing about the project. The experienced developers, who should be coding to catch up to the schedule, must now stop their work to train, mentor, and explain the complex architecture to the newcomers.
2.  **Communication Explosion:** Adding more people exponentially increases the complexity of team communication. Coordinating tasks, merging code, and resolving integration conflicts take significantly more time with a larger team, eating into productive development hours.
3.  **Task Indivisibility:** The tasks causing the delay might be complex, sequential problems (like debugging a core database algorithm) that simply cannot be split among multiple new people.
