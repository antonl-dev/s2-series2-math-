# Module IV: Maintenance and Project Scheduling
## 4.6 Case study: Project planning using JIRA software

### Introduction to JIRA Software
Jira (developed by Atlassian) is one of the most widely used project management and issue tracking tools in the software industry today. Originally designed purely as a bug tracker, it has evolved into a comprehensive Agile project management tool. It allows software teams to plan, track, release, and report on their software projects.

Understanding Jira requires mapping the theoretical concepts of software scheduling (like the Work Breakdown Structure) to Jira's digital interface.

### 1. Key Terminology in JIRA (The Work Breakdown Structure)
Jira uses specific terminology to decompose a large project into manageable pieces. This represents the digital "Task Set".

1.  **Issue:** The foundational building block in Jira. An issue can represent a bug to be fixed, a new feature to be built, or a generic task.
2.  **Epic:** A large body of work that can be broken down into smaller tasks. Epics usually take several weeks or months to complete. *(Example: "Implement User Authentication System").*
3.  **Story (User Story):** A feature or requirement expressed from the perspective of the end-user. Multiple stories make up an Epic. *(Example: "As a user, I want to log in using my Google account so I don't have to remember a new password").*
4.  **Task / Sub-task:** The actual technical work assigned to a developer to fulfill the user story. *(Example: "Create Google OAuth API connection").*
5.  **Backlog:** A prioritized list of all the Epics, Stories, and Bugs that need to be addressed in the project. It represents the "Software Scope."

---

### 2. Project Planning and Tracking Process in JIRA
A standard software project plan in Jira usually follows the Agile (Scrum) framework. The case study of planning a project involves the following chronological steps:

#### Step 1: Project Creation and Configuration
The Project Manager creates a new project in Jira and selects a template. The two most common are:
*   **Scrum Board:** Used for projects with fixed-length iterations (Sprints). Best for building new products.
*   **Kanban Board:** Used for continuous flow of work without fixed sprints. Best for IT support and software maintenance.

#### Step 2: Building the Product Backlog
The Project Manager and Customer (Product Owner) populate the Jira Backlog. They write User Stories and group them into Epics. At this stage, the scope of the software is fully defined in the system.

#### Step 3: Estimation
Before scheduling, effort must be estimated. In Jira, teams often use **Story Points** (a relative measure of complexity) rather than exact hours to estimate how hard a User Story is to implement.

#### Step 4: Sprint Planning (Scheduling)
A **Sprint** is a short, time-boxed period (usually 2 weeks) where the team commits to completing a specific set of work. 
*   The manager creates a Sprint in Jira.
*   They drag prioritized User Stories from the Backlog into the Sprint.
*   Tasks are assigned to specific developers ("Assignee").

#### Step 5: Tracking Progress (The Board)
Once the Sprint starts, developers use the Jira Board to track progress. The board is divided into columns (workflow states):
*   **To Do:** Work that has not started.
*   **In Progress:** Work the developer is currently actively coding.
*   **In Review / QA:** Code is written but needs testing.
*   **Done:** The task is 100% complete.

#### Step 6: Reporting and Dashboards
To track if the project is on schedule, the Project Manager uses Jira's automated reports:
*   **Burndown Chart:** Shows the total effort remaining in the Sprint. If the line doesn't reach zero by the end of the Sprint, the project is falling behind.
*   **Velocity Chart:** Shows how much work the team successfully completes in each Sprint, aiding in future estimations.

### 📝 EXAM QUESTIONS & DETAILED ANSWERS FOR 4.6

#### **Question 1: (Standard University Exam Case Study Question)**
**Question:** Discuss how Agile project planning and tracking are executed using JIRA software. Explain the hierarchy of work items used in Jira to break down a project.

**Answer:**
**Project Planning and Tracking in JIRA:**
Jira facilitates Agile project management by providing a digital environment to plan, estimate, execute, and track software projects.
1.  **Planning:** The project manager acts alongside the product owner to list all system requirements into a central repository called the **Backlog**. 
2.  **Scheduling (Sprints):** The team decides what subset of the backlog they can complete in a 2-week iteration called a **Sprint**. These items are moved from the backlog into the active Sprint.
3.  **Tracking:** Once the Sprint begins, tracking is done visually using a **Scrum Board**. Developers move their assigned tasks through columns labeled *To Do*, *In Progress*, and *Done*.
4.  **Monitoring:** The manager tracks overall schedule health using a **Burndown Chart**, which graphically plots the amount of work remaining against the time left in the Sprint.

**Hierarchy of Work Items (Work Breakdown Structure):**
Jira breaks down complex projects using a specific hierarchy:
*   **Epic:** The highest level. A large, overarching feature that spans multiple sprints (e.g., "Build E-commerce Checkout System").
*   **User Story:** A specific requirement derived from the Epic, written from the user's perspective (e.g., "As a user, I want to pay using a Credit Card").
*   **Task / Sub-task:** The smallest unit of work. This is the technical implementation assigned to a single developer (e.g., "Integrate Stripe API for card processing").

#### **Question 2: (Standard University Exam Case Study Question)**
**Question:** In Jira, project managers frequently choose between a Scrum board and a Kanban board. Differentiate between these two project tracking methodologies and identify which software engineering phase (e.g., New Development vs. Maintenance) suits them best.

**Answer:**

**Difference between Scrum and Kanban in Jira:**
| Feature | Jira Scrum Board | Jira Kanban Board |
| :--- | :--- | :--- |
| **Pacing / Time** | Work is organized into strict, time-boxed iterations called **Sprints** (usually 2 weeks). | Work is a **continuous flow**. There are no sprints; tasks are pulled continuously from the backlog. |
| **Commitment** | The team commits to a specific amount of work at the start of the Sprint. No new work should be added mid-sprint. | Work items can be added, changed, or reprioritized at any time as long as they haven't been started. |
| **Key Metric** | **Velocity** (how many points the team completes per sprint). | **Lead/Cycle Time** (how long it takes an issue to go from 'To Do' to 'Done'). |
| **Control Mechanism** | The Sprint time limit forces delivery. | **WIP Limits (Work In Progress limits)** restrict how many tasks can be in the "In Progress" column at once to prevent bottlenecks. |

**Best Use Cases in Software Engineering:**
*   **Scrum Board:** Best suited for **New Application Development** projects. Because building a new product requires complex architecture and sequential feature building, the strict planning and time-boxing of Sprints allow the team to focus on building features without distraction.
*   **Kanban Board:** Best suited for **Software Maintenance** projects (Corrective/Adaptive maintenance). In maintenance, high-priority bugs (like a server crash) can arrive unpredictably. Kanban's continuous flow allows the team to immediately grab the highest priority bug without waiting for a new "Sprint" to start.
