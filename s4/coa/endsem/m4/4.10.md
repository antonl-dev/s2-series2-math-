### 4.10 Pipeline Hazard Detection and Resolution

**Pipeline Hazards** are situations that prevent the next instruction in the instruction stream from executing during its designated clock cycle. Hazards reduce the performance from the ideal speedup and create "stalls" or "bubbles" in the pipeline.

---

#### 1. Structural Hazards (Resource Conflicts)
A structural hazard occurs when the hardware cannot support all possible combinations of instructions overlapping in the same cycle. 
*   **Cause:** Two different instructions try to access the same physical resource at the same time.
*   **Common Example:** A single memory unit being used for both **Instruction Fetch** and **Data Access** (FO) in the same clock cycle.
*   **Solution:** 
    1.  **Hardware Duplication:** Using separate caches for instructions (I-Cache) and data (D-Cache).
    2.  **Stalling:** Forcing one instruction to wait (inserting a bubble) until the resource is free.

#### 2. Data Hazards (Data Dependency)
Data hazards occur when an instruction depends on the result of a previous instruction that is still being processed in the pipeline.

**Types of Data Hazards:**
1.  **RAW (Read After Write):** Instruction $I_2$ tries to read a source register before instruction $I_1$ has finished writing to it. This is the most common hazard.
2.  **WAR (Write After Read):** $I_2$ tries to write to a destination register before $I_1$ has had a chance to read it. (Usually only occurs in very complex out-of-order processors).
3.  **WAW (Write After Write):** $I_2$ tries to write to a register before $I_1$ writes to it, potentially leaving the register with the wrong (older) value.

**Solutions for Data Hazards:**
*   **Stalling (Bubble):** The hardware detects the dependency and stops the dependent instruction from moving forward until the data is written to the register file.
*   **Data Forwarding (Bypassing):** Adding special circuitry (wires) to move the result directly from the output of the ALU to the input of the ALU for the next instruction, without waiting for it to be written to a register.
*   **Software/Compiler solution:** The compiler reorders the code to insert independent instructions between dependent ones.

[Click here to see Data Forwarding (Bypassing) mechanism diagram](https://www.google.com/search?q=pipeline+data+forwarding+bypassing+logic+diagram&udm=2)

---

#### 3. Control Hazards (Branch Hazards)
Control hazards occur during the pipelining of branches and other instructions that change the **Program Counter (PC)**.
*   **Problem:** The pipeline fetches the *next* instruction ($PC+4$) before it has even finished decoding the current instruction to know if it's a branch. If the branch is "Taken," the instructions already in the pipeline are wrong and must be discarded (**flushed**).

**Solutions for Control Hazards:**
1.  **Stall/Freeze:** Stop fetching any instructions until the branch address is known and the condition is evaluated.
2.  **Branch Prediction:**
    *   **Static Prediction:** Always assume the branch will NOT be taken (or always assume it will). If wrong, flush the pipeline.
    *   **Dynamic Prediction:** Use a hardware table (**Branch Target Buffer**) to remember previous branch behavior and predict based on history.
3.  **Delayed Branch:** The instruction immediately following the branch (the "Delay Slot") is *always* executed regardless of whether the branch is taken. The compiler fills this slot with a useful instruction.

### Summary Table: Hazard vs. Solution

| Hazard Type | Primary Cause | Main Solution |
| :--- | :--- | :--- |
| **Structural** | Hardware resource clash | More hardware (e.g., dual-port memory) |
| **Data** | Result not ready yet | Data Forwarding / Bypassing |
| **Control** | Branch address unknown | Branch Prediction / Delayed Branch |
